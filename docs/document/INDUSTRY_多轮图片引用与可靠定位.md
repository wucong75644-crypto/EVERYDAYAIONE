# 多轮图片引用与可靠定位：行业证据及项目建议

研究日期：2026-10-05。状态：研究结论与建议，尚未作为新实现或已发布能力验收。本轮仅研究、复核代码和更新本文；不调用生图供应商，不修改生产数据，不提交或部署。

## 问题与项目证据

用户在包含上传图、生成图和重复引用的多轮对话中确认生成，`generate_image` 接收到 `file_id=fid_2a8b9c3d`，返回 `IMAGE_INPUT_UNAVAILABLE`。本次工具字段结构正确，症状主要涉及图片身份与上下文传递，不能一概归为字段名填错。

此前生产只读审计证据显示：该对话有 10 条消息、7 个图片块、4 张不同图片，原文件均存在。该 ID 未匹配审计覆盖的授权工作区文件或对话图片；重建对话提示的解析器返回 `RESOURCE_NOT_FOUND`。工具调用前的模型上下文包含视觉图片，但未发现可复制的 `fid`。这支持“上下文缺少可信定位，模型填入无法追溯的 ID”的解释；未检查运行中 Actor 的全部临时内存，不声称这个字符串在任何历史环境中都从未存在。

另一个独立缺口是旧消息 `context_revision=NULL`：正常历史加载按父任务版本过滤，精确读取的消息解析器也拒绝无版本历史消息。当前故障对话中的旧生成图和部分旧上传引用受此影响。文件存在不等于本轮模型可以发现或工具能够引用。

需要分别回答三个问题：参数是否符合合同、引用是否能在授权范围内解析、解析出的图是否符合用户此次选择。结构合法只能回答第一个问题；文件存在也不能证明最后一个问题。

## 官方机制与适用边界

以下是已核验的厂商建议和具体产品行为，没有证据表明存在统一强制的“聊天图片定位标准”。

| 来源 | 官方机制 | 对本项目的意义 |
| --- | --- | --- |
| [OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling) | 已知参数由代码补齐；用枚举、对象结构减少无效状态；支持的接口可用 strict 约束工具参数结构。 | 用户、会话、默认模型和明确选定的来源应由服务器绑定；模型只处理仍需判断的意图。 |
| [Claude Files API](https://platform.claude.com/docs/en/build-with-claude/files) | 上传后返回文件 ID，后续请求复用；应用需要维护用户到文件的映射，供应商工作区文件隔离不等于应用终端用户隔离。 | 真实资源身份由系统提供和校验。厂商文件 ID、本项目 file_id 和用户权限不能相互替代。 |
| [OpenAI Image generation](https://developers.openai.com/api/docs/guides/tools-image-generation) | 多轮编辑可引用此前 response 或 image ID。 | 生成结果也必须保留结构化来源；仅保留“刚才生成了一张图”的文本不能替代原图引用。 |

| [Gemini thought signatures](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures) | 对该文档适用的模型/API，保留并回传结构化响应中的签名；官方 SDK 可通过完整响应历史处理。 | 多轮状态不只是自然语言摘要。此为 Google 特定协议，不能推导出本项目必须新增签名字段或切换供应商。 |

## 对本项目的建议（推断，非行业强制要求）

建议用现有消息、资产、资源权限和异步快照补齐以下闭环，保留 `generate_image` 单次单图合同及服务器默认模型。

1. **让模型看到图片时也看到可信来源。** 上传图和生成图均从持久化消息投影现有 `message_id + content_index`；已登记资产可使用现有 `asset_id` 或授权 `resource_ref`。索引取原始消息块位置，不取压缩后的视觉数组位置。附带来源类型、名称及必要预览，帮助模型区分原图和生成结果；名称与视觉描述不能充当身份。需要多图时保留顺序及用途，不把分析用图自动列为生成参考。
2. **持久化此次选择，而非依赖最后一条消息。** UI 已明确选定的图由服务器绑定；通过对话指定的图，模型从系统返回的现有来源中提出选择。有影响结果的歧义时用候选缩略图或明确描述询问。确认“开始”应沿用已确定的提示词和参考图；替换或追加则更新后续请求使用的选择，不能改变已受理任务。即使某轮只有一张图，也不据此自动判定用户选了它。
3. **历史可以按需精确恢复。** 复用 `get_conversation_context` 获取真实消息块和提示词原文；摘要用于帮助发现，不能作为执行输入原文。补齐旧上传图、原生生成图及 NULL 版本消息的兼容读取。兼容路径必须证明消息属于当前授权会话，并位于父任务允许的历史边界；不能简单放开所有 NULL 版本消息，也不能只凭服务器当前时间判断可见性。具体安全边界仍需技术设计及验证。
4. **模型引用仍视为待校验输入。** 从本轮已授权且已展示/读取的候选来源解析引用；已明确选择的来源尽量由代码绑定。对可支持的供应商可考虑候选枚举约束，但先验证 Schema 子集、透传和实际效果；每次执行仍校验当前权限、文件可读性、图片字节和版本。缺来源时返回可诊断的未受理错误，可先读历史或请用户澄清，不静默换成最新图，不凭相似文件名猜图，也不自动重建付费任务。
5. **受理时冻结，执行时复核。** 使用已有版本化输入快照保存最终提示词、原图定位、内容哈希、版本、顺序和用途；Worker 基于该快照复核权限及地址。刷新、后续聊天、重试和签署地址过期不能把输入替换为最近消息；成功结果另存新版本并保留其来源。

不需要为此新增图片资源编号、图片任务表、通用 Agent 或另一条同步生图出口。Skill 继续定义创作流程；真实资源身份、权限和输入冻结由系统承担。若 Skill 正文含有错误的参数示例，可按实际合同修正，但不能把改正文作为定位可靠性的唯一措施。

## 当前实现与尚未完成的保证

已在本任务本地完成的修复包括历史图片定位投影、缓存前缀升级、资源错误分类及避免把资源错误引导为参数纠正。此前相关回归为 774 passed、3 skipped；这些本地变更未部署，不代表生产已修复。本轮未重跑代码测试。

现有 `ChatImageInputResolver` 已校验消息/资产作用域、图片字节、版本和内容哈希；已有快照可复用。但不能据此宣称用户选择已被确定性地绑定。本轮发现/复核的剩余重点是：旧 NULL 版本图片兼容、已确认选择跨轮持久化、来源投影与按需历史读取在压缩/重启后的完整性，以及选错有效 ID 的处理。

供应商层 strict 也尚未形成统一的已验证通路：本地 DashScope 适配器发送工具定义；Kie `FunctionDefinition` 没有工具 `strict` 字段，而 `response_format` 的 strict 是另一条结构化文本机制。OpenAI 兼容请求格式本身不能证明供应商实施了约束解码。

## 后续验证必须覆盖的真实行为

- 上传 A 分析并打磨提示词，随后上传 B，明确使用 B 生成；读取的原图内容哈希必须是 B。
- 同一消息多图，或多轮同名图片，按用户指定顺序保留用途；不能把视觉截断后的下标当原消息下标。
- 生成结果继续编辑；旧原生生成图、旧上传图及 NULL 版本历史均能在安全边界内发现和引用。
- 仅回复“确认”、刷新、上下文压缩、服务重启后，原选择与提示词原文保持一致。
- 无效 ID、越权来源、晚于父任务边界的图片、删除/损坏原图，均在受理前明确拒绝；歧义或缺失不能替换原图。
- 有效但可能指错图的引用应触发澄清或遵循已持久化的明确选择；Schema 通过不能当作此项已通过。
- 受理后替换或追加图片不改变已有快照；重试仍使用原快照，多张输出仍由多次单图调用完成。

推荐先补全来源与旧历史兼容，再完成明确选择的跨轮绑定，最后评估供应商可支持的候选约束。以原图哈希及受理快照作为验证依据，不能只观察工具卡片显示成功。
