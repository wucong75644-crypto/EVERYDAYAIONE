# 聊天任务从发送到交付的执行契约

本地实施和验证，未部署。以任务工作树的 `30bd9f35` 和本地差异为基线。适用入口为个人交互聊天中从用户消息到普通回答、可复用文字成果、图片、视频或文件交付。手动图片入口、定时任务及现有专用流程继续按原入口受理。ERP、确认、计费、租约和访问控制沿用各自现有契约。

## 用户体验

用户发消息并选传资料，按需手选 Skill。要方案时，看到保存成功的完整原文。下轮说「用刚改的第二条出图」，AI 找到最新版第二条并选工具，后台把同一段正文、原图和规格填进实际请求。受理后看进度，图到达后看结果。刷新、掉线、暂停或供应商暂未返回时，接口按原任务恢复状态。

```text
用户发消息 → AI 选方法并产出 → 后台保存原文 → 页面展示
下一轮选方案 → 后台验证并映射 → 原生工具受理 → 结果入库和展示
```

普通问答直接交付消息。用户在新对话直接说「帮我生成一张图片」，有图就按已确认用途绑定原图；文字生图就用该次文字要求。AI 在同一条用户消息内选工具并准备完整执行输入。沿现有内容对象入口在后台登记并继续执行，由原生工具检查并受理；页面从接收请求进入确认、进度和结果。若用户要写好方案再执行，仍先保存完整原文，并根据当轮请求决定继续执行或只交付文字。

### 必须同时通过的用户操作

| 编号 | 用户操作 | 通过标准 |
| --- | --- | --- |
| U1 | 在已登记方案的对话说「第一个方案生成图片」 | 找到原任务和真实成果，接续后只执行选中项，原文、原图、规格和操作身份均可核查。历史样本用于复现接续；新产出的方案另验正向和负面均完整 |
| U2 | 新对话上传图并要求几条新品提示词，下一轮说「新品 5 生成图片」 | 第一轮真正保存各条提示词，页面只显示一份。下一轮找到第五条并正确绑定原图；如果登记失败，第一轮明确说明未完成，执行型 Skill 只在有可执行成果时启用 |
| U3 | 不手选 Skill，在新对话直接说「帮我画一张图」；另用一张上传图请求按它改图 | 一条消息内完成工具选择、后台准备、受理和结果回执。纯文字、带图参考各验一条，分别检查对应模式、正文、原图和规格；沿用原确认和计费 |
| U4 | 在普通对话说「用刚改的内容做成视频／Word」，再发一个可以直接回答或支持现有工具读取的请求 | AI 按目标决定回答、发现业务工具或使用 Skill。成果只在有依赖时读取；各工具收到其支持的参数并核对真实交付。缺少关键输入或权限时说明所缺条件，支持范围以工具目录和当前权限为准 |

直接执行、先写后执行及改稿后执行共享同一套来源绑定和原生受理规则。会话负责传达用户目标，Skill 提供方法，工具声明实际可执行能力。

## 一条映射链

简化前的 `chat_input` 把来源、用途区间、目标字段和执行素材作为显式输入。后台核验来源版本、区间和覆盖情况，按类型生成目标参数并记录证据。这能审计传了什么，同时仍依赖模型判断区间的语义用途。简化后的 `ContentRecord` 在写作时固化每条完整原文、素材和规格，`compile_input` 仍把这些值映射到工具参数。前一版的模型分段提交入口已撤下，旧快照的校验代码仍在。此次方案延续版本核验、字段归属、素材用途、冲突检测和证据可重放，将它们接入当前成果对象链。

应保留一份权威正文，采用现有 `content_source` 与工具适配器。正常执行一次选择就能明确对应哪些数据。下面是模型提交与后台映射的关系示例。

| 数据 | 模型提交或选择 | 后台取值及校验 | 工具真正收到 |
| --- | --- | --- | --- |
| 目标工具 | 按用户意图从当前可见 Schema 选工具 | 目录校验工具可用、当前 Skill 允许及当前权限满足 | 原生工具调用 |
| 成果版本和条目 | `content_source={artifact_id,sha256,item_index}` | 从受信目录定位所属任务，核验同会话/用户/组织、提交状态、版本、摘要和序号 | 宿主记录来源证据 |
| 完整正文 | 只选上述条目 | 从 `ContentRecord.document.items[item_index-1].body` 逐字读取。正向、负面和执行限制在保存时已属于正文 | 图片/视频的 `prompt`，文件的 `chat_source_text` |
| 原始资料 | 创作时登记明确的资料身份和用途，执行时沿用 | 只解析 `usage=input`，校验当前访问、版本和原文件摘要。分析素材只留在成果记录 | 有类型、角色与完整性证据的原生引用 |
| 输出规格 | 创作时登记用户要求，修订时只提交明确变化 | 原生 Schema 校验规格，明确规格冲突或不支持时返回错误。省略值采用已有工具默认 | 比例、分辨率、格式等该工具实际支持的参数 |
| 改稿 | `base+updates` 指定旧版和修改项 | 替换修改项完整正文，按现有规则保留未改项、素材和规格，产生新版本 | 新调用引用新版本，已受理请求继续使用原快照 |

`artifact_id+sha256` 验的是整个保存版本，`body_sha256` 验的是选中条目的正文，`arguments_sha256` 验的是最终参数，素材文件另有字节摘要。它们分别沿用现有成果、调用绑定、资源校验和原生快照。外部 URL 由原生适配器对已核实的素材生成，模型提供的描述和 URL 不能替代文件身份。用户要求翻译或改编时先形成新的完整成果版本，执行时继续走同样的映射。

## 从发送到结束的接口对照

| 环节 | 前端发送或显示 | 后端输入 → 输出结构 | 接口契约 |
| --- | --- | --- | --- |
| L1 发送、上传和接收 | 发文字、附件引用、模型设置和可选 Skill；先显示用户消息与助手占位，订阅任务 | `GenerateRequest` 与 `ContentPart[]` → 请求回执、用户及助手消息 ID、任务 ID；`client_request_id` 作为幂等键 | 原请求重试复用身份；HTTP 接收对应消息或排队，用户可见状态与受理回执一致 |
| L2 排队和恢复上下文 | 展示排队或处理中 | `input_message_id, turn_id, task_id, base_context_revision` → 带作用域的上下文锚点、租约、检查点及可接续任务候选；一轮消息和跨轮逻辑任务分别有身份 | 从同一锚点读历史和附件。原任务候选可读时可供本轮选择；同名标题和相邻消息不能决定接续 |
| L3 选 Skill 和工具 | 显示实际启用的 Skill；普通用户通过自然语言表达目标 | 用户手选 `SkillSelection`、Skill 目录元数据和工具目录 → 固定的 Skill 版本和本轮可见工具 Schema；按需发现补充业务工具 | 手选优先且遵循能力边界。执行型 Skill 只在有有效成果时自动启用。普通问答、成果编写、执行和改稿各走其入口 |
| L4 创作和登记 | 普通问答照常显示；可复用方案只呈现已保存的完整正文 | `save_task_text` 的 `ContentDocument{title,notes,items[]}`，或 `base+updates` → `Artifact`、`StepResult`、`ContentRecord` 和可读目录 | 保存成功先于发布该正文。允许解开一层 JSON 对象字符串并按原结构校验。有图时每条方案须声明素材用途。登记失败的草稿不作为完成结果发布。失败保留上下文与旧版；已保存的正文按成果 ID 投影，避免重放时重复或被后续回执覆盖 |
| L5 跨轮选择 | 用户说「第二条」「全部」或「刚改的那版」 | 当前与可接续成果目录 → 目标工具调用及有序的版本、条目选择；单项执行用一个 `content_source` | 只有可验证归属的版本可选。引用仍属于旧任务时，复用接续事务先转移所有权。把已核验的条目选择留在原检查点，恢复沿用既有选择，接续前的调用仍未受理；语义歧义时才问用户 |
| L6 映射和固定参数 | 正常只显示业务进度，输入冲突给可操作的说明 | `ToolCall+ContentReference` → 原生参数、调用绑定、资源证据及输入摘要 | 映射后同时核对正文、资料和规格。最终执行入口校验收到的就是这组参数。固定默认由适配器填充，并在快照内记录。不允许二次改写正文或静默修改用户规格 |
| L7 正式受理 | 按已有规则呈现确认、额度不足或已受理 | 已校验参数 → `Operation`、`effect_key/effect_version`、原生请求快照、受理回执；异步任务产生子任务 ID | 核实权限、确认和预算后才派发。提交前失败、已受理和受理不明分别处理。恢复优先对账，既有操作身份和计费沿用 |
| L8 执行和结果登记 | 图片/视频有进度或占位；文件准备好才展示可下载文件 | 图片/视频 Worker 或原生文件工具 → 验证过的业务回执和文件/图像资产 → `Artifact`、`StepResult`、操作状态 | 将供应商及服务端事实关联到原操作。已受理和实际交付对应不同状态。部分成功保留已完成项，只接续符合条件的剩余项 |
| L9 终态和页面投影 | 实时流、结果消息、刷新、重连和多标签都显示同一终态 | `commit_ready` 写好最终 `ContentPart[]`，数据库提交后投递 `message_done/message_error`；实时数据以 `stream_id/execution_attempt/delivery_seq` 对齐 | `stream_end` 只表示本轮模型流结束。异步产物用子任务回执更新。已保存成果的正文只有一条权威投影；多个文本块应各自对齐，不能只按「最后一块文字」覆盖 |
| L10 加要求、暂停和重试 | 用户追加、取消、刷新或点继续 | 用户事件、任务检查点、原受理回执 → 恢复同一逻辑任务或明确开始新任务 | 派发前的新要求使尚未派发的输入重新核对。旧版本已受理时保存原快照并查原操作。断线不触发业务重发，恢复也不另计同一次操作 |

## 三种完成状态各由谁确认

| 事实 | 权威记录 | 用户看到的状态 |
| --- | --- | --- |
| 方案写好了 | 成果 Artifact 和 StepResult 已随 checkpoint 提交 | 完整方案只显示一次，可在后续选用 |
| 执行请求受理了 | 原生子任务或操作回执已持久化，Operation 保留原操作身份 | 已受理，等待图片、视频或文件 |
| 结果交付了 | 原生回执验证成功，成果已登记，最终消息已提交 | 图片可见、视频可播或文件可下载 |

页面事件用于投影这些事实。可见文字、模型口头描述和进度信号都不能作为新的执行证据。多项任务按条目核对已完成与未完成项。改稿后执行全部时，验收要区分原来已受理的同一条执行、可复用的未改项和真正的新版本生成。禁止仅凭标题或模型新生成的调用 ID 判断应该重做。

## 同一成果到三种交付

用户写六条方案，然后只改第二条。宿主生成新版，第一、三至六条沿用，第二条正文整体替换，原图和规格只在用户明确改动时更新。之后以下执行各自在同一个映射入口进入对应的原生契约。

| 交付 | 对接到服务端最终输入 | 完成证据 | 本轮状态 |
| --- | --- | --- | --- |
| 图片 | 完整 body → `prompt`，核验过的原图 → `references`，规格 → 原生图片快照；供应商 URL 由适配器生成 | 图片子任务真实完成，资产已登记，页面可显示 | 隔离 PostgreSQL 回放覆盖两条失败和两种新对话，核对原生请求、受理快照、Worker、资产和页面事件 |
| 视频 | 完整脚本 → `prompt`，只传当前原生入口支持的字段 | 视频子任务回执与资产及终态对应 | 冻结请求保留原文的首尾空白，以去除空白后的文本判断是否为空。相关本地回归已通过。本轮未新增真实视频交付验证 |
| Word 等文件 | 完整文字 → `chat_source_text`，交给现有文档工具/沙盒读取 | 核验 `FileRef`、工作区权限和文件摘要，能下载并打开成品 | 本轮回归覆盖内容入口和文件核验。独立交付验收以实际导出文件为准，核对段落、顺序和限制条件 |

## 两次失败定位

| 线上现象 | 首个断点 | 对应验收 |
| --- | --- | --- |
| 第一条方案有正确 ID 和摘要，提交显示找不到或已变化 | L5。目录给了前一任务的成果，业务校验只查了尚未加载该成果的新任务。已有登记记录与请求一致 | 模型给出真实旧成果引用，后台先完成带租约的接续，再用同一选择流入 L6。覆盖错误摘要、过期版本、重复批次和跨会话拒绝 |
| 新品 5 显示过文字，编排 Skill 找不到可执行成果 | L4。三次登记都传了 JSON 字符串，内层方案仍缺少参考图用途，聊天随后显示了未登记的草稿。L3 后续自动启用了执行型 Skill，工具目录已没有登记能力 | 保存失败只报告未交付，旧成果仍可见。新对话在写作成功之前不能走执行型 Skill。结构化登记成功后，下一轮正常发现并执行。旧聊天中未登记的文字维持历史记录 |

同一条用户请求内，后台经原接续事务恢复任务，读取检查点中已选定且尚未派发的条目调用，再通过当前可见工具、用户事件及原生受理核验。存在更新的用户输入或缺少接续证据时，交还模型按当前上下文决定。失败样本中未登记的历史文本保留原样。

## 持续验收范围

1. **定清字段及状态。** 先对齐 L3–L6。用现有成果、目录、任务接续、调用绑定和快照表示数据。逐字段记录来源、校验点和失败状态；优先统一 `compile_input` 的消费证据，复核旧区间映射只核验已有受理/恢复记录。统一前后端的「草稿、已登记、已受理、已交付」状态含义，尽量沿已有事件和 UI。
2. **先完成一条真实样本的全链。** 用两条失败原记录和六方案原素材，按先写、改第二条、另起下一轮选单项、选择全部的用户操作回放，并执行 U3 的单轮文生图和带参考图执行。检查保存正文/页面/原生参数的逐字摘要，原图字节、实际比例、请求身份及日志；图片供应商用替身，核对从受理到终态回执。错误来源和未登记文案应在映射前被拦住，既有结果保持可见。
3. **验证同一个架构用于视频和 Word。** 用含中英文、换行和开头结尾空白的同一修订稿，视频截获原生供应商请求，Word 打开实际生成文件。普通聊天和已有只读工具样本用于核对 AI 是否只在需要时发现和使用工具。工具不支持的规格和素材各走一条明确失败用例。
4. **验收边界和恢复。** 对同一请求重发、发出后立即改稿、写入后断线、已受理后丢失回执、部分项失败、权限失效、暂停继续等情形，逐项核对原任务和操作 ID、确认和计费事实、已有产物、刷新后的展示。对同一状态分别比对前端消息、检查点与后台账本。
5. **交付范围。** 优先改现有 `execution_engine`、`direct_loop/followup`、`content_objects` 与对应原生适配器。仅在现有文本事件无法可靠区分成果块时补最小展示字段。当前规划复用现有表和状态字段；若证明检查点或幂等机制需要修改数据库契约，先核对旧快照兼容和回滚范围。发布可回退应用路径，已受理快照和产物保持可核验。独立报告本地、真实模型及线上证据；付费模型调用另报预算，原图回放使用替身。
