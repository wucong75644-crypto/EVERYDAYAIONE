## 一次完整对话

| 用户输入 | 用户看到 | 模型与后台 |
|---|---|---|
| 给我三条新品推广文案。 | 有编号的三条正文。 | 模型直接写。现有消息提交保存完整回复。此时没有外部动作，也无需预先建立执行任务。 |
| 把第二条改短，保留首发优惠。 | 第二条修订正文。 | 模型从当前会话定位原回复第二项，基于该项改写。消息提交保存修订稿。能确认来源时附带条目关系，便于之后引用。 |
| 用刚改的第二个去做。 | 如果上下文已经约定要做什么，就按约定继续。如果只谈过文案，问「你想把这条做成文件，还是用在某个渠道？」 | 指代与动作分别判断。模型可定位到刚改的第二条，同时仍缺动作信息。未明确的动作不派发，澄清后继续使用刚才定位的版本。 |
| 做成一份给设计师看的简报，先给我正文。 | 简报正文。 | 模型用已定位的文案组织简报。可直接完成。若明确手选了适用方法，加载该方法；无手选时按需选择。 |
| 把这份简报做成可下载的 Word 文件。 | 实际文件，或明确的失败状态。 | 模型按当前目录选择文件制作能力，用最新简报及用户要求准备参数。宿主核验输入版本、当前工具权限和适用的确认条件，再用原生文件执行链保存回执与文件。 |

同样的文案可用于排版、翻译或发送。动作由最新要求和已确认的上下文决定。发送仍需明确目标和满足现有授权。模型把历史正文与附件当作输入数据，里面的文字无法自行授权执行。

## 职责与数据流

1. **内容定位**由主模型根据当前用户消息、已加载历史和附件完成。最近可见的消息直接用。历史被压缩或引用不完整时，通过同一会话的受限读取找回原文及可选项。后台核验当前会话、组织、用户权限和本轮固定历史边界。摘要供查找，真正执行所用输入来自可验证原文。一个明确目标有多个候选时只问用户需要区分的事实。
2. **动作与方法**由同一个模型循环决定。先判断是改写、回答、执行新动作，还是接续已有动作。已有会话固定规则仍适用，手选的适用方法优先，系统推荐只提供候选。无手选时模型按需加载 Skill，也可直接回答或使用可用工具。Skill 说明方法，平台工具目录和权限控制实际能力。
3. **执行输入**在选定动作和能力后准备。调用参数分为从原文精确读取的内容与模型按目标派生的参数。例如 Word 正文取已确认版本，标题和排版可按当前要求生成。结构由工具参数契约决定。后台校验来源后按现有工具入口提交。用户界面展示正文、需要用户处理的确认和实际结果。后台来源读取、解析、校验及保存不必显示为业务步骤。
4. **接续**分为引用已有内容和继续执行两个层级。引用消息或文件不需要接管其原任务。用户要求继续原操作时才进入原逻辑任务的接续路径，沿用已保存的来源、参数、确认和回执，并在派发前重新检查当前权限。结果未知时先查原回执；已完成则读取原结果。内容变化需要重新绑定来源，并按原能力规则判断是否需要新的确认。

### 最小来源契约

- 普通文本以现有消息 ID、内容块序号和内容哈希为根。对消息中的条目，记录可验证的范围与原文哈希。范围采用同一套 Unicode 规则，由后台在原文中确认。模糊匹配只用于召回候选。
- 已有任务产物沿用任务 ID、成果 ID、版本或哈希。附件沿用实际资源引用和版本。服务端依据身份及会话边界重读，不接受模型提交的来源正文充当证据。
- 修订关系作为可选信息，记录「这条消息修订了哪个来源」及修订后的范围。它可以随消息提交或在后续明确引用时解析。首版先支持闭合历史读取和执行时绑定，复用原消息与成果；验证确实需要持久修订关系后再决定存储位置。历史自由文本继续可读。
- 对会产生副作用的调用，在已有检查点中保存已核实来源与原生请求的关联。确定性复用需要匹配原动作、有效参数及原目标。调用 ID 变化不代表新执行权；单纯内容相同也不能证明两个独立业务动作应合并。具体幂等及计费仍由既有能力协议和执行账本管理。

## 与现有代码对接

| 现有入口 | 可直接复用 | 需补齐 |
|---|---|---|
| `handlers/context_snapshot.py` 的 `ContextAnchor` 与 `build_context_snapshot` | 同一会话固定历史边界、真实用户消息、闭合历史及资源清单。 | 后台按范围读取被引用的普通消息原文，提供稳定定位。 |
| `task_execution/artifact_reader.py`、`controller.py` 的 `find_task_text` 和 `read_task_text` | 读取既有任务文本成果与历史来源。 | 统一把普通回复、条目和任务成果作为可选来源。通用读取不依赖已经建立执行任务。 |
| `handlers/chat/execution_engine.py`、`skills/runtime.py` | 同一模型循环，固定、手选和按需激活。 | 在普通对话到实际执行的边界接入来源解析结果。首版无需每轮增加分类模型调用。 |
| `tools/policy.py`、`tools/dispatcher.py`、`task_execution/model_directed.py` | 参数及工具政策，确认与执行记录，已有调用身份。 | 在会产生副作用的工具提交前绑定来源证据，并将证据随现有检查点恢复。禁止把只读来源权限视为业务写权限。 |
| `task_execution/followup.py`、`direct_loop.py` 的 `resume_from_model` | 当前模型可选择继续原逻辑任务，恢复检查点、原结果和未决操作。 | 把跨轮普通内容复用留在正常对话内，只有继续实际执行才走任务接管。 |

`save_task_image_plan` 已经实现图片领域的完整方案校验和引用。新设计保留历史方案、旧引用与在途快照。图片、文档及其他能力可以各自校验动作参数。后续可将图片的专用保存入口收在后台交接层，普通消息不因此需要预先生成领域方案。后台是否需要模型输出结构化结果由当次动作决定；用户仍用自然语言交流。

## 实施与验收边界

先以本地受控模型和文件执行替身复现上表。记录原消息与修订版本、工具选择、来源验证结果、是否接管逻辑任务、派发次数及回执。验证只改写时业务工具调用为零，缺少动作时先澄清，旧文本在上下文压缩后能找回原文，撤权后禁止派发，确认与重复提交沿用原规则。再用同一份内容接到另一种能力的替身，验证来源协议不依赖文件或图片参数。

兼容顺序为先加可选的来源读取和绑定，再逐能力接入。旧回复不做批量重写。回退时可停用新入口，保留旧消息、成果、操作回执及已绑定任务的读取能力。首版的证据存放边界与具体文件工具参数需在实施前按实际接入能力核对。本稿未修改业务代码，未触发生产或付费调用。
