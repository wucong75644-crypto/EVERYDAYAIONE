# 两个图片 Bug 的真实客户对话验收（2026-11-25）

## 验收口径与环境

用户要求验证两项修改：统一图片编辑参数，保留不同来源选图；同一会话切换任务后，不把旧任务结果冒充新任务回复。按客户文字发送，不预设模型工具调用或目标绑定。核对实际模型请求、工具参数/纠错、真实原生子任务、底图字节指纹、供应商结果和最终图片消息。

在本任务独立工作树运行，本地临时 PostgreSQL/Redis、测试用户和会话，走 HTTP 消息入口、Actor、生产同源模型适配器、KIE 和 OSS。没有访问生产数据库或部署；真实模型和供应商调用产生外部使用量。原始完整 messages/tools/SSE、路由、检查点、原生任务、WebSocket 记录、图片和临时数据库转储保存在本机私有目录，未写入仓库或输出密钥。

实际主模型为应用非思考模式选出的 `qwen3.8-flash`；图片为 KIE `gpt-image-2-image-to-image`。不能把该配置的结果推广为所有模型或所有客户情境。脚本是 `backend/tests/manual_two_bug_customer_acceptance.py`，复用真实 HTTP/Actor 验收夹具；测试用户认证和本地数据库隔离替换，模型响应及供应商图片未 Mock。供应商故障保留原任务，不自动重新付费提交。

## 第一轮：真实测试暴露的失败

证据：`/private/tmp/skill-supplier-two-bugs-customer-7188657012/`。

- 初次上传，要求暖米白背景、保留商品：实际生成并发布 1254×1254 图片，来源正确，无工具错误。人工查看仍见商品构图/裁切与部分文字漂移，视觉保真不判完美。
- 对上一张说“背景换成浅蓝色”：模型重复填写底图素材，触发两次重复来源错误；后来受理了正确底图，但继续无效查询并出现受理后“未提交”说明。真实图片供应商最终返回 `Image fetch failed`。没有以受理代替成功。
- 引用较早图片编辑：路由把文本前置消息中的实际图片位置 1 填成 0，路由失败，主模型未成功纠正，无新图片。
- 讨论新任务再说“开始生成”：仍试图选旧任务；原生接回还因旧 inline 检查点字段冲突失败。没有把此结果计为通过。

第一轮实际付费提交 2 次。原失败保留，未用修改后的结果覆盖。

## 第二轮：修正后的局部通过与剩余失败

证据：`/private/tmp/skill-supplier-two-bugs-customer-c86891b671/`。

- 把第一轮实际产出的图片上传到全新测试会话，再要求浅蓝背景：底图指纹一致，真实模型完成受理，0 次工具错误，单次业务调用后由宿主依据原生回执结束。图片供应商仍报同样抓取失败。这是模型参数/来源链路通过、最终出图失败。
- 新图新任务只复述不生成：没有派发，记录为新的业务焦点。
- 随后泛指确认：误选旧内容被后台阻止，但模型纠错抄入后台 hash 字段，不能成功完成新任务。无旧图冒充新图，也无新图成功交付，因此业务验收失败。

第二轮实际付费提交 1 次。连续浅灰、旧浅蓝图查看/重做因前序无成图未执行，不能写成通过。独立 GET 验证上一轮生成图片 CDN 返回 200 且字节指纹一致；这不能证明 KIE 内部为何抓取失败，暂不能归因给 URL 或图片大小。

## 根据真实证据补齐的机制

- 当前真实用户输入在完成前是 pending、context_revision 可空；同源候选查询纳入该认证输入，仍保留历史消息完成/版本/租户边界。
- 同一底图又列入 input materials 时去重；角色冲突仍拒绝。
- 选图路由使用可枚举短引用，后台映射到真实 message/index；不要求模型数含文本消息的位置。
- 业务焦点与是否生成分开：新设计讨论保留为 current_request；无关解释只有显式 retain_previous 才不覆盖。没有用户关键词匹配。
- 模型上下文按当前焦点提供原始需求，历史恢复候选不占用“当前需求”位置；后台 hash、执行窗口等验证字段不进入可填写目标投影。
- 纠错返回具体结构约束；执行前可纠正语义目标，原生归属和版本验证继续保留。明确底图来源不因错填 current_input/active_request 的等价关系切换图片。
- 接回 SQL 区分旧执行事实与当前窗口字段，保留新目标/输入，清除旧 inline/解释标记；不删除已受理操作或放松租约/指纹校验。
- 单张已受理编辑按本次回执结束，不靠模型重复查询猜测成功；后续独立图片消息发布才算真实完成。

## 第三轮与最终回归

证据：`/private/tmp/skill-supplier-two-bugs-customer-88f5b32942/`。本轮实际提交 2 次，均生成并通过原生图片消息发布；三轮合计 5 次真实图片提交，3 次完成、2 次供应商失败。没有自动重购失败任务。

| 客户对话 | 最终业务结果 | 模型传输记录中的工具错误 |
|---|---|---|
| 上传 A，只换暖米白背景，保留商品 | 实际生成并发布；来源正确，视觉保真不判完美 | 7 次：两次合法 draft 同底图被误拦，其后无效状态查询等 |
| 上传另一张 B，把五角星改细线月牙，先复述不要生成 | 只讨论，无图片派发 | 0 |
| “没问题，开始生成吧。” | 最终使用 B 原图并实际生成月牙版本；未用 A 的旧图作答 | 1 次纠错字段不完整，随后成功纠正 |
| “把前面暖米白色背景那张原图再发我看看，不要重新生成。” | **失败**：最终只有文字，未向客户交付图片；没有派发新生图 | 2 次展示引用与所选目标不一致 |
| “回到前面暖米白色背景那个版本，再生成一张……” | **未执行**：上一项展示断言失败导致原脚本退出 | 不计通过 |

本轮模型路由仍有误选：确认 B 时先选过 A 的旧内容，主模型后来通过纠正工具改为 B，才执行正确。它证明纠错可完成本次任务，不能证明路由稳定率达标。旧图展示中模型看到图片和客户收到图片是两回事，不能把 `view_image` 的视觉读取或文字“图已取到”算成交付。

原 `customer-results.json` 曾把无派发的展示回合标为 passed，随后的外部图片断言实际失败。原始记录不改写；`pytest.log` 退出 1 和 `customer-wire-audit.json` 保存真实失败及全部控制工具错误。已把交付断言移到回合验证内，并把完整模型传输中的错误纳入严格验收，避免渲染工具块未显示控制调用而漏计。没有重新付费运行这个修正后的脚本。

第三轮后补齐两处有直接证据的小修正：同一所选底图的合法 inline draft 不因缺少 edit 简写字段被误拦，仍核对第一个真实供应商输入；纠正成功回执也隐藏宿主 hash/执行窗口。新增正反例回归通过；这两处最终代码尚未再进行真实模型/供应商复测。

最终受影响单元/合同回归：468 passed、4 skipped。隔离数据库两种所有者分别 49 passed、9 skipped，合计 98 passed、18 skipped；跳过的是既有私有样本条件。日志 `/tmp/two-bug-acceptance-final-unit.log`、`/tmp/two-bug-acceptance-final-pg-runtime.log`、`/tmp/two-bug-acceptance-final-pg-owner.log`。固定响应和 MockTransport 用例不计为真实模型/真实出图通过。

## 当前结论

**验收未通过，不能宣布“两个 Bug 已完美执行”。** 首次编辑和新任务确认各有真实出图证据，但仍出现纠错、选错目标后恢复、旧图展示未交付；连续改图的供应商抓取失败未解决。不同历史选图、连续多次改图、按旧方案重做尚无完整真实通过证据。

固定响应回归可证明归属/版本/恢复等不变量，不能替代上面的真实客户结果。下一步应优先解决动作路由与主模型目标不一致、目标纠正合同复杂、只读查看与客户交付未闭环，再对相同客户语句复测；供应商抓取失败需独立诊断，不能靠重发旧结果掩盖。没有提交、生产迁移或部署。
