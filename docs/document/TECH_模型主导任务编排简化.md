# EVERYDAYAIONE：模型主导编排的简化方案

## 2026-11-02：右上角任务计划与执行账本分离（本地验证完成）

用户确认普通读表/计算不应因为工具调用登记而显示多任务编排。根因是新模式直接把 TaskState 存在当作公开进度入口，而有计划无原生工具时又没有可读状态。当前修复沿原 Actor、checkpoint、进度接口、ToolRuntime 和消息恢复链实施，不新增执行器或规划模型调用。

- 新模式只有模型显式保存非空工作计划才发出可见计划发现标记；普通 code_execute 仍登记完整账本、防重复调用和真实回执，不创建可见计划。旧模式原计划/步骤展示保留。计划更新与清空携带内容版本，保存成功后再发布，失败恢复原上下文及内容块。
- 模型拥有步骤名称及待处理/进行中/已记录完成状态；具体目标名称逐项展开显示，不按工具次数制造用户任务。模型标记完成不代表真实成果核验通过，整轮结束只显示“本轮执行结束”。
- 迁移373只扩展原 read_agent_task_progress 只读函数：没有 TaskState 时，从原消息绑定的、同轮次有效 checkpoint 读取明确归属于当前任务的工作计划。沿用原 actor/org、活动用户/企业成员、会话所有权及 assistant message 校验；不伪造 TaskState，不改操作权限或成果记录。原 TaskState 查询与回滚保持兼容。
- 顶部“查看任务”弹出面板取代正文 task_progress 卡片。旧版本留下的普通执行标记经原鉴权读取确认无计划后隐藏并停止轮询，不计入计划数量；旧真实计划仍可读取。计划版本变化使列表重新读取，不让缓存的旧名称覆盖新要求。计划-only checkpoint 版本和原生执行 revision 分别处理，只允许从前者进入后者，不倒退。
- 一个逻辑任务的续接合并展示，保留原任务标题，使用最新源消息；任务内部各项工作名称单独列出。面板展示原消息加载链已加载的最近计划，不另建任务索引。切换会话中止旧读取，关闭面板卸载轮询；错误读取不保留旧成功状态。
- 原工具步骤、错误、确认、正文和已有成果保留。暂停/继续/停止沿原消息接口、handleResume/applyTaskResume、订阅与重载，不复制恢复链。完成的纯标记消息不误显示“已取消”；中断消息原恢复入口保留。Skill、ERP Agent、新增ERP写适配关闭状态、上下文、权限与计费不改。

本地最终验证：后端140项通过，前端106项通过；生产构建、类型和PDF worker检查通过。验证使用禁用模型密钥的本地替身和独立 loopback PostgreSQL；涵盖普通计算、计划先于工具、计划清空/修改、多项名称、旧标记、跨会话、失败保存回滚、消息协议、原恢复/确认/去重，以及迁移前后/回滚、个人和企业权限撤销。未进行付费模型测试、未生图；发布状态以受控 release 记录为准，页面实际视觉及生产业务验收仍未进行。以下为原设计历史记录。

## 结论与决定对象

推荐在原Actor、Gateway和ToolRuntime执行链内，将通用任务从强制“提案—独立语义核对—计划—手动完成登记”改为主模型连续行动。模型的工作计划与宿主的真实执行记录分开承担职责：计划辅助推理，不授予执行权限，不要求预先覆盖所有未来步骤；操作身份、权限、确认、原图/文件版本、预算、受理与完成回执仍是强制约束。

这不是删除所有程序控制，也不是替换成另一个Agent框架。公开实现并非统一标准：自主循环、明确计划模式和固定业务工作流都存在。选择模型主导是为了匹配本产品的开放任务，并非证明现有每项检查都错误。

## 当前代码查明的事实

- ChatGenerationExecutor在符合范围的个人会话建立TaskBootstrap；普通单步聊天/查询可直接走原循环。不是所有消息都被强制创建逻辑计划。
- 主模型提出start_task_execution的action、交付种类/数量、原文证据和适用方法。新bootstrap启用require_coverage_review；requirement_review的v2会以另一轮模型独立提取交付，再由宿主比较，可能缓存复用，也可能纠错/等待输入。
- start_task_execution和update_task_plan作为控制批次屏障；同批业务调用不直接执行。模型随后需要继续发起调用。
- 特定图片/方法文本通过save_task_text保存后，complete_task_step可能触发plan_facts另一轮模型核对；已保存规划、事实核对证明、原图资源绑定、ready步骤共同影响generate_image放行。
- TaskState包括requirements、steps、artifacts、results、operations。完成要求所有计划步骤结束、要求具有相应可验证成果、无reserved/accepted/uncertain操作。客观事实检查与模型语义核对不是同一种机制。
- 用户追加要求和跨任务接续另有语义核对路径；同时保留原始输入、修订版本、旧派发拦截、成果与操作账本。这些能力不应一并删除。
- 图片及写操作的binding、operation_store/native_writes和部分数据库RPC直接依赖step_id、effect_key、requirements_revision。340/341及后续任务迁移有服务端一致性检查。当前结构不能简单取消计划、直接裸调用业务工具，否则可能绕过持久化身份/结果绑定。新协议须逐一复核最终有效RPC，不能只依据最初迁移编号修改。
- 当前正式状态version仅支持1，Pydantic extra=forbid且服务端也校验版本/结构。不能宣称这次只改提示词或一定不需迁移。
- ToolRuntime已有独立的权限、模式、参数/资源版本、确认、执行生命周期及缓存/重放顺序。它是简化后继续使用的执行入口，不应复制一套。

## 建议的工作方式

用户输入经原受理/排队/上下文加载交给主模型。模型直接回答，或按实际信息缺口调用已有工具/Agent。复杂任务可以使用已有计划入口维护目标、待办和阶段进度，也可以先完成明确的业务动作再补充计划；不要求一次预测全部步骤。

每次工具调用仍沿ToolRuntime检查真实权限/确认、资源和预算。需要持久保护的业务操作，由宿主在原账本内建立/复用稳定执行记录并保存检查点，再实际派发。结果回来后自动登记能够证明的执行事实与产物，交给模型决定后续。无需模型再发一次“导入回执/标记步骤完成”才能让程序承认已经成功的原生操作。

不存在真实操作/产物的todo不能变成执行凭据。工作计划改名或删除不得清除操作历史、付费记录、用户原要求或已有成果。依赖某工具输出的下一次调用仍要等待真实结果，不能为省模型轮次假装依赖已满足。

## 具体保留、简化和移除

| 当前机制 | 建议 | 必须保持的边界 |
|---|---|---|
| 通用start_task_execution前置 | 不再要求所有多步工作先完成该控制仪式；按需记录计划 | 原请求/选定Skill/上下文仍完整保留 |
| 默认独立要求抽取与覆盖评审 | 新通用执行不再固定调用；主模型维护任务理解 | 不能把其提案视作新增权限或付费授权 |
| 默认图片规划事实评审 | 从通用执行必经门改为显式质检或明确业务工作流的按需能力 | 原图身份/访问/版本、实际参数和原文提示词绑定仍强制 |
| update_task_plan必须覆盖全部要求、每次改动阻断工具 | 改为可修订工作记录，不因未来步骤未列齐就阻断当前合法动作 | 保留已受理/已完成操作的稳定身份与历史 |
| 每项真实工具成果都要模型导入/complete | 原生适配器在原事务链自动登记；工具没返回的不能自动认定 | 不能拿“success”文字伪造文件、图片或业务回执 |
| 通用模型独立修订/接续评审 | 新协议由主模型阅读真实追加指令并调整工作；取消默认复核往返 | 保留输入版本、旧参数派发拦截和接受不明状态 |
| 现有Skill协调 | 保留用户选择来源、真实Skill正文和兼容/权限约束 | 不因关键词换掉手选方法；不将所有任务强制套入电商规划模板 |
| 业务自身的前置约束 | 保留。例如明确要求先规划/用户确认、原ERP表单审批、plan只读模式 | 主模型不能自行升级权限或跳过用户明确流程 |
| 防重、预算、原生回执、上下文/检查点、异步消费者 | 保留并与可选工作计划解耦 | 不能通过关掉整个agent_task_execution开关冒充实现 |
| 模型判断已完成 | 可结束当前回复；系统按真实操作状态显示完成/等待/部分完成 | 不能让语言承诺覆盖尚未完成/不确定的实际任务 |

不建议“所有逻辑删掉、只相信模型说完成”。也不建议仅合并几个工具名但底下仍原样轮流评审；这会保留原复杂度和成本。

## 最重要的授权与能力取舍

1. 原ToolPolicy的权限和审批来自宿主真实上下文；模型的新计划/自报意图不授予权限。新增或更改参数后，原确认按既有绑定失效/重新核实，不能复制旧确认。
2. 删除独立语义评审后，不再提供“每次理解错误都会被另一轮模型拦住”的旧产品保证。自然语言的“只要提示词不要生图”需要模型遵守；若产品要硬保证该项，必须有宿主可验证的只读/仅文字模式或既有明确执行确认，不能依赖同一模型返回一个布尔值。不能声称不增加确认、删掉语义检查同时又绝不误解意图。
3. 不建议默认每个工具都新加一次用户确认。沿原权限模式处理；有实质付费/不可逆歧义时澄清/确认，明确已授权操作不反复询问。
4. Skill方法要求仍应遵守，不能为了更快跳过用户明确要求的分析/完整提示词。放宽的是通用宿主审批仪式，不是删除用户交付。
5. 真实Skill冲突返回可修正原因，主模型可以补依赖、替换辅助Skill或分阶段交接；不能暗中丢掉用户手选，也不能因一个辅助Skill不兼容就把整段聊天当作系统崩溃。无法兼容用户明确选择与目标时说明冲突并澄清。
6. 程序可以证明文件存在、图片已完成、某笔操作仍在等待，但无法仅凭这些证明所有自然语言要求或设计质量已满足。主模型负责解释、对照目标和质量判断；用户明确需要额外质量复核时再使用核对能力。

## 执行账本如何保持可靠

- 复用现有状态/事件/operations/artifacts和原事务、执行token与版本校验。工作todo不再是创建操作身份的必要条件；业务调用首次受理时由宿主生成相应执行记录。
- 操作身份必须保持用户指令版本、真实参数、资源版本、业务输出槽或对应实际操作的绑定；不能仅按prompt哈希去重。相同参数可能是用户要求新的多份成果，也可能是重试，不能混淆。
- reserved/accepted/uncertain先核实已有操作；禁止通过换调用ID、改todo或重启绕开。结果不明时等待/反馈，不能自主重复花钱。
- 校验错误且可确认未派发时，模型可以纠正参数；实际业务请求是否受理不明时先用现有回执查询协议。预算按已用费用/轮次保留，不无限自动循环。
- 原始工具结果和产物持久化后才对外声明成功；登记失败不能展示为完整成功，不能因模型最终回复就丢掉待核实操作。
- 确认可复用的旧图片/提示词/文件继续复用，保留来源。新要求只使不再符合要求的关联失效，不删除原成果。

## 新消息、恢复与异步

- 真实新用户输入仍通过原命令/消息锚点进入。主模型看到原指令、修改内容及执行事实，不由关键词切整套流程。
- 派发前比较当前真实输入版本；旧轮次生成的付费/写参数失效后不能继续执行。已受理操作仍核实结果，不能假装撤销。
- 异步图片/视频/确认等待沿原持久事件和消费者唤醒；没有新事实时不重复调用模型“看看好了没”。只读后台补偿不是新的模型轮次。
- checkpoint保留真实消息、Skill版本/阶段、原图资源、操作身份/状态、产物来源、预算和用户修订；工作计划只是一部分，不用摘要重建已经存在的完整提示词。
- 区分对话回复结束、异步执行结束、用户目标满足；未知结果保持等待/部分完成，不能合并为一个completed。

## 范围与兼容

不改知识检索算法及背景准备、前端流式/终态对账、模型供应商/型号、原ERP Agent、现有工具业务实现或发布链；新增ERP写适配继续延期。398发现的检索逐层往返、ERP默认时间和审计分区问题保留为独立未解决项，不暗中并入。

必须为新语义增加明确的版本/策略兼容，而不是全局关闭保护。旧活动任务按原冻结协议恢复，不在继续时悄悄放宽审批；新任务沿同一engine进入新语义。数据库修改只加前向迁移，不改已执行迁移；具体字段和最终RPC需在方向确认后完成实施设计。

回退首先停止新增任务使用新语义，保留已经产生的操作、状态与恢复能力。不能把未知新检查点直接交给旧14077717程序解析；启用前必须验证兼容回退版本/数据格式。旧状态只读恢复、原不透明扩展和上下文边界不能因迁移丢失。

## 已确认的实施顺序

A. 固定当前行为、状态/RPC调用图和免费历史验收素材；先设计计划与账本解耦及兼容边界。
B. 同一执行链实现主模型连续行动、可选计划、原生结果自动登记，收回默认语义评审/逐项控制调用的前置地位。
C. 接齐通用参数与原图来源绑定、权限确认、旧任务恢复、新消息版本拦截、异步续接与结果复用；原Skill专项阶段另行修复。
D. 整套完成本地验证再形成受控部署候选。真实供应商验收另报样本、费用与次数，用户确认后才运行。不以分批开发为由留下双套未完成链路。

不承诺仅改几个函数、零迁移、固定减少多少秒或调用数。目标是消除人为固定模型往返，而不是保证所有业务步骤一次完成。

## 验收与性能证据

先用脚本 Provider、原生传输替身和隔离 PostgreSQL 验证宿主；复用已有协议与失败/恢复测试，不把它当真实千问语义或生产性能成功。原两个 Skill 专项验收移至后续任务。

- 普通聊天/知识问答/单次ERP只读：不新增固定规划、分类或复核调用；原流式和知识按需工具不变。
- Skill 选择与加载不在本轮重做；专项提示词/套图方法问题另行处理，不作为本轮完成门。
- 已有提示词直接执行：原文/原图/版本匹配，失败或压缩后不重写；已有可用图片不重复生成。
- 参数错误、权限拒绝、审批拒绝、受理丢确认、原生登记失败：分别给出可纠正、终止或待核实状态，不盲重试、不伪造成功。
- 新消息与旧派发交错、暂停/取消/继续、重启、断线与刷新：真实输入版本和执行token仍有效，保留原成果与账单。
- 异步图片/视频/确认：一次受理、事件续接、无结果时不反复模型轮询；完成/部分/失败如实交付。
- 旧检查点、历史导入、其他入口/渠道、原ERP查询与新ERP写关闭：不扩大范围或丢功能。

按同一输入/上下文/Skill版本记录：受理与排队、上下文准备、模型首正文、第一次实际业务调用前的管理类调用数、总模型轮次/真实工具调用、等待阶段、积分及最终交付。脚本比较只证明宿主开销消除，真实模型质量/页面延迟需要另行授权验证。最近57积分的知识查询没有进入结构化编排，不可用它宣称本次改造能省掉同样费用。

## 已确认决定

用户已授权：通用任务默认由主模型连续推进，计划用于工作记录；取消默认独立要求/修订/规划事实语义评审和逐项手动成果登记，保留明确业务流程及客观安全/回执约束。接受语义误解不再由另一轮模型固定拦截的取舍。范围内已实施，当前证据和未执行的生产/真实模型验收见 IMPL 文档。
