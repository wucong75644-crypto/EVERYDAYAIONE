# 变更审查

共同约定：[共同协作规则](../../../docs/development/COLLABORATION.md)。本 Skill 的职责边界不构成新的用户确认门；已有授权与证据按共同规则继承。

## 目标

判断本次实现是否正确满足已确认需求和设计，并识别会造成真实错误、风险或维护问题的高置信发现。

审查是只读诊断工作。除非用户同时要求修复，否则只报告问题，不修改代码、文档或外部状态。

## 准备

优先复用同一任务已经确认的任务地图、范围、最终差异、调用链、设计决定和测试证据。证据缺失、状态变化或彼此冲突时，才通过 Git 状态、目标差异和相关文件定向补充。用户已有或无关变更必须区分并保护。

Review 不启动新的全量调查阶段。已有证据足以支持审查时不重复读取、重新建立调用链或重跑测试；不足时只围绕明确缺口逐步补充相关变更文件、上下游调用方、类型、状态、数据访问、需求、设计和测试，使审查能够追踪：

```text
需求与决策 → 设计 → 实现 → 测试
```

没有现成文档时，根据任务上下文重建最小验收依据，并明确证据限制。

## 审查方式

根据变更本身动态选择能够发现不同风险的专业视角，不使用固定角色清单限制审查，也不为了凑数量制造角色输出。

无论选择什么视角，都必须检查代码正确性、信任边界和变更影响。其他视角只有在与当前改动相关时才加入。

数据库、安全、权限、核心状态、生产事故或其他高风险变更中，独立性能够显著提高发现质量且工具条件允许时，可以让不同代理独立审查后汇总。普通低风险任务不得为了流程形式拆出独立审查。

检查清单只能帮助发现遗漏，不能替代对代码和系统行为的理解。任何发现都必须对应具体代码、可复现场景或明确违反的项目约束。

## 重点判断

审查当前实现是否：

- 满足已确认需求和成功条件；
- 遵守已确认决策和设计边界；
- 保持调用方、数据和协议兼容；
- 正确处理实际相关的失败、状态和时序；
- 在输入、权限、数据和副作用边界上安全；
- 没有引入无关复杂度、死代码或不可维护耦合；
- 具备与风险相称的测试和运行证据；
- 同步了必须更新的文档。

审查Bug修复时，必须判断实现修复了经过验证的根因、恢复了相应系统约束，还是仅在症状位置增加默认值、防御分支、重试或异常吞噬。只有止血措施时，必须确认其被明确记录为尚未根治。

这些是质量目标，不是要求机械输出的固定章节。根据变更自由扩展到其他真正相关的专业问题。

安全判断必须结合实际认证方式、信任模型和输入来源。例如，不能脱离上下文把所有状态变更都判定为 CSRF，也不能因使用某种函数就自动认定存在漏洞。

重复、复杂度和结构问题必须判断实际维护风险。项目确有硬阈值时按适用规则执行；没有明确门槛时按实际维护风险判断，不从旧提示词恢复固定行数规则。

## 测试证据

直接复用 `test-coverage` 留下的验证结果，判断它是否仍有效并覆盖当前风险。

对于Bug修复，检查回归证据是否能够关联用户症状、因果链、根因机制和同类入口。只覆盖最终报错代码行不足以证明系统性问题已经解决。

证据不足时只补充缺口对应的定向验证。代码内容、配置、依赖、环境和范围未发生相关变化时，不重复已经通过且仍覆盖风险的测试；不得在 Review 中默认重跑全量测试。

测试失败要区分本次回归、既有失败和环境限制。不能把无关失败归咎于当前变更，也不能因环境受限宣称通过。

## 发现与严重度

只报告有充分证据、会产生实际影响且能被开发者采取行动的问题。

每个发现应包含：

- 简短结论；
- 精确文件和行号；
- 触发场景；
- 实际影响；
- 严重度及依据；
- 最小修复方向。

严重度根据影响和发生条件判断，不由固定检查项预设。阻止合并的问题必须说明为什么当前实现不应发布。

不报告纯风格偏好，不把未经验证的担忧写成确定缺陷。低置信风险可以作为待核验项单独说明，不能混入正式缺陷。

发现位于未改动代码时，只有它被本次变更新增路径触发或属于高风险安全问题才作为当前审查发现；否则按无关异味报告，不扩大修改范围。

## 输出与结论

先输出按严重度排序的发现。没有发现时明确说明未发现高置信问题，并同时说明审查范围和未验证内容。

结论应包含是否可以接受、阻塞问题、必要的非阻塞风险、证据范围、环境限制和剩余不确定性。没有发现时不复述实现内容。

不要用冗长过程描述掩盖关键问题，也不要因为输出简短就省略必要证据。

## 阶段边界

本 Skill 不负责：

- 重新进行需求分析或方案评审；
- 擅自修改被审查代码；
- 为了给出问题而制造问题；
- 默认运行全量或外部测试；
- 审查与当前变更无关的整个代码库。

## 质量要求

高质量审查必须基于完整上下文、具体证据和真实影响。

宁可少报，也不要用固定角色、固定清单或表面模式制造误报；但不能因此跳过安全、正确性和兼容性硬风险。

## 交付格式

遵循项目 `AGENTS.md` 的增量精简输出合同。发现优先；无发现时只给结论、范围和未验证项。
