## 2. 已实现行为

### D0：模型只输出一份完整执行文本

原平台封装要求每张图的正向、负面文本同时出现在 `scheme_markdown` 和独立字段里，模型必须写两遍。现在模型的 `scheme_markdown` 完整填写前三节（方案内容、视觉设定、参考图使用方式），完整执行文本仅写入 `positive_prompt`、`negative_prompt` 各一次。程序按原文补齐展示稿的第四、第五节，并生成原有 `request_text` 及 SHA-256。

这是内部模型交付格式调整。落库、读取和现有生图消费仍为完整五节方案与完整执行稿；九栏目、比例保真、参考图身份与顺序、张数、画布和自检校验保留。仍兼容旧五节模型输出，但重复文本不一致时继续拒绝。三份专业提示词及哈希不改，没有删减设计内容。

`prompt_versions.stage_three_delivery_version=single-prompt.v1` 标识本批封装。复用上游时继续比较原专业资源、Schema、参考协议及模型设置，不因仅新增交付封装版本废弃有效阶段一／二。

### D1：第三阶段采用受控的输出封装处理

增加第三阶段专用解码入口；阶段一保持现有严格 JSON 解析，阶段二保持完整 Markdown。

1. 先等待 KIE 正常终止和完整 usage；部分流、超时、incomplete、取消仍不能产生 ready。
2. 完整响应必须以 JSON 对象开始，允许开头空白。用标准 JSONDecoder 解析一个完整对象并取得结束位置；不以正则截取、不从任意解释中搜索花括号、不修补缺失括号或字段。
3. 无尾部内容时走原校验；出现尾部时仅兼容明确的建议菜单：最多512个字符、12行，首行必须为“继续完善[这组／本组][商品]主图”“后续建议”或“可选建议”，后续行只能为项目符号及“优化／挑选／比较／查看”建议。拒绝结构括号、代码围栏、第二份 JSON、协议字段/状态声明、审核失败及执行变更声明。无法明确识别的尾部仍进入错误分支，不能任意选取多个候选中的一份。
4. JSON 内部的所有字符串逐字保留。拒绝重复键；完整 `validate_images` 继续核验结构、数量、图片顺序、引用身份、画布、完整正文及自检记录。
5. 只有封装尾巴且主体通过校验时，直接按本次 completed attempt 原子保存并结算一次，不标记 validation_failed、不再付费重写。正文或身份不合法时仍修正或报错。
6. 尾部内容不成为模型控制指令，不进入 `request_text`、主 Agent 工具结果或生图调用。

在现有 attempt usage/audit 中记录交付协议版本、响应哈希、JSON主体哈希、尾部处理原因与长度；保留原尝试编号和实际 usage。各阶段正常完成或异常还记录 `elapsed_ms`、`first_output_ms`、`output_characters`，用于后续分析真实模型耗时；日志不复制完整商品文案或供应商原始响应。

### D2：平台封装明确输出结束位置

仅调整 `prompt_resources.wrapper(3)`：JSON 结束的 `}` 后立即结束回复，禁止后续建议、解释、邀请继续和 Markdown 围栏。专业内容仍完整写入现有字段。

三份用户原始专业提示词及其哈希保持；入口 Skill v3 的既有调度与失败分支不改。新增交付版本和响应哈希写入尝试审计，不能因为封装措辞变化使合法的阶段一、二输出全部失效。

### D3：阶段三采用首包/空闲超时与不可续期总预算

当前 `_call` 显式传 `timeout=min(180,remaining)`；Gateway 对显式 timeout 使用总 deadline，因此健康流也在180秒结束。Gateway 已有预算内的空闲超时机制，可按请求显式启用，无需新建工作流框架或 KIE 客户端。

- 在 `ModelCallRequest` 增加可选的请求级 `idle_timeout`，默认值为空，现有调用行为保持。策划第三阶段传 `timeout=None, idle_timeout=180`；前两阶段继续原有阶段时限。
- 排队和首包合计受180秒限制；收到输出后，连续180秒没有新输出则停止。HTTP SSE 心跳不能刷新有效输出的空闲计时。
- 第三阶段始终携带只读 budget view，remaining 取父预算和 `reserve_ecom_plan_attempt` 返回的持久化截止时间的较小值，并给最终校验/保存预留约5秒。持续输出只能刷新空闲时间，不能刷新总截止时间。
- 保持现有600秒执行上限和每阶段最多3次持久化调用额度。跨轮、修正、重启不能另获自动预算；无父 budget 的内部调用同样必须受持久化截止时间约束。
- 对齐现有租约：有效阶段保存已把租约续至600秒，但直接复用阶段1/2进入阶段3时没有这次续租，当前claim公式只给560秒。初始claim改为既有RPC允许的600秒，模型仍受更早的总截止时间及保存预留时间约束；复验缓存续跑的流结束与原子保存，不新增定时续租器或延长执行窗口。
- 读取超时或部分输出继续归类 uncertain，保留有效上游，不自动重发付费调用。正常终止但真实内容错误才可进入剩余额度内的修正。

单纯把总超时改为更大常数，仍无法区分健康长流和卡死请求；取消全部时限又会破坏已有预算。上述设计分别约束首包、空闲和整任务耗时。

### D4：传回真实首稿，定位到某张时只替换该张

第三阶段首稿内部字段、引用或审核不合格时，在同一子 Agent 修正调用的数据区传递 `previous_stage_three_output`、`validation_error` 与 `repair_positions`，保留用户原文、上游完整结果和有序原图。首稿是待修数据，不能覆盖 developer 规则。

可定位到单张的错误使用 `ImagesRepairOutput`：只返回该张完整替换项与复查后的 `review_records`。服务端严格检查仅有一张、position 与待修位置一致，再按原稿数组位置合并并复验整组；其他图片保持原稿。即使原项的 position 缺失或错误，待修位置也以实际数组位置为准。模型返回整组、多张、错位置或缺字段时不采纳，也不更新原稿；后续调用仍使用原范围。下一张再有错误时沿用已修正草稿和同一个额度，不重新开始。

不能定位到单张的 JSON 语法或根结构／整组问题，传回完整原稿（无法解析时传原始文本）和错误，要求修正交付格式、保留有效设计。此类分支仍须重新交付完整 JSON，不宣称所有失败都能局部修复。

仍只修第三阶段，共享现有三次额度和总截止时间。现有模型上下文/请求大小限制继续适用，不能静默截断专业正文。尾部封装问题已经由D1处理时无需模型修正。
