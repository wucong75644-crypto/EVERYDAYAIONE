# 生图提示词与素材投递边界：Grok Build、官方接口与本项目对照

后续实施与真实Image2完整复测见[修复及验收记录](TEST_Image2执行稿职责修复与完整复测_20261123.md)。下文保留调研时点的事实与证据边界，不将建议冒充已证明的效果。

本轮只调研和核对，未修改业务代码、模型配置或数据库，未调用付费模型/生图，未部署。本文建议尚未实施，也不代表此前的商品保真失败已解决。

## 结论

用户提出的职责方向有依据：对话模型理解图片、需求和适用方法，形成面向图片模型的执行提示词；执行器把这份提示词、选定图片及支持的参数送出。**给对话模型的方法说明，与给图片模型的画面指令，是两种内容。**

但“所有大厂都一定润色”“图片服务内部绝不会再处理提示词”“提示词必须很短”均不是已验证事实。Grok Build 有明确原文执行入口；官方对话式图片工具也有模型润色入口。要区分产品入口和接口层级。

当前项目已发现两处实质差异：

1. 明确指定本轮底图的编辑分支，会丢弃模型的 edit_instruction，换成用户原话和程序模板；这不是普通对话下保留模型理解后的最终指令。
2. 电商方案执行前会拼入内部资源标识、第二阶段的整组规则原文及固定保真/负面段落；有必要的画面信息，但没有把执行内容和内部管理信息充分分开。

供应商适配层本身没有继续塞入完整聊天、思考或工具日志。污染/覆盖主要发生在其上游，不能只检查最终 JSON 有 prompt 字段就断言边界已经正确，也不能据此把出图错误全部归因供应商。

## 二、Grok Build 怎么处理提示词

### 普通工具调用

[ImageGenInput](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_gen/mod.rs#L365) 提供 prompt、aspect_ratio；[ImageEditInput](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L233) 提供 prompt、image列表、aspect_ratio。工具说明告诉主模型分别何时生成/编辑、如何描述图像、如何引用附件及处理结果。主模型填写调用参数。

后台[文生图发送处](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_gen/mod.rs#L224)使用传入 prompt；[编辑发送处](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L352)直接使用 input.prompt。**在这些已核对的客户端执行路径，没有再拼一套电商业务模板、固定负面清单或完整主模型系统提示。**

后台仍会增加API运行参数：model、n、resolution、response_format，多图时还有aspect_ratio。这些属于参数，不是追加画面语义。权限、令牌、文件解析、保存目录等由程序处理，相关工具说明给主模型使用，不作为图片正文整体下发。

### `/imagine` 是原文直传的显式入口

[imagine_instruction](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools-api/src/slash_commands.rs#L82) 明确要求立即调用图片工具，原样传用户提示，不扩写。[真正命令入口](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/src/slash/commands/imagine.rs#L23)将这段要求注入主模型。

这证明它会添加**主模型指令**，但不是把整段命令说明都当生图prompt。也证明“正常由模型整理”与“显式要求原文执行”可以并存，不需要后台在普通编辑时一律覆盖模型的执行文字。

### 图片绑定与顺序

编辑器通过当前附件登记表解析 `[Image #N]`，不让模型编造文件位置。随后按 input.image 的原有顺序逐张解析，形成同序图片数组；单图写image，多图写images。没有根据图片长宽、文件名或主观猜测统一重排为“底图必须首位”的算法。[对应循环与请求构造](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L352)。

ImageEditInput 文档中的“priority order”指附件token、用户给定路径、data URL这几种**引用形式的解析优先级**，不能误读成所有编辑的底图优先规则。

该客户端会按接口限制处理图片字节；小JPEG/PNG可原样，部分较大/其他格式会重编码。这是供应商兼容处理，不证明降低原图质量适合我们的电商保真场景，不能机械复制。

### 供应商内部是否还会加工

客户端发送 input.prompt，不等于整个供应商内部没有其他提示处理。其image_gen源码注释就说明部分Imagine模型会先扩展提示词。服务端完整私有逻辑不可见，因此不能声称“Grok绝不润色/绝不增加任何内部提示”。我们能验证的是本地工具参数到公开请求字段这一段。

## 三、官方产品/接口文档的交叉核对

[xAI对话式生图工具](https://docs.x.ai/developers/tools/image-generation)明确由主模型编写图片prompt，并在输出中提供实际prompt以便核对；已有精确提示词时，可用直接图片接口控制参数。这和开源客户端的职责方向一致，但不是同一个服务实现。

[OpenAI图片工具文档](https://developers.openai.com/api/docs/guides/image-generation#revised-prompt)明确：在Responses的图片工具模式下，主模型可以修订提示词，结果中的revised_prompt用于观察这份内容。这是API公开行为，不代表已取得ChatGPT所有内部提示或其完整网页代码。

[xAI图片编辑指南](https://docs.x.ai/developers/model-capabilities/images/prompting-guide)建议把本次改动放在前面，再说明保留项；还提醒大段重述完整新画面可能使编辑变成重新布景。这个建议支持避免把整份策划报告不断塞给编辑模型，但不是所有图片模型通用的强制字数或模板标准。

[xAI多图文档](https://docs.x.ai/developers/model-capabilities/images/multi-image-editing)要求按实际传入顺序理解图片；第一图默认影响画幅，但可显式覆盖比例。画幅默认依据不等于“第一图永远决定商品主体”，也不能外推成KIE所有模型的底图规则。

“图片位置”要区分：输入图序号/用途由实际图片列表与prompt对应；商品在画面中的位置则由构图指令表达。不能凭空为某接口增加不支持的position字段。

## 四、我们的真实调用链

### 普通聊天编辑

主模型可根据图像和需求输出编辑文字；单图成图继续编辑时，通常通过SingleImageEdit.content_item()保留edit_instruction。后台做来源、尺寸和授权核验后冻结请求，图片worker读取snapshot.prompt，KIE适配器序列化为prompt、input_urls、aspect_ratio、resolution。

实际样本manual17的蓝色编辑提示词238字符，有针对性地描述修改和保留内容，没有附带整个聊天或内部资源引用。

### 指定当前附件为底图的特殊分支

在 `backend/services/task_execution/inline_image_action.py:193–216`，先读取模型edit_instruction，然后在current_attachment_edit命中时重建ContentItem。重建的body使用legend和用户原文，**模型润色被覆盖**。

这段的初衷是保护真实选图、不让模型虚构商品，但它把两种职责绑在一起：验证哪个图片可以执行，是后台职责；怎么准确表达本次编辑，是模型职责。验证引用不需要顺便丢弃模型写出的执行语义。

双图波点样本实际最终prompt154字符，没有完整聊天，也没有内部资源字符串；因此该样本出错不能简单归因“大段报告太长”。当前能确定的是该分支的润色覆盖及角色投递边界有差异，不能据此证明搭扣错误的唯一原因。

### 电商方案按编号执行

`backend/services/agent/image/ecommerce_planner/assembly.py:48–78`负责从设计字段组装request_text：

- 本张目的、场景、构图、光线、文字等实际画面信息；
- 每张参考图的内部source_id、role和用途；
- 第二阶段第八节“整套共同边界”的原文，包括允许变化/建议的说明；
- 固定保真句、固定负面词和“不得重新策划”等执行说明。

这些共同进入同一个prompt字符串。manual17某条编号出图实际4329字符，包含fid/fref资源定位字符串。**长度本身不是缺陷；内部句柄、不适用于本张的备选内容、重复或相互竞争的规则才是需要治理的对象。**不能为了缩短而丢失整套图必须一致的视觉要求。

`backend/services/handlers/chat_image_preparation.py`按plan_id/revision/item_id读取保存原稿，核对权限、原文哈希和尺寸；这部分避免模型重新创作已选择的方案，应保留。

最后 `backend/services/handlers/chat_image_lifecycle.py:271`读取已冻结prompt发送，`backend/services/adapters/kie/image_adapter.py:320`写入KIE请求，没有再把系统提示/思考/任务日志加进prompt。因此应修正**最终执行稿形成之前**的职责，不应在图片适配器里用字符串替换临时删词。

## 五、逐项差异和建议方向（尚未实施）

| 问题 | 已核对的Grok/官方做法 | 我们应收敛到的边界 |
|---|---|---|
| 谁负责画面提示词 | 普通工具调用由模型填写prompt | 保留模型结合图片和需求整理的最终执行文字 |
| 方法/Skill规则 | 主要指导主模型怎样选工具和写prompt | 不把整个方法说明或管理规则复制给生图模型 |
| 程序额外拼接 | 已检查客户端路径没有固定业务长模板 | 程序负责绑定与校验，避免再次添加语义要求 |
| 参考图片 | 真实资源解析，保持调用指定顺序 | 图片定位与授权留后台，prompt只保留可理解的图号和用途 |
| 已确认方案 | 精确提示词可以直接图片接口执行 | 按编号读取已保存最终执行稿，不再润色或偷偷删字改哈希 |
| 可观察性 | 工具输出可查看实际prompt/revised_prompt | 复用现有请求快照核对实际发出文字及顺序，不增加审核模型 |

建议保留“给用户看的方案说明”和“给图片模型的最终执行文字”这两个含义，利用现有方案/稿件/请求快照承接，不另建通用治理系统。最终文字应包含已选定的画面要求、准确文案、必要保留项、参考图用途；完整需求推理、候选方案比较、内部ID、版本/恢复/计费信息和指挥主模型的操作话术应留在其所属层。

不是把所有保真约束或共同风格都删掉，也不是设置统一最大字数，更不是强制再调用一个模型“清洗”。复杂套图的执行文字可以长，但内容必须对本张生图有用且已确定。

原文执行应对应用户明确要求按原文、或选择已经保存的最终稿；不能因为识别出“图二”就自动剥掉模型的润色。后台仍应核验实际底图、参考图、用户生图授权、尺寸和旧任务状态。

任何后续实施都要保留旧方案/已受理任务的版本和冻结请求，不在后台批量改写历史prompt、重算旧哈希或自动重发。聊天、追加素材、连续编辑、权限、取消/恢复及单次付费派发沿原链路保留。
