# 主图 Agent 失败恢复与流程约束方案

日期：2026-10-07。状态：已在任务工作树实施并完成离线验证；本轮尚未提交、部署、发布 v3 或进行新的付费测试。

调查对象：任务工作树 `.worktrees/ecom-three-stage-agent`，代码 `ed814c63a897262ba86d4938cecede11164022cd`。沿用已确认的唯一平台入口 Skill、内部三段提示词、现有 KIE / ModelGateway、平台默认 KIE 密钥、`gpt-5-6-luna`、1–15 张及 `plan_source` 生图方式。

## 2. 推荐职责与失败行为

保持现有主 AI → 一个入口 Skill → 三阶段子 Agent → `generate_image` 结构。程序决定哪些动作可执行，Skill 向主 AI 解释这些动作。三段原始专业提示词不修改、不分别注册。

| 情况 | 执行者与处理方式 | 主 AI 的边界 |
| --- | --- | --- |
| 提交前参数格式错误 | 纯校验返回字段路径、格式要求、可修改范围；允许主 AI 一轮等价纠正。 | 可修正拼写、类型等明确格式问题；不能猜素材 ID、换图、重排、改风格、减张或改用户原文。真正缺素材/规格须提问。 |
| 明确可安全重试的临时错误 | 子 Agent 在失败阶段内按统一额度采用 1/2 秒退避，受持久化截止时间与父预算限制。现有 KIE 错误未提供 Retry-After，不编造该值。 | 不在主 AI、HTTP、阶段修复各开一套重试循环；固定使用 Luna。 |
| completed 空正文或输出协议不合格 | 子 Agent 使用具体校验反馈修复该阶段；合法上游输出不重跑。 | 不直接修改子 Agent 的专业执行稿。 |
| 原始信息不足 | 维持 `needs_input / insufficient`，输出真实问题或资料限制并保存方案。 | 向用户准确反馈，回答后沿用原图和原始需求。 |
| 鉴权、权限、余额、配置、程序错误 | 分类后停止并给出安全、具体的说明；保留有效阶段。 | 不能描述成“商品信息不足”，也不能临时换密钥、换模型或改走普通生图。 |
| 租约忙或执行结果不确定 | 返回 `wait_existing`，读取已有任务/回执；不重新派发。 | 不改 call_id 来避开账本，不把 retryable 当作执行授权。 |
| 额度/时间耗尽 | 停止自动执行，说明失败阶段、已完成阶段及未提交图片事实。 | 不自动另起一轮恢复额度；用户明确重试才能创建新的执行窗口。 |
| 部分图片已受理 | 保留已有回执，只提交尚未受理的方案项。 | 不重发成功或不确定的图片；单项失败准确反馈。 |

对网络错误的“可重试”必须结合副作用证据：连接未建立、明确未受理的限流等可进入有限重试；读取超时、已产生部分输出、供应商是否受理未知时不能仅凭错误类别重发。服务端已完成但保存/回包失败时先读已落库状态，不再次调用模型。

## 3. 主 AI 能看见的恢复契约

不替换现有 `AgentResult.status`、`ToolResult` 或 `is_failure` 定义。新增严格类型的主图领域结构，写入 `metadata.retry_context`，同时明确投影进主 AI 的工具结果；用户展示仍使用安全摘要。复用 `ToolResult.with_model_content`，不暴露数据库异常、凭证、供应商原始请求或全部运行 metadata。

已实现的协议示例（示意值不是生产记录）：

```json
{
  "version": 1,
  "workflow": "ecommerce_main_images",
  "status": "error",
  "plan_id": "真实方案UUID或null",
  "failed_stage": 3,
  "error": {"code": "PLANNER_IMAGE_JSON_INVALID", "category": "output_validation"},
  "recovery": {
    "action": "report_error",
    "remaining_attempts": 0,
    "preserved_stages": [1, 2],
    "allowed_changes": []
  },
  "generation_allowed": false
}
```

`recovery.action` 使用有限枚举：`repair_arguments / ask_user / resume_plan / wait_existing / report_error / generate`。只有 ready 使用 generate；内部模型重试由子 Agent 消化，通常不需要让主 AI再次调用工具。只有服务端确认存在安全的续接动作时才返回 `resume_plan`。

`retryable` 是提示；策划工具仍有付费调用与数据库副作用，继续保持 `effects=("unknown",)` 和通用 `safe_to_retry` 的保守规则。领域恢复通过经过核验的方案状态、额度与 lease 执行，不能把工具假装成 `effects=none`。

当前 `stop_workflow` 保留为兼容终止标记。主图控制器对可纠错/可续接结果只开放返回契约允许的调用，其余结果终止业务工具。未 ready 始终没有生图许可。错误类别不得解析自然语言摘要推断。

## 4. 持久化额度与续接

沿用现有三个阶段的三次上限：每个阶段在一次自动执行窗口中，首次调用加最多两次额外调用；网络重试、空稿和结构修复共同消耗该额度。参数提交前的纠错不消耗子模型次数，最多一轮。600 秒父预算及阶段 timeout 仍为上限，不承诺用完每个阶段的三次机会。

在 `ecom_image_plans` 扩展 `root_plan_id`、版本化 `recovery_state`，复用 `stage_attempts` 作为审计记录，不引入新工作流框架。恢复状态至少保存执行窗口 ID、固定截止时间、每阶段已预留调用数、稳定 attempt_id、尝试结果、已结算事实和最后错误。窗口由可信服务创建，主模型不能指定预算或重置计数。

增加领域 RPC：

1. **预留模型尝试**：先锁根方案再锁当前方案，核验归属、当前父任务/恢复关联、lease、有效输入、截止时间和额度；生成稳定 attempt_id 并占用一次额度，之后才调用 KIE。
2. **提交尝试结果与阶段输出**：以 attempt_id 幂等保存 usage、校验结果、扣费及有效阶段输出。重复提交同一结果返回原回执，冲突结果拒绝；不能重复扣费。失败稿与成功稿走同一个结算边界。
3. **恢复协调**：若已经有完成记录先复用；仅有 started 且供应商状态未知的尝试标记不确定，不能因新 worker / call_id 自动重做。

同一工作流的自动跨父任务恢复共享根方案额度；后继方案不得复制出一套新额度。用户明确点击重试或发出重试指令才创建新的执行窗口，复用有效上游；仅模型自己重复调用不构成新授权。等待用户补资料结束当前执行窗口，用户回答后开启下一窗口，不把等待时间计为持续模型运行。

`continue_plan_id` 扩展到经过分类允许恢复的 `failed` 方案；用户/组织/会话校验保持。仍采用创建后继方案的已有模式，保留原失败记录和 `supersedes_plan_id`，不改原方案的父任务归属。

复用判断：

- 纯重试：保持原始业务消息及素材快照，重试控制文字不被当作新的风格要求；核验提示词/Schema 版本、素材 ID、内容 hash、文件版本、用途顺序及上游输出后复用。
- 新需求：当前用户正文仍一比一保存；改变商品事实或原图使阶段一及后续失效，改变风格至少使阶段二、三失效，改变张数通常重跑阶段三；不能无条件复制阶段一、二。
- 阶段二失败可复用有效阶段一；阶段三失败可复用有效阶段一、二。失败阶段来自保存的状态，不能靠异常摘要猜测。

## 5. 工作流绑定与生图门禁

在可信 `tasks.request_params` / Actor checkpoint 中保存 `_ecom_workflow`，包含关联的根任务/方案、Skill 包及版本哈希、执行窗口、生成轮次和恢复来源。请求入口剔除同名客户端私有字段；主 AI 提供的参数不成为可信状态。每次使用仍核验当前权限、素材版本与工作流关系。

显式选择主图 Skill、有效会话绑定及同一主图任务的恢复可直接建立关联。跨轮关联必须来自明确的原任务操作或经核验的继续意图，不能让整个会话永久进入主图模式，也不能仅取“最近一个失败方案”绑定新话题。记录模型自动选择的真实来源，不伪装成用户手选 Skill。

**首次自然语言请求在主模型调用前识别。** 当前消息含真实结构化图片，或准备好的模型上下文含图片时，未绑定且未明确选择其他 Skill 的交互聊天先执行一次轻量语义判定。输入保留该轮原始文字及图片类型/名称，剔除 URL/base64；返回 `main_images / ordinary_image / needs_input / unrelated`。复用现有 `IntentRouter.call_tool_model` 的结构化 Function Calling 传输，不重启旧 Web 首次路由，不混入暂停/取消动作，也不做关键词硬匹配。纯文字且上下文没有结构化图片时，保留图片业务批次提交前的惰性判定；只有历史文字素材描述的场景尚不能保证在首个主模型回合前识别。

- `main_images`：先持久化工作流关联，程序实际激活唯一入口 Skill，读取正文并保存版本/哈希 checkpoint 后才调用主模型；界面显示真实 `skill_step`。目录或正文不可用时停止，不退回普通聊天。惰性判定的原始生图批次不执行，先经过同一 Skill 屏障。
- `ordinary_image`：保留当前普通生图能力。
- 不确定或路由不可用：前置判定直接给出用途问题并保存服务端 checkpoint 标记，不调用主模型；惰性判定在图片付费提交前停止。不默认当成普通图片放行；已知主图身份不能因开关/模型错误退回普通生图。

同一请求最多判定一次，必须发生在任何图片受理前，避免前几张已接受、后几张才拦截。已绑定/显式入口不增加这次模型判定。自然语言分类仍可能误判，需要真实请求评测；程序保证的是已识别/绑定的主图任务无法绕过，不能宣称语义识别绝对正确。

主图身份建立后，在本轮服务端产生完成的 `plan_ecommerce_images` 工具回执前，主模型文字/思考不流向界面或最终消息；仍正常记录模型 usage 和工具事件。主模型只输出文字、未调用子 Agent 时，程序明确报告遗漏调用并停止。查素材等工具不能解除此限制；历史方案或“已调用”的文字不能代替本轮回执。Actor 恢复使用冻结的真实工具块，完成的策划回执允许主模型解释 ready、资料问题或等待状态；仅参数校验错误不解除限制，真实失败仍由错误与恢复门禁停止。

`generate_image` 的主图判断扩展为读取可信工作流关联，再核验 ready 的 `plan_source`；当前“active Skill 或本任务已有方案”继续作为兼容防线。仅有提示词、历史“已激活”文字或模型传来的 workflow 字段都不构成许可。

跨轮出图沿用服务端生成轮次 ID。`ecom_image_plan_acceptances` 保留旧父任务主键，扩展非空生成轮次的唯一约束及 RPC 查询：同一轮次、方案版本、item_id 返回已有回执，即便父任务改变也不再受理一次。回执保留原图片任务和消息身份。用户明确重新生成才创建新轮次；不能用永久的 `(plan_id,item_id)` 唯一键禁止合法重画。
