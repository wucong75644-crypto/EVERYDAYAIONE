## 1. 根因与证据

本次生产现象不是下载链接丢失。实际失败链是：不完整名称被当精确路径；没有找到目标后又把 basename 当工作区根路径，先确认，再由 Handler 发现文件不存在。生产中正确的 keyword 搜索 → 完整相对路径/fid → 批准删除已有成功记录；拒绝确认也有正常未执行记录。

系统缺少统一的“目标是什么、属于谁、是否存在、是不是用户看到的那个版本”的契约。搜索、分析、删除、恢复、缓存分别解释字符串，局部路径安全检查只证明路径在工作区内，不证明对象选对或版本未变。提示词修正必要，但不足以保证这些约束。

## 2. 已批准行为

R-01：名称是搜索条件；明确路径、资源引用是定位条件。明确路径不存在时，不得悄悄去其他目录找同名文件。旧参数继续接受；basename 和省略扩展名进入候选解析，不再用 `cache.resolve(...) or 原字符串` 猜路径。工作区根文件可用 `./report.csv` 明确定位。

R-02：所有查询在当前已授权范围内进行。零候选明确未找到；多候选要求选择，列出相对路径、名称和必要区分信息；只有一项且候选集合完整才能进入操作准备。搜索被截断、超时或某目录不可读时，不得把“当前看到一项”当“唯一”。current 没有命中不自动升级到 workspace；定时任务不能扩展已有授权。

R-03：不存在、歧义、失效引用、越权、目标变化均在业务 Handler 和 invocation 开始登记前返回明确未执行。批量破坏性操作先完整核验所有目标，任何未解决目标都不执行整批，也不弹删除批准框。该变化要说明与旧“跳过不存在文件后删除剩余文件”的兼容取舍。

R-04：沿用现有确认界面，显示核实后的相对路径/数量/作用域；一次正确批准对应一组确定对象。批准后目标、参数、范围、权限或文件版本变化，原批准失效，返回目标变化；由新提案重新确认，不在同一个调用中循环弹窗。无变化的 Actor 恢复继续使用现有持久化确认，不再弹一次。

R-05：恢复选择具体删除记录和备份对象；同名多记录先选择。目的地有文件时返回冲突，不覆盖。恢复到新名称/覆盖恢复属于另一个明确业务操作，本次不暗中增加。

R-06：分析缓存匹配实际完整源内容及转换配置；修改 CSV 尾部、同大小替换、同名前缀不同文件不得复用错误结果。读源失败不得退化成“路径哈希即版本”。

## 3. 设计与责任

### 3.1 一个目标解析服务，两个处理阶段

在既有 Runtime 前置检查中引入共享 `FileTargetResolver`；内部返回明确的 `Resolved / NotFound / Ambiguous / Stale / Forbidden / Incomplete`，替代 None 加猜测回退。

内部目标至少包括 org、storage scope、workspace owner、canonical workspace 相对路径、资源类型、可选已有 asset ID、观察到的版本。真实 actor 继续来自 ToolContext，与 owner 分开。展示名和 URL 独立保存，不参与模糊授权。复用现有 `assets/asset_identity.py` 的规范化和 `FileExecutor.resolve_safe_path` 的边界检查，不另建一套租户路径规则。

必须分开：

1. **身份/权限解析**：验证资源属于当前允许的 owner/组织/清单，得到原调用的规范身份。完成后才允许读取旧 ledger 的回放结果。
2. **新执行准备**：仅当没有已完成回放时，检查存在性、类型、唯一性、当前版本，生成内部 `PreparedFileCall`，把其绑定冻结进 ToolContext，再确认/执行。

这个顺序很重要：删除成功后文件本来就不存在；不能为了前置存在性检查，把合法成功回放拒绝掉，再引导模型执行一次新删除。回放仍检查权限，不重复 Handler。未知 invocation 仍遵循现有 uncertain 处理，不因新解析器自行重试。

Handler 接收准备后的精确目标，不再重新通过名称、可变缓存、模糊 SQL 选择目标。内部执行接缝只由 Dispatcher 调用；旧 execute 同样走这一准备路径。返回依旧通过板块 03 的兼容投影交给旧消费者和 ledger，不保存新 ToolResult/replay 版本。

### 3.2 跨进程引用：已实现的签名定位信息

使用带版本前缀、完整 owner/组织/相对路径的签名资源引用 `resource_ref`，作为可跨 worker 解码的定位信息。签名只防引用内容被改写，不代表访问授权；每次仍检查当前资源权限。不要再把 8 位哈希和进程内表当完整身份系统。

复用已有资产身份及已有 asset ID（存在时）；不假设 `user_assets` 覆盖所有工作区文件，因为当前上传登记是 best effort，代码产物/历史文件也不一定完整登记。因此不推荐本次先建设强一致的全文件数据库，再依赖它才能删除普通文件。

新引用在工具参数边界解析为规范路径；不把内部 prepared DTO 写入 ledger。仅对相关工具做向后兼容的可选引用参数扩展，旧 files/path/file_ids 保留。多个形式同时给出而目标冲突时拒绝，不能择一忽略。

旧 fid 保留只读兼容反查：在已授权 owner 的清单、已有资产事实及有界文件枚举中计算候选，必要时重建本 owner 索引；多候选/枚举不完整/超预算明确失效，要求重新搜索。不全租户扫描，不用缓存缺失猜名字，不承诺旧短 ID 永久无冲突。重命名或删除重建后，旧路径引用应明确失效，不能自动指到新同名对象。

签名用途必须独立，具备版本/密钥轮换解析规则；签名密钥只用服务端已有密钥管理能力，不能把裸 JWT 凭据或路径作为授权令牌发给模型。实际编码为 fref1_ + URL-safe base64 JSON + HMAC-SHA256，载荷绑定 org/owner/context_scope/相对路径/stat 版本。已有服务端 JWT 密钥经用途隔离派生签名密钥，不公开密钥；换钥或不识别版本明确拒绝，重新搜索可获得新引用，不承诺旧引用跨换钥永久有效。该参数扩展已经用户批准，不收拢其他工具定义。

### 3.3 搜索直接输出结构化命中，最后才渲染

为文件搜索新增与 `file_list_entries` 同层的结构化命中结果，包含规范路径、可用性、版本观察值、匹配原因和完整性状态。列表、关键词、清单、单文件描述、图片分支共享此结果。

缓存登记、资源引用和旧文本投影均从该结构生成。删除“生成展示文本 → 正则读回路径”的反向流程。文件名含空格、竖线、冒号、换行也不能改变身份；显示时转义与定位原始值分离。没有实体验证的附件清单项明确标不可用，不签发可操作引用。

这只是查询内部数据源调整和现有 summary/text 内容补足，保留 AgentResult / FileReadResult 和既有图片注入、WS 字段及结果消费；不提前改造结果展示系统。

### 3.4 准备、确认、最终执行绑定同一个对象

`PreparedFileCall` 固定规范目标集合、操作、源版本和恢复 record ID/备份对象（如适用）。Policy 的确认摘要额外绑定这些事实，不只绑定路径字符串。目录/文件变化不得继承旧批准。

等待确认期间不持有文件写锁。批准返回后重新检查权限和生命周期，然后获取短期、跨进程的资源协调锁，复核同一对象/版本，再进入 Handler。实际按 owner 工作区加读写锁，因此多文件与目录移动覆盖同一子树冲突域；锁失败、预算用尽或取消均不得登记业务开始。保留现有 Actor lease、安全点、内核锁、ERP 锁和单次 invocation 机制。

协调层应覆盖会改动同一工作区文件的应用路径：AI 删除/恢复、文件管理 API 的写入/移动/重命名、上传/产物发布；具体写入点须形成清单并由集成测试证明覆盖。实施核验发现现有 nsjail 的源工作区挂载可写，因此 Runtime 的 code_execute 与 SandboxExecutor.execute 都进入同一排他协调；原挂载、沙盒能力和 kernel 锁保留。只在一个 Python 进程加 asyncio.Lock 不能满足要求。

恢复下载到临时文件，验证备份后以不覆盖方式发布，再按原流程标记恢复；预检查和 Handler 不再分别模糊查询。复用既有恢复业务保留期，不改成会立即删除 OSS 的 FileExecutor.file_delete。文件与数据库原记录仍可能部分失败，沿用真实执行结果/uncertain 规则，不声称跨系统事务或零丢失。

**并发保证的实际边界**：应用内写入必须参与同一协调；生产 NAS 的跨进程锁与安全发布语义需要实测。stat/hash 后再 unlink 仍有 TOCTOU，单独加二次检查不是根治。若外部程序可任意并发改写 NAS 且不参与协调，就不能承诺原子“只删除所确认版本”；需要限制直接写入，或进一步引入存储层版本条件操作。后者属于单独存储架构决定，未验证前不能称全部技术通过。

### 3.5 内容版本与分析缓存

以完整内容 SHA-256 和转换版本/参数确定分析缓存身份。选中文件时按预算流式读取全量内容；转换读取稳定快照，摘要和转换输入必须来自同一快照，不允许边读边变。可复用可靠的已有内容摘要，但前提是同一文件版本可验证；旧元数据字段不能代替当前源内容证明。

更新路径版本后重新获取衍生产物映射；失效文件别名不得继续指向旧 Parquet。提升数据转换缓存自身版本，旧缓存自然不命中，无需清理用户文件。此处是已复现文件数据正确性修复，**不是板块 06 的 ToolResult 回放/审计迁移**；code_execute 的整体缓存资格和原结果 ledger 格式不变。

### 3.6 定时任务复用同一“不得静默选择歧义对象”规则

完整 ID 精确优先；短 ID 收集全部候选，一项才允许，多项沿用现有候选选择。不以列表顺序决定目标。候选展示必须给出足够区分的完整 ID。仍由现有 ChangeSet 提案和确认提交执行，不新加工具确认，也不把文件 resolver 生搬硬套到任务业务。

## 6. 实施结果、覆盖与明确边界

- 统一目标：FileTargetResolver 服务搜索、分析、删除；完整路径不退化为名字，名字只在完整授权候选集中唯一选择。旧 fid 从当前 owner 范围重建，碰撞拒绝；新 fref 不依赖会话缓存。搜索结果直接从 structured hits 生成路径/fid/fref，已不存在清单项标不可用。
- 执行顺序：身份/Policy/action/范围 → 规范身份 → 已完成旧 replay → 版本准备 → 既有确认 → 当前身份再验证 → 工作区锁 → 同目标版本再核验 → 缓存/invocation/Handler。版本只加入内部确认与缓存键，不进入新持久化协议。批量目标任一缺失/歧义整批拒绝；已开始执行后的取消停止余项并保留原已删除记录逻辑。
- 文件版本：stat 元组及完整 SHA256 绑定确认；分析仅转换临时稳定快照，源发生变化明确失败。CSV/Excel 内容缓存升级 v3.1，旧前缀指纹缓存自然不命中；路径缓存按源版本失效。衍生缓存锁改为可取消异步等待，线程 IO 取消后排空才释放协调。
- 恢复：指定删除记录；同名多记录不默认最新；固定备份 ETag，执行前复核，OSS 条件 GET；隐藏临时文件完成后 os.link 不覆盖发布。沿用原 30 天保留及 mark_restored，不新增跨 NAS/OSS/数据库事务。
- 写入协调：新 workspace_coordination.py 的共享/排他 flock 覆盖 Runtime 文件读写/code_execute、FileExecutor 的 write/edit/delete/mkdir/rename/move、两个文件上传 API、图片 NAS 上传、URL 下载发布、企微文件接收、SandboxExecutor。定时模板复制取共享锁。只包含 source 文件，现有 staging 产物、ERP、媒体内部编排保持原业务。
- 取消收尾：文件线程 IO 和 OSS workspace 同步/删除/缩略图等待实际结束；内核执行等待 SIGINT 响应，超限销毁并读完协议；仍保留变量、kernel 锁、Actor lease/安全点。锁不会在确认等待期间占用。
- 调度任务：短 ID 多匹配明确候选并显示完整 ID；所有管理 action 继续通过已有 ChangeSet 提案/确认提交，不额外弹窗。

本次公共变化仅为可选 resource_ref(s)、restore record_id，及用户已批准的“批量缺失整批不做”“恢复不覆盖”“内容缓存版本修正”。保留所有旧工具名/输入别名；不改变 ToolResult/ledger/WS 载荷、ERP 查询写保护、restore_file 原风险或 code_execute 原缓存资格。

**当前部署拓扑的保证**：生产 NAS 是 NFSv3，挂载 `nolock,local_lock=all`。已有锁文件的双进程检查已证明同机共享读重叠、排他阻塞及释放后获取；Web 与 conversation-actor 均由同一主机 root 用户运行。此锁契约只覆盖当前同机应用写入，不能用于跨主机分布式排他。未来多主机写入或外部直接写 NAS，必须先提供存储级条件操作/可靠分布式协调；本次不声称外部任意写入下的原子版本删除。生产“不覆盖发布”独立临时探针已在本次提交部署准备阶段通过，临时目录已清理；本地真实文件测试也已通过。
