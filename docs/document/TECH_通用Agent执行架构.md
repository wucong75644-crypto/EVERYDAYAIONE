## 从用户输入到结果

主模型从本轮输入和受限上下文中同时判断来源与动作。它可以先确定其中一项。例如用户说「用刚改的第二个去做」，系统能找回修订后的条目。若前文明确约定动作，就按约定执行；若动作不明确，只问缺失的问题。普通文本随现有消息提交保存。只有某个动作需要结构化输入时，才根据该能力的契约准备结构化参数。可独立编辑、长期复用的内容可按产品需要保存为成果。

内容、工作计划和执行记录分别表达三件事。内容回答「用什么」，工作计划回答「准备怎么做」，执行记录回答「实际发生了什么」。调用之前，宿主重新读取有权限的原始内容，把来源版本与实际参数关联。批准绑定到原有的作用域与请求，具体字段以原能力契约为准。业务结果由工具回执证明。用户新消息、调用 ID 变化、刷新或恢复均不单独授予再次执行权。

以文案为例，写三条、改短第二条、解释改动都可以直接交付。把修订稿导出文件会选择文件能力。用户另行要求按相同内容创建定时任务时，沿用定时入口的配置、确认和快照。用同样的来源协议，可以引用上一轮 ERP 查询结果写摘要或导出。ERP 查询结果仍受自身组织、数据范围与权限约束。媒体生成只在用户意图和输入已明确时通过对应适配器提交。

## 约束与验收

1. **内容引用独立于动作。** 用普通回复、旧文本、文件、ERP 查询结果分别做来源；至少让一种来源驱动两种能力。校验同名条目、历史压缩、修订版本及跨组织越权。普通聊天与纯修订没有业务派发。
2. **模型在已授权能力内选择。** 相同场景分别运行无 Skill、适用手选、会话固定和可选候选失败。系统按真实任务意图行动，缺少目标、收件人或其他关键条件时只澄清对应事实。无需每轮固定分类或额外复核调用。
3. **应用对实际副作用负责。** 验证来源变更、撤权、确认后参数变化、并发请求及定时快照。读取权限和执行权限独立校验。受理与完成分开，原有计费和防重复机制继续生效。
4. **恢复以回执为准。** 引用旧内容可以开始一个新动作。明确续做原操作时恢复原任务。覆盖暂停、取消、刷新、部分成功和结果未知，保留已完成项，核实未决操作后再决定是否重试。
5. **展示以用户任务为准。** 保存、来源定位和校验可在后台完成。用户看到真正的进度、需处理的确认、可用结果或能指导下一步的错误。覆盖实时流、断线恢复和历史消息三处展示。

## 行业依据与适用边界

- Google Agent Platform Sessions 将消息及函数调用等动作记为事件。Gemini 函数调用允许模型按上下文回答或选择函数。这支持会话记录和动作提议分别设计。https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/sessions
- Microsoft Copilot Studio 使用上下文与能力描述来选择工具，可按工具配置身份、执行前确认及完成后反馈。这支持模型选择、应用授权和前端呈现各有职责。https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-tools-custom-agent
- Claude Agent Skills 分阶段加载方法资料。它为按需加载提供参照。https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview
- AWS Step Functions 的 redrive 保留成功步骤和历史，从未成功处接续。它为可靠执行和回执恢复提供参照。https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html

这些是公开产品和平台机制。普通消息条目如何精确定位、何时保存修订关系、哪些动作绑定版本，以及现有 Actor 如何接入，是本项目需实现和验证的工程决定。

## 落地顺序

第一步在现有主循环补来源定位与执行绑定的最小契约，用两个不同能力做同源接续。第二步将流式、恢复与历史展示按用户需要统一投影，并接入已有确认与权限。第三步沿用各能力的原生账本验证重复、部分成功和定时快照，再按能力逐步采用。旧消息、图片方案与历史快照保持可读。兼容策略优先采用可选字段和渐进接入，停用新入口时保留已记录来源及回执的读取能力。

### 一条数据如何流动

1. 第一轮写三条文案，第二轮改第二条。正常消息提交分别保存两次正文。即便没有单独记录修订关系，模型仍可用历史定位第二轮修订。
2. 第三轮用户说「用刚改的第二个做成 Word」。主模型从已见消息定位修订后的片段，必要时按 Anchor 读原文。来源候选包含实际消息标识、内容块位置和片段范围，服务端以原始记录重算版本及摘要。前文没确定动作时只澄清动作。
3. 主模型决定是否使用适用 Skill，然后提出文件能力调用。明确要求沿用的文案正文由宿主从已验证来源填入绑定参数。标题、章节或样式等派生参数由模型提供。仍由文件能力自己的参数契约核验。
4. 宿主在派发前记录来源、最终参数和操作身份，按现有策略处理确认。之后来源失效、权限撤销或请求参数变化时停止该次待派发操作，保留原文及已有结果。
5. 业务适配器返回文件及回执，按既有流程入账。刷新后用回执重建交付状态。若用户改说「把同一条安排成每周提醒」，模型可以复用来源并另起定时动作，使用定时入口的权限、确认和快照。

首批建议只接普通消息、文本成果和两种现有能力，优先跑通来源绑定和任务恢复，再接更多能力。跨轮持久化修订索引及通用导入协议延后到有实际需要时验证。新入口可分能力启用，回退时保留历史消息、已存方案及在途操作记录。

## 工具发现与使用说明（待审查）

### 当前链路

`ToolSpec / ToolCatalog → Registry + ToolPolicy → 各入口的展示策略 → 模型实际 tools → ToolRuntime → Dispatcher`。

- 注册定义集中于 `services/tools/definitions/`。`ToolSpec` 有能力标识、参数定义、作用域、公开级别、开关及执行绑定。能力目录用于稳定映射，包含部分关闭的定义，搜索不能把它直接当作可用列表。
- 交互聊天由 `stream_setup._prepare_permission_and_tools` 准备基础列表，`tool_loop.prepare_tool_turn` 按轮重建。普通聊天的核心定义来自 `config/chat_tools.py`。最终模型收到的列表还受 `execution_engine._run_loop` 的 Skill 工具上限、知识路由、任务阶段及恢复状态约束。模型内部控制动作有些由循环直接注入，供应商原生工具也有独立配置入口。
- ERP 有已有搜索、域隔离与子 Agent 展示逻辑。聊天的 `ToolLoopContext` 从 ERP 搜索结果提取名字。旧 Agent 循环还存在策略控制的扩展路径。两者都经过目录与策略。定时和预检从批准范围或快照构造工具列表。
- `ToolRuntime.execute` 与 `ToolPolicy` 执行时重新核验权限、模式、资源、确认和调用状态。回执接续走现有操作账本。以上是本地代码走查，生产账号逐场景的实际模型工具清单尚未采样。

### 补齐办法

1. **先盘点入口与可达性。** 从现有注册表和调用点生成交互、ERP、直接入口、定时与预检的覆盖矩阵。每个工具标明常驻、按需、内部、供应商内置或按当前条件不可用，并验证对应路径。按权限、Skill 和任务阶段用实际最终模型请求确认工具定义。已有可达路径继续复用。
2. **为有缺口的交互工具补通用发现。** 在聊天工具投影处设计一个轻量只读入口。模型用目标或能力名称查询。服务端先依据同一会话的域、权限、模式、Skill 上限与任务阶段生成候选范围，再做相关性匹配。精确名称与能力标识优先，补少量业务同义词和用途描述。返回少量相关候选与结构化工具身份。首版可直接查现有目录，排序和召回质量先测后扩。ERP 专用搜索保持原入口。
3. **下一模型轮提供实际定义。** 用经核验的工具身份接入现有 `discovered_names` 和工具组装机制。检索摘要用于挑选，调用用的名称、描述、参数及可用变体来自原定义与当前投影。重点补清含义、必填字段、已核实内容怎样作为输入、实际返回什么及易错示例。带子动作的工具保留参数组合和动作边界。提供按能力分类浏览或精确查询的兜底，限制单次结果和反复查询。
4. **可见性与执行分别核对。** 新发现仅影响模型工具投影，继续使用原执行权限。搜索结果在当前任务内有效。如需跨暂停恢复，则只存经宿主核验的工具标识，恢复后从注册表重建并按当前状态过滤。确认与派发使用实际参数和来源版本。外部工具返回的文本不能自行登记工具或授予执行权。
5. **验收先测可达性，再测模型行为。** 对每个允许由模型使用的公开工具验证能常驻看到或按需找到，且最终定义与执行契约一致。脚本模型覆盖已知工具、模糊查询、同名工具、不可用、撤权、跨域、等待确认后变化和恢复。真实模型后续验证中文需求命中率、参数正确率、额外轮次与上下文成本。第一批选择现有两种能力，通过真实业务替身验证，无需引入新业务工具。实施前再按覆盖矩阵确定接入清单。

用户继续用自然语言交流。发现步骤在后台完成，只有缺少关键条件、能力不可用或动作需要确认时才反馈。该方案不变更旧图片方案读取及定时快照，首批可以按交互入口启用，回退时恢复原工具投影并保留执行回执。

逐项本地投影与场景证据见 [《工具可见性与发现盘点》](TECH_工具可见性与发现盘点.md)。首批验证聚焦通用聊天中的视频能力发现和旧内容回读。原图读取已有固定历史边界及精确片段定位，可先核对其复用边界。服务器策划走既有 Skill 路径；ERP 和定时保留原入口及作用域。
