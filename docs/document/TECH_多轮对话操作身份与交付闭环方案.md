# 多轮对话从理解到交付的统一方案

评审稿 · 2026-11-21

## 1. 诊断结论

保留现有 Conversation Actor、工具策略、内容版本、异步 Worker、操作账本和前端重连机制。最重要的改动是让**本轮用户要做的操作**贯穿模型调用、来源核验、派发、恢复和交付。方案可以使用多次，每次用户明确发起的新生成或编辑都有自己的操作。一次操作内的网络重试、换模、回调和恢复沿用原操作。

| 已发生的故障 | 证据 | 暴露的边界 |
|---|---|---|
| 首轮上传福字图，说「用你写的提示词」时出现 `CONTENT_SOURCE_REQUIRED` | 生产检查点有图片，当前对话没有旧提示词，生图参数里的 `draft` 又是非法 JSON，原生派发为 0。已有修复区分旧稿引用和参数错误，单句复测不足以证明各入口使用统一错误语义 | 工具输入的语法、用户引用的资料、执行授权需要分别判定 |
| 线上发「第二个方案帮我做出图片给我看看」后显示未收到受理回执 | 生产检查点已有方案目录，主模型没有发出工具调用，图片任务与图片扣费均为 0。这是派发前无调用，单凭零回执无法解释为什么停下 | 主模型声明的意图、实际工具调用和退出条件之间缺少统一核对 |
| 用户明确说「再帮我生成一次」，系统显示旧成品 | 生产消息有「已复用已有图片」，按该用户消息查到新增图片子任务为 0。发布版给同一条目默认编译固定 `variant_id`，随后按规格、素材、原文和版本查旧成品 | 条目身份与生成操作身份共用了同一层去重 |
| 新图已经发布，自动接续又显示「尚未收到图片任务的受理回执」 | 原生产记录有已发布的图片子任务和回执，接续轮没有新调用。已上线修复将完成事件和新请求区分，用户已确认这类现象通过。通用结束契约仍须覆盖其他交付组合 | 用户看到的状态应来自对应操作的受理、终态和交付事实 |
| 已下线的「聊天图片编排」仍进入模型候选 | 当轮检查点里官方版被过滤，同名个人版仍可见。后来另一次用户操作在停用之前确实激活了个人版。后台已停用该个人版，复核其可用已发布版本为 0 | 候选与激活的身份粒度应到包 ID、范围、版本和入口；历史卡片只能说明历史记录 |

前三个故障发生在不同位置，针对文案或单句加规则只能各自覆盖一条路径。共同缺口是会话各层没有用同一个操作表达「要什么、用什么、钱有没有花、结果有没有交付」。后续把这张表做成回归入口，每次变更同时核对四类事实。

## 3. 全链路差距与优先级

P0 是本次统一执行必须收口的缺口。P1 是接入到同一契约的域或历史路径。标为验收缺口的事项目前证据不足，按测试优先，测试表明现有实现满足要求时沿用原实现。

| 范围 | 我们已有的基础 | 需要补齐和验收 |
|---|---|---|
| 输入身份与追加要求 · P0 | `message.py` 有客户端请求幂等。Actor 有 turn、固定上下文、检查点和续跑所有权；`followup.py` 能交接原任务，`user_changes.py` 有追加消息 | 在同一个入口明确来源是用户新操作、系统恢复、后台完成或追加要求。旧计划可供引用。追加要求只授权它实际改变的范围，已发出的子任务保持原身份 |
| 目标与成果身份 · P0 | `content_objects.py` 保存完整原文和版本，`artifact_reader.py`、`image_sources.py` 能读取历史内容和媒体 | 本轮明确区分读旧成果、改稿、按稿新执行、按相同规格出新结果、编辑指定成品、继续剩余项。引用要带对象类型、所属组和可核验版本。历史散排正文只在能核实条目边界时执行 |
| 工具可见与实际合同 · P0 | Registry、Policy、Skill、`model_contracts.py` 和 provider adapter 已存在；视频和部分工具允许按需发现 | 在最终给模型的 schema 上同时检查工具资格和调用参数。检查点能说明本轮工具及版本、显隐原因和兼容模式；限制发现出的工具与真正允许执行的集合一致。核对旧 Skill 同名、固定版本、接续和重新发现四条入口 |
| 参数风险与恢复 · P0 | `tool_argument_repairs.py` 已有持久化参数纠错预算，`pending_batch.py` 可先闭合原批次，网关可处理部分暂时故障 | 将错误码、阶段、是否已派发及动作建议放在同一结构上。损坏 JSON、来源无匹配、素材不可用、权限拒绝和受理未知的补救动作各自明确。另测模型应调用工具却没有调用的分支，普通问答照常结束 |
| 异步操作与计费 · P0 | 现有原生图片、视频 Worker，工具操作账本、发送标记、回执事件和扣费事务 | 带同一操作 ID 查提交、追踪同一供应商任务，后台唤醒沿用事件与操作。确认同一条用户请求的工具改参和回放不会多花，另发明确指令时能针对同一条目创建下一次操作 |
| 结束与用户展示 · P0 | `direct_loop.end_candidate` 按操作与结果推导状态。前端有任务卡、序号去重、断线快照和空接续隐藏 | 提交完成、成品发布、用户全部交付三个条件分别验证。模型无调用时不能仅凭「没有回执」断言失败。复用与拒绝并存时要说明分别对应什么，或者只显示该动作的真实结论 |
| 长对话与跨模型 · P1 验收缺口 | 历史快照、摘要、源文件读取、模型网关、内置搜索和模型回退 | 验证裁剪、省略和切换模型后仍能定位正确版本、绑定原调用结果、区分本轮新增工具和等待任务。保留可重查的原始事实及定位，无需把全部历史或原图送进每次模型请求 |
| 领域覆盖 · P1 验收缺口 | 普通聊天、看图、改稿、图像编辑、文字转视频、文件导出、搜索、ERP 及定时任务各有入口 | 让已有能力复用共同操作和状态语义，再逐类验收。当前通用视频合同以文字脚本为主，图片转视频、参考视频和剪辑须以已实现入口逐项核实。缺能力时返回明确可用范围，避免引导模型试错甚至误派发 |
| 诊断与持续验收 · P0 | 已有生命周期日志、工具调用、检查点、任务/积分流水和供应商回执 | 给每个案例一个可查询链路，串起输入、提供给模型的工具、模型选择、来源校验、操作、回执、账本和前端序号。只记录需要的 ID、状态和脱敏摘要。用连续会话覆盖产品行为，避免孤立工具用例全绿却漏掉跨轮问题 |

## 4. 一条可执行的目标流程

**用户输入或后台事件 → 固定本轮上下文 → 模型选择动作及引用 → 宿主核验并绑定操作 → 工具与 Worker 执行 → 事实回写与交付 → 继续剩余工作或结束**

### 4.1 分清五个身份

| 身份 | 核心作用 |
|---|---|
| 用户请求 | 服务端已受理的消息和命令身份证明用户发起了这次动作。页面重发同一请求保留原身份，明确发送下一次操作有新身份 |
| 会话与执行窗口 | 维持固定上下文版本、执行所有权、续跑检查点和当前消息。一个会话可承载多次顺序或受控并发的操作 |
| 方案、素材与产物 | 方案标识条目和修订版。素材标识上传原图、生成成品或用户明确指定的其他文件。成品保存对应操作、素材和上一版本关联 |
| 业务操作 | 用可信请求和已核验的动作及目标登记一次执行。举例，同一请求对同一方案指定重做一张，最多预约一个新操作。一个明确的多张任务可以有多个受授权的结果位置 |
| 工具调用、尝试与回执 | 工具调用要有唯一终态并配对原调用。换模和重采样可以有不同调用 ID，已确定的业务操作仍沿用同一身份。供应商任务、支付或积分交易、成品都绑定这一个操作 |

继续使用现有 `Operation` 的 effect 机制与操作存储。新字段如确有需要，先确认已有检查点和原生数据库校验可双读，再决定版本和迁移。方案正文哈希、图片哈希、模型调用 ID 和供应商返回的任务 ID 都有各自用途。业务操作身份由宿主决定，模型无法靠改提示词或随意填版本号创建额外扣费。

### 4.2 明确用户动作及必要证据

| 用户动作 | 必需信息 | 结果 |
|---|---|---|
| 问答、分析或只写提示词 | 当前要求、已授权的资料范围 | 正常流式正文或保存稿件。零生成派发 |
| 查看以前结果 | 可定位的既有产物 | 交付旧产物。零新生成扣费 |
| 修改原方案稿件 | 当前稿件或指定历史版本、要改的段落 | 新稿件版本。只在用户同时要求执行时再创建生成操作 |
| 按原方案再生成 | 原稿件可核验版本、冻结的原图和规格、本轮明确要求的新图片数量 | 每个指定位置创建一个新操作，继承原输入。旧图仍能查看 |
| 修改刚才那张成品 | 目标成品及本轮修改要求 | 成品成为这次编辑的输入。用户说「用原图重做」时才回到上传图 |
| 继续剩余项 | 已明确的目标集合与各项操作状态 | 对未提交且有授权的项派发；等待已受理项，保留已交付项 |
| 重发、恢复、查进度或后台完成 | 现有操作及可信回执或事件 | 对账和补交付，同一操作只提交和结算一次。取消能否生效以供应商或本地账本状态为准 |

首版优先在现有媒体工具入口上表达动作和引用，让主模型根据整段对话选择。普通聊天直接答复，避免为每轮强制开启额外的意图模型或工作流。允许同义说法、引用上一张、按钮操作和组合请求。短语检测可辅助提示和兼容旧入口，付费派发使用本轮用户证据、有范围的引用、业务操作预约和已有授权策略。歧义真的会改变成品或扣费时，提一个带具体候选的短问题。

### 4.3 从工具状态到界面状态

| 宿主已知事实 | 可见反馈 | 恢复动作 |
|---|---|---|
| 缺引用、格式错误、权限拒绝，且确定未派发 | 显示具体缺项或失败原因。只有确有生成请求且缺少必要信息才追问 | 允许范围内的有限纠错；输入歧义交给用户 |
| 用户意图明确，模型未调用工具 | 显示当前动作仍未提交的真实原因；可先按当轮工具做一次有界修正 | 在尚无副作用且目标可核验时允许纠正；预算耗尽保留待办和已做结果 |
| 已发出，暂时查不到受理 | 显示正在核实现有操作 | 查原回执和供应商任务。恢复前不可再发一笔 |
| 已受理 | 展示任务卡和真实进度 | 等待或轮询；后端重启后认同一个任务 |
| 已失败或部分成功 | 显示确切失败项；保留成功的图片、视频或文件 | 用户明确再做失败项时检查原状态并创建相应操作 |
| 成品已发布 | 直接展示可打开的成品；刷新后仍可定位 | 本轮只有该交付时可静默收尾；另有任务时用完成事件继续 |

前端消费可信任务状态，通过同一事件键去重。历史消息照常显示在原位置，历史 Skill 卡片应指向当时使用的版本。状态文案由结构化事实产生，避免模型自由文本覆盖成品、扣费或操作状态。

## 5. 实施阶段、改动位置和放行条件

| 阶段 | 最小改动范围 | 独立验收 |
|---|---|---|
| 1 冻结证据与输入契约 | 固定现网版本、生产问题快照、记录与本地草案的差异。定稿用户请求、来源、操作、回执和产物字段。核对 `message.py`、`executor.py`、`replay.py` | 用历史样本稳定再现三类故障；对同一网络重发、真正的新用户消息、后台事件、暂停恢复验证身份不同或相同的预期 |
| 2 统一引用与动作 | 在 `content_objects.py`、`content_groups.py`、`image_sources.py` 和 `direct_loop.py` 收紧动作与来源关系。用同一套接口支撑页面按钮和自然聊天。使用已有范围和版本校验 | 先写、修稿、选第 2 条、再做、编辑成品、回退原图和继续剩余项走一条连续会话。旧图、原图、方案都不串；引用歧义时零派发 |
| 3 接通工具与操作账本 | 调整 `model_contracts.py`、`content_tools.py`、`execution_engine.py`、`pending_batch.py` 的共同校验及错误字段。复用 `operation_store.py`、`image_operations.py`、`video_operations.py` 和现有 Worker | 在模拟供应商和真实隔离 PostgreSQL 验证每个明确新操作一笔受理和一笔结算。恢复、并发、重复提交及工具入参被模型改写时，原操作不会多派发。保证无权限输入零副作用 |
| 4 统一结束、恢复与页面反馈 | 扩充 `image_continuation.py`、`receipt_continuation.py` 的可信事件接口及前端状态投影，保留现有刷新、序号和恢复入口。核对长会话和跨模型事实 | 覆盖完成先于回执回放、回调乱序或重复、刷新、进程重启、部分成功、后续文案、新消息打断。展示结果和账本一致，图片发布后没有虚假的未受理通知 |
| 5 全渠道验收与完整上线 | 完成应用真实模型、图片和适用视频接口的验收，整理失败证据。内部用户采用既定方式完整上线测试，通过受控发布和就绪检查 | 百炼实测当前生产模型与此前验证模型。模拟 supplier 的回归仍保留，用真实供应商确认至少一次媒体闭环。生产核对浏览器、任务、供应商标识和账本，全部验收维度满足后再走任务关闭流程 |

各阶段按依赖合入同一个方案。阶段 2 到 4 可以在同一版本内逐步交付验证，不用为每发现一个句式单开一版。前端状态只消费已上线兼容的事件。涉及持久格式时采用先双读、再写新格式，未结束的旧任务沿原身份查账。回退到旧应用前检查旧版本能读新检查点和未结算动作，遇到未知状态先核对，再决定归档或恢复。代码回退和外部付费操作结算分别处理。

## 6. 最终验收矩阵

| 用户连续操作或故障注入 | 验收标准 |
|---|---|
| 随便聊 → 上传两张图问区别 → 只要第二张提示词 | 普通回复实时显示，第二张引用正确，零生图提交或扣费 |
| 写六个方案 → 只改第 2 条 → 做第 2 条 | 旧方案仍可追溯，仅修改目标条目。派发的正文、原图和规格与选择一致 |
| 看第二个方案的旧图 → 再帮我生成一次 → 这个再做一张 | 查看为零派发。两次新指令分别增加一个供应商任务和一笔图片结算，不复用旧成品。两次说法应体现同一语义 |
| 把刚才那张改蓝 → 用最初上传的原图重做 → 只做剩余项 | 存证分别指向指定成品、原始上传图及剩余条目。无歧义时不多问，存在多个可选来源时指出候选 |
| 页面双击、请求响应丢失、进程重启、重试改参数、回调多次或逆序 | 同一输入的已登记操作没有第二笔提交或扣费。已提交操作的身份不会因为字段改写而变化 |
| 第二张失败，其余已接受或已交付 → 继续做文案 | 成品不丢，失败对应正确项；没有虚假的「都成功」「未受理」，后续文案独立交付 |
| 用最新版文字脚本做视频 → 刷新后播放 → 导出原文 | 视频任务只接受当前支持的素材合同；可播放、同一受理一次结算；文件打开后与指定版本逐字核对 |
| 没有旧稿、非法 JSON、无法取图、权限拒绝、模型没调用、长对话裁剪或换模 | 不编造受理或新来源。确定未派发时有针对性的下一步，状态不明则先查原操作。句式变化和常用模型均通过 |
| 普通问答、文件、搜索、知识、授权的 ERP 查询、定时任务 | 工具能按权限发现；只读无写副作用；需确认的操作保留确认边界；回执恢复和工具结果回写满足相同契约 |

同一句话的首跑、再次发送和网络重试要分别验收。每一个付费案例记录本轮输入、实际工具、使用的来源版本、业务操作、供应商任务、发布事件和账本行数。发布确认需看到页面的真实成品和最终状态。纯文字、合成场景、真实模型、真实图片或视频以及生产运行是不同层的证据，报告分别标记。

## 8. 失败后继续执行

Grok Build 在固定提交的工具执行路径中，按调用 ID 回写结果；MCP 参数兼容时会把转换提示附在结果中。采样重试与业务工具执行是两条路径。轮末检查待办是否仍需行动，并以该用户输入为单位限制提醒次数。该公开实现可证明工具循环、结果配对和提醒预算。托管媒体服务的收费和重传规则仍需以自己的供应商合同与业务账本核对。 [工具结果回写](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/acp_session_impl/tool_calls.rs#L3073-L3105) · [采样重试](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/acp_session_impl/turn.rs#L3130-L3165) · [轮末待办提醒](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/acp_session_impl/turn.rs#L3623-L3678)

- 派发前的确定性来源校验失败使用现有持久纠错预算。按原调用回写错误码、未派发状态和可用恢复动作，纠错时重新读取当前版本并保留用户目标。已记录的受理未知、权限拒绝、原调用证明变化均按原有保护处理。保存检查点时已把拒绝的调用闭合，进程恢复不会把它们提交出去。
- 图片已使用受理事实检查。视频沿用实际受理或成品，文件沿用实际成品。明确要求执行已保存条目时，模型未调用工具可提示一次，优先发现工具或读取来源。纠错仍无交付时，界面显示真实状态。
- 图片 Worker 在原发布记录内保留失败判定。后台接续保留数据库核验过的原事件消息，在内部检查点附带与事件绑定的判定，旧检查点缺少判定时使用未知状态。明确未发送、供应商拒绝、受理未知和已知供应商任务失败都允许继续不依赖它的交付。受理未知按原操作查看账本状态，自动接续不重发原图片。
- 验收以来源错误后成功受理且只出现一笔图片结算、视频或文件漏调时无假回执、失败续跑可读原操作且无新增派发为准。真实供应商与生产环境另做整链路验收。
