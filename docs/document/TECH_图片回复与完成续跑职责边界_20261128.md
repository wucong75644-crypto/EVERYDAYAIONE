## 4. 推荐设计：保留同一事实链，分开表达和执行

### 4.1 两个时刻必须分清

A. 工具刚受理：需要一次正常模型回复，读真实回执说清所做更改。接受这一必要模型轮次，不把它算成“图片完成后的空转”。
B. 图片发布完成：先应用原生事件；如果完整交付条件已满足，零模型调用收尾。还有后续工作才恢复模型。

只更改R1/R2对应边界，不重构选图/稿件/图片worker和通用Actor。

### 4.2 自然回复流程

1. 当前主模型按原方式调用工具，不改变任何业务参数。
2. 执行器通过原消息配对提交实际tool_result：accepted/completed/failed/unknown、task_id、真实规格/所选条目。保留原生参数、用量与回执。
3. 图片工具成功后不再走finish_inline_receipt的固定聊天回复；进入同一个正常loop下一轮。
4. 主模型根据真实回执自然回答。仅在这个阶段明确“accepted不是已完成”；收到unknown不承诺已受理，失败说明原因；不能把模型话术作为已保存、已展示或完成证明。
5. 模型仍需独立工具时沿原循环执行；不能对所有工具后轮次统一tool_choice=none，避免破坏并行或多步骤。
6. 模型结束时沿原review_model_completion和checkpoint提交。若图片仍accepted，逻辑任务转waiting_dependencies，当前chat回复完成；不能保持LLM轮询。
7. 回复因预算/取消/供应商故障没形成时，已受理图片不撤销、不重发。任务组件显示真实状态；原错误通知保留，不补一段伪装成模型的成功文案。

过程表达不需要逐句关键词过滤：自然文本沿既有流式协议；承诺执行结果的正常最终回复建立在真实tool_result之后。结构化稿件/展示守卫仍能阻止“只说成功”结束交付。自然语言偶发失实仍是模型风险，不能声称本方案从程序上证明每句话真实性。

### 4.3 补齐语义范围，不能再用空列表表示已经没有剩余任务

当前`deliveries`只列generate_video/code_execute，`continue_delivery`只有布尔值，不能把默认false/空列表当作“语义上已经证明全部交付仅图片”。

最小补充：在现有`ImageRequestContext`（经freeze_frame进入唯一action）增加一个**可选的语义范围声明** `image_completion_scope`。不在TaskState另外保存一套，不新增结束工具、不复活独立要求审查模型。建议结构如下，字段名在实施中按此合同固定，不再各入口自拟：

```json
{
  "image_completion_scope": {
    "after_images": "terminal",
    "evidence": ["第三个做成一张图，正方形，一千就行。"]
  }
}
```

- `after_images`仅`terminal | continue | unknown`，缺失等同unknown；terminal表示本轮实际图片发布就是最后交付，不表示图片已完成。
- evidence仅为当前认证输入（含已递交追加要求）的原文短引；宿主从固定输入绑定消息ID/输入版本，模型不再填写一类新ID或短号。数据由现有语义分类请求输出，无额外模型服务。引文校验只核对真实来源和逐字一致，不靠词语判断需求。
- continue表示出图后还有分析、比较、其他处理；具体文件/视频仍由原deliveries/等待条件核验，不在scope里复制第二份对象或批准。
- known deliveries、continue_delivery、待确认、真实未完步骤、待执行工具、错误、未处理追加消息均优先阻止terminal结束。scope不能覆盖或取消它们。
- unknown/缺字段/无合法来源证明/旧检查点均继续原主模型路径；不能用兼容默认terminal。
- 数量由本轮实际选中条目、image_count、已冻结执行与原生回执核对；不从引文提取数字，不用目录总项数代替本次数量。
- 此语义声明仍可能被模型误解；它不是权限，也不能从源引文不存在额外关键词推出“没剩余要求”。以多步骤真实模型测试约束漏判风险，不能许诺零误判。
- 初始语义入口的完整JSON、schema/examples、路由纠错及workflow投影同步包含该字段。新catalog_v2选图纠正工具保持其原职责，不能借本次开放它去取消已验证交付或批准；对纠正后不适用的scope降unknown，不沿旧来源继承terminal。
- 真实steer使声明按原input_revision失效；同一输入的内部恢复不是新授权，只有经现有来源RPC证明的内部owner转移可以只读使用源声明。

如果实施验证发现必须对主模型增加新的修改scope工具才能保证正确，则超出本最小方案，先停下给出证据，不能顺手扩大选图工具。

### 4.4 单一完成决策：派生，不持久化第二个状态机

在现有`content_action`旁增设一个纯派生函数（建议`task_execution/image_completion_policy.py`），输入为已核验的action/交付约束、原生结果、当前待处理输入、原continuation证明。仅返回：

| decision | 含义 |
| --- | --- |
| finish | 本次请求的全部事实与语义条件足够，沿原checkpoint/Actor终态出口收尾；逻辑任务是否completed另由原物理规则判断 |
| resume_model | 有可运行后续工作，或范围unknown，调用原主模型 |
| wait | 仍有未终态依赖，等原事件，不模型轮询 |
| wait_input | 原批准/澄清条件未满足，保留原等待 |
| recover | 错误、未知受理、来源/版本待核实，保留原恢复规则 |

这是当前事实的计算结果，不成为新的数据库权威字段。先执行原安全点和追加读取，再计算。决策中的reason_code仅用于可观测性，不作为新的业务授权。

finish必要条件：可信同一输入/owner链来源且scope=terminal；全部本轮所需图片真实published并有合法图片part/message/资源哈希；本次因果范围内没有失败/unknown/reserved/accepted，数量、条目和相关未退役步骤覆盖；本次没有未交付正文/文件/视频、等待批准、未处理追加事件、pending batch、正在生效的要求变化。不能把未选兄弟条目的待确认状态当成本次尚未完成。逻辑TaskState仍须保留其他真实未决操作，不能为本次静默收尾强制completed。可选工作笔记有可能相关的未完成项时保守resume，笔记全completed不能证明finish。

`end_candidate`作为物理可收尾条件继续使用，但不能扩展成自然语言识别器。不同输入、独立条目和兄弟项的既有受理操作不能被“一刀切输入变化”退役。

### 4.5 完成事件处理与静默路径

保留现有Consumer→enqueue→claim→load/apply完整事件链：

1. worker先发布真实图片，不提前使用供应商返回URL宣告完成。
2. 原RPC应用图片事件、操作和制品，事件status、owner和检查点在原事务中一致。
3. executor在启动可见输出/模型准备前调用统一决策。不能在Consumer侧读一份过期TaskState就直接完成，也不以跳过入队方式丢失原子接回。
4. finish时提交按原物理规则得到的TaskState和本Actor的commit_ready空结果，不能为了闭合本次请求退役其他输入的操作；usage仅本owner真实用量（零新调用应为零），随后由ConversationExecutionService走原commit_generation_turn、终态通知、slot释放。保留空assistant的审计/上下文闭合记录，不物理删除消息。
5. resume_model才启动正常可见流、加载原Skill/上下文并请求主模型；实际图片需要分析时，按image_visual_input/历史查看证明送入真实图片，完成事件中的文字URL不等于模型已看图。
6. 不改SQL343规定的精确内部facts消息头、内容和源历史前缀。不通过修改它把自然聊天或新权限塞进事件；最新动作信息在模型投影层提供。
7. 先保持图片apply的现有candidate形状，再按原允许的checkpoint扩展规则提交完成状态；若PostgreSQL守卫不允许，应先确认具体限制，新增向前迁移及回滚，不删除/弱化trigger或重写历史SQL。当前调查未证明需要新表或必须迁移，因此不能提前承诺完全无需SQL变更。

### 4.6 空气泡与状态展示

不能仅隐藏一个字符串，也不能全局把空消息都藏掉。

- 内部continuation在SQL中已有pending消息，此记录保留。只对服务端认证的内部continuation增加可见性投影：尚未决定调用模型且没有真实内容时，不占用户可见streaming气泡；不能由客户端参数伪造此标记。
- finish路径不调用ActorWebSink.start、不发message_start/thinking；仍发送原终态事件，使订阅、任务列表与slot收敛。内部记录最终空completed仍沿现有隐藏逻辑。
- resume_model路径开始真实模型工作才对该消息发start。消息ID/session/attempt/seq仍原样，重连在已有内容时正常恢复。
- 后台普通等待由图片任务卡片表示“生成中/完成/失败”，优先复用现有独立图片child消息与工具回执组件，不新增一套进度outbox或人为拼接聊天正文。
- `stream_end`不等于commit成功的规则不动。图片child完成不能clear父chat streaming；后来的内部终态也不能关闭其他新消息的streaming。
- 新可见性投影必须覆盖WS、任务恢复/订阅snapshot、REST消息列表/任务对账，不能仅修改MessageBubbleContent导致刷新后复现。暂停/失败/有真实工具block的消息仍可见。

### 4.7 消息可见性接口的具体边界

内部消息不能借用`message_kind=tool_internal`或修改context_revision来隐藏，因为那会影响历史读取与当前轮次协议。建议给消息DTO增加服务端派生的`delivery_presentation`信息，模型工具参数不包含此字段：

```json
{"delivery_presentation":{"origin":"internal_continuation","output_started":false}}
```

origin来自RLS范围内对应task.delivery_context.input_kind；output_started来自原delivery session中已确认的message_start事实/恢复投影，不用task.status=running猜测。普通用户请求仍按原机制显示初始加载；内部消息在output_started=false且没有真实内容/错误/暂停信息时不占可见气泡。此元数据不是完成证据，不作为执行授权。

需补齐的具体消费者：`message_utils.format_message`及消息列表返回、`ActorTerminalDelivery`、任务订阅snapshot/对账、前端`types/message.ts`与API归一化、`messageStreamProjection`和MessageItem可见性。静态消息格式化缺少task来源时，用有界批量受权查询或已核验task上下文供给，不在每一行新增无限N+1查询。原begin/append的fence不改。

服务端没有足够来源证明时不能把普通pending消息标记为内部而隐藏；前端不会仅凭空content和pending通用隐藏消息。消息一旦产生工具block、自然正文或错误，即使没有思考内容也按原逻辑展示。已完成但无正文的内部收尾记录继续保留在数据库并使用原静默隐藏规则。

## 9. 实施顺序、风险与回滚

1. 先添加能够复现当前固定覆盖和完成后空模型调用的失败测试；保留既有B01—B35断言，不把旧断言一概删除。
2. 同步scope合同及最终投影/案例，缺失保守unknown；先实现纯决策及所有反例，不急于让生产直接finish。
3. 解除指定固定文案与提前return，复用正常工具后回复；保持原交付guard。验证accepted后正常回复与操作不重复。
4. 内部完成事件沿原RPC应用后，在可见流和模型准备之前决策；实现commit_ready和终态恢复；再删除新路径隐藏标记。
5. 补齐服务端内部消息可见性、前端pending/start/终态和snapshot；保持stream_end与DB提交分离。
6. 执行对应定向/真实PostgreSQL/前端恢复验证；完整发布仍按release门禁，部署需用户另行授权。线上验收核对真实模型调用数和账本。

每批修改均列“移除判断→接管者”：固定受理话术→模型真实回执后回复+现有任务组件；隐藏完成标记→纯决策+原终态事务；过早message_start→内部continuation受控可见性；零散额外交付判断→同一action+原交付事实消费者。无法指出接管者的判断不删。

主要风险：语义漏识别提前结束；续跑owner变化导致取错输入；去除早停造成重复生图；延迟start破坏seq恢复；静默终态漏slot释放；正文恢复重放重复；新字段打破动态schema/SQL严格快照。以上分别由unknown保守路径、可信源事件核验、原操作账本、同一delivery session、原终态出口、commit_ready以及V01—V20覆盖。

回滚应用候选恢复原reply/continuation分支，不删除历史稿件、图片、事件或操作账本。新增scope只影响语义判断，不授予权限；旧版本不认识字段的Pydantic extra=forbid与源checkpoint恢复必须在发布前验证，必要时提供版本化只读投影，而不是假定向后可读。若新增SQL迁移，单独验证向前/回滚与真实owner；存在新字段快照不能安全降级时先说明回滚前置条件，不盲目回退SQL。

## 10. 审阅结论与实施边界

推荐在原统一链路上区分：自然回复、真实状态、完整交付判断和可见消息生命周期。保留原生事件与账本，只消除“用固定回复替代模型”和“为了隐藏标记再次采样”两种行为。

这不是简单删两个if，也不需要重做ID、选图、稿件或执行系统。现有代码已经具备可信结果、事件恢复、commit_ready与前端去重等基础；需要补齐的是语义终止条件和真实可见输出边界。设计不能证明自然语言理解永不漏判，因此未知范围保守续跑，关键组合必须真实验证。

未决的实施证据：新的语义scope在真实供应商完整上下文中的准确率；现有SQL对目标零采样完成扩展的实际允许性；全部消息读取/订阅入口的内部可见性收敛；旧二进制对新增scope快照的降级读取。它们是明确的验证门，不是已经满足的假设；任一不通过则保留原安全路径，先报告证据再调整方案。

- Microsoft Agent Framework的[Durable Extension](https://learn.microsoft.com/en-us/agent-framework/hosting/durable-extension)：状态和外部事件持久化、恢复及模型执行分离；仅参考职责，不引入Azure基础设施。

本次以实际函数体、调用方、原生SQL、前端投影、既有测试断言及之前真实只读验收记录为依据。大文件按相关函数和上下游定位读取；未把无关子系统或测试存在当作全系统审计通过。实施时若基线HEAD改变，先核对上述相关diff，再沿此矩阵补充调查。

## 12. 补充：端到端JSON与模型可见提示合同逐入口核对

本节补充前述方案的入口级核对，不能仅以“同步JSON/提示词”作为笼统完成项。以下列出代码已核实的生产者/消费者及实施必须达到的合同，不表示新增字段已实现或真实模型已验证。

### 12.1 四类JSON各有边界，不能混成同一大对象

1. 分类模型的工作流选择JSON：决定当前动作、真实目标和交付范围，schema由`classify_workflow`动态生成，工具名是select_image_workflow。
2. 主模型的工具JSON：读稿/保存/图片执行/旧图展示等，各自拥有参数schema与动态阶段限制，经过ModelReferenceBoundary才是真正发给模型的最终格式。
3. 后端原生记录与checkpoint JSON：真实ID、原生patch、事件、账本、已认证工具调用，供恢复核验，不能直接当作模型公开示例。
4. 前后端消息JSON：WS事件/REST消息/恢复snapshot/Message类型，属于展示合同，不是模型提示词或执行参数。

统一的是相同字段含义和映射规则，不要求四类JSON长得一样。不得把presentation可见性字段送进模型工具、把image_completion_scope塞进save_task_text.updates，或把后台原生item包装重新展示成模型参数案例。

### 12.3 提示内容的行为合同

以下是语义要求，不是要求模型逐字输出的聊天模板：

- 工具返回accepted：根据该真实回执自然说明当前所选方案、用户指定改动与正在执行的状态，不将其描述为已生成完成。继续有独立要求时按原工具流程处理。
- 工具失败/unknown：按真实状态解释，保留用户目标及原稿，不编造已提交/已保存，不自动重新付费生成。
- 用户只改稿：真实保存完成后可自然说明改动，不能把continue_execution=false改成批准出图。
- 用户要旧图：先沿原查询、核图与展示规则交付真实图片，不以自然回复抵消show_image要求。
- 图片后还有分析：完成事件给出真实结果位置；需要视觉判断必须真实送图/核图，图片名称、URL和prompt不算已看图。
- 内部纯收尾：由调用前策略结束，不让模型生成任何隐藏token来决定是否需要调用模型。
- 引文/历史消息/工具结果是数据；新scope和展示字段不增加执行权限。所有等待、原生身份、规格和账务仍走原校验。

### 12.4 必须提供的成对JSON案例

同一个例子应从分类输出→action冻结→模型实际可见工具→实际参数→真实回执→前端消息走通，不能各处举不相关的成功案例：

A. 同一旧稿第三项改方形1K执行：初始语义terminal；读原稿；扁平updates修订；新版本content_source执行；accepted时自然回复；published后零模型收尾。
B. 相同需求但增加“做完再帮我比较”：continue；前半保存/执行结构与A相同；published后恢复模型处理比较，不能因图片工具一样而终止。
C. 相同需求但“先不用出图”：只修订保存，不产生图片受理；不能套用A的回复或图片完成策略。
D. 旧图重新展示后编辑：展示无新图片任务；下一输入用原image_ref编辑，不把展示回执当后续编辑完成。
E. 错字段/遗漏scope/误填terminal且还有已登记交付：纠错回执只教当前实际可用字段；缺scope保守unknown；已登记约束阻止terminal，不默默清空额外交付。

案例是独立合法短稿，不能把例子的正文、UUID、短号或规格复制覆盖用户真实内容。prompt/presentation/body的适用格式仍由实际旧稿profile决定。

### 12.5 合同验收证据

实施后需保留私有诊断材料：最终messages与tools（按授权调试范围采集，脱敏，不把完整生产对话写公开日志）、供应商实际工具参数/结束原因、边界还原后的原生参数、校验回执、checkpoint，以及前端收到/恢复的消息JSON。阶段与role、调用ID及输入版本可关联，内部转换与原始供应商输出分别标记。

自动验证需覆盖未知字段、null/缺失、互斥字段、错误引用类型、旧检查点、动态阶段不可用字段和错误回退，不用测试工厂静默转换来掩盖模型端错误。真实模型测试核对完整上下文冲突，并记录首轮错误和续跑次数；schema合法不等于语义正确。


## 13. 补充复核发现的边界与方案修订

本节来自对方案本身及相关代码的再次交叉核对。不是另外发现了十一个已复现线上Bug；其中H01/H02/H03是代码约束支持的方案细化，其他为实施必须验证的失败方式。本节约束优先于把“完成”笼统理解为整个root_task完成。

| H01 | 当前请求、内部Actor和逻辑root任务不是同一个完成层级；原目录允许同组兄弟项独立等待确认/受理 | finish只代表本次Actor可收尾。未选兄弟项不触发额外确认；真实其他未决操作也不能被强制completed/退役。关联按owner/已认证输入/条目/call binding原生证据，无法限定则保守原路径，不新建独立窗口账本 |

| H10 | 语义scope的新字段可能在分类模型被遗漏，或上下文压缩后误取旧original_goal；模型中途停下可能只写完部分要求 | 新请求最后发送schema显式要求scope；旧持久化记录解析允许缺失为unknown。scope依据当前完整认证输入，不能从旧摘要缺少后续要求推导terminal；截断/解析失败不授予完成资格。真实模型A/B场景必须包括后置分析/比较/否定及等待 |

### 13.1 新增保护场景（与V01—V20共同执行）

- V21：第三项完成，第一/二项尚待用户确认：第三项正常收尾，不询问批准其他项，也不把其他项状态改掉。

- V23：受理已成功，回复轮次恰好没有预算/供应商返回空或截断：状态组件仍正确，不扩大预算、不重复派发、不补伪成功自然文案。

不增加独立关键词匹配、不增加第二次结束判断模型、不开放已绑定后随意改scope、不改变任何生图收费重试策略。不能为了让优化命中率变高把unknown改terminal，也不能为了漂亮自然回复放开原稿/展示/批准守卫。上述任何边界需要扩大时，先返回实际阻塞证据和修订方案，再实施。


## 14. 本次实际实现与验证

### 14.1 实现落点

- `workflow.ImageRequestContext`增加可选`image_completion_scope`，初始分类最终schema、required、说明和JSON examples同源更新。仅有`after_images`和原文`evidence`；初始schema仍拒绝多余字段。运行时对这一**非授权提示**的非法值整块降为unknown，不解析字符串、不删除未知键后保留terminal，更不丢弃其他合法业务字段。业务目标、尺寸、批准和素材仍按原严格合同校验。
- `request_resolution.freeze_frame`将该字段随唯一action冻结，核对当前输入或当前owner已送达追加原文。目标纠正不继承不再适用的旧scope；catalog_v2选图工具不新增修改完成范围的能力。
- `execution_engine`删除`finish_inline_receipt`和两处提前返回，不再将有效图片回复整体替换成`image_status_reply`；保留调用工具前的临时文案缓冲、稿件/展示完成校验、预算与失败停止。RESPOND新写入保留模型原文；已经提交的旧恢复记录仍按原记录恢复，避免篡改已交付历史。
- 已受理图片后在原主循环让模型读取真实回执自然收尾；同一说明覆盖generate/edit/execute_saved/repeat/write_then_submit_images及有无短引用目录。完成事件不再要求隐藏的`<image-delivery-complete/>`，且不再拼入普通生成阶段的“尚须实际提交图片”说明，避免已完成事件与生成指令冲突。
- `image_completion_policy`只读检查源owner、输入版本、范围、数量、真实子任务、未完成操作/稿件/计划、批准和追加消息。只有finish进入现有continuation事务的completed候选；其他结果保留原等待、恢复及模型路径，不新增终态写入口、不退役兄弟任务。待确认集合扣除已经批准的所选条目，不能把已满足批准当成仍缺批准。
- `image_continuation`仍先核验原生published图片及消息/来源/哈希，再应用既有RPC。纯完成不调用模型；后续工作或不确定继续原模型。`execute_chat`对已证明完成的内部接回不启动流；后续安全点发现新增工作时，可在真正采样前补发同一个start。
- 前向迁移389在原内部入队消息的`generation_params.delivery_presentation`写`origin=internal_continuation, output_started=false`。原带fencing的持久start事件同事务切true。函数原owner/ACL/security属性不变，未改原迁移、表结构和执行凭据；提供逆向回滚并验证重新应用。
