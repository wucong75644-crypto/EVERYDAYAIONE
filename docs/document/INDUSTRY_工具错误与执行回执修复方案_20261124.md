# 工具错误与执行回执：诊断和建议方案

> 2026-11-25 实施更新：下文保留为当时建议。实际修复沿用 Artifact/TaskState 既有字符及字节预算，未采用另设 128KB；未新增数量审稿器或数据库迁移。补齐了图片成果类型读取、按真实输入隔离的重复检测、保存与文字结束的独立语义。实现和验证以 [修复记录](TEST_工具交付与回执衔接修复_20261125.md) 为准。

## 核实结果

### 修订参数结构错误

真实失败调用的 updates 三项均为 {item_index, body}；实际 SaveContent / ItemUpdate 契约要求 {item_index, item:{body}}。工具已返回逐字段 issues，模型随后纠正。这是模型未遵守已存在的结构，不是尺寸错误。历史检查点携带同一错误，不重复计为多次独立发生。

代码：backend/services/task_execution/content_objects.py 的 ItemUpdate、SaveContent、save_parameters。当前 schema 由 Pydantic 生成；不能在没有证据时宣称工具 schema 本身写错。后续须验证正式模型请求真正披露的 schema 及供应商支持的约束，不能假设开启 strict 就能约束所有模型。

建议：维持单一 schema 来源；修订入口展示明确嵌套说明，错误继续返回路径、预期结构与当前调用身份。参数修复使用现有有限纠错机制，保留原稿、版本、素材和执行意图，不因纠错自动获得生图授权。不增加模糊兼容分支去猜参数，不添加词表。该错误本身已恢复，优先级低于后两项。

### 长稿不是没写出来，而是已写出后保存被拒

任务 a55be3db 的失败调用已有三套完整正文，工具参数序列化约 53,229 字节；三项 body 分别 14,182、17,208、18,923 字节。content_objects.save 将包含正文及材料的 ContentRecord 序列化，超过 50,000 字节即拒绝。随后模型重新生成并只保存第一套。

关联预算还包括 Artifact.inline_text 的 50,000 字符和 TaskState 所有内联成果合计 256,000 字节。不能只改一个数字而忽略版本保留、正文投影和恢复快照；也不能把中文字符数当成 UTF-8 字节数。

model_bridge.review_model_completion 的 model_directed 分支直接使用 direct_loop.end_candidate；后者核对已建立的工具步骤、物理操作和结果。只保存第一套也可能满足已建立的步骤，未自动发现原来承诺的三套还缺两套。这解释任务 completed 与正文少交并存。

建议最小方案：

- 对当前常规多方案范围统一对象/条目/任务预算。建议对象上限先评估为 128,000 字节，同时保留既有单成果 50,000 字符和任务合计 256,000 字节约束；实施前以修订多版本真实快照验证容量。该建议值是项目配置选择，不是厂商标准。
- 保存前预检完整序列化尺寸，容量内一次保存三套，原文不重写。超过剩余任务预算时保留已生成原稿与明确的未完成保存状态，返回可恢复的容量错误及实际/允许尺寸；不要让模型删两套换取成功。
- 在既有工作计划/成果状态中记录本轮结构化交付预期和已有条目数。修订继承已有三项，不能在存储修复时悄然降成一项；数量变化须来自本轮真实要求的语义更新。仅检查客观交付数量与保存状态，不引入内容打分模型、词法计数或全文审稿。
- 到达纠错预算仍未保存完整时返回 partial 及已完成/缺失项，页面不声称全部交付。超大文档外置或分块作为将来确有需求时的扩展，本次不先建新存储系统。

### 编号执行被未决操作和批次屏障共同阻断

编号请求开始时，三个上一批图片任务仍在执行，检查点对应操作 accepted。因此 model_directed.record_calls 返回 TASK_DIRECT_EFFECT_UNRESOLVED 有真实未决状态依据，不能删除防重复执行保护来放行。

更具体的缺口：record_calls 按 capability 阻止新操作，而非只判断同一方案项/版本/素材/规格是否冲突；任务恢复已携带旧图 accepted 时，模型被要求读原结果。execute_control_batch 又用 len(controls)!=1 拒绝同批多个控制调用，包括两个 read_task_result。真实记录显示第 8 至 20 轮各两个读取全部返回 TASK_CONTROL_BATCH_BARRIER，共 26 次，且 retry_next_round=True 没说明可执行的下一步。当前测试覆盖“两个修改控制应拒绝”，未区分只读结果查询与修改计划。

随后回调已把旧操作更新 completed，但本轮未成功派发的编号意图没有变成明确待续交付，最后仅文字描述。这不是供应商拒绝。

建议最小方案：

- 将读取/核实结果与修改控制的批次策略分开。允许多个结果读取，由宿主对同一已提交快照核实并依次暂存、一次检查点提交；这类读取可能导入证明或刷新状态，不直接并发修改共享 TaskState。仍保留修改控制与业务副作用之间的顺序屏障。
- 接续时宿主从现有子任务回执核对 accepted/uncertain 状态，并保持既有权限、归属和检查点确认。图片已完成则导入并展示真实结果；仍运行则明确 waiting_dependencies，不把等待变成反复模型轮询。
- 复用现有媒体槽位、方案项、版本、材料、规格及操作键判定同一操作，不能用“同属生图能力”阻塞全部后续动作。相同操作只复用或等待；真实修改/明确重新生成走已有新操作语义，不增加无限重试或重复扣费。
- 本轮选中的第 1/3 项在原版本上保留待交付状态；需等待则在原任务接续，不能因旧图回调结束就把新要求一起标 completed。若满足复用条件，交付实际图片块并说明复用；不是只回复两段方案文字。
- 同一工具、参数及相同错误/状态重复不算进展。复用现有重复调用保护，在无状态进展时进入等待或有界失败，避免继续 13 轮相同错误。

## 关联缺口及实施顺序

本方案不能被解释为上轮四类业务问题全部解决。误触发生图、跨轮漏传波点图仍须连带验收：模型语义决策负责是否执行、选哪项和素材用途；后台保留原稿身份、所有有效材料引用及真实授权状态。不能以新增“必须出现生图关键词”或新审批来处理。

建议先修批次读取/回执接续与保存容量/完整交付，再处理参数披露和纠错提示。随后将误触发生图和素材遗漏纳入同一条正式入口复测，不先单独宣布上线可用。
