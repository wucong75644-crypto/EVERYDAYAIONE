# 多轮对话中的方案选择与图片绑定

开发基线为 `56ae1a89`。第四节记录方案对比，第七节记录本次实现和本地实测。

## 一、从用户的两句话走到图片任务

用户先上传产品图 A，说“参考这个产品写四个新品方案”，随后说“用第四条做图”。

| 时点 | 前端 | 模型 | 后台 |
|---|---|---|---|
| 上传消息 | 显示附件和上传状态 | 读取本轮允许使用的图片 | 保存消息和附件来源，用消息 ID、内容位置定位这次上传 |
| 写四条方案 | 流式显示，最终呈现一份原版内容 | 按用户选择的创作 Skill 或普通聊天方式写一次 | 保存这次真实输出。边界已知时登记整组，关联产生本组的消息、图片用途及已确定的规格 |
| 选择第四条 | 接收自然语言指令 | 识别目标组、条目和动作；仅在用户改图或改规格时表达变更 | 在本轮有权限的上下文内解析选择，读取对应版本。尚无组记录时，首次需要执行或修订再从权威原文建立整组索引 |
| 提交和完成 | 有受理回执后显示进度，收到结果后显示图片 | 可以解释结果或询问歧义 | 从原文取执行正文，解析执行参考图，确认规格，复用校验、计费、防重、受理和结果回写 |

首轮的聊天消息本身就是可交付内容。正文已经保存、整组索引尚未完成时，保留正文。下一轮从已保存的同一版补建索引。流式输出中途断开时，不把未完成条目当作可执行输入。

## 二、上下文分别回答三个问题

1. **用户指哪一组、哪一条？** 会话界定查找范围。复用现有任务接续判断、成果目录和修订版本。明确说“手账本的第四条”就定位手账本组；紧接着刚交付的笔袋方案说“第四条”，优先定位该组。组的选择要有本轮指代、刚交付的消息或任务接续记录支持。两个目标都说得通时，用组名发起一次简短澄清。同一会话可有多组同序号条目。
2. **执行哪段原文？** 从权威的已完成回复或已登记成果取原始文本。对已有成果，沿用成果版本和组内条目；对普通正文，保存来源消息、内容位置、版本或摘要及从该原文获得的精确边界。摘要核对版本，条目边界区分执行正文和展示说明。两项分别验证。修订只替换选中条目，其他条目及其素材和规格保留。用户指定旧组时取该组有效版本，明确指定某个历史版本时按那个版本核实。
3. **用哪张图、什么规格？** 上传时登记来源，方案阶段区分执行参考和仅供分析的图，执行时冻结实际选择。已明确“这组执行沿用 A”时整组记一次，有条目专用图则记录例外。仅凭曾上传过一张图，不足以覆盖已有绑定。本轮明确说“换 B”只改变本次请求；说“以后这组都换 B”属于方案修订。规格优先采用本轮明确覆盖，其次采用该条目已确定的规格；实际请求中尚未确定的部分交给现有尺寸和模型适配规则处理。约束矛盾或模型不支持时，在派发前说明冲突。

| 操作 | 方案正文 | 执行图片 | 对旧方案的影响 |
|---|---|---|---|
| 做完手账本任务，又上传 B 写笔袋方案 | 新建笔袋组 | 新组使用 B，取决于该任务确定的用途 | 手账本组仍关联 A |
| 只上传 B | 暂无新的执行指令 | 仅保存上传来源 | 原绑定保留 |
| 回到手账本，做第四条 | 手账本第四条当前原文 | A | 复用旧组 |
| 用新图 B 做旧第四条，规格照旧 | 同一份第四条原文 | 仅本次用 B | 旧组仍关联 A，沿用旧规格 |
| 只改第二条 | 建立该组修订版 | 保留既有绑定 | 第四条正文逐字符相同 |
| 做剩下三条 | 先确定目标组，再查各条受理记录 | 各条自己的参考图 | 已受理、执行中或已完成的项复用已有进度、结果；结果不确定时先核对回执 |

## 三、接入现有代码

| 位置 | 拟变更与复用 |
|---|---|
| `backend/services/handlers/chat/execution_engine.py`、`backend/services/task_execution/content_objects.py` | 在完整回复交付处连接已有的分条正文、成果保存和渲染。结构化输出只写一次；页面与执行读取同一份条目正文，版式说明保留在现有展示字段。普通回复仍可直接交付。来源消息与成果采用可核对的关联，使回复完成、断线恢复或登记重试时只登记一次。 |
| `backend/services/handlers/chat/content_tools.py`、`backend/services/handlers/chat_input_handoff.py` | 为未登记的回复复用历史读取、精确片段、版本校验和来源图片查找。在后台完成整组登记。模型侧按可见目录表达“一组中的第四条”；组标识、文件定位、摘要、字节边界从服务端记录取得。把“读整篇、报行号、登记、再提交”的固定流程从模型操作说明中收回。 |
| `backend/services/task_execution/followup.py`、`backend/services/task_execution/direct_loop.py` | 复用新任务、继续、修订和不确定四种关系。把当前交付组与可访问的历史组作为选择依据；跨组指代受同一会话、任务身份及权限约束。继续整组时复用按条目的受理与防重记录。 |
| `backend/services/handlers/chat_context/image_sources.py`、`backend/services/handlers/chat_image_preparation.py`、`backend/services/handlers/chat_image_request.py` | 复用消息图片标记、原件解析、规格检查和请求冻结。`compile_input` 取选中版本的执行正文。提交前核对图片身份及文件摘要，固定这次的参数，后续上传和修订不改变已受理请求。 |
| `frontend/src/contexts/wsTaskMessageHandlers.ts` 等现有消息事件入口 | 先核对现有显示与重连行为。只有在状态未正确接线时调整。聊天答复完成、图片任务受理、图片发布分别依各自事件展示。明确要求执行而缺少受理回执时，显示待澄清、未提交或受理待核实等实际状态。 |

**条目边界从哪里来。** 优先采用创作时已有的条目结构或该 Skill 声明的交付格式。普通正文在首次使用时检查原消息内容块与可确定的文档结构。精确取回包括换行和负面段在内的原文。诸如“参考图判断”“使用建议”按作者的展示与执行边界处理。回放中识别两种 Markdown 样本的临时解析程序不能直接作为所有场景的生产规则。遇到没有可信边界的自然段，可让模型提出所指片段，再由后台核对唯一、完整的来源；来源或范围仍有歧义时让用户选清楚。

**直接生图和其他工具。** 用户一开始就说“画一张……”时，本轮文字就是创作输入；上传图并明确要求改图时，本轮上传就是执行参考。沿用现有直接执行入口及后台需要的内部准备，用户无须先制作方案。文字来源、版本和素材选择可供视频、文件等入口复用；具体工具仍按自身定义接收它支持的字段。提示词 Skill 保留原有创作和排版职责。本方案不依赖重新启用聊天图片编排 Skill。

## 四、为什么采用整组登记

本地以两份真实聊天正文作为输入，分别比较了首轮登记、次轮只登记选中条目和首次使用时登记整组。普通第四条为 501 字符。原 Skill 第四条为 554 字符，含 154 字符负面内容。首轮登记和首次使用时登记整组都保留了原文，修订第二条、换图做旧第四条也能得到预期参数。只按行登记单条多取了末尾换行，随后从同一来源登记第二条会触发 `CONTENT_MESSAGE_SOURCE_ALREADY_REGISTERED`。保留现有来源身份校验，整组复用这份身份即可。

六条方案的原消息还有一份简版。两个正文块都出现“第四条”，简版缺少独立负面段。回放用已记录的首轮原始输出核实来源；另用现有 Skill 版式校验独立区分了这两份内容。不能只挑最后出现的一份。

此次证据到本地冻结请求为止，图片按文件哈希核对，两张真实原图均为方图。候选索引由离线程序生成；真实线上模型在自然多轮对话中的选择、不同画幅换图及浏览器受理体验仍需验证。

## 五、实施顺序与异常处理

1. 固定现有成功和失败样本，以原消息、真实上传、自然语言指令启动。把独立的预期正文和图片摘要放在断言端。
2. 先接“完整回复 → 整组索引”，再接“选已有成果或按需补建 → 现有执行器”。相同来源重复登记返回同一结果；并发修订核对版本，过期选择重新定位。实现时检查现有写入事务与检查点，覆盖“消息成功、成果登记失败”和“登记成功、页面重连”两种顺序。
3. 接通“明确换图、新任务、继续剩余项”和受理反馈。能够从回执证明已受理的任务继续跟踪；状态不明时先按既有操作标识查询。已完成的正文不会因图片提交失败而丢失。
4. 本次只在任务工作树实施和离线验证。沿用现有成果与消息记录，按需读取；不安排历史全库转换。若后续授权发布，按项目发布入口交付。回退应恢复上个版本的读取、选择行为，保留已写正文、成果及受理记录，不重放图片任务。新增持久字段如确有必要，实施前单独验证旧版本读取和恢复能力。

## 六、上线前验收

| 场景 | 通过条件 |
|---|---|
| 普通四条与原 Skill 六条 | 首轮完整显示一次；第四条逐字符匹配原文。原文有负面段则完整包含，没有则保持原样。剔除组外说明。 |
| 先选第四条，再只改第二条 | 两轮共用同组来源，只有第二条变化；执行第二条使用新文，第四条与其他条目的原文和原图不变。 |
| 第四条、剩余项、重复指令 | 逐项对照受理清单。模拟成功、部分失败、超时未知、重连与重复事件，避免重复创建图片任务或计费。 |
| 同一对话 A、B 两个任务，各有第四条 | 选新组、点名旧组、用 B 做旧第四条都取对。仅发 B 不修改旧组；含两种合理指代时先澄清。有分析图、多张执行图时核对角色和顺序。 |
| 跨画幅换图 | 方形方案换竖图但说“规格照旧”，核对冻结请求仍是旧规格；用户明确改竖版时核对本次覆盖。验证旧条目及原绑定可再次读取。 |
| 普通正文、重名、重复版本、上下文压缩 | 从持久化来源恢复准确版本及正文；歧义可见，越权、资源失效和已过期版本在派发前拦截。 |
| 直接文生图、上传原图改图 | 两类都可从正常聊天入口启动，无需用户先登记方案；生成模型的真实请求、受理、页面结果分层核对。 |
| 模型只说“准备提交” | 无图片回执时界面不得显示已受理。记录实际停点；用户可在同一对话接续。 |

回放先使用本地模型输出记录和图片服务替身。真实模型决策、真实图片供应商结果分别报告；任何付费验证先列预算和调用上限。开发、提交和生产部署按用户后续授权进行。


## 七、本次实现与本地回放

普通聊天和创作 Skill 共用现有成果登记。可识别的整组正文在回复完成时登记，页面使用同一段原稿。原 Skill 在一轮里同时返回原版正文和简版保存调用时，以这轮实际展示的完整原稿建组。未完成的流不能作为执行来源。分条边界无法确定时保留正文，接续时走已有的原文范围核验。回放也单独从未登记的历史消息开始，只给原消息身份，由后台定位整组并核对原附件。

当前组和同会话内近期可接续的历史组共用成果目录。新上传作为来源登记到生成该组的用户消息。执行时重新检查选中版本、参考图身份、原文件和规格。需要在多组之间换图时，目录提供每组上传的名称与消息定位。执行者可以在同一调用里选旧条目和新图。迁移 `378_agent_content_followup_groups` 沿用原任务接续的身份、租约、消息修订和锁校验，模型只收到历史组的目录信息。近期目录最多检查 32 个符合条件的历史任务。成果沿用 v2 正文和备注结构，已有的消息、计费和图片回执记录继续由原模块读取。

| 本地操作 | 四条普通聊天记录 | 六条原 Skill 记录 |
|---|---|---|
| 首轮保存和展示 | 四条，页面正文逐字符相同 | 六条，固定原 Skill 版本，完整正文只展示一次 |
| 选择旧第四条 | 原文 501 字符，SHA-256 以 `7635318a2ad3` 开头。原文没有独立负面段 | 原文 554 字符，SHA-256 以 `68fc87a916dd` 开头。正向和负面段整体逐字符匹配 |
| 只改第二条 | 原组修订到第二版，其他三条原文和素材逐项相同；执行剩余三条使用新版第二条 | 原组修订到第二版，其他五条原文和素材逐项相同；第四条保留原 Skill 来源校验 |
| 竖图开启新任务 | 同一会话新建四条笔袋方案，新第四条配竖图，输出 3:4 | 同样通过 |
| 用竖图做旧第四条，规格照旧 | 请求中原文摘要等于上面的第四条；图片摘要等于竖图。输出 1:1、1K、PNG | 同样通过，负面段随正文传入。旧方案仍指向原图 |
| 直接生图与回执 | 新对话直接文生图、上传原图直接改图分别检查本地受理、供应商适配参数及页面完成事件。模型仅口头称已提交时，流与最终正文均显示无回执 | 共用同一执行和回执入口 |

两份原始记录和素材在私有证据目录中。普通记录从实际输出分块开始，Skill 记录还使用原保存调用与原发布版本。后续选择由本地模型替身根据用户话语及当轮实际可见的目录完成。原文预期摘要只进入断言。测试使用独立 PostgreSQL、本地文件和图片供应商替身，覆盖到前端 WebSocket 消息处理器。真实模型在线选择、生产迁移和真实供应商生成质量留待单独验证。

本次本地后端相关用例 363 项通过，前端消息处理用例 109 项通过。独立数据库验证了迁移及回退，本轮未调用付费模型或图片服务。
