## 对统一方案的明确约束

1. 统一用户动作与目标的决定入口，不合并或删除不同事实证据。当前输入、原始选择、保存后的有效版本、真实执行回执必须能分别追溯。
2. 来源解析只读取与核验。执行所有者变更仍使用原接管事务；不能把预检或读原文当作接管，也不能让统一接口绕过 B04 的绑定限制。
3. 一套阶段评估必须覆盖混合条目：同一组可同时包含原样可执行、待修订、等待确认、已受理和失败条目。不能用整组一个布尔值取代。
4. 原格式渲染、尺寸解析、素材字节解析、权限与操作账本继续作为领域职责。统一评估调用这些规则，不重写第二套，也不把领域校验挪成提示词。
5. 保留动态工具提供的差异：当前目标类型、已激活方法、交付种类和业务阶段决定参数形式；模型边界负责投影并核验当前实际提供的合同。不能为了“JSON统一”强行让内部存储和模型章节格式相同。
6. 旧稿新增后续等待必须有明确的独立来源；不能用批准动作兜底创建条件。原来有等待与原来没有等待必须分开验收。
7. 不统一重试额度，不增加纠错模型，不自动批准，不自动改选最新版，不修改供应商、计费和媒体展示规格。

## 已发现的冲突与仍需补足的证据

- C01（代码与失败记录均已证实）：保存入口 conditions = save_value.confirmation or media 混用后续等待条件和本次批准；旧无等待稿修订后可以新增等待，而批准仍指向旧版。现有“原稿本来就在等待”的测试不能代表这一组合。
- C02（代码证实）：工作流持有 action/target/size/materials，request_resolution 另存核验目标；恢复时有复制当前窗口与重绑 input_revision 的桥接。需要区分权威决定与只读投影，不能再按消费者补同步。
- C03（代码证实）：content_delivery 与 content_revision 的 input_revision 算法不同；inline 编辑、通用纠错与原生操作还有其他有意不同的身份。不能全局替换哈希；必须先逐一注明职责和有效期。
- C04（代码证实，未宣称本轮新复现）：content_source/content_revision 对版本变化要求先核对指定版本、不自动换最新；tool_argument_repairs 的 CONTENT_BASE_VERSION_CHANGED 指导却要求读最新版。统一错误政策时应保留“用户明确历史版本”与“本轮自己保存的新版”的区别。
- C05（代码证实）：当前内容来源新解析器之外仍有 content_followup_state、格式和素材目录的候选回退。它们中有纯历史上下文用途，也有执行来源用途，不能整段一刀切删除。
- C06（需重点验证）：request_resolution.check 的同轮新稿放行条件用于支持新稿立即执行。历史稿修订应有同对象保存链证明，但不能通过删除这条放行直接破坏新稿能力。
- C07（代码证实）：阶段提示、工具过滤、保存预检、完成检查与展示恢复是不同消费者。共同评估可以统一决定，事务前版本/权限重检仍必要，不能把防并发校验当重复代码删掉。
- C08（既有真实证据）：正确读取后供应商仍可能生成缺括号 JSON；统一状态不能保证语法合法。上一轮跨任务客户验收因此停止；另一次确认版本失败仍存在，不能写为全链路通过。

## 验证不能只覆盖正确调用

实施前应把 B01—B35 对应到保留、迁移或补充验证；已有单项测试只证明它实际覆盖的断言。尤其补足以下完整组合，而不是只给 helper 填入正确状态：

| 组合 | 必须观察的结果 |
| --- | --- |
| 上传写三稿 → 第三项改方形1K执行 → 改2K但不出图 | 同一对象连续版本、兄弟条目与素材保持、实际出图次数正确 |
| 新绿叶任务 → 明确返回旧灯塔第三项改规格并执行 | 默认接续任务不改变来源，先读旧稿，保存与实际执行使用同一新版 |
| 原稿无等待 → 明确改完出图 | 不凭路由 media 创建新的等待条件；不错误要求用户再确认 |
| 原稿有等待 → 只改稿 / 批准原样 / 批准修订后执行 | 三种行为区别保持，仅本次批准条目获得执行资格 |
| 多条目含 ready、待修订、待确认及已受理兄弟项 | 各项阶段与批准隔离，已有受理操作保持有效 |
| 同轮新稿执行与旧稿修订交叉检查 | 保留新稿立即执行能力；本轮无关稿不能冒充历史修订新版 |
| 读 A 再读 B、默认候选为 C、读取后原稿变化 | 读取不改目标、不改所有者；版本变化不自动换稿 |
| 保存提交前失败 / 保存已提交后取消 / 接管后重启 | 候选和证明不提前生效；真实已提交成果不丢失；同输入不重新授权 |
| 生图受理回执丢失、完成事件重复送达 | 查询原任务与幂等收尾，不重复生成或扣费 |
| 旧原图展示 → 旧成图展示 → 选该图继续编辑 | 两次真实图片块、正常缩略图、原始身份与编辑底图哈希一致 |
| 补第二张主体图、保留第一张风格图，反转输入次序 | 主体/风格用途和画布都跟随真实素材身份 |
| 错误字段、非法JSON、坏控制与合法业务同批、模型只说完成 | 原纠错边界与批次屏障保持，不能形成虚假保存/提交/展示 |

## 实施前的完成判据

每一个拟删除的判断都必须注明被哪个统一规则或现有领域组件承接；每一个现有存储字段都标注为权威决定、不可变事实、派生投影或临时缓存。未确认用途的分支不先删除。本文是后续设计与实施的保护基线，不是对当前实现“没有其他问题”的保证。
