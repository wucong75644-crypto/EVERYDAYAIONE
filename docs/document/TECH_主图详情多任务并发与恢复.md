# 主图详情多任务并发与异常恢复

状态：本地实施，未提交、未推送、未部署。用户授权一次完成前后端修复与验证，明确暂不部署。
日期：2026-10-16（北京时间）。基座：e9707990。

## 问题与证据

原后台恢复循环先 await 图片生命周期整轮扫描，再扫描主图详情。图片扫描逐张 await 供应商提交、文件持久化和交付，因此一个慢请求会延后其他图片和策划发现。策划扫描也在发现过程中同步执行整组受理、恢复及汇总；组织扫描/项目读取/汇总异常可以退出整轮。

前端定时轮询、窗口 focus 和手动刷新可产生同一生命周期内的重叠请求。旧响应晚到会覆盖新状态，令已完成任务退回“生成中”；旧失败也会覆盖新成功。原有 lifecycleVersion 只能隔离切换任务或账号，不能隔离同一任务的请求先后。

三项前端竞态回归在原版本均失败，修复后通过。上述是可复现的代码路径，不等于已确认截图中历史任务的生产根因。

## 实现及职责

- `background_task_worker.py`：图片与策划使用独立恢复扫描循环，分别隔离扫描错误；退出时取消两个循环并关闭任务池。
- `background_jobs.py`：共享的进程内有界调度器，只为获得容量的工作创建协程。按用户/组织、项目、项目内部任务三级轮转；记录各级最近调度顺序，跨轮次与分页优先处理尚未调度或最久未调度的工作。每分钟清理超过一小时未出现的历史记录，运行中的任务记录保留。以持久化任务 ID 防止本进程重复执行，完成、异常、取消均回收容量。记录活跃数、候选数、时长和异常类型。
- `chat_image_lifecycle.py`：扫描仅发现任务、维护游标、提交到本地任务池，不等待供应商/文件处理；每个操作重新读取持久化状态。组织扫描失败不影响其他组织。
- `detail_page_generation.py`：发现策划与分组维护候选；策划、受理/恢复/汇总分别使用有界任务池；主图与详情组分别调度，慢组不占住整个产品。项目读取、组织扫描、单组维护错误分别隔离。发现时轮转 updated_at（带当前 run_id 条件），避免失败或慢维护项目占据扫描前 20 项。
- `useDetailPageStore.ts`：详情刷新和列表刷新分别增加请求序号，仅最新请求允许更新状态、错误和后续轮询；原任务/账号生命周期检查保留。

## 扫描与回调的关系

扫描读取的是数据库任务状态，不是部署/发布队列，也不会每轮重新生图。

1. 主图详情策划生成方案后受理图片任务，任务先进入本地 `queued`。
2. 图片生命周期扫描发现排队任务，获得 Redis 容量及数据库领取后只提交一次供应商请求。
3. 供应商生成结束后调用 `/api/webhook/kie`。该路由验证来源、解析结果并交给 `TaskCompletionService.process_result`，随后通过 `ChatImageLifecycle.record_provider_result` 保存结果、落盘、登记资产和结算。
4. 快速状态扫描负责未完成的本地操作与异常恢复。另有既有供应商查询兜底：配置回调时默认 120 秒轮询，具体可由配置覆盖；有回调也保留兜底，防止回调丢失。

回调、查询兜底和恢复扫描都沿用相同的任务状态、Redis 结算锁和数据库幂等账本。供应商发送标记已写而受理未确认时进入 `uncertain`，不凭扫描直接重发。

## 配置及恢复语义

| 配置 | 默认值 | 含义 |
|---|---:|---|
| `DETAIL_PAGE_IMAGE_CONCURRENCY` | 150 | 主图详情按用户/组织的活跃槽位准入上限 |
| `CHAT_IMAGE_PROCESSING_CONCURRENCY` | 20 | 每工作进程的图片生命周期操作上限 |
| `CHAT_IMAGE_PROCESSING_TIMEOUT_SECONDS` | 300 | 单次图片操作期限 |
| `DETAIL_PAGE_MAINTENANCE_CONCURRENCY` | 20 | 每工作进程的分组受理/恢复/汇总操作上限 |
| `DETAIL_PAGE_MAINTENANCE_TIMEOUT_SECONDS` | 120 | 单次分组维护期限 |
| `DETAIL_PAGE_PLANNING_CONCURRENCY` | 20 | 每工作进程的策划组上限 |

这些是本地处理容量，非平台生成额度；全局用户/会话额度仍由现有 Redis 原子槽位控制。默认值是保守初值，未声称为生产容量最优值。

供应商创建仍只提交一次，跨进程数据库 claim、send marker、lease、账本和结果发布门禁不改。操作超时只取消本地执行、释放本地容量，不能直接重发：发送标记已写但回执未知的任务由现有租约/uncertain 核实与结算流程恢复。图片落盘重试复用已记录结果。关闭取消不清除持久化任务或伪造失败；策划仍沿用已有中断保存、租约续期及阶段预算。

异步期限不能强行终止已经开始的同步数据库或文件线程；因此超时不等于远端/线程操作已撤销，持久化领取和结算门禁仍是正确性依据。数据库整体不可用时扫描只能重试，不能保证任务继续推进。

## 二次审查后的排队修复与真实进程验证（2026-10-16，未部署）

第一次实现遗漏了项目内部任务公平性：同项目的第一组/前几张图在每轮扫描仍然存在，虽然只是等待回调或维护无操作，也会重复获得处理位置。默认 4 个位置被反复占据时，后续图片或详情组无法进入处理。只保存“上一个任务 ID”仍不足以应对分页，因为上一页的 ID 可能不在当前页。

修复采用三级最近调度顺序。每轮扫描只更新候选的最后出现时间，只有真正获得容量才推进用户、项目和任务的调度顺序。活动任务及当轮重复候选先去重，不分配等待协程。跨分页发现时依然优先选择项目内部从未调度或最久未调度的任务；过期历史元数据定期回收，关闭时清空。

## 三项恢复遗漏修复（2026-10-16，未部署）

复核通过真实 PostgreSQL/Redis 复现了三项遗漏：释放异常被吞掉后仍确认交付；旧 queued 快照对终态任务重新占槽；同 run 的旧项目汇总覆盖人工恢复。它们会造成槽位残留或任务退出扫描，不涉及新增收费策略。

- 图片交付使用严格释放，Redis 失败时抛出并保留数据库 `delivery_pending`，后续扫描只重试交付与释放，不重发图片请求或重复结算。普通旧调用的 best-effort 释放契约保持兼容。
- 领取 SQL 返回 `not_queued` 后刷新数据库，只有 `published` 才幂等回收；accepted/submitting/uncertain/settling 不误释放。新增 Redis→DB 有界对账，以 Redis 占槽记录为恢复证据，覆盖重新占槽后立即进程退出的窗口。跨轮保存 SCAN/SSCAN 游标，每轮处理一个集合、最多 50 成员，核对用户/组织/图片生命周期；未知或活跃槽位不回收，查询或释放失败保留批次重试。对账异常不阻断正常任务分发。
- 聚合在单一 scoped 数据库事务中先锁当前项目，再重读本轮计划与图片任务并写回；与人工 resume、受理和图片发布遵循相同项目锁顺序，不额外锁计划行。校验用户、组织、run 与活动项目状态；旧轮、归档及终态项目不会被旧维护任务重启。迟到的受理错误改为原状态 CAS 合并，避免重新写回人工恢复已清除的错误。

验证增加人工恢复两种交错、新轮/归档保护、迟到受理错误与正常错误落库；锁竞争场景通过 PostgreSQL `pg_stat_activity` 确认 resume 实际等待项目锁。容量测试扩展到 150 满额时释放失败，重启后恢复释放，第 151 张继续提交，并核对单笔扣费/退款及总余额。

该对账用于终态槽位泄漏，不是 Redis 数据丢失后重建全部活跃槽位的实现。验证仍使用隔离测试库和供应商替身，不代表生产供应商吞吐压测。无数据库迁移，未提交、未推送、未部署。

## ready 兄弟组退出扫描的 P1 修复（2026-10-16，未部署）

并行分组维护使“本组处理完”不等于“整个产品已获得受理机会”。旧投影在一组硬阻塞且没有活动图片任务时直接写整单 failed，遗漏已经 ready、尚未进入维护池的兄弟组。项目随后退出 active 扫描，三级公平调度也无法继续发现它。此前修复项目锁只消除了旧快照覆盖，并未修复这个终态条件。

聚合现按 `(plan_id, item_id)` 对照本轮最新持久化图片任务。只要 ready 且没有 acceptance_error 的组仍缺少图片项的任务记录，就保留可扫描状态：有策划为 analyzing，有已受理任务为 generating，否则为 plan_ready。不修改受理、供应商调用、积分或退款 SQL；全部可受理项已有任务后继续原结算/失败判定，不把硬阻塞组无限当作待受理。
