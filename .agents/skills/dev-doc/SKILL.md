# 技术设计

共同约定：[共同协作规则](../../../docs/development/COLLABORATION.md)。本 Skill 的职责边界不构成新的用户确认门；已有授权与证据按共同规则继承。

## 目标

把已确认的需求、行业结论、方案决策和 UI 设计转化为能够安全实施和验证的项目技术方案。

根据实际问题自由选择设计深度和表达结构。技术设计不是填写固定模板，也不是重新进行需求讨论或行业方案评审。

## 前置输入

开始前确认：

- 需求及成功条件已经确认；
- 关键方向和风险取舍已经确认；
- 涉及界面时用户可见行为已明确，可来自当前对话、既有设计系统或 UI 设计；确有未决设计问题时再进入 UI 职责；
- 仍需技术阶段决定的问题边界清楚。

缺少需求时返回 `requirement-analysis`。缺少行业事实时调用 `industry-analysis`。存在会改变产品行为、重大成本或长期架构的候选方向时返回 `evaluate`。

当设计由Bug诊断触发时，把 `testing-bugfix` 提供的复现证据、系统模型、因果链、已验证根因和修复层级判断作为设计输入。不得丢弃根因重新从用户症状设计，也不得把临时止血措施直接固化为永久机制。

## 项目调查

优先复用当前任务证据，按设计实际需要补充相关实现、上下游调用方、数据流、测试、运行约束与仍有效的架构或历史文档。简单局部方案不要求先读取全套索引或部署资料。

技术栈、目录、依赖和运行方式必须从当前项目事实获得，不在 Skill 中长期写死。

调查应足以回答当前设计依赖哪些现有行为、可以复用什么、哪些约束必须保持、计划改变会影响哪里，以及文档与代码是否一致。

只调查与本次设计有关的范围。发现无关问题时按 `AGENTS.md` 报告，不顺手纳入方案。

## 设计原则

用最小充分的机制满足已确认需求，优先复用项目中已经验证的模式。

已由用户确认的上层决策是设计约束，不因个人偏好重新比较。只有代码调查产生的新证据证明原决定不可行或风险显著变化时，才暂停并返回方案评审。

存在多个真实的落地方式时，可以比较其对当前项目的影响；只有一个合理实现时直接说明，不为形式制造替代方案。

先描述系统行为、职责、数据和失败语义，再选择具体框架或实现技术。需要外部标准或当前技术事实时调用行业分析并引用可靠证据。

所有重要设计决定必须能追溯到需求、已确认决策、项目事实或明确风险。

系统性Bug修复必须明确恢复哪个被破坏的系统约束，为什么局部补丁不足，以及如何避免同类入口继续违反该约束。

## 设计内容

根据问题本身决定需要设计什么。方案应覆盖实现所需的职责边界、数据流、状态变化、接口契约、错误和恢复行为、并发影响、兼容迁移、可观测性、部署回滚或其他实际相关内容。

不涉及某类内容时不要创建空章节。例如，不涉及数据库就不生成数据库表模板，不涉及 API 就不生成接口模板。

追踪计划改变的完整调用链和连锁影响，明确：

- 新增和修改的文件及职责；
- 受影响的函数、类型、接口、状态和调用方；
- 必须保持兼容的现有行为；
- 实施顺序和依赖关系；
- 对应的验证和文档更新。

新增依赖必须说明必要性、精确版本、维护和安全情况。能用现有能力解决时不新增依赖。

数据库和协议变化必须说明兼容、迁移和回滚。尚未获授权的不可逆变化或破坏性接口选择必须暂停确认；已明确授权时保留相应执行门禁与验证。

## 风险与边界

主动分析实际失败方式和极限情况，但不机械套用固定清单。重点关注那些会导致数据错误、状态不一致、安全问题、用户不可恢复、调用方破坏或生产故障的情况。

高风险问题没有可靠缓解方式、设计需要扩大已确认范围、项目事实与上层决策冲突或关键前提无法验证时，停止设计并明确返回相应阶段。

## 技术方案产物

根据复杂度选择最清晰的结构。最终方案必须使实施者能够确定：

- 要实现什么行为以及为什么；
- 现有系统如何工作；
- 采用什么设计及其依据；
- 数据和控制如何流动；
- 需要修改哪些具体位置；
- 兼容、失败、迁移和回滚如何处理；
- 如何验证每项需求和重要风险；
- 哪些问题仍未解决。

复杂方案使用稳定编号关联需求、决策、UI 和测试。简单方案保持简洁。

## 确认与交接

涉及尚未获授权的重大选择、不可逆变化、破坏性兼容影响、外部基础设施、显著持续成本或未获接受的风险时，等待用户确认相关决定。

必要决策已明确后，仅在复杂设计、架构变化或需要长期追溯时，将技术方案保存到 `docs/document/TECH_[功能名].md`。简单局部方案直接在当前任务中交接，不为流程形式创建文档；需要实施时把明确的修改范围、任务依赖、验证要求和文档清单交给 `implementation`。

## 阶段边界

本 Skill 不负责：

- 修改已确认的需求和 UI；
- 重新完成行业方案评审；
- 编写业务实现代码；
- 用未经调查的假设填补项目事实；
- 为满足模板生成无关设计。

## 质量要求

方案必须基于实际代码、覆盖真实影响范围、保持向后兼容，并能被实施和验证。

设计复杂度不得超过问题本身需要的复杂度。

## 交付格式

遵循项目 `AGENTS.md` 的增量精简输出合同。确认方案只包含影响范围、推荐设计、关键边界、文件职责、验证与回滚；不复述已确认需求和研究全文。
