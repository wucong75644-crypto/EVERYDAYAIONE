P2-4 已增加计划任务级预绑定与版本锁定，见 [计划任务 Skill](TECH_Skill计划任务预绑定与版本锁定.md)。scheduled 仅使用任务显式绑定的已审核 revision，不允许动态激活；本文交互式发现与激活约定不适用于计划任务。

日期：2026-09-22 设计，2026-09-23 实施。状态：用户确认通用方案后已在原任务工作树实现；本轮未提交或部署。实现及验证记录见本文后半部分。

## 目标与通用性标准

在平台已经具备的工具能力范围内，新增不同业务的 Skill，只增加该 Skill 的操作说明、用途与资源，不修改平台业务分支、提示词模板或数据库结构。需要新外部能力时，通过独立的工具接入扩展平台，而不是让 Skill 文本虚构连接或授予权限。

用户已经确认对齐官方逻辑和公开标准。依据见 [官方机制对照](INDUSTRY_Skill正文附件与执行边界.md)。开放规范定义内容组织；具体授权、组织管理、受控存储与恢复属于宿主职责。本文不把任何单一业务案例定义成平台规则，也不声称各厂商的权限字段完全一致。

## 职责分工

| 组成 | 负责的内容 | 不应承担的职责 |
| --- | --- | --- |
| Skill 内容包 | 名称、用途、操作说明、引用资料、模板与示例。步骤、所需资料、缺失时如何处理、输出方式在此定义 | 不创建工具授权，不假定外部系统已经连接 |
| Skill 加载与资源服务 | 确定可见 Skill 和选定版本，加载正文，解析资源引用，校验路径、哈希、预算，提供可追溯来源 | 不解释成某一业务固定步骤，不修改用户正文以适配单个测试案例 |
| 平台权限与工具服务 | 根据用户、组织、会话、执行模式及现有授权提供可用工具；每次调用继续检查权限 | 不因 Skill 内容声称授权就扩大访问范围 |
| 现有通用 Agent | 同时理解当前用户请求、Skill 指令、必要历史和可用资料，按同一模型与工具循环处理任务 | 不为每个 Skill 启动另一套业务执行器 |
| 反馈与验证 | 区分激活、资源加载、工具执行及回答；记录版本和实际调用供检验 | 不把加载成功等同于业务内容正确，也不以关键字匹配伪装成流程验证 |

## 统一处理过程

1. **发现与选择：** 提供用户有权使用的 Skill 摘要。用户手动选择或现有模型选择机制确定 Skill；不新增特定业务的路由规则。
2. **固定版本：** 激活时确定不可变版本，后续读取、任务快照及恢复使用该版本。身份、组织和可用状态检查继续保留。
3. **提供指令与资源：** 正文作为本次任务采用的 Skill 指令，明确与当前请求的关系。资源默认展示摘要；只有正文明确引用、校验通过且预算允许才加载原版本的读取文本。资源如何用于任务由正文说明。
4. **统一上下文：** 将当前请求、已选 Skill、正文、资源来源与内容、必要历史和实际可用能力按一致的职责组织。明确 Skill 不能绕过平台权限与当前执行模式；不向上下文额外注入任何特定业务前置条件。旧聊天保留相关信息，不把已完成任务自动当成本轮任务。
5. **使用现有执行循环：** 模型按上述输入回答或请求工具；工具服务执行权限检查并返回真实结果，模型继续处理。平台不将任意自然语言说明自动编译成固定工作流。
6. **交付与恢复：** “已启用”只对应激活事实，工具过程对应实际调用。加载失败、预算不足、权限拒绝等给出相应原因；不伪装成功。历史任务恢复继续验证资源、版本和已保存权限上限。

## 权限契约调整

已实现的统一行为：新建普通 Skill 使用当前平台已授权的能力，不要求作者填写内部工具名。组织、用户和执行模式的限制继续生效，明确的额外限制只能收窄。

当前 `catalog.allowed_tool_names` 是本项目的限制名单，不能直接解释成 Claude Code 的预批准字段，也不能把旧的空集合原地解释成继承全部工具。需要为新语义建立明确版本边界；旧版本和旧检查点仍按原来的收窄结果运行。已有 Skill 采用新行为时走新版本及原有审核发布流程。该迁移适用于全部 Skill，不按名称、附件内容或用户身份设特例。

平台模式规则也应只有一套有效定义：用户要求仅规划时仅规划，需要审批的操作按现有权限机制处理；是否展示了文字计划本身不应另行创造权限。调整需针对统一上下文与既有工具策略的一致性，不能让某个 Skill 的正文覆盖安全边界。

## 如何证明通用，而非修补个案

验证数据使用至少三种内容不同的 Skill：文本改写、基于模板整理报告、需要获准工具的数据分析。测试可包含业务名称，平台实现不能依赖它们。

共同验证：手动选择和现有自动选择入口、同一 Skill 不同版本、多个资源的引用与未引用、预算不足、资源漂移、不同用户权限、旧任务恢复、已有聊天干扰、无工具/有工具两类任务。新增同类 Skill 应只变内容与资源，公共运行代码保持不变。

真实模型验证用于评估指令遵循和输出质量；权限、路径、哈希与版本一致性由程序测试验证。不能用真实模型的偶然一次成功替代机制测试，也不能用机制测试通过宣称模型必然理解所有业务流程。

此前用户的店铺分析失败只作为回归样例之一；企业十问、店铺平台、取数计划和报告结构等业务要求都不写入通用运行器。需要确定性业务工作流时，应另行明确其契约，不在本次通用 Skill 机制中隐含加入。

## 实施合同（2026-09-23）

### 权限与版本

- `catalog.tool_policy` 新增 `platform` / `restricted`。缺省解析一律为 `restricted`，旧 `allowed_tool_names=[]` 继续禁止工具；旧序列化不增加字段，保持审核哈希、revision 文件及旧 checkpoint 元数据兼容。
- 只有新建 Skill 且调用者未明确指定权限策略或工具列表时，创建服务才默认 `platform`。前端新建显式发送该值；保存、复制旧草稿和读取历史版本不会隐式升级。
- `platform` 使用“平台工具目录 ∩ 当前会话权限上限”；实际可见与执行仍由现有 ToolRegistry / ToolPolicy 检查组织、成员、功能开关、模式、授权及审批。没有修改 ToolPolicy。多个 Skill 只继续取交集；恢复只使用已保存权限与当前权限的交集，不因平台新增工具而扩权。
- `platform` 与非空额外名单同时声明会报 `SKILL_TOOL_POLICY_CONFLICT`，避免两种含义混用。旧 Skill 编辑页显示原限制，点击“改用当前会话权限”只改草稿，经过原审核发布流程才产生新 revision，历史快照保持原权限。

### 上下文与恢复

- 新运行快照写 `context_version=2`；缺字段的旧快照按版本 1 恢复原指令文本与位置，不重复注入。版本 2 明确选择来源、正文职责、资源使用方式和前置输入要求。
- 持久化上下文保留受预算限制的原渲染正文。发送模型时，构造一次请求视图，把完整已激活方法移到当前用户消息之前、无关历史之后；每份正文和附件仅出现一次。用户原文、缓存块及 assistant/tool 结果对不变。
- 能力提示由**本次最终过滤后的 tools schema**构建，每轮重新生成，不将工具目录或 Skill 声明误当实际能力，不把过时能力写进 checkpoint。没有工具时说明限制，禁止将伪调用文字当成真实执行。未激活 Skill 与旧版快照保持原模型消息装配方式。
- 统一规则保留 auto/ask/plan 的权限边界；明确自动推进不能跳过方法要求的必要输入，文字计划不额外创造审批，缺少规划工具时不伪造调用。
- 手动激活失败的安全原因同时进入模型消息，并在暂停保存前写入，恢复后仍不能声称用过未加载的 Skill。

### 资源与使用界面

- 复用上传、提取文本、revision 内只读文件、哈希清单、白名单引用和预算机制。已加载资源增加名称与类型说明，计入原预算；未引用资源仍只有摘要。
- 文件是方法、参考、模板还是示例，由正文定义如何使用。引用按钮插入中性的附件引用，避免所有文件都被描述成“参考”；系统不自动将每份参考资料变成可覆盖用户任务的指令。
- 作者只需填写用途与操作说明、上传文件并点击引用。详细方法可放在附件中，在正文写清“按此文件的方法处理请求”等用途。不新增业务专用表单、MCP 或 Skill 可执行脚本。

## 生产验证步骤（部署后）

1. 新建一项 Skill：上传方法/模板文件，在正文写清用途并点击“在操作说明中引用”，按现有流程审核发布。工具区应显示使用当前会话权限，无需填写内部工具名称。
2. 验证原有测试 Skill：编辑新版本，点击“改用当前会话权限”，确认正文说明附件用途，再审核发布。旧版本不应原地改变。
3. 在空白聊天和有旧任务的聊天中分别选中同一 Skill。缺少该方法要求的资料时应先询问；资料齐全时按方法输出。有查询要求时检查实际工具轨迹及结果，不能仅凭“已启用”判断业务完成。
4. 用不具备相应能力的会话和 plan 模式复验：应说明限制或仅给计划，不声称已查询/已执行；实际权限与审批继续生效。
5. 更换附件并发布新版本；恢复旧暂停任务，核验它仍使用旧 revision、旧附件和旧权限上限。预算超限、哈希变化、废弃版本等机制已由临时文件系统与数据库回归覆盖，不在生产破坏文件来验收。

## 回滚点与限制

本次实施前任务 HEAD 为 `f56dd3fb3dc9cee1b81cd5f429a03b4c6e1f2bde`，是本任务上次已部署版本；本轮不发布、不合并、不清理工作树。

新字段和版本 2 快照**不支持直接交给旧二进制继续运行**。如发布后需要代码回退，应先停止新的 Skill 入口与运行（`SKILL_CATALOG_ENABLED` / `SKILL_RUNTIME_ENABLED`），保留 DB、NAS 及所有 checkpoint，再在当前任务分支形成恢复上述版本行为的回退提交，经受控入口测试发布；回退期间保持 Skill 关闭。`--rollback` 只接受 `origin/main` 历史提交，不能直接传入尚未合入 main 的任务 SHA。恢复新版本服务后再恢复新快照。不删除或改写历史数据来迎合旧代码，无数据库反向迁移。

若只需回退某项 Skill 的业务内容，应通过已有审核流程从保留的历史内容建立新版本，而不是篡改原 revision。实际发布仍须用户明确“提交部署”，并由 `deploy/release.sh` 执行。
