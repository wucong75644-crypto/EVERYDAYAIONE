问题：用户希望知道 Claude、Codex 的 Skill 机制是否等同于此前提出的“附件执行/参考分类、权限选项、步骤检查”。本记录用于修正方案依据，不把项目自定义功能当作行业标准。

## 已核验的官方机制

1. OpenAI 文档把 Skill 定义为可复用的工作流程说明及配套资源。先展示名称和用途，手动指定或任务匹配时加载 SKILL.md；参考资料、模板以及脚本属于可选内容。其创建器默认可以只生成说明，无需脚本。[OpenAI Build skills](https://learn.chatgpt.com/docs/build-skills)
2. Anthropic 采用名称/用途、正文、按需资源的分层读取机制。正文写操作方式，引用的额外文档也可承载详细步骤；模板和资料按需读取。一个普通文件被上传并不自动形成完整的 Skill 入口和用途说明。[Anthropic Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
3. Agent Skills 开放规范规定主文件及元数据、正文和可选资源组织方式；没有要求每份附件都有“执行/参考”界面开关。allowed-tools 是可选、实验性的预批准工具字段，具体支持取决于宿主实现。[Agent Skills specification](https://agentskills.io/specification)
4. Claude Code 当前文档明确：allowed-tools 用于当轮工具预批准，不用于移除其他可用工具；未列出的工具仍走通常的权限规则。文档也明确，Skill 内容存在于上下文并不保证模型持续遵循；可以加强说明，必须确定执行的规则需要 hooks 等程序机制。这是 Claude Code 产品行为，不外推为所有厂商相同实现。[Claude Code skills](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill)、[内容生命周期](https://code.claude.com/docs/en/skills#skill-content-lifecycle)

## 与当前项目的对应关系

| 项目机制或此前建议 | 对照结论 |
| --- | --- |
| Skill 名称/用途、正文、引用资产 | 与官方的分层结构相近 |
| 资产摘要、正文明确引用后才读、预算限制 | 与按需读取方向一致；本项目通过服务端确定引用和预算，不能称为所有厂商的完全相同实现 |
| revision 固定快照、哈希、路径白名单、审核 | 本项目的管理和安全设计，不是所有 Skill 客户端必须具有的协议功能 |
| allowed_tool_names 留空就禁止全部业务工具 | 本项目的显式收窄策略；不能把它解释成官方 allowed-tools 的统一含义 |
| 上传后选择“按文件步骤执行/作为参考” | 此前提出的自定义交互，没有官方规范要求，尚未获用户确认 |
| 模型必须逐步遵循任意附件，否则自动纠正 | 普通 Skill 机制本身没有这个确定性保证；不应承诺靠加载或一句提示就实现 |

## 对当前故障的解释与建议

生产诊断已确认附件全文存在、有效工具为空、回答沿用旧订单话题。官方资料支持把调查分开：受控读取是否正确、任务指令是否清楚、宿主是否提供必要工具、模型是否遵循指令。不能从模型未遵循直接推定附件没有读到，也不能因为缺少通用“语义校验器”就断言整个架构不符合 Skill 标准。

对用户的这份《全店经营诊断提示词》，更接近官方机制的组织方式是：正文明确说明按该诊断流程工作、先检查企业十问、资料不足如何处理，并引用详细文件和输出模板。用户可以直接上传现有文档，由产品帮助导入或明确引用；不必要求用户理解文件目录、内部 ID 或工具名。是否提供两类附件用途按钮应依据实际使用需求决定，不能以“大厂都这样”为理由增加配置。

后续建议优先补齐本轮选择意图、正文用途和引用表达、现有授权范围内的工具能力及规则冲突；用真实模型验证旧聊天干扰、缺少资料、权限不足和正常分析。对确实不可跳过的关键业务前置条件，再明确哪些应由服务端检查；不把任意自然语言说明转换成确定性工作流视为本次默认范围。

本项目既有“不引入 MCP、不执行 Skill 附带脚本”的约束保持有效。本次只做研究，没有实施、提交、部署或修改生产配置。

## 用户确认后的对齐基线

确认来源：用户明确表示“这部分细节肯定要和大厂的逻辑和标准统一”。对齐对象是本次涉及的发现/激活、操作说明、附件读取与权限边界，以 Agent Skills 开放规范为共同依据，并标明 Claude Code、Codex 的产品差异。此指令不等于取消先前的组织授权、哈希、路径、预算、审核、旧快照及禁止脚本/MCP约束。

| 编号 | 本次对齐要求 | 依据及性质 | 实施影响 |
| --- | --- | --- | --- |
| SA-01 | 名称和用途负责发现；手动选择明确表达本轮使用意图；激活后正文指导任务 | 官方共同机制；本项目只保留当前已支持的触发范围 | runtime 的消息组装及手动选择测试 |
| SA-02 | 正文说明何时读取、如何使用附件；详细步骤可以留在被引用文件中 | 官方共同机制 | 编辑页说明、引用表达、renderer 输出上下文；不增加未经确认的“执行/参考”必选分类 |
| SA-03 | 已声明且正文引用的资产按预算加载，保留原文件与提取文本完整性；未引用不读 | 按需读取符合共同方向；具体白名单和哈希为项目约束 | 保留已有资产机制及相关测试 |

| SA-05 | Skill 指令是模型指导；必须确定执行的业务条件由明确的业务机制约束 | 官方机制及其限制 | 不把通用自然语言步骤校验器当成本次标准化必需功能；真实模型验收覆盖偏离风险 |
| SA-06 | 简单操作说明与文件上传保持为用户入口，技术标识由系统管理 | 本项目易用性要求，并非规范规定的界面 | 沿用现有上传和摘要；工具设置如有调整使用可理解的说明 |

当前 `allowed_tool_names` 是私有 catalog 中的收窄字段，与开放规范的 `allowed-tools` 不是同一个契约。权限改造应覆盖 `contracts.py`、`resolver.py`、`runtime.py` 的新激活与旧快照恢复、草稿/审核/发布链和管理页；旧 revision 及已经保存的执行权限不能静默扩大。新行为应使用明确的新版本语义并经过既有审核发布流程。这是必须落实的兼容设计，不应对外宣称已经完成标准兼容。

当前存储 frontmatter 还包含私有 `skill_key`、`revision`、`catalog`、资产清单等字段。对齐运行逻辑不自动意味着已支持原封不动导入 Claude/Codex Skill 包；完整格式互操作不在此次对齐声明中冒认。后续若需要互导，应单独明确支持的规范字段和项目扩展转换。

验收至少覆盖：手动选中 Skill 后当前任务意图明确、正文引用资源按需可见、原有平台拒绝规则仍生效、旧空白名单及旧任务不扩权、历史资源不漂移、权限/资料不足时的实际模型行为、有旧订单上下文时仍遵循当前诊断要求。原有路径穿越、哈希漂移、预算、废弃与快照恢复验证继续保留。
