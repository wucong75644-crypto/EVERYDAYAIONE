日期：2026-10-11。状态：兼容范围内的入口升级已实施并本地验证，未部署；监控类完整业务验收尚未完成。

## 0. 本轮确认的升级边界（优先于原草案）

用户要求严格沿用现有软件能力，保持原有逻辑，以不破坏的方式升级。因此本轮只规划已有能力的衔接和兼容性扩展，不新建平行系统，不更改已有创建、确认、审批、发布、计费、调度、重试、暂停和投递语义。

- 不新增任务准备服务、任务状态机、通用任务表、通知队列或模型调度框架。
- 不把新字段、试运行、预算输入、静默通知等要求施加给现有任务。
- 不修改原有 Skill 创建/发布权限、版本固定规则和默认执行模式；不自动发布 Skill。
- 不改组织账号共享范围、执行身份、数据权限和外部写入确认。
- 不将原聊天自动续写、自动暂停失效账号任务、高频轮询或通用结构化记忆作为本次既定功能。
- 如现有设施无法满足某项能力，记录缺口并留待独立决定；不得为满足理想流程擅自新建或重写。

允许范围是：在现有入口中接通已经支持的 Skill 选择、对已有 Agent Reach 只读 action 增加受控的后台适用性、补足现有数据的展示和错误说明。以上仍须经过实际调用链和兼容性验证；不是保证无需修改任何代码。

## 1. 目标与设计结论

让用户在聊天中提出业务目标后，系统能准备执行方法、验证能力、配置自动运行、保存业务进度，并根据实际变化通知用户。覆盖一次性、多步骤、周期执行三类任务，不局限于素材监控。

沿用现有 Agent、调度器、Skill 版本、ChangeSet、组织权限和通知 Outbox。增加任务准备与上下文衔接，不替换整个执行框架，不默认更换模型，也不直接移植 Grok Build 或 Codex。

“持续关注”沿用当前任务支持的周期检查，界面显示真实频率与最后检查时间。未接入平台事件源时不能宣称实时监听。时间和接收对象沿用现有补齐与解析规则；已有 max_credits、retry_count、timeout_sec 保持原默认值，不额外强制用户填写预算。

任务可使用现有 Skill 或写入原 prompt 字段的独立执行说明；不新增说明存储。仅在用户明确要求且有复用价值时走已有 Skill 创建流程。组织账号沿用组织授权，不要求管理员逐次批准业务操作。已有外部写操作的操作者确认不因本方案被取消。

## 4. 用户行为与主流程

示例：“持续关注小红书上电商主图素材，增长快时通知我。”

1. Agent 整理范围、数据来源、筛选条件和输出要求，检查平台连接与可用操作。
2. 从授权目录选择匹配 Skill；无合适 Skill 时准备独立可读的任务执行说明，不把当前聊天省略指代传到后台。
3. 复用现有创建表单、字段和缺项处理，仅补接当前任务面板已经支持的 Skill 选择。不新增强制预算、状态策略或通知策略输入。
4. 按当前表单确认→ChangeSet/草稿预检→现有审批/提交链执行。各环节顺序以现有实现为准，不用新流程替换。对新增后台 Reach 操作，预检只执行有界只读验证。
5. 显示现有任务 ID、下次执行时间和预检结果。严格区分待表单确认、检查中、awaiting_approval 与 applied，不把预检通过说成任务已生效。
6. 后续运行继续使用现有 prompt、Skill 快照、权限策略、last_summary 和结果投递机制；复杂跨次指标比较尚未验证，不能提前承诺。
7. 用户继续通过现有聊天管理工具和任务面板查看、修改、暂停、恢复任务；修改沿用原 task_id，不删除重建。暂不承诺后台结果自动续写到原聊天。

现有创建流程保留一次配置确认。本轮不决定取消确认，也不允许模型自主发布组织/平台 Skill。任务专用说明随任务保存；用户明确要求保存可复用 Skill 时继续现有候选流程。将来如需自动发布 Skill，单独确定权限和产品规则。

## 5. 职责与接口设计

### 5.1 复用现有草稿预检

取消原草案的 task_preparation.py、preparation_id 和准备状态机。沿用 create_draft_and_preflight、scheduled_task_drafts、scheduled_task_preflight_runs、config_hash、latest_preflight_id、completion_gate 和已有执行事件。

缺项沿用 task_definition_input.missing_fields；版本和权限沿用 bind_scheduled_skills 与现有提交检查。需要展示的预检摘要从已有回执读取，不建立第二份真相。

配置变化与断线恢复沿用当前配置哈希、修订、ChangeSet 和幂等回执；先验证现有行为，再补实际缺口，不另设状态转换。

### 5.2 模型工具与 API

首批只评估接通现有 skills: SkillSelection。取消预设 connections、notification_policy、state_policy、budget 新字段。账号选择先沿用 Reach 当前组织连接解析；如果后台不能正确解析，查明现有接口缺口后单列设计，不创建第二套账号绑定规则。

先核查 task_definition_input、task_request_content、表单、API 与 ChangeSet 校验链，模型入口复用当前 API 已支持的 SkillSelection 契约。注意现有 _validate 是简化 schema 校验，不能只加 schema 而忽略对象数组、maxItems 等校验；优先复用既有类型校验，不为此重写通用校验器。缺省保持原值，update 不传 skills 保留快照；清空选择的语义与现有 API 一致。

任务读取、更新和执行继续通过原作用域与服务端权限校验。首批不新增模型可调用的业务状态读写工具。

### 5.3 Agent Reach 后台能力

不直接给整个 agent_reach 加 scheduled。注册表可暴露该工具，但 action_rule 必须在执行前按操作、执行模式、平台能力和授权共同判断。

- 第一批开放 search、read 及实际支持的评论读取；用实际 schema 名称映射，不虚构 action。
- preflight 仅执行有界只读验证，不发帖、点赞、评论或上传。
- 写操作保持现有交互确认；定时发布需另行设计持久授权、幂等与撤销规则，不能继承聊天中的一次确认。
- 沿用执行器当前权限刷新和连接检查；登录失效按当前失败、重试和通知规则处理，展示重新连接入口，不自动改变任务暂停逻辑。
- 超时、限流、认证失败、内容不存在、部分成功分别返回结构化状态，不能统一为“没有搜索到”。

### 5.4 执行状态与恢复

继续使用 scheduled_tasks / scheduled_task_runs 的实际状态及前端当前映射，不新增来源聊天字段或状态枚举。展示现有草稿预检、任务与运行记录时区分它们各自状态。周期运行的一次成功不等于整个长期任务完成。

沿用已有 task_id、run_id、config_revision、执行身份和快照，不新增 trigger_id 或 source_conversation_id。上下文继续使用 prompt、计划、模板、Skill 和 last_summary；不复制整段聊天，不把外部内容当作指令。

复用现有 scanner/task_executor 的领取、配置修订及恢复约束。现有成功提交 RPC 已同事务保存 last_result、last_summary、运行结果和通知 Outbox；本次不改其签名、锁顺序和提交规则。另核对是否已有后续迁移覆盖，不以单份迁移代表全部运行行为。

失败、重试、计费、超时和暂停沿用当前语义。新增只读工具需要正确返回现有执行器能够识别的成功、失败和错误原因；不得在适配层额外启动另一轮后台重试或绕过预算。外部写操作仍不开放到后台。

## 6. 数据设计与监控方法

取消原草案 task_context、task_observations 和 Outbox 新 dedupe_key 的预设。首批使用已有 last_summary、last_result、运行历史和工作区输出制品；不改这些字段的原结构或在其中偷偷塞入新的强制协议。

跨次数据比较先验证已有工作区文件/制品能否由同一授权执行身份稳定读写，以及是否能保留与任务匹配的历史。必须验证路径隔离、并发、更新和失败恢复，不能仅凭“能写文件”就认定足够。如果现有能力不足，精确热度统计与跨次业务去重列为未实现，不擅自新建持久化系统。

数据沿用组织 RLS、工作区作用域、制品和保留规则，不新增统一数据保留策略。凭据继续由原连接系统管理。

素材热度示例：对同一平台同一 resource_id，以采样时间差计算点赞/收藏/评论增量和增速；窗口、最低增量和阈值由任务配置确定。首轮仅建立基线；缺失指标表示未知，不算零；平台隐藏指标或只返回元数据时明确降低结论强度。搜索排名变化不能直接当作热度增速。

热度计算优先使用现有 code_execute 和文件能力，Skill 描述方法及指标定义，不新增监控计算服务。该案例需通过历史保存验证后才能纳入验收；ERP 异常检查和报告仍沿用各自原有业务工具。

## 7. 前端交付

复用聊天创建表单与 frontend/src/components/scheduled-tasks/，不再增加管理员账号弹窗。

TaskForm/ScheduledSkillPicker 优先复用已有 Skill 选择组件。TaskCard、TaskRunHistory 只补充现有 API 确实返回但尚未展示的字段；若接口没有采集、判断、保存等阶段记录，就不虚构阶段进度。保持现有页面布局与操作入口，明确运行成功和通知送达的区别。

管理员后台仍负责组织账号连接；任务页可沿用现有导航提供失效提示。修改任务继续现有变更和预检规则。普通任务的结果推送保持不变，“无变化静默”及“回到原聊天”不在首批中强制实现，需先确认现有能力和任务级适用方式。

## 9. 迁移、发布与回滚

本轮不安排数据库迁移。保持旧 API、旧任务、既有 Skill、组织账号和推送目标兼容。新增后台只读能力先在测试和限定任务验证；是否使用已有开关由实施核对，不预设必须新增基础设施。

回滚前先识别已经使用新增 Reach 后台能力的任务，通过现有任务管理入口处理，防止代码回滚后任务仍调用不可用工具；不得自动批量暂停普通任务。回退代码不改变旧任务配置和 Skill 数据，无新表需要删除。正式回滚操作须有相应授权。

发布遵守受控 release.sh；本设计不授权生产写入、部署或改变当前组织任务。

## 10. 待实施阶段明确的事项

1. 现有运行租约、配置修订、检查点与 Outbox 的完整调用链；重点验证新工具适配，不预设改造这些设施。
2. 底层已支持标准 cron，API 已有 cron_expr；聊天 schema 只有 once/daily/weekly/monthly。首批不扩展频率类型。确需分钟/小时表达时，单独核对如何经现有表单和授权入口传递，而不是新建调度器。
3. 各平台实际可读指标与限流；不能承诺所有素材均能计算热度。
4. 现有文件/制品能否满足跨次指标历史，以及现有通知机制是否支持任务级条件投递。没有证据前不承诺精确热度监控或静默提醒；已有预算与数据保留默认值保持不变。
5. Skill 自动发布、后台外部写入、任意脚本/浏览器执行与多 Agent 调度不在当前推荐首批范围。如后续确需，单独设计其授权和运行隔离。

上述未知项不妨碍 A/B 的调用链核查，但任何需要新增持久化、改变调度或原产品行为的结论均留待独立决定。本次方案不能作为这些改造的实施授权。

## 11. 必须保持的兼容性验收

1. 不带 Skill 的旧聊天创建请求、任务面板创建及已有定时任务，仍按原确认、预检、审批和提交顺序工作。
2. 未传 skills 的修改保留原快照；只改输出形式、时间、暂停或恢复不意外改业务范围、账号或 Skill。
3. 原有 ERP、报表、模板文件、费用预算、重试和超时行为不变；不因新增 Reach 强制增加步骤或必填项。
4. 原组织成员共享账号范围和服务端权限不变；后台工具不能因只读开放而越过连接检查或获得写权限。

## 12. 四阶段实施记录

### 阶段 1：调用链核对

确认模型工具→task_definition_input→聊天表单→表单提交→ScheduledTaskChangeSetService→Skill 服务端绑定→现有预检/审批/提交的链路。底层 API 已支持 skills，缺口在聊天模型 schema 与表单传递；不需要新增 API、表、RPC 或服务。

确认预检可用工具目录原先没有 agent_reach_enabled 标志。仅注册 execution_modes 还不够，规划入口也需传入该既有功能标志。后台执行器已从共享 runtime_context 读取此标志。

### 阶段 2：入口升级

- Reach 注册 scheduled/preflight；action_rule 对后台全部写 action 明确拒绝，包括原本低风险的 set_like。交互写入确认逻辑保持不变。
- 预检目录沿用 agent_reach_enabled 开关；实际账号解析、组织作用域、锁内复查和执行预算复用原 handler。
- manage_scheduled_task 增加可选 skills，复用 SkillSelection 验证，限制最多四个不同 Skill。模型不得传权限、快照或任意正文；服务端绑定和审核要求保持不变。
- 结构化创建表单在既有 Skill 功能开启时复用 ScheduledSkillPicker，用现有 hidden 字段协议携带 JSON 选择。没有 Skill 的旧表单继续兼容；未传 skills 的修改保留绑定，显式空数组使用原清空语义。
- 未补齐的修改表单保留 Skill patch；非法选择在进入 ChangeSet 前报具体错误。更新已有任务仍走原检查和确认规则。

### 阶段 3：结果展示与兼容验证

TaskRunHistory 展示已有 push_status：queued、retrying、pushed、push_failed、partial、skipped。skipped 显示“无企微投递”，不把网页结果误称为没有通知。不改 Outbox、通知频率、收件人或推送逻辑。

本地测试覆盖后台只读与所有写 action、功能开关、组织执行身份、连接复查、授权撤销、Skill 非法输入、表单确认、patch 保留、旧任务创建、审批、预算、Skill 快照及原通知投递链。外部平台响应在执行器测试中使用替身，不代表生产账号登录有效或外部网络成功。

前端相关六组测试共 52 项通过，TypeScript 项目类型检查通过。测试中的无效输入 stderr 是预期失败路径，不是实际运行故障。工具 schema 合同 fixture 随授权新增的 skills 字段同步，历史其他字段继续比较原合同。

### 阶段 4：持续任务能力验证及边界

真实本地 SandboxExecutor→KernelManager→kernel_worker 实验在临时工作区保存模拟点赞、订单及报告数据，销毁并重建内核后仍可读取和计算差值；另一执行身份的工作区没有该文件。此实验确认文件能跨内核保存，不代表模型会自动构造可靠监控方法。

现有工作区目录按组织和用户划分，不按业务 task_id 自动划分。现有 sandbox.execute 已使用 workspace_lock 协调工作区读写；任务文件仍需使用唯一名称，不能把同一用户的全部任务共享文件误认为任务独立状态。本轮没有新增任务状态协议或修改工作区规则。

现有摘要能作为上次运行参考，文件可承载业务历史。完整素材监控仍需验证真实平台指标、首次基线、窗口计算、文件命名、失败时基线更新和条件通知。ERP/报告保留原工具执行路径，未用生产数据运行三项业务验收。

因此本次完成的是兼容入口升级和持续执行基础能力核验；没有实现自动发布后台 Skill、跨次通知去重、无变化静默、原聊天自动续写或任意任务自我修复。后续实际任务只能依据已验证能力承诺结果。
