# 近似尺寸与纯文字意图修复验证（2026-11-23）

范围：任务工作树 `20261121005427-skill-runtime-performance`，基线 `e084259011dbcbfec739dbc476510696bc0ba265`。本地修改与隔离测试；没有提交、部署、生产迁移或生产数据写入。真实测试使用独立 PostgreSQL/Redis、测试身份和测试素材目录。

## 根因与修改

1. **只写文字误判生图**：执行意图规则把“可以生图的提示词”中的修饰语和引号里的“生成图片”当作操作；另一个全句提示词规则又可能拦截“先生成图片，再写提示词”。现按子句识别动作，引用内容只作为数据，修饰提示词的生图用语不授予执行权。工具投影和最终派发使用同一判断，真实独立生成动作仍可执行，运行中已送达要求仍按原机制参与判断。没有新增模型分类器。
2. **近似像素被当成精确像素合同**：用户明确允许近似时仍进入精确宽高校验。现后台将明确的“约/左右/接近即可”等像素要求匹配到供应商支持比例和最近分辨率档；记录请求像素与匹配规格，页面展示实际返回尺寸。明确指定的分辨率优先。模型不能自行开启近似，严格精确像素的能力校验保持。
3. **连续改图把近似尺寸重新变成精确尺寸**：真实第三轮中模型给新草稿填了上一轮1920×1080，而实际成图是平台16:9/2K。新编辑草稿沿用真实选中成图的原生尺寸，不能用模型自行填的宽高取代；用户本轮明确的新宽高仍优先。原文、素材哈希和消息引用不改写。
4. **真实正文完整，但未形成可引用编号**：真实模型交替使用“选项一/方向一/套系一”和加粗标题、中英多段引用。后台普通创作索引扩展到同等的连续编号语法，保留完整段落和限制，不让模型重新写。专业Skill已有方法格式校验保持。还发现使用建议内同时出现`--ar 3:4`和`--ar 1:1`使保存失败：保存阶段只从唯一声明推断规格；有多个建议时不猜一个，原文完整保存。执行尺寸仍由既有受理层决定。

主要代码：`content_tools.py`→`execution_engine.py`原有登记入口→`content_groups.py/content_objects.py`→`chat_image_preparation.py`→`image_size_requirements.py`→原生受理/供应商/结果。前端仅补充近似请求与实际结果的信息展示，不增加按钮、审批、后台表、迁移或评审调用。
