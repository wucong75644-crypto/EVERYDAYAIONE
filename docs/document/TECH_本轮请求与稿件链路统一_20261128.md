## 来源、修订和阶段

content_source 只读核实明确指定的根任务、稿件和版本，校验权限及本次选择范围。来源缓存绑定任务、输入和选择；读取不接管任务。格式要求、章节合并、所需修订字段、执行预检使用相同来源。本次保存新版本后，必须通过同输入、同对象、不可变父版本、实际哈希及选定条目的保存证明才能继续执行，不能让同任务任意新稿冒充修订。

content_action 从原读取证明、保存成果、批准和执行回执派生阶段，不新增持久化阶段状态。工具提供和最终完成检查共同使用它；每个条目保留 ready、待读取、待修订和待确认差异。提示词与案例继续由实际开放的 JSON 合同生成，不用关键词判断用户意图。

同一对象观察到较新版本后，不再把已替代版本作为当前可选稿件；旧短引用仍保留供历史记录渲染，其他对象不受影响。版本变化的恢复提示要求核对用户指定版本，不擅自换最新稿。

## 后续等待与当前批准

新增 request_context.confirmation 的 WaitingConditions 类型，只包含 tool、wait_for、wait_all；schema 和后台都禁止放入 approved 等批准字段。media 表示已保存等待条目的本次批准。普通 ready 稿件出图不会因为路由填写了 wait_for 而凭空产生新等待。

保存时，显式 save.confirmation 或本次明确新增的 confirmation 才能增加后续条件。旧稿原有条件仍保留。本次批准原样执行、批准修订后执行和只修订不执行仍分别走原证明逻辑。wait_all 由稿件领域层在恢复完整文档后展开，因此局部修订也能正确设置整组等待。

## 接管、失败与恢复

接管来源由显式返回值传递，不再临时覆盖默认 task_followup_candidate。原接管事务、所有者校验和状态转移保持。

接管前持久化宿主验证过的结构化调用提案，绑定所有者、根任务和调用摘要。恢复读取该提案并通过原准入重新核验，不从聊天文字或工具回执反推要执行的调用。提交前异常回滚所有内存工作流投影；已经提交的保存、接管和原生执行不因取消而抹除。

不增加纠错模型、strict 开关、重试额度、自动批准或 JSON 括号修复。保存失败仍由原有有限纠错处理。供应商语法不可靠不能靠统一状态保证解决。
