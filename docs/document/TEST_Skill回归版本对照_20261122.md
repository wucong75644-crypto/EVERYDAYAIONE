# Skill 优化前后两个线上失败场景的本地版本对照

日期：2026-11-22（Asia/Shanghai）。这是诊断实验，不是修复验收或生产图片生成测试。

## 版本、输入和隔离

- 修改前基线：`78cbce12`，包含此前确认的尺寸、旧方案执行和多轮图片修改改动；通过 `git archive` 导出为独立本地副本。
- 当前候选：`e084259011dbcbfec739dbc476510696bc0ba265`，与本次线上 Skill 优化候选相同。
- 没有切换、重置或回退任务分支，没有修改业务代码，没有连接生产数据库写入，没有部署或重启线上服务。
- 模型：真实 `qwen3.8-max`，DashScope Responses；temperature=1、top_p=0.95、top_k=40、max_tokens=8192，关闭本地会话缓存。每组独立运行三次，没有为结果强制指定输出格式或补充用户未说的画布选择。
- 输入复用线上保存的原始用户消息、历史和附件说明。实际原图为 360×360 PNG 和 1280×1707 JPEG；本地使用相同原图字节、来源引用与尺寸读取逻辑。
- 真实模型运行使用项目 `_run_loop`、工具投影、正文登记、素材解析和派发前校验。数据库和检查点确认使用本地测试替身；图片供应商派发边界截停，不实际提交图片，不声称验证了最终图像效果或生产 RPC。
- 本地初始请求为 13 个函数工具，low 模式另带 2 个内置工具、none 模式另带 1 个；与线上快照的 26 个函数工具不完全一致；所以本实验用于比较版本/契约变量，不能作为线上失败率估计。对照各组使用相同本地工具集合和相同历史。未激活额外 Skill。
- 生图实验的版本/参数对照保留相同 10-turn/240 秒预算；编号引用独立实验保留相同 4-turn/180 秒预算，因此其等待时长不能和线上九轮约八分钟直接比较。

## 结果一：多图编辑的尺寸校验

“参考图一的产品里面的波点。给图二的产品加上一些波点”。下表的通过指进入原生图片工具的派发边界，尚未调用图片供应商。

| 条件 | 通过派发校验 | 三次模型 HTTP 请求数 | 三次耗时（秒） |
| --- | --- | --- | --- |
| 修改前＋旧关闭开关语义 | 3/3 | 1 / 1 / 1 | 35.251 / 47.842 / 37.708 |
| 当前＋旧思考参数 | 0/3 | 5 / 4 / 6 | 49.782 / 43.977 / 85.592 |
| 当前＋真正关闭思考 | 1/3 | 3 / 9 / 6 | 18.615 / 53.371 / 30.891 |
| 当前＋旧思考参数＋旧保存工具定义 | 3/3 | 1 / 6 / 1 | 18.11 / 79.031 / 28.84 |
| 当前＋真正关闭思考＋旧保存工具定义 | 3/3 | 6 / 7 / 6 | 34.318 / 37.449 / 31.065 |

旧界面关闭开关对应的实际请求是 `reasoning.effort=low`，仍有思考输出；当前真正关闭为 `reasoning.effort=none`，没有思考输出。两者不能混称为相同推理模式。

### 单变量对照

比较“基线＋旧思考参数”和“当前＋旧思考参数”的首个实际 HTTP 请求：只有 tools 字段不同；其中只有 `save_task_text` 定义不同，用户/历史/图片输入和其他参数相同。

临时对照仅在当前测试进程发给模型的请求中替换该工具定义，不修改当前后端实现。替换后首个请求 JSON 与基线首个请求完全相同，已用字典逐字段等值断言确认。替换后两种思考模式的三轮均通过校验。

这支持本次保存工具契约变更是该场景稳定性退化的一个因素，不能继续以“尺寸函数没有改动”排除本次优化的影响。工具列表中的另一个定义也能改变模型选择图片参数的表现。三轮不能估计总体失败率，也没有把差异进一步隔离为某一句描述或某个 JSON Schema 关键字。

同时，恢复旧工具定义后仍有多轮纠错，不能把旧契约直接恢复视为完整修复；也不能以偷偷恢复 low 思考冒充“关闭思考”。

### 固定模型输出交叉回放

每个版本各重复三次：

- 输入早上成功请求的实际 draft（只将来源消息 ID 重绑到同一隔离输入，正文/图片字节/options 不改）：两版本均 3/3 通过，最近画布比例为 3:4，默认分辨率为 1K。
- 输入本次失败请求的实际 draft，随后按线上顺序保存并引用：两版本均 3/3 被 `IMAGE_CANVAS_REFERENCE_REQUIRED` 拦截。
- 两张不同画布的图片同时作为 input、未指定 reference_index 时，两个版本都不能把自然语言“图二是目标图”自动转成确定画布。
- inline 路径还把具体尺寸错误折叠为 `CHAT_INLINE_IMAGE_INPUT_INVALID`，导致模型拿不到准确纠错原因；此行为在基线也存在。

可确定的另一处共同契约矛盾是：SIZE_GUIDANCE 写“省略 aspect_ratio 或使用 inherit_reference”，但 aspect_ratio 枚举不接受 inherit_reference；正确写法须位于 size_requirement.mode。关闭思考实验反复出现这一错误填写。该矛盾也存在于基线。

所以：最近比例算法和 1K 默认值没有被删除；共同缺口是确定编辑目标与画布参数之间缺少可靠绑定。当前契约变化在这个共同缺口上产生了可复现的模型调用稳定性退化。

## 结果二：正文显示但未自动登记，下一轮编号引用失败

冻结线上最新五条方案的完整原文（1486 字符，编号标题加普通段落）进入两个版本的实际执行循环，各三次：两个版本都完整产生正文输出块，但没有登记可执行成果，自动索引均返回 None。

真实模型从相同历史编写新方案、保持该线上场景的 deep_think/low 参数，各三次：修改前 3/3、当前 3/3 都产出五个编号标题和完整正文，但未登记成果。均只进行了一轮模型调用；没有把工具参数失败伪装成成功登记。

原因是共同自动索引仅接受有限的明确正文边界格式，不接受本次常见的“编号标题＋普通段落”。`content_groups.py`、`image_size_requirements.py`、`chat_image_preparation.py` 在上述两版之间没有源码差异。

将线上连续七个保存失败的原始工具记录逐条输入两个版本的重试判断函数：两版本每次均返回 pending=true、exhausted=false。混合的错误类型和其他工具调用使连续失败计数无法构成有效总预算；该循环缺口在基线已存在。

### 真实模型处理下一轮“第一个和第三个帮我做成图片”

复用线上该轮的原始历史和最新正文，两个版本各三次；分别冻结相同下一轮输入，不把上文各次新生成的不同正文混入下一轮，以免输入不同影响版本归因。

- baseline：三轮 HTTP 请求数 3 / 3 / 1；登记成果数 0 / 0 / 0；进入图片派发边界 False / False / False。
- current：三轮 HTTP 请求数 3 / 3 / 3；登记成果数 0 / 0 / 0；进入图片派发边界 False / False / False。

baseline 的前两次为补存校验连续失败；第四次误选旧组成果，未提交新图片，均未完成用户选择的最新第 1、3 条。current 三次均为补存校验失败。

原始 baseline 第三次因测试替身缺少恢复分支的 input_message_id 而无效，已保留原始异常记录，不计为产品失败；补齐本地恢复交接替身并用第四次替代。恢复交接仍使用实际 payload/作用域校验逻辑，仅存储回执由内存替身提供。前两次没有走到该缺失字段分支，其保存校验失败证据仍有效。

## 归因结论与下一步

1. 尺寸场景：本次 Skill 优化后的模型调用稳定性在本地对照中发生退化。单变量实验将影响范围收敛到发给模型的保存工具定义；不是最近比例计算函数被删除。修复应处理工具定义的一致性、明确编辑目标到画布的绑定，以及保留具体校验错误，不能依赖模型多思考或简单全部回退。
2. 方案场景：自动登记漏掉本次格式，以及后续反复补存的缺口在修改前也可复现，不能归为本次新引入。应在不重写正文、不误登记普通聊天的前提下补齐登记边界；编号引用必须绑定最新已展示的整组，并建立覆盖各种保存错误的纠错总预算。
3. 三轮真实模型是可复现样本，不能承诺概率为 0 或 100%；本报告不声称已完成修复或已验证最终图片效果。
4. 本轮只诊断。保留真正关闭思考的目标，业务代码未修改；线上未回退、未部署。
