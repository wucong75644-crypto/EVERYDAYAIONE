# 主图详情任务列表与后台多任务方案

日期：2026-10-10。状态：已按用户确认方案完成本地开发及验证，尚未提交部署；生产业务验收待发布后执行。

依据：用户确认的右侧任务栏、新建、连续提交、后台执行、历史任务恢复及分类下载需求；当前任务分支 `ec416fdb`，以及尚未部署的“上传期间可输入文字”修改。调查没有调用付费模型或修改生产数据。

## 1. 推荐结论

在现有主图详情页面增加任务管理能力。继续使用 `detail_projects → ecom_image_plans → tasks`，明确以项目 ID 绑定所有编辑及上传操作，允许同一用户提交多个项目；任务由现有 Worker、策划租约和生图槽按容量执行。

不必等一个项目全部出图才允许提交下一个。任务提交与任务执行分开；用户退出页面后，服务器继续执行。保存、切换、刷新、下载都是读取或编辑指定项目，不触发重新策划或重新生图。

前端增加任务侧栏和摘要状态；后端补项目创建、分页列表、按项目上传，以及现有单任务假设的修改。复用三阶段 Skill、Kimi/Gemini、Image 适配器、平台承担失败重试成本的策略和积分账本。

## 3. 页面和交互

桌面布局：左侧现有创作设置，中间现有可滚动的进度与结果，右侧任务列表。左侧维持当前 360px；右侧建议 256px；中间占剩余空间，沿用等宽图片、按比例高度和自动排列。宽度不足时任务栏收起，通过“任务列表”按钮打开右侧抽屉，不把结果区挤成窄条。三处滚动区域独立。

任务栏顶部固定“＋新建任务”，下方按创建日期分组。每项显示第一张产品图缩略图、名称、任务类型、状态和完成数量；当前任务高亮。按 `created_at DESC, id DESC` 排列，使用同一字段进行游标分页；后台不断更新 `updated_at` 不得使列表跳动。

名称先使用“主图与详情／主图／详情图＋创建时间”；第一阶段已有可信 `product.name` 后，可由程序补为商品名称，不增加命名模型调用。原图缺失时显示默认图标。

| 操作 | 行为 |
| --- | --- |
| 新建任务 | 先保存当前可写草稿，再创建独立草稿并选中；已经提交或完成的任务保留 |
| 重复点击新建/网络回执丢失 | 创建期间防连点，使用同一个稳定 UUID 恢复同一草稿，不重复创建 |
| 提交任务 | 图片全部就绪、设置保存成功后，沿用稳定 run request ID 冻结并持久化；服务器确认受理后，才显示可离开等待 |
| 切换任务 | 先保存可写草稿，关闭并隔离 AI 帮写弹窗，再按目标 ID 读取；保存失败时保留当前任务和文字，允许重试 |
| 正在上传图片 | 文字仍可编辑，开始生成和 AI 帮写禁用；本期新建/切换任务等待上传关联结束，防止未完成附件被遗弃 |
| 查看已提交任务 | 恢复图片、设置、阶段及结果；设置只读，不能修改已冻结请求 |
| 重新进入页面 | 优先恢复 URL 指定任务，其次恢复当前账号/组织上次选择；失效时提示并回到可访问列表，不能越权读取 |
| 完成下载 | 点开该任务后用现有下载入口；部分完成也可下载已完成图片，主图与详情页分别归类 |

首次空白页面也先创建服务端草稿，之后文字自动保存和图片上传均有明确项目 ID，不再依赖“首次上传才产生项目”。已有草稿重复点击新建仍先保存，允许保留多个未提交草稿。

当前已完成的“上传期间允许输入文字”修改属于本方案必须保留的行为。

## 4. 状态、调度与时间边界

```mermaid
flowchart LR
    A[新建并保存独立草稿] --> B[上传图片和填写要求]
    B --> C[提交并冻结项目与有序图片]
    C --> D[现有数据库计划等待认领]
    D --> E[现有 Worker 按容量认领]
    E --> F[卖点分析 → 视觉定位 → 逐图提示词]
    F --> G[程序组装提示词和固定图片绑定]
    G --> H[现有 Image 队列和共享任务槽]
    H --> I[主图／详情图结果持久化]
    I --> J[回来打开任务并下载]
    F --> K[保留有效阶段并延迟恢复]
    H --> L[核实原请求后恢复失败项]
    K --> E
    L --> H
```

### 4.1 提交与执行

- 继续在提交事务中建立项目 run 和一个或两个 `ecom_image_plans`，不创建第二张工作队列表。
- 允许多个项目同时处于现有 `analyzing/plan_ready/generating` 状态；删除“有其他项目就拒绝”这一条件，其余校验保持。
- 继续使用现有策划 claim/renew/fencing，扫描器轮换项目并尊重本进程并发上限；批次内按用户/项目轮换，避免同一用户的多个项目持续占满认领机会。多 Worker 可以扫描同一项目，但只有租约持有者能执行和保存阶段。
- 一项任务内的三个阶段仍串行；默认模式的主图、详情两组继续使用当前独立计划，允许按容量推进。
- 项目还没获得执行机会时，在列表投影显示“排队中”；已有阶段调用或有效租约后显示对应阶段。不为展示再引入一个项目状态机或假进度百分比。

完整详情的每组计划同步增加不含租约 token 的 `execution_state` 投影，区分 waiting/running。当前 `DetailPlanProgress` 把所有 planning 都显示为正在分析，需改为读取该投影：等待认领时使用等待节点及“排队等待策划”，获得租约后才显示对应阶段动画。列表与结果区使用同一判断口径。

列表展示状态：草稿、排队中、卖点分析、视觉定位、提示词生成、生图中、自动恢复中、已完成、需要处理。运行中混有失败图片时，根据现有自动恢复状态呈现，不把可恢复失败直接显示成永久终止。

### 4.2 排队不能变成无谓失败

代码事实：`ChatImageLifecycle.advance()` 会在 queued 超过默认 600 秒时先判失败；`submit()` 遇到 `TaskQueueFullError` 则继续等待。这在多项目场景下可能把正常等待槽位的图片变成失败，再触发平台承担的重试。

本次需要给 `origin.destination=detail_project` 的可信页面图片请求补充等待语义：未发送供应商且等待容量时保持排队，不能仅因创建超过 600 秒就发布失败。继续检查权限、文件版本、费用变化等硬性问题；实际提交、受理未知、供应商执行、存储结算仍沿用现有各自的租约、超时和回执核实规则。聊天图片保持原策略，不能统一取消所有超时。

策划首次调用的持久预算目前在 attempt reservation 时开始，能够复用。恢复路径另有边界：手动/自动 resume 会在尚未获得 Worker 时提前建立新窗口 deadline。新页面恢复窗口须增加“待启动”标记，在持有有效租约并首次 reserve 该窗口时原子设置 deadline；等待认领不消耗新窗口时间。已经开始或结果未知的窗口保持原 deadline，不得通过浏览、切换、刷新或重复认领延期。

### 4.3 结算与恢复

多任务不更改积分规则：有效文字阶段一次结算、失败重试成本由平台承担，图片仍走既有失败退款/成功结算。提交多个任务不会预先承诺这些任务全部有足够积分；实际计费由现有原子账本判断，积分不足显示需要处理，其他任务数据保留。

UI 切换、关闭浏览器、列表轮询不能调用 start/resume/replay。已向供应商发出的请求先核实原回执，不得因为用户回来看任务就重复发送。临时恢复等待释放实际模型槽，其他项目仍可推进。

## 5. 数据与 API

### 5.1 数据调整

新建下一可用编号的迁移，具体编号在实施前核对：

1. 为 `detail_projects` 增加简短 `title`，已有项目保留原数据，用同一程序规则兜底展示。
2. 删除 `uq_detail_projects_org_draft`、`uq_detail_projects_personal_draft`，允许多个 draft；不删除表、项目、计划或文件。
3. 增加按 `user_id/org_id/created_at/id` 查询列表的索引，并核对当前 schema 已有索引，避免重复建立。
4. 新增按项目 ID 创建、绑定图片的原子函数；项目 ID 可使用创建请求 UUID，冲突时只向原用户/原组织返回原记录，不能泄露其他记录。
5. 更新 `start_detail_page_run` 的单项目拒绝条件，并保留同一项目同一 request ID 重放、版本检查和 source binding 约束。
6. 页面恢复窗口延迟启动需要同步替换 resume/reserve 对应函数；仅改变未启动的新页面窗口，保留 285 的计费、防重复和恢复 token 检查。

保持现有表归属、`SECURITY INVOKER`、runtime/worker 身份和组织隔离。不把 request body 中的用户/组织字段作为授权来源。

### 5.2 接口契约

| 接口 | 用途及关键约束 |
| --- | --- |
| 新 `POST /detail-projects` | `{request_id: UUID}` 幂等创建空白项目，返回 project |
| 新 `GET /detail-projects?cursor=...&limit=...` | 返回当前用户/当前组织摘要及 `next_cursor`；限制单页大小 |
| 新 `GET /detail-projects/status?ids=...` | 有界批量刷新已加载的活跃任务摘要，复用同一摘要投影；逐项校验当前用户/组织 |

| 新 `POST /detail-projects/{id}/images` | 明确绑定目标项目，原子检查归属、draft、9张上限、去重及顺序；返回该项目 |

新增固定路径必须放在 `/{project_id}` 路由匹配之前。列表和创建沿用现有响应 Envelope；错误沿用项目异常格式。

旧 `/current`、`/current/images` 保留兼容入口，新页面不依赖它们写入。旧图片绑定入口只能在唯一可写草稿时继续使用；存在多个草稿则返回明确 409，要求使用指定项目入口，不能猜测最新草稿。底层旧上传 RPC 也必须同步收紧，不能留下仍会任意选草稿的入口。

### 5.3 列表摘要和完成数量

每项包含 `id/title/created_at/content_type/status/display_status/thumbnail_url/expected_count/completed_count`，及当前阶段、恢复等待标记。按当前 `run_id` 取计划；按 `(project,run,item_id)` 选 `(created_at,id)` 最新图片任务，再统计 completed。失败后重试产生的新版本不能多计，旧 run 不能混入。

列表服务采用一页项目一次读取、关联计划及最新任务批量聚合，不逐项调用完整 `read()`，不传递完整提示词或 Base64。缩略图沿用工作区缩略图 URL。

完成数量由数据库事实导出，不新增一份需要手工维护的进度计数。原完整详情的任务排序也须明确 `created_at,id`，使列表、页面和下载始终选同一版本。

## 6. 前端状态与异步隔离

- `useDetailPageStore` 保留当前表单/图片/groups，增加分页摘要、创建/选择动作、当前 scope 和列表刷新状态。多任务执行事实存在服务端，不把浏览器内 Map 当成持久任务队列。
- URL 用现有 `/detail-page?projectId=<uuid>` 恢复选中项目；选择记忆仅保存 ID，按 `user_id + org_id/personal` 分开。任务列表不能复用聊天 localStorage key。
- 任务切换先完成设置保存，再增加请求代次、停止当前详情轮询，读取新项目；每个异步回写都验证账号、组织、project ID、代次。包括保存失败回调、删除/关联图片和开始分析响应，不能只保护读取请求。
- 上传调用启动前冻结目标 project ID；本期切换等待上传/关联结束，作为用户可见的保护。设置保存链继续保留用户边上传边打字的最新 form，不能被上传响应覆盖。
- AI 帮写在切换任务时 close/abort 并失效旧结果；“插入”还需核对原项目 ID，不能把 A 的分析写到 B 的输入框。
- 当前工作区按项目 ID 设置组件 key，清理前一个任务的提示词展开、预览弹窗、下载和重试瞬态状态；任务处理本身不取消。
- 详情继续复用当前运行任务轮询；列表滚动加载历史页，按有界ID批量刷新已加载的活跃项，不逐条读取完整详情，避免历史页进度不更新。页面可见/重新获得焦点时补刷新首页及已加载活跃项。页面隐藏时减少前端查询，但不控制后台运行。先复用轮询，不新增 WebSocket 服务。
- 用户/组织切换及退出登录时清理页面和列表状态，失效在途响应，再重新读取当前权限范围。读取失败保留上次已知列表和重试入口，不伪造成功或清除正在执行的服务端任务。
- “返回聊天”明确导航聊天入口，避免新增任务 URL 历史使按钮变成切回前一个任务。

## 8. 必须通过的验证

1. A任务提交后新建B，A继续执行；B有独立设置、图片ID及顺序；可以再提交B。
2. 多草稿来回切换、文字保存、刷新恢复；旧/current/images面对多个草稿不能误绑。
3. 图片 uploading/attaching/failed/missing 时文字可编辑，两生成入口不可点击；上传完成不覆盖新文字。

## 9. 上线、兼容和回退

先完成兼容读取、明确项目写入和调度，再开放新页面入口；迁移不重建历史任务、不变更原图及账单。现有未归档任务可直接成为列表记录，历史 archived 状态保持原含义。

第一版不增加删除执行中任务、外部通知或定时调度；“停止自动重试”保留当前含义，不包装为取消已发出的供应商请求。列表的首次能力是新建、切换、查看和下载。

存在多个草稿或活跃项目后，不能直接恢复旧唯一约束或部署仍假定单草稿的版本。回退采用前向兼容应用：停止新建及新增多任务受理，保留列表/指定ID读取和后台结算，让已接受任务继续交付；不归档或删除任务腾位置。若尚无新数据，受保护 rollback 才允许恢复约束及旧函数。保留285计费及恢复历史。

发布继续使用受控 `deploy/release.sh`，技术部署与生产业务验收分别记录。本轮任务列表及后台多任务已实施，未执行提交或部署。
