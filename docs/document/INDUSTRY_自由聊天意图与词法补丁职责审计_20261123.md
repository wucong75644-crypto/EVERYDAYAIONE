## 已确认事实与责任

Git 基线为 e084259011dbcbfec739dbc476510696bc0ba265。与 HEAD 比较，workflow.py 的 ready_selection 前置门槛、ready_execution 恢复分支是本任务工作树新增；image_execution_request 通用函数在 HEAD 已存在，本任务又扩展了多个消费者及词法规则。

这次设计错误不是“所有正则都不能使用”，而是将一个原先用于收口图片回复的启发式函数升级为业务入口、工具可见性和执行许可的判断依据。该函数自己的注释仍写着只延迟执行叙述，不开始任务，但其消费者已经超出该职责。

在同一版本实际复现：

| 用户表达 | 已有条目指针 | image_execution_request | selects_previous_item |
|---|---|---|---|
| 第一个和第三个做成图吧。 | True | False | False |
| 第一个和第三个帮我做成图片。 | True | True | True |
| 帮我写第一个和第三个做成图的提示词。 | True | False | False |

前两行含义相同却走不同分支；第三行证明不能只给正则补一个“图”就认为解决，写作对象、引用、否定及复合任务仍需结合上下文理解。

真实正式入口 count-contract-main5：用户先要3套主图，运行中追加图片与浅米灰背景，后台 ready 保存3项；人为模拟 durable pending 后工作进程丢失，恢复前后模型调用均为7，没有重新策划。随后“第一个和第三个做成图吧”被路由为 ordinary_image/new，未带回原服务器方案执行入口；模型激活方法、复制正文、调用 save_task_text，再以 content_source 提交图片。5张真实Image2虽然全部完成，原测试仅核正文相等、尺寸及素材，未证明来源仍是原plan_source。

现已补正式入口的 assert_native_ordinal：必须逐项核 origin.plan_source 的 plan_id、revision、item_id、request_text_sha256 以及实际提示词。回放同批真实记录失败，证明“图片完成”和“编号身份正确”应分开验收，没有降低原断言。

新增的行为回归保留原生方案身份、执行窗口和不重新策划的要求，不预设新协议。诊断集当前4 passed /2 failed；失败分别是“做成图吧”和“就用刚才那套，做出来看看”。该问题尚未修复，不能宣称回归全绿。

## 市场确实有词法分类，但适用边界不同

- Rasa 旧版官方 KeywordIntentClassifier 以关键词匹配意图，文档明确只适合小型、短期或起步项目。这证明市场有这种机制，不证明适合开放式、多轮、多素材的Agent。[官方组件说明](https://legacy-docs-oss.rasa.com/docs/rasa/components/#keywordintentclassifier)
- Anthropic 的公开路由模式可以用语言模型或经过适当验证的传统分类方法完成分类；建议按任务选择最简单可行的实现。它没有要求自由聊天必须经过关键词白名单。[Building effective agents](https://www.anthropic.com/research/building-effective-agents#workflow-routing)
- OpenAI 官方工具调用由模型产生结构化调用、应用执行；官方建议清楚定义参数，用结构表达合法状态，并把已知的ID交由代码处理。这支持“理解用户含义”和“确定实际数据身份”的职责分离，不能据此声称模型语义永不出错。[Function calling](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)
- Anthropic 2026年的Managed Agents说明将session事件日志、模型/harness和执行环境分开，持久状态用于恢复。该机制支持保留我们已有Actor和账本；不需要照搬其托管平台。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)

这些是公开机制与项目适配推断，不是某项“所有大厂必须遵守”的标准。未取得各公司闭源产品的完整代码。

## 本项目需要成批调整的消费者

| 位置 | 当前作用 | 推荐边界 |
|---|---|---|
| workflow.initialize / ready_selection | 决定是否恢复ready方案、是否保持执行窗口 | 删除词法前置门槛；从协调层语义动作及真实方案状态恢复 |
| execution_engine 初始化 / selects_previous_item | 决定是否初始化方案流程 | 不以用户是否匹配出图词表作为加载已有方案上下文的前提 |
| model_tools前的reuse_source和工具投影 | 根据词法结果限制保存或图片参数形式 | 由同一动作上下文和已保存成果目录提供适用参数，不重复解析自然语言 |
| image_writing_only_request的展示和派发前消费者 | 移除generate_image并硬拦调用 | 写作/执行动作应有统一来源；保留既有权限，避免每层独立词法判定 |
| native_plan_delivery / authored_text_request | 判断是否由后台交付并登记正文 | 使用明确的规划交付状态及输入修订，不能只靠“写、提示词”等词判断 |
| implicit编辑相关判断 | 判断是否编辑真实成图 | 模型理解修改；后台校验用户指定图或唯一已完成回执，不猜旧图 |
| explicit_image_batch | 用严格句式直接安排普通编号批量调用 | 不能成为唯一入口；收口时评估移除自动执行快路径，保留同一原工具链 |
| 格式、图片顺序、大小、UUID、Schema和摘要解析 | 校验确定性数据或明确语法 | 保留，与自然语言意图判断分开 |

## 推荐最小方案

目标：自然语言不要求命中特定词；同一轮意图只在协调处决定一次，后续模块消费同一结果。以下是本项目的推荐，不是逐字照抄Grok。

1. 复用现有EcommerceWorkflow协调入口与ActionContext，语义判断带上用户原话、已送达追加、真实上一轮方案/图像目录及状态。明确区分策划、执行已有方案、编辑结果和普通讨论。普通聊天不统一增加一次分类；需要业务分流时复用原路由，不新增审核器、投票或另一套独立意图平台。
2. 原入口路由负责业务动作，主模型负责内容与条目选择。若路由只返回ordinary_image/new就会丢失“执行既有方案”的信息，需完善该动作表达。所有消费者使用协调后的动作，不再用image_execution_request等函数二次否定或重新分类。工具调用仍是实际副作用的明确请求；动作分类本身不直接生成图片。
3. 后台保有原计划的身份、版本、原始执行稿、规格和素材顺序；模型选择编号后，只从该计划查真实item。输入已确定的ID不让模型靠抄写重建，执行已有项不复制正文、不重新save_task_text。复杂指代只有无法唯一定位时才询问，普通问答和新任务不因存在旧方案被迫执行旧任务。
4. 修改图片继续沿用已完成任务的真实输出；显式选图优先，唯一上一轮回执可供模型选择继续编辑，多结果不能任意猜一个。现有来源权限、哈希、尺寸匹配、受理幂等及账本保持不变。
5. 运行中追加进入原输入修订机制；已送达的补充与原要求一起解释。仅补背景/参考图不重置数量，新要求改变动作时重新协调并固定该修订；未送达的消息不算已执行。恢复已冻结的动作、引用和原受理回执，不重新运行意图判断或挑“最新文件”。
6. 提示词只讲工具职责和参数含义、给当前真实目录；不用无限追加员工话术示例。image_count说明应表达逐图项数并理解完整数量要求，不能把“N套=N张”作为普遍规则；还需覆盖“3套，每套5张”的多层数量表达。Schema校验不能保证数量语义正确。

以上沿用现有组件，不增加数据库表、额外审批或供应商自动重提交；不把整个系统中的正则一键删除。实施先处理上述消费者的共同动作来源，再完整跑用户链路，避免局部通过后在下一层继续误判。

## 验收应证明什么

- 同义自然表达：做成图吧、用第一和第三个、这两个做出来看看；不会因没有“图片/生图”字样丢失plan_source。
- 否定、引用和文字任务：先给我看方案、先别做、解释某句提示词、修改提示词；不产生图片受理。
- 新话题及复合要求：讨论旧方案不执行；新创作不被旧计划绑定；先改方案再出图不能直接执行旧版本。
- 原数量、未给数量、追加不改变数量、显式改数量、多组数量分别核对；不能只测“3套”一句。
- 编号执行必须同时验证页面正文、原plan/item/revision、来源摘要、真实供应商prompt/图片顺序与任务回执。正文相等但身份丢失要失败。
- 蓝→灰必须使用真实蓝图的哈希；中断恢复不得重新生成或换底图；跨用户、跨会话、过期版本仍按原权限拒绝。
- 在最终冻结版本下跑正式HTTP/Actor入口、真实模型和Image2，成功、业务错误、供应商错误及环境中断分开记录。公开设计和3次小样本不提供100%可靠性保证。
