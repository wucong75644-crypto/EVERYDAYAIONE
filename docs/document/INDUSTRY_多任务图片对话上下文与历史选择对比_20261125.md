# 多任务图片对话：官方设计与当前实现对比

调研日期：2026-11-25。范围：任务 A 已有成图、新任务 B 仅讨论、随后泛指确认，以及合法回看/重做 A。只采用官方文档与官方公开源码，不把 API 行为写成聊天产品内部实现。使用项目 industry-analysis 与 agent-reach；GitHub CLI 获取官方代码、Jina 获取官方文章，网页工具交叉核验。没有修改业务实现、部署或付费调用图片服务。

## 核心结论

公开证据支持：有意义的对象描述配合可验证引用、轻量目录加按需读取、对象作用域和版本、完整保留用户输入与真实结果、结构化输出仍需业务校验。这些与本项目改进方向一致。

没有查到足够公开证据证明 ChatGPT、Claude、Grok 网页聊天产品内部一律使用“先选业务任务，再选稿件”这种固定协议，也没有证明它们会把每个讨论回合自动生成保存稿。此前方案里的业务需求目录、焦点及归属规则是结合本项目故障的设计，不应声称是某厂完整实现。聊天会话作用域也不等于同一会话内业务任务作用域。

## Anthropic：先改善可理解性和信息检索

[官方工具设计文章](https://www.anthropic.com/research/writing-tools-for-agents)建议提供与目标有关的信息、清晰名称及关系；其内部评测发现，相比难理解的字母数字标识，语义名称或简单编号能提升检索精度，必要时仍返回机器 ID。工具结构需要实际评测，没有通用最优格式。

[官方上下文工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)说明 Claude Code 采用轻量标识和运行时按需读取，目录层次、名称、时间信息帮助理解；上下文应精炼且信息充分，按需探索也有额外时延。

与本项目对比：旧 A 的持久名称“编辑本轮指定图片”会在新轮次失去真实含义；新 B 与旧稿分散在不同目录，要求模型自行拼接归属。建议用真实需求摘要、来源、角色和状态解释短引用，不只改成另一个泛化标题；历史先给轻量索引，需要时加载全文/稿件。名称用于理解，引用绑定不能靠关键词或标题相似度。

## OpenAI：明确历史引用，不承诺语义永远正确

[图片工具官方文档](https://developers.openai.com/api/docs/guides/tools-image-generation#multi-turn-editing)支持通过历史 response 或 image ID 继续编辑；这提供可恢复的对象引用，不能据此证明系统会自动正确识别同一聊天里的 A/B 业务任务。

[Structured Outputs 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)明确结构化返回仍可能有内容错误，建议改善输入、示例或拆小任务。

与本项目对比：已有严格 JSON 和真实 artifact ID，仍发生“B 素材+A 稿件”。需要在进入执行前绑定所选业务来源、稿件版本及目标图，而不是将合法 JSON 视为正确意图。不能认为 previous_response_id 就代表“本轮正确业务任务”；它是引用/历史延续能力。

## xAI：工具引用与 Grok Build 的边界

[xAI 图片工具文档](https://docs.x.ai/developers/tools/image-generation#multi-turn-editing)说明通过 previous_response_id 或保留原输出项延续编辑。它披露历史图片可继续编辑，不披露网页产品的全部任务切换逻辑。

本次用 GitHub API 核验 Grok Build 当前 HEAD 为 `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`。在该固定版本：

- [`image_edit` 引用解析，199–226 行](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L199)：附件 token 映射到当前消息登记的真实引用；不存在即返回错误，并提示重新附图或给有效路径/data URL。
- [输入合同，234–243 行](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L234)：模型填写编辑 prompt 和图片引用，运行时解析实际内容。该文件还将结果保存并返回路径。

该版本短附件 token 的跨轮编辑有明确限制，不可把它描述为已解决全部历史选图。可借鉴运行时映射和明确失败语义，不能照搬要求用户重传而损失本项目已有历史能力。这里的 token 字符串解析是引用语法解析，不是按用户自然语言关键词决定任务。

## Google：可核对的索引→加载与资源作用域

[ADK 官方 Artifacts 文档](https://adk.dev/artifacts/)将产物表示为命名、带版本且属于 session/user 作用域的数据，允许按名称与版本读取。它本身不自动区分一个聊天中的多个业务任务。

本次核验 `google/adk-python` HEAD 为 `3e322e9a988d6360508e7f6c9fa68983741bea23`：

- [`LoadArtifactsTool`，512 行起](https://github.com/google/adk-python/blob/3e322e9a988d6360508e7f6c9fa68983741bea23/src/google/adk/tools/load_artifacts_tool.py#L512)先给模型可用名称列表，要求通过工具加载所需对象；核对可见名称，再把内容加入当前模型请求。不是把所有完整产物一直塞进历史。
- [`BaseArtifactService.load_artifact`，124 行起](https://github.com/google/adk-python/blob/3e322e9a988d6360508e7f6c9fa68983741bea23/src/google/adk/artifacts/base_artifact_service.py#L124)显式接受 app/user/session、filename 和可选 version；未指定版本取最新。这是资源寻址，不是用户语义保证。

与本项目对比：保留可访问历史索引，通过同一引用合同加载精确对象是可借鉴的。A/B 同属一个 session，仍需本项目维护业务来源关联，不能仅加 session_id 就宣布解决串任务。执行已确认稿件时，本项目原有精确版本保护继续保留，不照搬“默认最新”替换已确认版本。

## 对此前方案的保留与调整

| 内容 | 研究后判断 |
|---|---|
| 消除旧对象“本轮”这种相对描述，带真实来源和需求摘要 | 保留；与语义清晰的名称、关系元数据建议一致 |
| B 没有保存稿也保留为可见需求 | 保留；这是本项目需求事实投影，不虚构产物或执行授权 |
| 展示所有历史完整稿件 | 调整为当前所需详情+历史轻量索引，按需读取；已有权限范围保持 |
| 每次必须多调用一个“选任务”工具 | 不作硬规定；先明确目标再执行是逻辑约束，可复用现有调用，避免额外复杂度 |
| JSON合法、ID存在就接受选择 | 不足；继续核对所选来源、执行稿/成图和版本的归属关系 |
| 所有素材必须同属一个任务 | 不采用；跨任务风格/主体组合保留，编辑底图与参考角色明确 |
| 用最新任务覆盖所有历史选择 | 不采用；当前焦点是承接线索，明确回指历史仍可选择 |

推荐落地是：宿主提供同源的“当前需求详情+历史索引”，同一可理解引用在路由、纠正、执行之间映射；模型解释语义，宿主核对对象和状态事实；新 B 无稿时准备 B，不拿 A 现成稿补空缺。结构一致性可强制校验，用户自然语言含义仍需模型判断和真实对话评测，不能用规则伪装成百分之百语义验证。

具体对比样例：模型看到 B 的原话、B 原图、saved_contents=[]，另有“历史 A：暖米白背景，稿件A1、成图A2”索引。确认 B 时应准备 B 的新内容；明确回 A 时加载 A1 重做或 A2 编辑/展示。若返回 B 的归属却选择 A1，应在执行前纠正；如果模型把整套目标一致地误选成 A，结构校验仍可能通过，因此必须用真实 A/B 切换、回历史、多图合成、歧义澄清等评测验证，不能声称仅靠加ID根治。
