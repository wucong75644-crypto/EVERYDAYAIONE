## 已证实的缺口

### 1. 追加图片到保存方案，再到编号执行，丢失目标画布语义

策划任务 `97b30e6c-579f-5354-a9e1-1245f8681131` 接收了追加图片。保存记录的 source_images 有两张图，但每条 materials 为空、options为空，request_context没有画布选择。后续编号请求选 source_image_indices=[1,2] 时，真实两图比例不同，后台缺少可绑定的目标画布并拒绝。

这不是图片供应商错误：供应商调用尚未发生。已确认缺口在保存/交接的结构化事实不足；不能靠再补“后补/主体/波点”等词表处理。还需核对模型原控制信息、来源目录、稿件材料与画布事实的职责，不能简单删除多图尺寸校验。

### 2. 为解决尺寸冲突而丢掉视觉参考图

用户只补充“按后补那张活页本的比例”，没有取消另一张波点参考。模型后续把 source_image_indices 改为[2]。最终两张请求各只有主体图，第一张波点参考未传。后台没有以已保存的材料角色与画布选择分别约束交接，因为保存阶段没有留下这两类完整事实。

出图仍有波点不能证明图片参考完整：文字prompt本身已描述波点。必须按实际传入图片数组核验，不能以视觉上出现波点替代来源证据。

### 3. 编辑失败后的“再试一次”错误复用最初方案

用户说：“刚才浅蓝背景那张失败了，再试一次，还是改第一张，其他不动。”

模型调用采用原方案1的 content_source，附 image_override 指向原先第一张已完成成图，regenerate填写本次用户要求。宿主执行的是“原稿再生成”契约，最终prompt与最初方案1出图prompt完全相同：SHA256 `46febac196a51330fa5c4f6ce22e521bb39069d944d2934367ee5e60d8de1d3b`。

因此浅蓝要求没有进入图片模型，实际新图仍为米色背景。错误在“重试哪个执行意图/稿件版本”的衔接，不是供应商没理解一个已正确传入的浅蓝prompt。实际引用图片SHA正确，也不能弥补编辑文字遗漏。

### 4. 供应商失败后的自动回执恢复未能确认保存

在失败图片之后，自动续跑报 `TASK_EXECUTION_SAVE_UNCONFIRMED`。Actor日志确认对应任务失败；保存前检查点可读取，root为 `9cddcfdd-b48a-59ab-b4e1-5e9891e05e04`，expected revision=11、state revision=12。

代码中这是检查点写入异常、且回读不能确认同一完整payload时的保护错误。当前证据确认了失败边界，**尚未还原原始数据库异常或最终CAS冲突原因**；不能据错误名断言仅是网络或供应商。不得通过吞掉未确认写入让任务假成功。

### 5. 历史上下文内部定位信息进入用户正文

任务 `a9311442-2a3b-52ba-9676-61c8092a9ebf` 的页面曾展示“已登记并展示正文”、content_artifact_id、“正文来源定位”及内部message/hash等文字。数据库消息 `f3515947-c988-4a10-a8c0-3704429ef03e` 的正式text也包含这些内容，不只是浏览器调试信息。

历史上下文消息中确有宿主附加的来源定位及历史交付说明；在这次细化回答中被复制进可见正文。需要核对内部引用信息与用户稿件的边界，不能仅用CSS隐藏。后续刷新视口因历史分页未显示此较早消息，不能说问题已消失。
