# 独立文本结构化参数通道验证（2026-11-28）

范围：真实百炼qwen3.8-flash Responses API的text.format.json_schema通道；独立于业务Actor，不调用保存或图片工具，不修改应用代码，不部署。现有工作树的其他修改保持。

## 最终决策

用户已确认本轮不接入独立参数纠错通道。以下成功样本仅保留为研究证据，不是待实施方案。继续使用已有错误反馈、原模型有界纠错及后台校验；不启用未通过真实参数验收的strict开关，不自动补括号。

## 验证结论

该通道对两个已知缺闭合括号的保存参数，经过专用兼容投影后，最终2/2合法JSON、2/2通过原工具完整JSON Schema、2/2全部原有字段和值一致。可以作为后续参数纠错方案的验证依据，不能把整个原工具schema原样搬入，也不能仅凭strict=true或JSON能解析就自动采用结果。不是全量工具、所有错误类型或线上稳定性验收。

## 过程及失败证据

1. 简单对象schema及对抗性输出要求：200且结果符合schema。非法strict字符串返回400。无可满足实例的schema反而返回{}，说明仍应由本地校验schema及结果，不能依赖服务端失败关闭。
2. 真实完整保存schema：HTTP 400。schema同时包含多种操作形式、条件、字典属性名约束。官方说明propertyNames不支持；不能把本次400归为模型随机漏括号。
3. 将propertyNames的“禁止固定保留键”改为等价的allOf/not/required结构后，完整schema仍400。进一步限定为当前已确定的base/updates修订操作、移除永不触发的new_content条件及其他操作形式，接口200。此投影只描述当前操作的子集，不取消后台其他工具或历史恢复能力。
4. 此时结果虽然通过原schema，却出现正文被压成一个字符、prompt省略。最小对照中pattern=\S时，要求保留“alpha beta\nline two”却返回“a”；改成[\s\S]*\S[\s\S]*后仅返回“alpha beta”；去掉供应商侧pattern后才完整保留原字符串。这是本次接口/模型/约束组合的实测，不泛化为所有正则或模型。
5. 供应商侧移除该字符串pattern，后台原schema仍完整校验，两个真实样本各重复2次：4/4 JSON及原schema通过；其中2次逐字段一致，另2次仅省略continue_execution=false（后台默认False，未改变执行含义），仍不能算严格逐字段保留。
6. 最终投影要求显式填写continue_execution，再分别重放两种原错误：2/2完整保留全部已有字段、正文、引用、规格、执行标志和数组顺序，且均通过原schema。耗时6.111秒、5.751秒。没有业务工具调用，没有图片供应商任务。

## 验证标准

不以HTTP 200或JSON语法合法作为充分条件。逐一核对：响应completed；json.loads成功；供应商侧结构schema通过；未削弱的原工具schema通过；与已确认仅缺一个闭合括号的原样本逐值比较一致。诊断用的已知正确对象仅用于事后审计，没有发送给格式化模型。修复模型只收到原始坏JSON与输出schema。

## 研究记录：未来重新评估时的条件（本轮明确不实施）

- 从同一后台合同生成供应商兼容子集，按当前已确定动作选择形式，不能让纠错模型重新决定任务、引用或是否执行。
- 供应商不支持或含义不同的约束继续在本地完整验证；不能只删掉规则后宣称完全等价。
- 结果须做字段/原文保真检查，再经过原来源、读取、版本、批准、执行校验。当前用例的“已知缺一括号”审计不等于任意坏JSON都可判定原意。
- 仅把它视为失败后的候选纠错通道。一次额外调用在本样本约6秒；拒绝、超时、内容变化或新输入导致状态变化时不得自动执行。
