## 发现与处理

第二个 Responses 样本登记三次未成功，不能把它算作通过，也不能宣称原系统已经完全稳定。其原始参数未完整保留，不能事后认定具体字段。

补抓的成功样本明确复现一次参数错误：模型给仅交付文字的登记提交了 `new_content=true`，触发 `CONTENT_NEW_SOURCE_INVALID`。原校验正确拒绝，但通用反馈没有指出应该删除哪个字段。此次补充定向反馈：删除该字段、保留全部 document 原文，且不得为了通过校验擅自开启 continue_execution。没有放宽保存条件或业务授权。

新正式回归校验该反馈、不产生可执行成果、没有外部工具派发。修复后的真实样本再次遇到相同错误，模型收到定向反馈后删除字段，第二次登记成功。说明这条恢复路径有效，但仍有一次纠错调用成本；并非已经消除了模型首次参数错误。

没有可比的同输入、同缓存、同图片、同工具面的开启思考对照，不能将本次10–19秒与历史截图35–51秒直接换算为提速百分比。样本很少，不提供p50/p95结论。

## 第二轮：修复首轮参数歧义并重复实测

本轮进一步定位到共享工具契约：`new_content` 的旧字段说明没有强调必须继续实际执行，schema 也未表达后端已有的跨字段约束。模型会把“新系列、新方案”误当成该字段的用途；仅补失败反馈仍需再生成一次全部正文。该缺口涉及工具契约，并非已证实的 Responses 流解析错误。最初失败样本2的完整参数缺失，无法逐次还原其原因；样本4、5的同类错误有完整调用与校验反馈证据。

修复内容：

- 字段说明明确：仅在明确要求实际执行、`continue_execution=true`、随 `document` 提交时使用。仅撰写文字或新系列设计省略它。
- 工具 schema 同步表达 `new_content=true` 对 document 和 continue_execution=true 的依赖；后端原校验、授权、来源与确认机制保持。
- `new_content=null` 仍按原兼容语义处理；普通登记、修订既有稿件、获准的新编辑指令仍验证。没有自动删参数后强行执行，也不自动打开 continue_execution。
- 新正式回归以 JSON Schema 和实际模型输入类型分别验证拒绝与允许的组合；既有检查点和业务恢复协议不变。
