## 实际调用序列

接回原任务前的_task_followup_input_checkpoint保留本轮原始主模型阶段，不能只看接回后继承的旧_model_wire_v1。

1. resolve_request_target：选择更旧的content-ee0446d8d62a9b8ae62234be5a60736a并遗漏revision，被MODEL_TOOL_ARGUMENTS_INVALID拦截。
2. resolve_request_target：补revision=1但仍是旧稿，被REQUEST_TARGET_CONTENT_CHANGED拦截。
3. 主模型随后提交generate_image，参数仅为：

```json
{"content_source":{"artifact_id":"content-785463fcc97236bede204188d252f9b4","item_index":3}}
```

本轮没有先read_conversation_text读取完整第3项，也没有save_task_text修订其规格及正文。最后这个generate_image参数格式合法，选中的是第3项，不是模型在本轮直接填写aspect_ratio=auto。

4. 原稿属于历史任务。后台先返回content_followup=true/status=resuming/accepted=false，接回原任务；direct_loop.restored_content_calls以同一参数重放上述调用，调用ID追加:continued。此重放不是后台凭空独立选图，也不能据此断言主模型没有参与：重放前的主模型调用保存在输入检查点。
5. 后台读取保存稿，将其完整body与options展开。工具卡INPUT中的aspect_ratio=auto和完整prompt来自这一步，不等于本轮模型的原始函数参数。
6. chat_image_preparation检查保存稿约束：bound_specs.aspect_ratio=auto，而用户本轮规格规范化为1:1，比较不一致，抛IMAGE_SIZE_CONFLICT。此时尚未创建/派发生图任务，不是图片供应商返回失败。
7. execution_engine将IMAGE_SIZE等错误写入stop_message；image_argument_correction也将未受理的业务输入错误视为停止条件。没有接回模型执行“修订保存稿→提交新版”，直接结束本轮。

前两次目标纠错是额外的模型参数/版本选择错误，不能隐去；但最终终止出图的直接原因是第6、7步，不是最终用了灯塔图或错误图片。

## 可以确定的设计缺口

- 规格变化已经结构化识别，但“与所选条目不一致时必须先修订”主要放在工具说明中，未成为派发前可供执行器推进的步骤约束。
- 主模型可见的成果目录保存组items只有标题与编号，未直接列出每项options。该组来源标题对应此前“第二个方案、正方形、1K”的请求，不能代表第3项也已改规格。此次模型也没有主动读取完整第3项。这是可见信息不足与误用的风险，不能据此证明模型内部的唯一决策原因。
- 当前工具说明的IMAGE_REVISION_GUIDANCE已写先读取、base/updates修订并继续执行。说明存在不等于执行顺序得到保证；主模型最终没有完成该动作。
- 可修复的保存稿规格冲突进入了统一停止分支，缺少保持所选对象/用户要求、仅修订该条后再执行的受控纠错路径。尺寸冲突校验本身应保留，防止旧正文与新规格不一致。
