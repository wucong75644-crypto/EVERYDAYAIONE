# 定时任务交互简化方案

日期：2026-09-12。用户已授权“开始开发”；A–D 增量开发完成，尚未部署。实际接口、范围与测试见 [技术设计](TECH_定时任务增量升级边界.md) 和 [验收记录](SCHEDULED_TASK_UPGRADE_ACCEPTANCE.md)。下文的产品示例用于说明方向；当前实现边界以验收记录为准。

依据：[官方产品与源码调研](INDUSTRY_定时任务生命周期与确认机制.md)，以及项目 `75fced912ce1ee30668b1a588043b26120ee1e8d` 的原界面和任务管理链路。本次为 07 后续明确授权的产品行为升级，不启动工具统一 08。

用户已进一步明确“基于现有代码升级，不能重写”。复用模块、具体调整位置、兼容与迁移边界见 [代码核验与增量升级边界](TECH_定时任务增量升级边界.md)。

## 目标与判断

用户希望像使用成熟 AI 产品一样，一句明确指令就能完成常见任务管理，不需要理解规划、预检、变更集和提交阶段。

升级前代码显示：自然语言创建先解析并填表；提交后进入变更方案；创建界面展示“填写配置 → 规划与试跑 → 变更方案 → 已提交”；暂停按钮也提出待确认变更。任务卡主要操作在悬停时显示，运行中不允许暂停，暂停状态下不显示立即执行按钮。新组件已完成本地浏览器验证。

上一版“所有新建任务都确认一次”仍保留了不必要的重复操作。本次建议调整为：**明确的普通请求直接完成，信息不足只补问缺项，涉及重要后果才确认具体影响。**

## P-01 日常操作以一句话或一次点击完成

| 操作 | 建议路径 | 额外确认 |
| --- | --- | --- |
| 创建自己的只读定时报表 | 完整指令 → 必要检查 → 创建 → 显示结果卡 | 已有授权、明确时间与数据范围、站内发给自己、沿用已知预算时无需额外确认 |
| 暂停任务 | 一句话或点击暂停 → 实际提交 → 更新原卡 | 无；目标不明确才选择任务 |
| 恢复原任务 | 一句话或点击恢复 → 校验原定义和当前授权 → 更新原卡 | 原授权仍有效时无 |
| 改名称或时间 | 直接说修改内容，或编辑后点击保存 → 更新原卡 | 在原授权及费用边界内无 |
| 改普通只读报告内容 | 明确变更且数据、工具、通知、预算仍在原授权内 → 保存 | 无；不能把所有文字变化都视为高风险 |
| 立即运行 | 点击或明确要求 → 执行一次 → 显示进度和结果 | 普通已授权任务不重复确认；沿用真实执行权限 |
| 新增收件人、扩大范围、业务写入、明显提高预算或频率 | 展示具体变化及影响 → 确认或取得所需授权 → 应用 | 只做必要的一次确认；确认不能替代权限授权 |
| 删除 | 展示准确任务名称和保留/删除后果 → 确认删除 | 一次；本批不顺带改变历史保留和归档策略 |

这里的“普通”必须由实际动作、范围、收件人和费用判断，不能只看工具名、模型判断或旧工具风险标签。用户拥有查看某 ERP 数据的权限，并不自动授权发送给其他人或修改该数据。

## P-02 创建任务的完整体验

### 信息已经明确

用户：“每天上午 9 点，把昨天 A 店的销售汇总发给我。”

前提：用户已有 A 店数据和创建任务权限，所需只读工具可用，个人预算与时区已有明确设置。

系统短暂显示“正在设置…”，成功提交后在当前聊天返回一张简洁结果卡：

> 已创建：A 店每日销售汇总  
> 每天 09:00（北京时间）开始执行 · 统计昨天 · 发给我  
> 下次：9 月 13 日 09:00  
> 沿用当前任务费用上限；尚未执行  
> 操作：暂停 / 修改 / 立即运行

这是完成回执，用户不需要再次点击“确认创建”。展示的实际日期、额度和状态必须来自服务端，不照抄示例或由模型估计。创建不会隐式立即执行，也不会自动发送一份试跑结果。

### 信息不完整

用户：“每天给我发销售日报。”

有默认店铺或已选范围就沿用并展示；多店铺且上下文无法确定时需要补充。缺时间则直接询问“每天几点发送？”或“每天几点开始生成？”并给常用时间选项。文案必须符合产品实际承诺，当前建议使用“开始生成”。

如果同时缺少时间和店铺，在一个简短回复里一起补齐，不逐页填表，不重复问已经确定的信息，不擅自默认成“全部店铺”。最后一个答案补齐后自动完成，不再让用户把同一指令确认一次。

### 需要额外决策

用户：“改成每 5 分钟发到部门群。”

在当前聊天显示具体影响，例如：“将从每天一次改为每 5 分钟一次，并发送到销售部门群，预计每天最多触发 288 次。”同时标明费用上限和该群的实际范围，再让用户确认。权限不足则给出具体缺口，不能让一个确认按钮授予不存在的权限。

对用户询问“能不能每天做日报”或讨论可能性，不直接创建；只有明确的操作意图才执行。重述、复制来的指令也不能被当作新的执行请求。

## P-03 暂停、恢复和修改留在当前任务卡

暂停后，原卡更新为“已暂停，不再自动启动”，按钮切为恢复；不跳转到待处理变更页面，不追加一张内容近似的大流程卡。

聊天说“暂停第一个”应绑定刚才实际展示的列表和稳定任务标识。任务列表过期、任务已经删除或所指不明确时，只要求选择具体任务，不猜测操作另一个任务。

运行中也可暂停后续，卡片同时显示“后续已暂停 · 本次仍在运行”。“停止本次”是另一个动作，停止完成前显示“正在停止”，已发送的消息、已执行的写入和已发生费用不宣称被撤销。

恢复从下一次未来计划时点开始，默认不补跑；过期的一次性任务需要选择新时间。用户要求“改成十点”时，只更新相关设置，原任务 ID、历史和其他已授权内容保持连续。

历史消息保留当时操作回执；卡片展示当前状态时标明是最新状态，两者不能互相覆盖或造成“当时已暂停”被改写成“当时已恢复”。同一会话、任务中心和刷新后状态一致。

## P-04 任务中心只保留日常需要的信息

列表默认展示：名称、执行安排、通知对象、是否启用、下次运行、最近结果。当前正在运行时额外显示本次进度，暂停时不显示虚假的下一次自动运行时间。

暂停/恢复是常驻且带文字或清晰可访问名称的主要操作；手机、触屏和键盘都能直接使用，不依赖悬停发现。立即运行、修改、查看记录可以直接访问；删除放在更多菜单中。

新建入口首先是“你希望定时做什么？”；旁边保留手动设置。自然语言请求已完整时直接创建，手动填写时点击“创建任务”就是提交意图，不再跳到第二个确认页。

高级设置收纳时区、结束日期、单次费用上限等已有能力；重要范围、收件人和适用费用上限仍需在摘要中可见。工具调用路径、技术时间线等放到详情，正常操作不要求阅读。

确实等待授权的任务在原位置显示“需要你确认”，按钮说明具体后果。全局待处理入口可以保留作为汇总和历史兼容入口，不能成为完成一次普通暂停的必经之路。

## P-05 后台检查减少等待但保留必要保证

参数合法性、时间计算、用户/组织权限、资源范围、费用边界、幂等和版本检查继续自动完成。它们不需要每项都变成用户步骤。

创建前默认不运行一遍完整任务。需要实际读取才能确定可行性时，做有界的只读检查；无法确认关键权限或范围则不启用。完整真实执行通过“立即运行”发起，明确显示可能产生的费用和投递。

涉及工具、模型或业务能力的必要规划可以继续存在，但不要求用户阅读内部步骤。失败时告诉用户可处理的原因，例如“未连接 A 店”“没有销售数据权限”，避免只显示“预检失败，请重新规划”。已有输入要保留，补齐条件后继续，不要求重填。

不能仅在前端隐藏确认按钮并自动代点。直接操作必须通过同一套服务端授权、原子提交和回执，不冒用用户审批，不绕过 Registry/Policy/Dispatcher。工具动作从 proposal 变为实际写入时，同步维护副作用、缓存及回放事实。

## P-06 正常、失败和不确定状态的反馈

| 情况 | 用户应看到的反馈 |
| --- | --- |
| 正在设置 | 原位置显示处理中，防止重复提交 |
| 真正提交成功 | 已创建/已暂停/已恢复及准确任务状态 |
| 仅生成待确认方案 | 需要确认，任务尚未改变 |
| 无权限或参数不合法 | 具体缺项和可操作的修正方式，保留输入 |
| 网络中断，无法确定是否提交 | 正在核实结果；查询同一操作回执，不假报成功、不盲目新建 |
| 执行成功、消息投递失败 | 报告已生成、发送失败，可重试发送，不重新执行整个任务 |
| 用户重复暂停 | 已处于暂停状态，不产生另一个待处理变更 |

## 分批落地与验收

第一批完成当前结果缺陷和暂停/恢复体验：回执与真实状态一致，普通暂停不跳页面、不再确认，恢复显示下一次时间，运行中暂停语义覆盖任务完成、失败与超时恢复。若需要分开发布，旧审批路径在过渡期也必须显示真实待确认卡。

第二批完成普通任务的一句话创建、简单修改和仅补问缺项，拆分必要检查与完整试跑，保留高影响变更的有效确认。

第三批简化任务中心、补齐暂停时手动运行和当前运行控制，统一聊天卡与列表反馈。后台运行、权限和回放回归是每批的完成条件，不能推迟到界面全部改完后再检查。

具体验收目标：

- 完整普通创建指令：一次发送即可完成，额外确认 0 次，无需打开表单。
- 普通暂停、恢复、改时间：一句话或一次点击完成，额外确认 0 次。
- 缺少必要信息：只补问未确定项；一个明确答案后继续完成。
- 涉及群发、权限或重要费用变化：展示准确影响并进行必要确认，不出现多层重复确认。
- 可恢复错误：保留原输入；修正缺口后继续，不能让用户从头开始。
- 任务运行中暂停：本次和后续状态同时清楚，结束或恢复流程不自动重新启用。
- 刷新、重连和历史重放：任务状态与实际回执一致，没有假成功或重复创建。
- 跨用户、跨组织、领域及内部工具可见性保持原约束，简单交互不构成权限扩大。

本方案修改了上一版“所有新建和内容修改都确认”的建议，原因是该规则不能充分解决用户反馈的繁琐体验。用户已明确希望更方便；这里提出的自动生效条件、运行中暂停及省去完整试跑仍是具体产品建议，需在实施授权时作为明确范围。归档改造、历史清理、新调度基础设施均不在本次建议的必要范围内。
