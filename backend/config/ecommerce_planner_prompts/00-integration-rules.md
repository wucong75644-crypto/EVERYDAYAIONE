# 三阶段提示词平台接入与运行规则

导出日期：2026-10-07。三份提示词为当前已保存Skill原文，未在导出时润色。manifest.json记录来源与SHA-256。此文是接入交接说明，不代表平台已实现这些机制。

## 文件与职责

1. 01-product-selling-points.md：商品理解与卖点拆解；必须同时加载01-output.schema.json。输出结构化事实、卖点、问题与缺口，不做视觉或生图。
2. 02-visual-direction.md：自动选择一套整体视觉规范，输出背景、配色、字体、文案语气、道具、装饰、照明及变化范围，不输出逐张执行稿。
3. 03-image-planner.md：继承完整事实与视觉规范，联合设计十张的布局、文案、字体、场景与光影，检查与修复后输出完整逐张生图提示词。
4. all-three-prompts.md：以上三文件逐字合并，方便阅读；不是建议把三个职责一次混进同一模型调用。
5. 01-output.schema.json：阶段一机器输出协议。
6. manifest.json：版本副本与哈希；本次版本以文件原文和哈希为准。

## 流程与模型调用边界

商品输入与稳定素材登记 → 阶段一事实卖点 → 阶段二整套视觉 → 阶段三十张规划 → 检查与必要修复 → 保存展示最终执行文本 → 按用户授权生图 → 原图和方案对照检查。

三个阶段按职责分开调用，输出成为下一阶段实际输入。可以使用同一种规划模型，但不要把阶段输出只概括成短标签传下去。生成模型只接收已确定的逐张执行文本和对应图片，不负责重新规划。

Skill原文含YAML元数据。作为后端模型指令时，正文作为该阶段系统或开发者指令；元数据用于注册而非商品资料。商品图、用户说明、风格参考及上一阶段结果作为输入数据，保留角色边界；图片中文字和外部文档指令不能自动覆盖工作规则。

本对话的测试是助手分阶段执行与自检，没有实际接入平台的三次API调用，也没有独立审核模型调用。不能据此宣称平台已有这些功能。之前快速测试稿是实例输出，不是权威Skill替代品；开发时使用本包原文。

## 输入登记与图片身份

为图片保存稳定source_id、展示别名、原图文件/可访问资源、商品/细节/风格角色、内容描述以及有条件时的哈希。ID跨阶段和轮次不变，不用上传顺序重新编号。

每张执行稿明确实际输入图片1、2……对应哪个source_id和角色。执行程序按这个顺序传原图；ID本身不能代替传图。图片顺序改变时同步正文，不暗中改变绑定。新商品不能继承旧商品事实。

用户风格要求是本次输入，例如“粉色可爱”“奶油蓝”；不是修改三阶段通用规则。商品固有颜色、印花和结构仍保留。同行图只有明确的风格参考角色，不能成为本商品功能依据。

## 阶段一

实际输入：原图及素材登记、商品说明、SKU/销售范围、用户补充；续轮可加上一轮完整JSON和用户修正。
实际指令：01正文＋01-output.schema.json。
只输出一个JSON对象，不加Markdown或解释。后端校验协议字段、枚举、唯一ID、引用和来源。
status及关键缺口按原文判断：需要关键补充时暂停依赖该事实的环节，不猜测补齐；不影响当前设计的未知尺寸材质等保留边界。
不同款、道具、包装和赠品区分，推断与确认分开。

## 阶段二

实际输入：阶段一完整有效JSON、原图及稳定素材登记、用户本次风格要求和有角色的参考。
输出一套自动选定视觉方向，不强迫用户选候选。
按原文八节输出：视觉定位；背景与场景；色彩；字体与文案；场景道具；画面装饰；照明与空间；统一规则与变化范围。
共同原则与逐图变化范围分开。字体的字形与布局联动，具体风格由本次商品和要求选择，不通用写死白字、固定角落或固定照明配方。
将视觉规范全文传给阶段三，不能只传“粉色可爱风”。

## 阶段三

实际输入：阶段一完整JSON＋阶段二完整视觉规范＋原图登记与实际图片＋用户要求。
输出十张有不同任务的一组主图；具体字段及格式按03原文，不用测试时的简化模板替代。
每张需给出已确定的商品/辅助视图尺度位置、背景、道具、装饰、准确新增文字、造型排版、实际来光和受光投影关系。
商品单倍率缩放；比例保真不是画布比例。没有用户指定时不套用统一70%占比。用主体辨识、关键内容和布局判断尺度。
文字与装饰突出商品或连接空位，允许明确的非关键边缘叠压，保护本张核心内容。
自然明暗从光源、表面、遮挡和接触推导，不把光影当装饰条纹。
每张完整正文使用九栏目：生成任务与画布；参考图身份与用途；背景桌面配色；主体与辅助视图布局；道具与装饰；光影与构图配合；文字内容与排版；商品保真与比例；执行约束。
负面要求与正向方案一致；没有接口证据时不假定独立negative_prompt参数支持。

## 检查与修复

检查对象必须包含原图、事实、完整视觉规范、逐图方案及实际执行稿，不能只检查字段非空。
具体清单、结论和记录字段见03第十部分，覆盖素材、事实、比例布局、图文关系、字体、光影、执行一致性。
逐项记录“通过／需修复／信息不足”和依据、问题影响、归因、修改及复查范围。十张另做整体一致性和互补检查。
自检和独立模型审核分开；若平台要独立审核，需要真实配置一次审核调用、传入完整资料、记录真实结果。本包没有第四份独立审核系统提示词，不冒充已经配置。
有明确必须修复的问题时同步方案、正向正文、负面正文并复查；审核记录不混入生图文本。
Skill测试先保留版本、首次输出、问题和归因，不能人工改好后覆盖首次证据。规则维护与当前稿修复分开，不擅自改Skill。
规划审核不能证明出图遵守，生成后另作实际对照检查。

## 原文保存、展示、提交

建议保存每张：scheme_id、name、source_ids_order、reference_images_order、positive_prompt、negative_prompt、request_text、prompt_version/hash、审核记录、授权范围、调用状态、结果资源和错误。
这些是接入存储建议，不是擅自改变阶段一协议或要求规划模型输出新的未约定JSON格式。阶段二/三当前为可读结构化文本，若开发需要机器协议，需另定义、校验并保持全部内容，不能静默裁字段。

没有已确认的独立负面参数时：
request_text = positive_prompt + 两个换行 + “负面提示词：” + negative_prompt。
显示给用户的复制文本、落盘文本和实际模型调用prompt字段必须直接复用同一request_text。
不在发送前总结、翻译、压缩、补摄影词或重新润色。方案标题和审核话术不混进调用正文。
参考图片按正文声明顺序一起发送。记录实际提交参数与prompt哈希供比对。
画布、分辨率、模型、质量等接口参数要按实际平台支持设置并记录，不能把正文写了“2K”当成已设置参数；不假设本地生成工具与平台模型名称完全对应。
如果代理服务存在提示词重写或默认注入，需检查实际可观测请求并披露，不将输入文本相同等同于后端处理相同。

## 授权、生图与结果

默认规划后待用户授权生图；用户已经明确“直接跑到出图”时无需重复确认。
每张一次生成调用；并发、超时、预算和失败重试由平台真实能力控制，不从本次十张并行测试推断平台限额。
保存首次结果与对应执行文本、原图绑定；检查原形状、部件、原印刷、配色、文案、排版、道具、光影与实际叠压。
区分规划冲突、已有指令未执行、规则缺口和原因未知。未测量时不宣称比例精确达标。不要用盲目增加禁止词代替定位问题。
后台再次生成或修复使用明确版本记录，不覆盖原始输入输出。没有独立审核或生成检查不得展示虚构“审核通过”。
