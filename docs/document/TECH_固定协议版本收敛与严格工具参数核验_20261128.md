## 字段收敛

真实新建工具schema在document层暴露version=2（可省略的默认协议版本），模型将同值填入三个items。模型内部选择原因无法直接证明，但该不必要字段确实可见。现于content_tools.model_tools中统一收起ContentDocument的固定协议version及案例中的该字段。后台ContentDocument/ContentRecord仍保留version=2，历史稿件revision、真实ID、content_ref及image_ref完全不变。新建、修订、错误回执继续采用同一实际提供的参数合同。不删除模型乱填的未知字段，不静默代改参数。

相关模型schema/参考图/读取修订/历史及真实PostgreSQL检查168通过、18既有条件跳过。普通新建与参考图新建、例子一致性、原生schema不变和保存历史版本均有回归验证。

## 供应商能力核验

使用同一百炼qwen3.8-flash、原Chat/Responses端点，所有探测只请求模型生成参数，不运行保存或图片工具，不发布生产。

1. strict填非法字符串：Chat返回400并指出function.strict类型错误；Responses返回500并指出FunctionTool.strict类型错误。两接口均识别字段，不代表严格生成约束生效。
2. 合法strict=true与简单schema：两接口200，Responses回显strict=true。
3. 无合法实例的schema（必填字段未定义，且禁止额外字段）：Chat仍返回不合schema的{}；Responses拒绝该schema。
4. 实际新建/修订schema的去客户内容小请求：Responses均200，参数合法。
5. 真实失败上下文长参数重放，strict=true、完整实际工具定义、强制仅生成保存参数、供应商返回完成：流式原始完整arguments仍缺括号。解析器拼接不是错误来源。
6. 关闭parallel_tool_calls对照：流式一次通过；非流式仍返回缺括号的JSON，response.status=completed、parallel_tool_calls=false且工具strict=true有回显。不能把问题归结为客户端流式丢帧、超时截断或仅因开启并行。

曾临时为Responses保存工具加strict配置，真实失败重放推翻了简单探测结果后已完整撤回；当前adapters没有本次严格参数启用差异。不把接口接受strict、回显strict或单次成功当成严格模式验收通过。
