# 本地受控发布与失败恢复

生产只有一个执行入口：本地任务工作树的 `deploy/release.sh`。用户说“提交部署”授权本次提交、推送和生产测试；说“清理工作树”才授权验收合并和关闭任务。GitHub 用于代码托管和可选 CI 检查，不执行生产发布。历史 GitHub 生产开关设为 false，新的 delivery 工作流不再接收生产/验收标签或注入生产凭据；旧标签、脚本和历史工作流不构成当前授权。

## 正常发布

```bash
bash deploy/release.sh --message 'fix: description' --file path/to/task-file
# 无新修改时
bash deploy/release.sh --deploy-task <完整HEAD>
```

入口只提交显式任务文件；合入最新 origin/main 并推送确定提交，从隔离检出执行测试、构建和生产发布。冲突保留现场，理解双方修改后解决并重新验证。默认前后端完整发布；仅明确授权部分发布时使用 --frontend-only/--backend-only，部分发布不建立完整验收候选。

生产锁防止同时发布或验收；当前生产必须是候选祖先，未验收候选只能由原任务继续修复。生产状态未知时不直接覆盖，必须先恢复。迁移前核对独立生产数据库身份和实际迁移执行实例，按路径和摘要记录事务结果，已执行且摘要相同的迁移跳过；不重写历史迁移。只有测试/构建、同步、迁移、服务和 /api/health 全部成功，才记录当前完整提交并释放锁。

默认执行本地测试和构建。只有同一最终代码与环境已经完成相关验证时才显式 --skip-test 复用测试；它仍保留构建、身份、迁移和 readiness，合入 main 改变 SHA 后会拒绝复用。GitHub CI 可继续作为补充，但不需要标签审批链或生产凭据。兼容 `task_delivery.py deploy/accept` 命令只转到本地入口，不能把它用于云端部署。

## 失败与恢复

一次发布的完整私有日志位于 Git 公共目录的 release-logs/，权限仅当前用户可读；日志以时间、完整提交和进程编号区分。DEPLOY_STAGE 标识测试构建、同步、迁移和服务就绪等阶段。不要把原始日志上传到 GitHub 或聊天。

确认未开始远端写入的失败可以安全释放自己的锁；写入开始后结果不确定则保留原锁。不能因 SSH 断开或流水线结束就认定远端已停止，也不能只删除锁或伪造成功标记。

先只读核对错误、执行进程、生产文件、迁移账本及应用健康，修复根因；再显式调用：

```bash
bash deploy/release.sh --recover-lock <精确原owner> --failed-commit <完整失败SHA>
```

该入口要求失败提交属于当前任务，核对服务器记录的原提交/分支（旧锁缺少记录时，使用已识别失败提交的变更文件摘要核对），检查没有发布进程和活动迁移、数据库身份正确、服务及健康正常。它归档文件、迁移账本摘要和旧锁到服务器 .incident-evidence/，不删除证据。恢复记录绑定原任务与失败提交，不是成功候选。只有包含失败提交的原任务可以接续；后续成功发布才清除恢复记录并写成功标记。进程、文件、身份或健康不符均保留锁，先处理实际问题。

恢复本身不执行迁移或重启服务，不回滚已成功迁移；按账本核验后由正常入口继续。若已有迁移 checksum 不匹配，停止并新增前向修复迁移，不能修改已应用历史。

## 验收关闭

```bash
bash deploy/release.sh --accept-and-close
```

确认生产完整候选就是当前干净且已推送的任务，合并到 main 后代码树必须与已测试候选一致，再同步其他任务稳定基座元数据和关闭本任务。不同则保留任务，重新提交部署并测试最终版本。验收阶段不部署，不改其他任务工作文件。

## 历史云端发布

旧 GitHub SSH 网关和脚本保留作历史诊断材料，非日常生产路径。历史生产总开关保持 false，生产/验收工作流已移除；不要同时启用本地和 GitHub 两条生产路径。生产环境 secrets 不再由新工作流引用，不复制到开发环境。

### 知识整理依赖与启用

用户明确授权启用自动整理及历史回填时，在正常发布入口追加 `--enable-knowledge`。
受控锁内安装 FFmpeg/FFprobe、Poppler；Alibaba Cloud Linux 3 使用校验 SHA256 的 RPM Fusion EL8 仓库包，后续 RPM 保留软件源签名校验。解析程序逐一检查通过、模型及知识画布已配置后，仅更新 `KNOWLEDGE_DERIVATION_ENABLED`、`KNOWLEDGE_MEDIA_ENABLED`、`KNOWLEDGE_SEMANTIC_ENABLED` 三个键，保留私有备份及其他配置。随后按正常流程重启并检查 readiness。失败停止且不宣称启用成功。

历史回填由持久化 worker 按现有 actor/org 及实时写权限处理，无需批量修改正文或权限。关闭时仅通过受控配置入口将 `KNOWLEDGE_DERIVATION_ENABLED=false` 并正常发布重启；已生成内容及人工内容不删除。
