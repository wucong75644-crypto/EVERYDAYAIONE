## 1. 目标与判断标准

用户希望不必反复指定知识库，系统能准确选择资料并用于实际工作，同时保留显式 @ 的可控性。“和大厂一样精准好用”落实为可观测的六项能力：该查时查、范围选对、必要证据找得到、理解例外与冲突、资料不足不编造、普通任务不被过量检索拖慢。

不承诺复制厂商内部算法或在未评测前达到同等效果；对齐公开机制和真实业务评测。第一阶段范围为当前账号的个人主聊天及其工具执行；通道、群消息和定时任务需单独适配，不自动继承个人知识。

保留：保存即能读取；不用封装发布；用户只需选择总分支，模型自主定位子资料；当前权限、同轮版本一致性、来源定位、幂等与恢复。

明确变化：目前“无@不进入新库”改为“任务确需知识时可由系统选择获准根”；这是一项新的产品行为，不能通过偷偷改写用户的knowledge_refs实现。

## 2. 推荐路线与未采用路线

| 路线 | 好处 | 不足 | 结论 |
|---|---|---|---|
| 每轮全库先搜再生成 | 触发简单 | 混项目、噪声、延迟；不知道哪些规则是必读 | 不采用 |
| 给主模型工具，自由决定所有步骤 | 改动少 | 当前已有类似模式；难保证必读资料、执行前规则和可解释失败 | 作为对照基线，不作为唯一保障 |
| 任务决策＋可信范围＋自适应检索＋证据检查 | 保持自主性，同时能验证和约束关键路径 | 新增控制状态、索引、评测和部分推理成本 | 推荐 |

不新增一个能任意读库的“大Agent”。控制层管理范围、版本、证据和预算；模型做语义判断、子问题拆分和冲突理解；数据库负责权限。模型的判断结果不等于授权。

## 3. 完整状态流

```text
ACCEPT_INPUT
  → DECIDE（任务是否依赖知识）
  → RESOLVE_SCOPE（选择根，服务器校验）
  → FREEZE（冻结本次允许范围与版本）
  → BOOTSTRAP（框架和适用规则）
  → RETRIEVE（混合召回、去重、排序）
  → READ（正文、必要上下文、完整规则）
  → ASSESS（逐项证据是否足够）
      ├ sufficient → 执行/生成 → 核验输出 → COMPLETE
      ├ missing → 定向补查/导航 → READ
      ├ ambiguous → CLARIFY
      ├ conflict → CONFLICT
      ├ source_unavailable → PARTIAL / UNAVAILABLE
      └ no_progress / budget → PARTIAL
```

每次状态变化持久保存可恢复的事实：采用哪个范围、哪些版本、哪些证据已读、缺少什么、为什么停止。不保存模型隐藏思维链，不用自由文本“我觉得查全了”充当状态。

## 4. 自动触发机制（独立于搜索算法）

### 4.1 任务决策契约

建议增加KnowledgeDecision，包含：

```text
mode: none | required | optional | clarify
reason_code: explicit_ref | internal_fact | business_rule | product_fact |
             source_transform | general_question | ambiguous_scope
evidence_needs: [{id, question, entities, must_resolve, source_type}]
requested_root_candidates: [server_catalog_handle]
coverage_goal: relevant | exhaustive
```

none只表示本轮无需知识，不表示知识库为空。required表示不能在相关事实/规则无依据时作确定回答或发起依赖它的执行。optional可用于用户允许的增强资料，不把失败强制变成整轮不可用。clarify仅用于业务实体/范围有实质歧义且无法从现有上下文确定。

任务依赖信息分开判断：事实、业务规则、风格偏好、实时数据。用户上传了一段文案并不意味着可以忽略“按我司品牌规范修改”；查销售额也不意味着可以忽略“按公司有效付款口径”。

### 4.2 决策如何产生

1. 服务端先处理可确定输入：显式@必进入指定范围；用户明确限定“仅根据这段文本”且没有冲突约束时不扩搜；已有正式任务模板绑定按其授权范围；通道身份拒绝私人范围。
2. 对明确的纯文本变换、闲聊，不增加知识模型调用。不能用“润色”关键词一刀切跳过品牌规范。
3. 其他可能依赖内部事实的任务，用现有ModelGateway做一次结构化任务判定，输入用户当前问题、必要对话指代、当前可信范围、少量已授权目录描述；不输入全部正文。模型选择在评测阶段确定，不硬编码新厂商/模型。
4. 结构化结果只供控制层验证；缺字段、无效候选或判定失败不是“无需检索”。内部事实任务降级为当前许可范围的小规模探查；范围不明则澄清。
5. 主模型后续发现新知识依赖，可以升级none→required/optional并发起源发现；不得因前置分类漏判永久禁止检索。只允许缩小/提出候选，不能自行扩大授权。

不对每条消息强制增加一个外部分类调用。把“确定跳过”“单次决策”“复杂任务拆分”分别统计成本；分类误差也属于质量评测，不假设它天然准确。

### 4.3 触发示例

| 请求 | 决策与必要证据 |
|---|---|
| 把下面这段话压缩到100字 | none，除非已有明确品牌/业务规范要求 |
| 按我们品牌风格改这段文案 | required，品牌风格和禁用表达 |
| 这款笔适合宣传哪些卖点 | required，明确商品身份、实际参数和适用规则；身份无法确定才问用户 |
| 按公司售后规则判断这单能不能退 | required，订单实际状态由ERP取；政策和例外由知识库取 |
| 统计今天销售额 | 实时数值由ERP取；存在公司约定口径时知识为required，不拿知识文档的旧数字当今天数据 |
| 比较两个项目的方案 | required，明确的两个项目范围；允许本次比较，不变成默认跨项目全搜 |
| 继续按刚才规则处理下一单 | 保留稳定根身份，新消息重新验证权限和取得最新保存版本 |
| 总结这个框架所有材料 | exhaustive，必须枚举分页、解析状态和必要正文，不靠top-K宣称读全 |

## 5. 搜索范围设计

### 5.1 权限范围、任务范围、相关性分开

- 权限范围：actor/org/container ACL/RLS决定能读什么；模型不能改变。
- 任务范围：本轮请求和可信根绑定决定应该查哪里；“有权读”不等于“这轮全部都该读”。
- 相关性：在上述边界内找到有用内容；高相关不能绕过范围或权限。

推荐顺序：显式@与“只根据”约束 → 可信任务绑定/本轮延续根 → 唯一明确命名的项目 → 与业务需要相关的个人/团队知识。先查当前范围，不能因无结果自动把所有项目正文都搜一遍。

当没有当前项目时，允许对当前身份可见根的名称/简介做有界候选发现；这不是跨项目正文检索。候选元数据受同一ACL，超出预算不注入全部目录。只有目录不能判断商品/项目是否一致时，可在候选根做受控主题/型号探查；发现两个同等可能项目时询问，不用相似度高0.01当业务决定。

root candidate不是授权凭证。自动选择根后仍走check_roots/RLS，不能允许任意UUID读取。未授权对象不存在和无权保持统一外部语义，不能泄露标题、计数或存在性。

### 5.2 对既有契约的增量

- 用户显式knowledge_refs继续原样保存；不伪造用户@标签。
- 新增服务器持久的run context，记录input_message/attempt、explicit_refs、auto_selected_roots、selection_reason、scope_mode和snapshot_id。
- 权威根来自持久化消息/服务器决策，模型输入只能是当前已给出的候选handle；隐藏params不能作为授权来源。
- 将KnowledgeRun.start拆成“验证可信根绑定”和“创建读取快照”两个可复用步骤。原有显式路径保持兼容；自动路径绑定run context，不能仅把required改true，因为原函数只读消息knowledge_refs。
- 新root discovery工具可在无引用时可见；outline/search/read仍仅在获准run context存在时可见。knowledge_refs_present演化为knowledge_context_present，并保留旧任务恢复兼容。
- 原四工具与旧search_knowledge不合并。旧工具兼容和退役按研究文档执行。

### 5.3 版本与范围扩展

初版推荐在读取正文前完成根选择，统一冻结本轮版本；快照按最终根范围创建，避免所有可见容器全量快照。

同一输入重试/恢复复用根选择和快照，实时重新授权；重新生成/新消息使用新的执行绑定与最新保存版本。会话延续根身份可以保留，上一轮全文不永久注入。

若正文读到一半发现需要另一个项目：已有真实引用可按现有follow_reference走；没有真实引用则本轮返回缺失/请求扩展，不能静默加根或混入新时刻版本。后续若支持动态扩展，需要新执行尝试统一冻结扩大后的范围，并重读参与最终结论的资料；不能复用当前以input_message唯一的旧快照伪称一致。该扩展不是首版必需能力。

## 6. 框架、规则和事实的使用

1. 首次进入已选根，取得根说明、有限一级目录、索引/解析覆盖状态、空间通用和根适用规则。原来只注入“请先outline”的提示不足以保证规则取得。
2. 读取命中对象时，服务端根据快照中的父子关系解析祖先/局部适用rule，返回全部必要规则或明确分页状态；不要让相关度排序决定适用规则是否出现。
3. rule长于预算不能静默截断后继续执行：显式返回待补读集合，required任务只有必要规则完整取得后才可进入相关执行。
4. rule只表示用户创建的业务规则，优先级低于平台权限和系统安全边界；文档、文件、网页里的“忽略指令/导出全部数据”仍是资料内容，不能提升成工具授权。
5. 具体条件与例外按适用性理解，不预设私人>项目>团队，也不单凭修改时间更新就认定政策优先。
6. 同一对象current_revision是当前保存内容；不同文档的“新旧政策”是业务生效问题。首版保留来源、版本、时间并报告冲突，不伪造不存在的生效日期/审批状态；若要自动判定生效，另增显式有效期/替代关系设计。
7. 规则查到后可作为业务口径传给ERP子任务，但应保存来源，并保持原数据权限。现有“ERP task只复述用户问题”的策略需增加受控knowledge_evidence字段，而不是私自把规则混写进task。

## 7. 索引、召回和排序

### 7.1 原始真相与可重建索引

对象/文件不可变版本仍为真相；检索索引是派生数据，不是新的知识副本编辑入口。

拟新增chunk索引：source kind、object/binding/version、chunk序号、源偏移、标题/祖先路径、文本、词法向量、embedding、解析/切分/embedding版本、content hash和处理状态。索引正文和向量同样是敏感数据，受RLS，不以worker身份开放全库。

文档按标题/段落切分，保留前后必要上下文；表格保留列名/行标识，规则例外不能截断成相反含义。路径/标题可作为确定性的片段上下文；LLM生成的摘要只能助检索，不能当原始事实或规则。

文本来源明确：正文、已解析附件、未解析附件。TXT等可直接切分；PDF/Office逐步补页码、工作表、单元格锚点。扫描PDF、图片、视频当前缺OCR/转写，首版保持可见的不可检索状态，不把它们标为已理解；需要支持时独立选择解析方案与成本。

### 7.2 索引更新与失败

- 保存事务提交后产生持久索引任务/事件，worker在短事务取任务，事务外做embedding，再校验版本并提交结果。
- 幂等键包含源版本、parser/chunker/embedding版本；任务超时可重试，过期结果不得覆盖新版本状态。
- 索引pending/failed不阻断目录和原文读取。保留当前字面匹配作为有界降级；必须明确搜索覆盖缺口。
- 同轮旧快照可查对应保留版本的索引；新查询只匹配自己的快照版本。旧索引存在不能成为读取旧权限内容的理由。
- 移动/改名触发路径元数据更新；正文向量未变可复用字节，但带上下文的embedding需要按上下文hash重建。
- 删除/解绑/撤权先在实时授权层生效，再异步清理索引。最终一致索引不承担权限撤销的唯一责任。

### 7.3 检索过程

1. 根据evidence_needs生成少量子查询；保留商品编码、金额、否定、时间和主体，不能为了扩搜丢掉关键条件。
2. 在快照授权范围内并行做：精确编码/标题/短语，中文分词关键词，向量语义召回。
3. 词法先用项目已有jieba与PostgreSQL全文检索能力，准确称为tsvector/ts_rank_cd；不要冒充BM25。pg_trgm/短语匹配补型号和短词。是否采用真正BM25由对照评测决定。
4. RRF融合不同召回通道的排名；候选去重按来源版本/位置，不用语义相似覆盖原文。不同SKU/不同例外不能被合并掉。
5. 对多候选、歧义或复杂问题做语义重排；精确唯一命中可走快速路径，但仍读适用规则。重排模型/本地方案以质量、延迟、成本实测选择，不在研究阶段新增收费服务。
6. 适当增加来源多样性，补同一文档的上下文/例外；不让同一文件几十个相近片段淹没另一项必要证据。
7. 先返回位置、来源和有限片段，再读原文；限制由token预算而非只看“条数”控制。

阈值不能沿用旧库0.5/0.7；不同embedding/reranker的分数不是可比较概率。top-K、块大小、融合权重和最低相关阈值在业务评测后定，不把厂商实验参数当本项目标准。

## 8. 证据充分性、补查和停止

### 8.1 必要证据表

每个evidence_need维护：unresolved/resolved/conflict/unavailable，关联实际读取的源版本/offset、支持的事实及仍缺条件。例：“能否退货”至少包括商品/订单身份、适用政策、期限、例外；仅搜到含“退货”的段落不足以标记resolved。

确定性检查：来源来自本次有效handle、版本和offset真实；必要规则完整；文件解析状态明确；引用链接由服务端生成；实时数值来自实际ERP/计算结果。

语义检查：证据是否支持结论、遗漏例外、主体/时间是否一致、政策是否冲突。交给结构化模型判断并通过人工标注集评测；不宣称仅程序检查就能证明业务正确。

### 8.2 补查策略

| 缺口 | 下一步 |
|---|---|
| 同义表达没命中 | 保留实体，改写问题/拆关键词，再查同一范围 |
| 命中标题但内容不足 | 读取原文和相邻节，不重复搜索相同问句 |
| 多步骤/多条件问题 | 按缺失证据项分别查询，独立项可并行 |
| 只见一般条款 | 查同一框架的例外、限制和适用对象 |
| 目录存在但索引未就绪 | outline/read有界补读，并显示覆盖缺口 |
| 文件未解析/截断 | 读取已获准原件做适配分析，或报告缺失；不无限换关键词 |
| 相同问题属于多个项目 | 在有限元数据探查仍无法区分时澄清 |
| 相同查询反复无新证据 | 停止，说明未解决项 |

普通问答默认只针对相关范围；全框架总结走独立遍历模式。遍历完成、读取完成和回答充分三种状态分开，不能以检索top-K代替全量。

停止原因必须枚举：sufficient、no_match、ambiguous_scope、conflict、source_processing、source_unavailable、permission_revoked、budget_exhausted、no_progress、service_error。权限/服务错误不能包装成no_match。

预算由现有ExecutionBudget统一约束，增加知识专用的子查询数、读token、轮数、时间、费用计数。起始实验可比较一次检索与最多两次补查；这只是实验配置，最终值以业务成功率与延迟曲线决定。相同query+scope+snapshot+证据指纹无新增内容时不继续重复。

## 9. 回答与执行前保障

当前“先流式输出、最后附来源”不能拦住先输出的无依据结论。建议区分：

- none任务：保留现有直接流式输出。
- required任务：先发送“正在查找/读取资料”等进度；确定性事实结论在证据取得后再输出。最终答案草稿经过引用和语义依据检查后发给用户，付出一定首段等待以换取可核验性。
- optional任务：允许基于已提供内容回答，但明确哪些是资料依据、哪些是建议，不制造已查库印象。

来源尾注保留为审计兜底，同时把source refs关联到具体事实段落；“读过这个文档”与“这个结论被文档支持”分开记录。来源只允许本次有效回执产生，不能接受模型伪造URL。

商品生成、ERP执行等依赖知识的工具调用前，对应evidence_needs必须resolved，必要规则读完；校验失败则补读或返回缺失，不等到产物生成后才追加免责声明。工具授权仍走原Policy，知识规则不能解锁外发或写操作。

文件和工具动作的最终成功以实际结果为准；知识判断只决定前置依据，不替代ERP、生成、发送等成功证据。

## 10. 缓存、撤权与恢复

- 共享缓存只缓存无授权能力的派生中间结果；正文结果缓存绑定actor/org/context、根集合、快照、版本、查询、检索配置和权限版本。
- 缓存命中前仍校验当前身份和容器/文件状态；缓存不能绕过撤权。默认先复用当前新工具cacheable=false，质量稳定后再优化。
- 服务端run context、snapshot、evidence ledger和budget进入Actor checkpoint；恢复不重新选择根，不重复收费解析/检索而不记账。
- 已进入历史的正文不能宣称可以远程抹除；新一轮上下文组装必须过滤已撤权的知识结果/摘要并记录版本，不能只阻止新工具读取却继续用历史工具正文。属于ContextSnapshot/摘要/恢复链路的接入要求。
- 对于已物化文件，保持当前有限目录、重授权、结束清理；异步索引不得写进用户私人工作区充当共享缓存。

## 11. 评测与上线门槛

先建立业务金标，再选模型和参数；“43项代码测试通过”不能代替质量评测。

### 11.1 数据集

建议先建立约200个审核样例作为起始工作量，而非统计充分性承诺：纯文本/闲聊负例、隐式公司规则、商品/SKU、同义/错别字/中英混合、上下文指代、多项目、跨文档条件与例外、冲突、无答案、解析缺口、版本变化、撤权/跨账号、提示注入、整框架任务。真实业务样例须脱敏并获准使用；另准备有来源标签的合成对抗数据。

每例标注：是否应查、可选范围、必须命中的资料/规则、可接受答案、必须拒答/澄清条件、是否允许部分完成。训练/调参和保留评测集分离，不能边看保留集边改阈值。

### 11.2 分层指标

| 层 | 测什么 |
|---|---|
| 触发 | 必查召回率、触发精确率、无需查询时的误触发 |
| 范围 | 项目/根选择正确率、歧义澄清、未经要求的正文跨项目扩展 |
| 召回/排序 | 文档与规则Recall@K、MRR/nDCG、关键词/语义各自贡献 |
| 阅读/规则 | 必要规则完整取得率、例外识别、exhaustive覆盖是否诚实 |
| 答案 | 事实正确、逐结论依据、引用正确、必要信息完整、冲突/无答案处理 |
| 运行 | p50/p95首段与总延迟、每成功任务费用、无效补查、缓存/索引滞后 |
| 权限 | 跨租户、撤权、历史上下文/缓存/文件泄露测试 |

候选起始质量目标（待基线后确认，不是当前已达成）：保留集必查召回≥95%，触发精确率≥90%，必要证据Recall@10≥95%，引用准确≥98%；权限回归不得出现已知泄露，必查规则缺失不允许标记任务已依据规则完成。样本量、置信区间和分组结果一起报告，不能用总体均值掩盖SKU或撤权错误。

最终时延/费用门槛根据实际数据规模与用户等待取舍确定，本次不编造并发、毫秒SLA和预算。模型裁判辅助筛选，涉及制度例外和业务结论用人工核验，不能用同一个模型自评当唯一正确答案。

### 11.3 必做对照

同一数据、权限、源版本和提供商下对比：现有字面搜索＋模型自主调用；混合搜索；混合＋重排；增加任务决策；增加充分性补查。记录消融结果，确有增益再启用复杂机制。

按实际支持的主要模型分别跑：至少当前默认模型与故障切换模型；工具选择能力和结构化输出失败也算失败。真实提供商＋Web/Actor/WS完整端到端单列，不用mock或孤立工具联调替代。

先合成/离线、再小范围灰度。影子测试也会读取资料和消耗费用，只能在已允许的范围和预算中运行，不能无声复制生产私人内容到新服务。观测记录原因码、源ID/版本、候选分数、阶段延迟与缺口，默认不写全文/密钥。

### P1：控制层与证据闭环（先提升现有@路径）

- refactor chat.py，将snapshot/authorization/navigation/rule resolution与检索实现分离，复用现有handle、回执和来源。

## 13. 兼容、发布与回滚

- explicit @路径先保持；自动发现使用独立开关和名单，检索增强、证据前置与自动选择也可分别控制，避免一个kb_enabled控制全部职责。
- 关闭auto-discovery时，已创建的run按快照和权限安全完成或明确停止；不得静默丢掉知识绑定执行。
- 关闭新检索后可回到已有显式@＋原文导航；必须保留已承诺的规则/证据约束，不能把失败降级成凭空回答。
- 数据变更全部前向添加，保留原始版本、消息引用和历史快照。索引可重建；回滚应用不DROP业务资料。
- 发布仍仅经本地deploy/release.sh，在用户授权提交部署后执行。本次无部署、无数据库变更。

## 14. 推荐确认的产品取舍

1. 无@时自动查询当前身份可见且与任务相关的个人/团队知识；项目先按可信绑定或有限根发现选择，不默认遍历所有项目正文。
2. 明确内部事实/规则依赖使用required路径，允许先等资料核验再输出确定结论/执行；普通任务保留直接响应。
3. 用户明确引用、来源身份、权限、版本、例外与无答案处理优先于“尽量总能给一个答案”；资料不足时返回具体缺口。
4. 第一阶段只接个人主聊天；定时、企微通道、OCR/音视频不伪称已支持。

以上是具体推荐，尚未替用户确认。参数和收费模型选择通过评测决定；旧库删除需要独立盘点和明确授权。
