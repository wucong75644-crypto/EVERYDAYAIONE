# 聊天流式显示节奏修复

## 范围与证据

用户确认普通文字聊天也存在分段跳出的现象。本轮先修复显示节奏，不修改发送至首段内容返回前的上下文准备流程。

当前 WebSocket 的 16ms 缓冲只合并数据，不能把大块文字平滑展开；MarkdownRenderer 的普通回复与结构化文本调用均未传 isStreaming。服务端仍按 delta 输出，不能据此声称近期某个提交取消了流式输出。服务端分块间隔的实际贡献尚未测定。

## 修改

useStreamingText 仅对新增文字进行逐帧展示，保存层和 WebSocket 投影始终保留全部实际收到的内容。每批新增文字以 120ms 追赶窗口推进，不按固定慢速逐字播放；首段增量立即显示前缀。

首次挂载的已有内容、非追加快照、结束/暂停/取消/失败及减少动态效果偏好立即显示完整内容。动画卸载时取消，不拆分 UTF-16 代理对。多内容块仅最后的当前文本块平滑显示，前面的已完成文本立即完整显示。

不修改流式协议、数据库、计费、服务端持久化和首包准备路径。120ms 是显示层的追赶窗口，不是服务端等待的解决方案；完成状态立即显示完整结果。

## 验证

2026-10-14：134 项定向前端测试通过，包括大块增量、连续追加、完成与中断、恢复替换、历史快照、减少动态效果、代理对与卸载清理，以及原有 Markdown、内容块和 WebSocket 回归。TypeScript 编译和 diff 检查通过。

尚未部署，未调用付费模型。后续首包延迟排查独立进行：线上已有上下文准备耗时 5.7/11.7/14.1 秒及 Embedding 打分超时证据，本轮未改变该行为。
