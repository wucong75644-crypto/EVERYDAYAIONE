# 定时任务生命周期与确认机制：行业调研及建议

调研日期：2026-09-11。本篇保存行业研究和早期候选，实施状态以 [增量升级验收](SCHEDULED_TASK_UPGRADE_ACCEPTANCE.md) 为准。

2026-09-12 补充：用户反馈日常使用不方便后，确认策略在 [定时任务交互简化方案](PROPOSAL_定时任务交互简化.md) 中修订为“普通明确请求直接完成，只有必要情况补问或确认”，并已授权在现有代码上开发。本文保留 09-11 的研究证据及早期候选；下文“所有新建确认一次”不再是最新策略。

项目代码基线：`75fced912ce1ee30668b1a588043b26120ee1e8d`。本记录回应用户对暂停任务异常及“大厂、Grok Build 如何设置定时任务”的调研要求，不表示工具统一 07 已完成用户验收，也不启动板块 08。下述行为调整需作为明确的产品变更实施，不能混入定义所有权迁移。

## 1. 推荐结论

建议采用“直接管理调度、按变更内容确认、每次运行独立留痕”的产品逻辑：

- 用户明确指定任务并要求暂停，鉴权通过后立即停止后续调度，返回实际状态。
- 恢复原任务，从下一次计划时间开始，默认不补跑暂停期间的任务。
- 创建、改变任务内容、扩大数据或工具权限、增加收件人及明显提高运行成本，展示具体差异并做一次有效确认。
- 暂停后续调度和停止当前运行是两个操作；任务运行中也应允许暂停后续调度。
- 结果卡、任务列表和聊天记录使用同一份服务端回执，不能由模型自行宣称操作成功。

这是结合项目 ERP、费用和组织隔离约束提出的建议，不是所有厂商共同遵守的标准。厂商公开材料对后端锁、事务和确认细节的披露程度不同，不能从一个 UI 开关推断其全部实现。

## 3. Grok Build 的实际逻辑

Grok Build 是开发代理，提供终端交互、脚本和 ACP 使用方式，参见 [官方定义](https://docs.x.ai/build/overview)。它的 `/loop` 和 Grok 消费端 Automations 是不同能力，不能混用产品结论。

本次读取官方仓库 `xai-org/grok-build` 的固定提交 **`37949780c144e37df692e3d669051a21fec24f20`**；以下结论仅针对该源码版本。检索引擎缓存的移动分支内容与固定提交存在差异，因此采用固定提交引用，不宣称覆盖所有发布版本。

### 3.1 创建和执行

`/loop` 将频率和指令转换成调度工具调用；缺少频率时要求补充。每次触发交给后台子代理，因此保存的指令必须包含资源标识、检查目标和停止条件。一次触发完成一次有限工作，不应在里面再无限轮询。该入口会设置立即首次执行，并向用户报告频率、任务 ID 和到期时间。见 [命令实现](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-tools-api/src/slash_commands.rs#L19)。

公开创建工具支持最短 60 秒间隔、最多 50 个任务，循环任务 7 天到期。原始工具的首次立即执行默认关闭，由 `/loop` 显式打开。传入已有任务 ID 可原地修改指令或间隔。该版本公开入口拒绝一次性调度，但内部仍保留相关数据和恢复代码。见 [创建工具](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-tools/src/implementations/grok_build/scheduler/create.rs)。

### 3.2 暂停、重叠和回执

该 scheduler 模块的命令是 Create、Update、Delete、List，未提供独立 Pause/Resume 命令；`/loop` 的取消通过删除调度完成。不能把其他 workflow 的暂停能力当作该循环调度器的暂停契约。见 [命令和状态类型](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-tools/src/implementations/grok_build/scheduler/types.rs#L343)。

上一轮仍在初始化或运行时，本次触发跳过；如果无法核实上一轮状态，也跳过以免重复启动。删除流程等待持久化等确认后才回复结果，失败会返回错误；不能据此推断创建、修改具有同样的持久化确认屏障。见 [运行与删除实现](https://github.com/xai-org/grok-build/blob/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-tools/src/implementations/grok_build/scheduler/actor.rs#L580)。

**适用性判断：**借鉴独立执行上下文、防重叠、明确停止条件、结构化回执。长期 ERP 日报不照搬 7 天自动失效，也不照搬首次立即执行；每天 09:00 的任务应先显示下一次 09:00，用户另点“立即运行”才额外执行一次。创建工具属于写操作，不能因 `/loop` 流程简短就推断其绕过了 Grok Build 的权限系统。

## 4. 本项目的已知事实

### 4.1 此次异常是提案与生效状态脱节

此前对生产的只读排查显示：“暂停第一个”生成了 `pause` ChangeSet，但状态仍为 `awaiting_approval`，任务仍为 active，聊天却表示“已暂停”。未发现对应确认和应用事件。

代码链条与此一致：

4. 后续模型回答没有可靠绑定到 ChangeSet 是否已经应用，因而把“提案调用成功”说成了“暂停成功”。

### 4.2 已有机制应复用

- [现有 ChangeSet 设计](TECH_AI规划框架与定时任务ChangeSet适配器.md) 已包含授权、差异、版本检查和幂等提交。暂停、恢复、删除使用确定性资源检查，没有完整 Agent 试跑，不能把现状描述成“每次暂停都跑一遍昂贵 AI 规划”。
- [迁移 249](../../backend/migrations/249_scheduled_task_changeset_adapter.sql) 在提交时锁定任务、核验版本，目前拒绝运行中任务的修改、暂停、恢复和删除；revision 也随调度运行状态更新而递增。
- [迁移 242](../../backend/migrations/242_scheduled_task_delivery_outbox.sql) 已将完成结果、运行记录与投递记录一起落库，并有投递去重；成功完成路径只在任务仍为 running 时调整调度状态，已有保护不应删除。
- [scanner.py](../../backend/services/scheduler/scanner.py) 已使用数据库任务认领，并做超时恢复；若引入“运行中暂停后续”，需同时核对认领、启动、失败、重试和超时恢复，不能只修改暂停接口。
- [action_rules.py](../../backend/services/tools/action_rules.py) 当前将任务暂停等管理动作定义为 proposal。将其改成立即生效属于动作语义变更，必须同步 Spec/Policy 的副作用事实、结果和缓存/回放约束，不能新增旁路鉴权。

## 5. 建议的用户操作契约

以下均为拟议行为。组织、用户、领域及既有工具权限保持约束，操作简化不等于授权放宽。

| 用户操作 | 推荐处理 | 成功后应看到什么 |
| --- | --- | --- |
| 查询列表、查看记录 | 直接读取有权访问的任务 | 名称、启用状态、当前运行、下次时间、最近结果 |
| “暂停第一个” | 解析刚展示列表中的稳定任务 ID；目标唯一且有权管理时直接暂停。列表过期或目标含糊才要求选择 | “已暂停《订单数据简报》，不会再自动启动。” |
| 暂停正在运行的任务 | 立即禁止后续调度，当前运行继续；同时显示当前运行情况 | “后续已暂停；本次仍在运行。”并提供独立停止入口 |
| 恢复 | 定义、授权仍有效时直接恢复，从下一个未来计划时点开始，不补跑 | “已恢复，下次：9 月 12 日 09:00（北京时间）。” |
| 恢复已过期的一次性任务 | 要求选择新的时间或明确立即执行，不将过去时间直接重新激活 | 新的执行时间或一次手动运行记录 |
| 新建任务 | 整理一张完整任务卡，展示时间、数据范围、工具、输出位置和费用上限；必要检查后确认一次 | 已创建、下次运行时间；尚未实际执行 |
| 修改任务内容、数据范围、收件人、提高预算或显著增加频率 | 展示具体前后差异，检查受影响能力，确认一次；新增权限需要实际授权 | 应用后的版本和下次运行时间 |
| 重命名、在原授权内调整时间 | 明确编辑请求或点击保存可直接应用；时间变化展示下次时点 | 修改后的安排；不改变当前运行的任务快照 |
| 立即运行 | 创建一条真实运行记录；不改变暂停/启用设置，不隐式恢复任务 | 本次进度、结果、实际费用；定时状态保持 |
| 停止当前运行 | 请求在可停止位置取消；明确已发生的调用、扣费、发送不会自动撤回 | “正在停止”到“已停止”或明确无法停止的原因 |
| 删除 | 明确展示目标并确认一次；建议采用归档，停止后续任务并保留历史 | 已归档及历史入口；历史清理作为另外的行为 |

“创建前检查”和“立即运行”必须分开。前者验证参数、资源、权限和必要的只读可行性；后者可能真实查询、消耗积分、写文件或投递结果。Grok Bot 官方也明确其 Test run 会执行真实工作，参见 [运行测试的说明](https://docs.x.ai/grok-bot/skills-routines-and-automations#test-before-enabling)。

## 6. 运行可靠性与权限约束

### 6.1 分开表达调度和运行

任务的“是否继续自动启动”和某一次运行的“是否结束”必须独立表示。比如同一时刻可以是“定时已暂停，本次仍运行中”。投递失败也不应被说成整个任务执行失败后直接重做业务。

拟议概念关系如下，并不预先确定数据库字段或 API：

```mermaid
flowchart LR
    A[任务定义：指令、时间、授权、版本] --> B[调度：启用或暂停]
    B -->|到期且允许启动| C[一次运行：排队、执行、完成或失败]
    C --> D[投递：待发送、已发送或失败]
    E[手动运行] --> C
```

暂停的生效边界以服务端事务和实际启动检查为准：暂停先完成，则尚未启动的工作不得随后启动；已经跨过启动边界的运行按“本次继续”显示。成功、失败、重试及进程恢复路径都不能把用户已暂停的后续调度重新打开。

定义版本应与运行计数、最后状态等操作性更新分离，避免正常执行一次就让用户正在编辑的定义过期。真正的任务内容变化仍必须产生版本冲突，不能放弃并发校验。

### 6.2 默认执行策略

- **时间：**使用明确时区，默认沿用项目 Asia/Shanghai；展示未来几次安排。ERP 默认承诺“到点开始执行”，报告标明查询范围和数据截止时间，不承诺任务一定在该秒完成。跨时区及夏令时需补专门契约。
- **遗漏：**恢复和服务恢复后默认不堆积补跑过期日报；记录漏过或跳过原因。需要补日报时，用户明确指定日期单独运行。
- **重叠：**同一任务默认串行，上一轮未结束则跳过该次时点并留痕，不静默积压无限队列。手动运行遇到同一任务运行中应提示已有运行。
- **重复：**同一计划时点具有稳定发生标识；重复认领、网络重发和投递重试不能重复提交业务副作用。尽量复用现有幂等回执和 outbox，不承诺所有外部系统都提供恰好一次执行。
- **重试：**网络等可恢复错误做有限退避；权限撤销、资源失效等需要用户处理的错误展示原因并停止无效自动重试。外部写入结果未知时先查证回执，不盲目重做。投递重试不重新执行已完成的业务。
- **权限：**每次运行用固化授权范围与当前用户、组织权限及 ToolSpec/Policy 的交集；授权被撤销即拒绝，新增能力不能自动继承。定时任务不成为扩大 ERP 可见性或绕过工具执行链的入口。
- **上下文：**保存能独立执行的任务指令和资源引用，每次建立独立请求上下文，不把创建时的聊天对象或组织上下文存成全局请求状态。
- **费用和通知：**沿用单次预算、超时和通知基础能力，展示实际费用和异常原因。日报可每次通知，巡检可只在异常或状态变化时通知。
- **有效期：**长期报表默认持续有效，可选结束日期；短期巡检显式设置停止条件或有效期。任务无数据时返回“无数据”，不能生成看似正常的虚构报告。

### 6.3 成功必须有证据

工具执行成功、变更已提出、任务状态已提交，是不同事实。拟议回执应能表达操作目标、操作类型、实际阶段、提交后版本、下次时间和当前运行情况。

待确认时只能显示“待确认，任务尚未改变”；生效后才能显示“已暂停/已恢复”。响应中断且结果未知时查询同一操作回执，不猜测成功，也不创建另一条操作。聊天实时流、刷新后历史、任务面板和重放应呈现同一事实。

直接暂停仍需经过公共授权、原子提交、审计及幂等机制。不能冒用人工审批身份调用 confirm，也不能从聊天工具直接更新数据库以绕开统一路径。

## 7. 方案取舍与实施顺序

| 方向 | 收益 | 代价与判断 |
| --- | --- | --- |
| 仅修复变更卡和错误回话，保持全部确认 | 可以先消除“没有生效却说成功”，变更范围较小 | 暂停仍需额外确认，运行中仍不能暂停后续。适合作为当前缺陷修复，不足以完成整体体验目标。 |
| 按操作区分确认，统一提交与回执（推荐） | 暂停、恢复符合直觉；创建及权限、费用变化仍有明确审阅；可复用现有框架 | 需调整管理动作语义并打通调度状态、运行、恢复和回放的契约测试，不能只删掉确认按钮。 |

不建议为本问题先引入新的工作流平台或消息队列；当前已有数据库认领、ChangeSet、运行记录和 outbox，证据支持先补齐这些机制之间的契约。

建议按依赖分批，前一批验证后再继续：

1. **修复当前事实呈现缺陷：**让待确认提案完整进入聊天卡、持久化与重放，所有管理回复绑定真实回执。先保持现有审批语义，覆盖旧入口与统一执行链。
2. **实现经确认的暂停/恢复规则：**统一鉴权与提交，明确重复操作、过去的一次性任务、过期列表和版本冲突。同步动作副作用、缓存资格与回放契约，禁止旁路权限。
3. **实现运行中暂停及恢复保证：**分离调度与运行含义，检查启动边界、失败和超时恢复，保证任务完成后不会重新打开已暂停调度。需要迁移时先形成明确兼容与回滚设计。
4. **补齐任务中心体验：**完整创建/变更卡、真实试跑、运行与投递历史、停止当前运行；归档及历史保留另列迁移影响。完成后按 ERP 代表流程生产验收。

当前没有实施工期承诺；工期依赖第 2、3 批的兼容迁移设计和第 4 批选定范围。不应将后续生命周期改造包装成工具统一 07 的机械迁移，也不借此启动工具统一 08。

## 8. 实施后的验收场景（尚未执行）

| 场景 | 应验证的证据 |
| --- | --- |
| 暂停日报 | 聊天回执、任务列表、数据库调度状态和实际下一时点均一致；无隐藏待确认步骤 |
| 暂停重复提交、响应丢失 | 同一回执可查询或重放，没有重复变更，未知结果不报成功 |
| 暂停与启动同时发生 | 暂停先提交则不启动；已启动则明确“本次继续”，不能两种状态都声称 |
| 暂停运行中任务后完成、失败或进程恢复 | 所有结束及恢复路径均不重新开启后续调度 |
| 恢复跨过多个计划时点 | 只安排下一次未来运行；不自动补跑；过去的一次性任务要求明确处理 |
| 改内容与任务正常运行交错 | 无关运行状态不造成定义冲突；真实并发改定义仍被拦截 |
| 暂停时手动运行 | 产生独立运行，完成后仍暂停；不额外创建定时计划 |
| 重复触发与投递失败 | 业务副作用和扣费按实际契约去重；只重试投递时不重做 ERP 查询或写入 |
| 用户、组织、工具权限变化 | 无组织 ERP 可见性不扩大；跨用户拒绝；撤权后定时执行拒绝；内部工具不泄露 |
| 旧入口与新执行链 | 旧导入、合法参数、别名、ToolExecutor、Registry/Policy/Dispatcher、实时结果、历史回放一致 |
| 数据和预算异常 | 无数据、源失效、超时、预算耗尽有可核验状态，不能生成虚假成功日报 |
| 生产代表流程 | 创建次日 ERP 日报 → 立即运行一次 → 暂停 → 恢复 → 到点运行 → 核对历史和投递 |

## 9. 尚待确认和证据边界

推荐用户确认的产品取舍是：暂停及原定义恢复直接生效；暂停不自动中止本次；恢复默认不补跑；新建及涉及内容、授权、收件人或明显费用增加的修改确认一次。删除转归档与历史保留属于另一个范围选择。

外部证据是官方文档和指定版本源码阅读，未执行厂商内部系统测试；未确认其所有账号、地区、权限模式下的交互。上述是研究时的候选契约，当前实际实施范围见 [升级验收](SCHEDULED_TASK_UPGRADE_ACCEPTANCE.md)。本研究记录不改变生产任务状态，也不替代部署和用户验收。
