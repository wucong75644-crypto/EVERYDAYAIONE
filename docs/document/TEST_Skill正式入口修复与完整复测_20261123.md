# Skill 正式入口修复与完整复测

本记录补充此前内部 `_run_loop` 实验，验收以真实 HTTP/Actor 入口的记录为准。工作树 `20261121005427-skill-runtime-performance`，基座 `e084259011dbcbfec739dbc476510696bc0ba265`；本轮修改保留在本地，未提交、推送或部署。未连接生产数据库，未改变线上会话。

## 核对依据与职责

Grok Build 固定公开提交为 `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`，相关两批共 47 个文件已核对 Git blob 身份，详细来源见 [逐项源码对照](REVIEW_Grok源码与三个新问题逐项核对_20261122.md)。公开仓库是编码代理，不提供本项目的电商策划表、图片计费或全部生产实现；没有运行其 Rust 测试，不把阅读源码当作我们的业务验收。

| 链路 | 采用的成熟机制及项目职责 | 本轮核对/修复 |
|---|---|---|
| 手选 Skill | 选择、元数据、正文、资源逐级加载；已明确的手选不再增加模型选择回合 | 明确手选电商 Skill、带图并要求写方案时直接进入已有策划流程；其他编辑/无关用途继续原路由 |
| 关闭思考 | 供应商请求参数为实际边界，不能只隐藏页面思考块 | 主模型、策划子模型和空回复续接保留 disabled；不支持的配置不能静默切回开启 |
| 多套正文 | 模型负责内容，后台登记、原文投递和恢复 | 普通稿件保持整段原文与条目范围；原生策划 ready 后由后台发布已保存全文，不再多叫主模型保存或转述 |
| 按编号执行 | 模型表达选择；后台核验稳定身份、版本、原文、尺寸和素材 | 后续轮复用原生 plan_id/revision/item_id，不回到重新策划或通用 save_task_text |
| 追加素材 | 控制消息持久化，消费与模型收到输入分别验证 | 已消费文字原样进入策划快照并带事件来源；原有图片资源验证与引用授权保留 |

| 错误恢复 | 区分没有稿件、可修补稿件、供应商结果未知 | 空 JSON 不作为已有设计反复修补；有效设计仍限制修补范围，不扩大原尝试次数 |

补查了 [阿里云结构化输出官方文档](https://help.aliyun.com/zh/model-studio/qwen-structured-output)：JSON Object 模式只能约束合法 JSON，不能保证业务 Schema；多模态输入也不能直接假定严格 JSON Schema 有效。本轮没有未经支持就切 strict、移除图片输入、增加核验模型或放宽业务校验。此限制说明仍需处理格式失败，不能承诺千问每次首轮输出完整结构。

## 已验证的具体缺口

1. **写作目的被误识别为生图动作。** “写可以生图的提示词”等目的修饰被扫成执行授权；改为识别写作对象，保留独立正向生图动作。中性追加图片不撤销之前的“只写文字”。引用、否定、混合写作/执行均有反向测试。
2. **用户规格被模型建议覆盖。** 普通稿件登记时结构化 options、正文解析与用户规格合并顺序不正确；现在显式用户规格最后覆盖，正文原文不改。
3. **原生方案生成后仍让模型保存。** 修正 workflow 提示与工具边界；后台从 ready 行逐字投递全部 request_text。已消费的追加消息不再永久关闭这条投递路径。
4. **首次工作流与 Skill 组合投影不一致。** 首次进入时领域投影先存在、组合链接尚未同步，正式入口触发 `SKILL_COMPOSITION_WORKFLOW_INCONSISTENT`。现在通过原保存事务同步二者，尚未激活正文不授予领域工具权限。
5. **下一轮编号执行丢失原生计划。** 原生 ready 行没有被下一轮编排入口识别，主模型退到通用稿件目录；现在恢复稳定计划身份和条目目录，直接执行对应原稿。
6. **主模型收到追加，策划子模型却没收到。** 真实 wire 中主模型包含“浅米灰色”，策划各阶段输入原先不包含。现在复用已验证的当前任务 UserChanges，按事件去重、保留原文和来源，不伪造历史消息 ID。
7. **发布前的恢复检查点缺少完整回放状态。** 只有逻辑安全点未保存工具消息对和待发布正文。现在发布前用原检查点接口保存完整 payload；真实模拟 worker loss 后同 claim 恢复，主模型/子模型调用次数不增加。
8. **数组字段修补粒度错误。** fact_ids 内混入 null/数字等元素时，按元素索引生成补丁会产生移位/范围冲突。对类型化数组的元素校验错误按整个受影响字段修补，其余图片和字段仍受原范围校验保护。
9. **空回复续接重新开启思考。** 显式 disabled 被改为 None；续接保留原参数，并加入真正执行循环的回归。
10. **把空 JSON 当有效稿件保留。** 真实第三阶段连续返回 `[]`，后续分支仍要求“只修补包装、保留有效设计”。现在空数组、空对象和 null 不生成可修补稿件状态；保留已完成商品分析/视觉阶段，重新请求当前阶段完整对象。截断 JSON、已有设计和定点补丁仍保留原修复行为，最多三次不变。
11. **引用已生成图片后编辑丢失清晰度。** manual15 在真实页面引用契约下把 2K 成图作为附件，底图身份/比例正确，但 fresh inline draft 清理模型参数后只给 source=generated 继承规格，source=quoted 回落为 1K。现在经过原有引用任务/文件/所有权核验的 quoted 成图也从真实来源消息读取已确认档位；不从客户端声称的尺寸推断，不取消显式用户规格优先。回归覆盖跨自有会话引用、2K/4K继承、新指定1K优先、原任务不一致和既有跨用户/企业拒绝。
12. **底图/参考用途没有完整投影到供应商输入；商品保真仍未解决。** manual16 的编号、原文、素材和规格自动断言全部通过，但人工对照最后一张发现额外迁移了参考产品的搭扣，不能计效果成功。已保存材料角色中有“编辑底图”，供应商实际 prompt 却只有“输入图N对应用户图N”。已把真实目标和有限参考角色同步写入实际执行文本，原始用户指令保持原样。manual17 说明仅补用途文字仍不够，搭扣偏差再次出现。随后固定相同图片、要求、比例、分辨率，仅交换实际输入顺序并同步编号映射，底图首位的单变量供应商诊断未出现搭扣；但manual18完整复测中主体反而换成参考产品，否证了单图探针的稳定性。**已撤销这项未经稳定验证的顺序调整，最终保留原始传图顺序和明确用途说明。没有把提示词调整或单次诊断当作保真已修复。** 老受理任务及其恢复不重排、不重发。

第12项依据 [KIE Sunburst 实际接口](https://docs.kie.ai/43286923e0) 与 [OpenAI 编辑指南](https://developers.openai.com/api/docs/guides/image-prompting) 核对：该 KIE 接口通过有序 input_urls 和 prompt 描述编辑，不在本轮虚构不支持的 input_fidelity/mask 参数。明确要改什么、保留什么，是对既有角色信息的执行投影；不新增商品识别、审核或像素级强制锁定机制。

未新增通用调度器、审批步骤、商品专属硬编码、固定追问、质量审核模型或数据库迁移。

## 正式入口与测试边界

新增 opt-in `backend/tests/manual_skill_formal_entry.py`。请求从正式 `/conversations/{id}/messages/generate` 路由进入，实际经过队列登记、数据库领取、ConversationExecutionService、ChatGenerationExecutor、聊天准备/PromptBuilder、Skill、工具授权、原生策划、图片任务与结算。追加使用实际 WS handler 和控制消息存储，检查持久回执、已消费状态和真实模型 wire。

外层只注入测试身份、独有本地 PostgreSQL/Redis、模型凭据和事件采集。数据库使用真实迁移函数和应用角色，TCP 关闭；没有生产数据库。模型与 KIE/OSS 为真实调用，图片确实生成下载。HTTP 使用 ASGI 客户端，不是线上浏览器实操；页面部分使用该链路的真实脱敏事件进入前端投影、store、实际组件渲染和刷新测试。不能表述为整站浏览器 E2E 全覆盖。

完整场景依次为：

1. 手选“电商主图策划与生成”，上传原始失败商品图，要求三套完整方案、只写文字、16:9/2K；真实模型运行时追加图片和“全部浅米灰背景”。
2. 确认后台 native ready、三条完整原文已投递、写作时零图片任务；在发布前注入 worker loss，用同 claim 恢复，不新增模型调用。
3. 请求“第一个和第三个帮我做成图片”，近似 1920×1080；精确核对两条执行原文、计划条目、原图 SHA 和原生 16:9/2K。
4. 用已有页面图片引用契约明确选定其中一张，改浅蓝；接着对单张新结果改浅灰。核对两轮真实底图 SHA、素材来源、尺寸、完成和单次结算。
5. 新对话上传原始方图+竖图，原样重放“参考图一的产品里面的波点。给图二的产品加上一些波点”；核对参考顺序、图二作为底图、3:4/1K和真实输出。

两张并列输出后的“刚才那张”没有唯一对象。此前 manual11 模型选第一张，测试却假定最后生成的一张，因而 SHA 断言失败。该失败保留，不新增后台猜图规则；后续使用已有图片引用明确对象，SHA 断言保留。单张结果后的隐式继续修改仍测试。
