## 1. 范围与版本

2026-09-12，沿用 `codex/task/20260911215117-tool-unification-07`，基准/生产为 `eeccf3bd9485f1e91d253fdacc2c3828700efdd6`。本轮为其上的未提交修复，实际文件由 [指纹](scheduled-task-content-evidence/source-checks.json) 固定；尚未提交部署、合并或关闭，不进入 08。

用户截图请求：“创建一个定时任务，查询昨天的付款订单数按照平台划分”。生产只读确认：任务 prompt 保存整段原话；创建 ChangeSet 来自聊天表单提交；原 form 的 prompt 是 hidden，频率和时间默认值均为空。每天 08:00 来自后续表单提交，不是此请求自动补出的默认值。本轮不修改原任务或其时间。

根因：严格解析得到业务内容后，`parse_task_request` 为保护原话中的范围信息，强制覆盖 `prompt = text.strip()`；补全表单又隐藏已解析字段，用户只填写时间，看不到被覆盖的执行内容。旧测试直接断言完整原话等于 prompt，固化了错误行为。原话应当作为事实依据，不能整体当成每次运行的指令。

本轮仅修改严格创建解析、其内容提取辅助模块、聊天补全表单和必要测试。旧 `parse_task_nl` 预填 API、工具名/schema/别名、授权快照、ChangeSet/Planner/任务提交与执行链保持。没有新迁移、调度/暂停/领取/通知行为变化或 ERP/文件/沙盒/媒体内核重写。

## 4. 问题清单与复验

| 问题 | 原因与处理 | 复验 |
|---|---|---|
| ST-11 整段创建话术成为运行指令 | 移除原文强制覆盖。模型划分原文的 request/execution/schedule/delivery 片段；辅助模块核验来源、重叠、移除依据，执行内容仍从原文取出 | 原现象、自由改写成所有店铺、业务筛选/口径/日期/分组、纯时间/缺信息 |
| ST-12 执行内容在补全表单中不可见 | 创建补全表单始终显示可编辑执行内容；原文放说明中。无法整理时留空并要求补充，不再把原操作话术预填成可运行内容 | 后端 JSON 与前端刷新/提交事件对照，解析失败时保留说明原文而执行内容为空 |
| ST-13 模型片段遗漏/错分输出要求 | 片段必须能在源文定位且不重叠；忽略分隔标点移动，按源位置恢复顺序；遗漏文字默认保留。通知片段夹带输出要求时仅移出经过核验的发送尾句 | 真实模型曾遗漏“以表格显示”、错序每周安排、遗漏时间后的“执行”；均补定向回归并复验 |

不会把模型输出的同一句业务要求自由换成“所有店铺/所有订单”。未知或不可靠的管理信息划分仍可能需要用户补充；这是显式补全，不会自动使用整个原话继续创建。现有任务的旧 prompt 不自动重写。

## 6. 结论与交接

本轮本地技术复验完成，尚未部署，用户验收未关闭。最终生产版本须由之后的受控发布回执确定，不能把 eeccf3bd 的发布当成本轮修复已上线。

`parse_task_request(create)` 内部增加模型 `request_parts`，只用于原文事实提取，不透出工具 schema 或面板 API；最终仍输出原 `changes/missing_fields/recipient`。`update` 和旧 `parse_task_nl` 不使用此提取机制。辅助模块只有调用局部变量，不依赖 Registry/Handler、不引入循环导入或全局请求状态。严格解析输出上限调整为 1200 token，以容纳源片段；旧解析仍为 300，不增加模型调用次数。

剩余 legacy 是原业务/兼容适配，不是新策略或权限路径。回退本轮代码无需数据库回退，但会重新出现整段原话被保存及补全表单隐藏执行内容的问题。旧消息继续兼容读取；不迁移历史 form 或任务数据。01–07 验收链仍由 [共同交接](TOOL_UNIFICATION_HANDOFF.md) 追溯，08 不启动。
