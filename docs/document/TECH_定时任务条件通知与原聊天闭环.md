# 定时任务条件通知与原聊天闭环

状态：2026-10-12 本地实现与定向验证，尚未部署或进行真实模型／平台连续验收。既有持续任务基础能力的生产验收记录见 `TECH_Agent持续任务与自动化闭环.md`；本文件是其后续增量，不把早期“尚未实现”记录当成当前代码状态。

## 1. 范围和兼容

复用现有聊天工具、确认表单、ChangeSet、Skill 固定版本、ScheduledTaskAgent、cron 调度器、scheduled_task_runs、scheduled_task_deliveries 和 messages。无新增调度服务、模型供应商或通知存储系统。

- 旧任务默认 `notification_policy={"mode":"always"}`，不自动迁移收件人、频率或原聊天。未关联原聊天的普通旧任务仍走原消息保存和在线投递路径。
- 新聊天表单创建时，WS 从经校验的表单所属 conversation_id 注入来源。REST 聊天引用入口也从已经验证的 conversation_id 关联。ToolSpec 不允许模型填写用户 ID、聊天 ID 或执行权限。
- 更新未传字段保留；修改原任务，不删除重建。Skill 发布和任务确认沿用现有流程，较高频率的预算／风险确认保持原规则。
- 独立任务面板创建不猜来源聊天；新式条件任务未关联来源时，网页接收人仍使用其现有默认对话。给同事的投递写入同事自己的对话；任务创建者的结果副本保存到原聊天，即使另设企微／同事等投递目标，也保留这个副本。

## 2. 配置和调用链

`manage_scheduled_task.definition` 增加：

- `schedule_type=interval` 和 `interval_minutes`，服务端转换为现有 `schedule_type=cron`，保存 interval_minutes 便于显示和编辑。支持整除60的分钟间隔，以及整除24的小时间隔，例如30、60、120、360分钟；按任务时区整点对齐。90分钟、5小时等不会伪装成均匀间隔，返回明确校验错误。未新增固定时长计时调度器。
- `notification_policy.mode=always|conditional`。conditional 使用一个数值指标 `metric`，判断 `value|delta|percent >= threshold`。增长量／率必须提供 window_minutes；百分比以100为100%。已知执行间隔时，窗口必须为执行间隔的整数倍。
- `repeat_increment` 可选，指较上一次通知入队时原始指标增加多少，必须大于0；`cooldown_minutes` 只是附加最短间隔，不能单独导致重复提醒。

聊天模型直接整理参数，面板 AI 填写复用同一 schema 校验。聊天确认表单和面板使用正常的选择／数字字段，不要求用户编辑 JSON。ChangeSet 卡片显示通知条件、频率、原聊天关联及下一次执行时间。分钟间隔不会要求填写每天执行时间。

流程：聊天需求 → 现有确认表单 → ChangeSet 规划／权限／试跑 → 确认生效 → 现有扫描器领取不可变配置 → Skill／工具采集 → 服务端判断 → 原子保存执行结果、通知预留状态和 Outbox → 现有 Worker 投递 → 原聊天持久消息及网页在线提示。

## 3. 数据和判断

条件任务的系统提示要求最终报告附一个 `task_observations` JSON 数据块，每次最多100个对象：platform、稳定 entity_id、title、url、含时区的 collected_at、数值 metrics。Agent 提取后移除数据块，文字报告仍用于执行历史。平台别名统一，实体标识去除首尾空格。系统只接收本次运行时间范围内的采集值；缺失、缩写、布尔、负数、NaN／Infinity 不转换为零。

这是模型采集结果的数据契约，不是任意代码或发送指令。模型必须依据实际工具结果填写；服务端结构校验不能独立证明上游数据真实。条件任务完整试跑还检查有效结构化指标，不能仅靠能力范围检查冒充采集成功。正式执行缺少有效数据时记录“数据不完整”，静默且不覆盖有效历史。

每次有效观察保存到 scheduled_task_runs.observations，比较不依赖文字摘要或 Skill 自行维护的 CSV。先读取最近记录，再定向读取比较窗口附近的记录，避免一分钟任务无法访问一周前的基线。每个查询最多1000次运行；缺少合适基线时不估算。

- 首次遇到对象只建立基线，包括绝对数值条件。
- 增长比较只选择窗口目标时刻之前最近的有效样本，最多容许窗口20%的向前偏差（至少1分钟），不会把半小时数据称作一小时增长。
- 零基线的百分比不可判断；口径／数值缺失不计算。
- 未达标静默；持续相同触发去重。回落后重新达标且原始指标发生变化可再次提醒；另设 repeat_increment 可在持续达标时按新增量再次提醒。
- 按任务、规则签名、平台、实体区分状态。规则明确修改后重新建立通知判断身份。每任务最多保存5000个通知实体状态；超出时新实体不发猜测通知，执行历史记录不完整，需缩小任务范围。

通知正文由程序按本次真实命中的对象生成，只包含命中对象的标题、链接、采集时间、指标和判断值，避免把未达标对象随整份报告一起提醒。完整运行报告保存在 scheduled_task_runs.result_text，在任务执行历史中可展开查看；静默不会把报告发进聊天。

## 4. 原子性、重试与权限

迁移295增加任务来源／规则／间隔／通知状态和运行观察／判断字段。扩展现有配置快照及 ChangeSet 提交函数，确保领取后读取的是确认版本；notification_state 是运行状态，不改变任务定义 revision 或 config_revision。

`complete_scheduled_task_success` 继续承担成功事务：执行结果、观察、通知状态和结果 Outbox 同时提交。每个任务沿用现有单个运行领取机制；丢失领取权的旧运行不能覆盖状态或创建第二批队列。

去重状态明确是“已经为通知入队预留”，不是“用户收到”。预留阻止后续相同任务重新排队，尚未投递的原队列沿用租约和失败退避重试。重试耗尽后保留失败记录，不冒充已送达；不会通过重复运行 Agent 来重复计费发送相同通知。

Web 投递复用 ScheduledTaskDeliveryWorker，新增 `save_scheduled_web_delivery`：

1. 校验投递租约、目标组织、用户、对话归属和成员仍有效。
2. 使用 delivery UUID 作为固定 message UUID，原子插入既有 messages 并更新对话预览／计数和 run.result_message_id。
3. 插入后进程中断，后续同租约／重新领取的重试只返回 existing，不重复创建消息。
4. 原聊天被删除、归属变动或成员无权时保留失败并重试，不回退到其他聊天。
5. 持久保存后才确认队列；在线 WebSocket 通过现有 Redis 跨进程发布 conversation_updated、scheduled_task_result。前端刷新原聊天并给出有固定消息键的 toast。

网页离线不影响已保存消息。实时提示本身不持久化，也没有新增已读回执。历史中的“通知已投递”对网页表示消息已保存，绝不等同于用户已读。

## 5. 历史、发布与回滚

现有执行历史区分首次基线、未达条件、重复命中、数据不完整、达到条件；原有 push_status 继续显示排队、重试、投递失败或已投递。普通旧任务的“无企微投递”语义保留。

发布通过 release.sh 的迁移入口。295加入既有定时任务排空切换清单：等待已开始任务完成，在任务写锁内停止旧进程，再应用迁移并重启后端、企微 Worker 等既有服务。不得在任务运行中直接改快照函数。

回滚前暂停条件任务和绑定原聊天的新任务、排空 Web 队列。rollback/295 会拒绝仍有待处理 Web 投递或活跃新式任务的回滚；恢复旧成功 RPC，保留新增列、历史及持久消息以便恢复。功能回滚意味着暂停这些新任务，不能声称旧代码仍具备新通知能力。

## 6. 验证和剩余验收

定向测试包括规则连续采样、窗口缺失、零基线、无效指标、冷却与再次增长、实际 cron、聊天表单参数、组织和对话权限、旧任务投递、真实 PostgreSQL 配置快照／状态事务／消息重复重试、前端表单与通知展示。实际生产模型是否按结构化契约采集、平台持续运行和网页在线／离线交付，需部署后进行业务验收。

上线验收序列：创建全新原聊天监测任务 → 首次基线静默 → 未达标静默 → 达标后原聊天出现消息 → 同值重复运行无第二条 → 新增长按规则再提醒 → 离线后重开仍能看到 → 暂停任务。只使用授权查询工具，不向外部平台发帖、点赞或评论。
