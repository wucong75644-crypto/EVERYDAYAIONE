# 三项发布阻断的官方设计对照与建议

日期：2026-11-26。研究对象为任务提交ab38d5b03d592b4c3eb8bf601a27cba60f17f98a。仅调研和方案，没有修改业务代码或重新部署。上次发布在本地测试阶段停止，未同步生产代码、执行384迁移或重启服务。

## 结论及证据边界

建议保持现有轮次目录与统一编辑参数，修补版本边界、规范化规则及测试夹具。官方公开资料支持“可理解的选择引用＋持久对象身份＋宿主验证”“用结构减少非法组合”“按合同和实际工具轨迹验证”，不支持把所有参数错误悄悄修成可执行请求。不能由这些文档推出ChatGPT、Claude或Grok线上私有聊天后台与我们采用同一字段或算法。

此前“真实ID更稳定”的说法应明确适用层：持久身份与跨轮引用需要稳定ID；让模型抄写长UUID未必比局部短引用准确。短引用必须有当前输入版本内的映射，不能跨轮独立当身份。真实消息ID通常不是密钥；禁止把签名引用、后台证明摘要和权限决定混入模型选择参数。

## 1. 图片引用：明确模型选择与持久身份

### 官方依据

- [Anthropic：Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)：强调返回高相关信息、使用有意义名称，指出UUID等晦涩标识不利于模型检索，语义标签或从0开始的编号在其评估中改善准确性。这是特定评估结论，不是所有模型与任务的普遍保证。
- [OpenAI：Multi-turn image generation](https://developers.openai.com/api/docs/guides/image-generation)：公开支持携带图片生成输出或image ID，以及previous_response_id承接多轮。证明需要明确的历史对象关联，不证明模型必须直接填写数据库UUID。
- [Google ADK：Artifacts](https://google.github.io/adk-docs/artifacts/)：用作用域内filename和version保存/读取资料，区分session/user归属。模型可从目录选择加载，而后端服务解析实际内容。不能把默认加载最新版本当作精确重做的版本策略。
- [Grok Build image_edit源码（固定2bdd1d6a）](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/image_edit/mod.rs#L168)：解析[Image #N]，宿主在本消息AttachedImages注册表解析到真实引用；越界返回错误和可选项，未绑定历史token不自动落到当前另一张图。其测试覆盖删除附件后编号不连续的情况，按编号而非数组位置查找。该固定版本明确不支持跨轮附件token，不能照搬这项限制到我们的历史选图能力。重新下载的源文件SHA256为58a1b1f54abaaafeb759b56d4d7af88a8679de4ed6ae12f2d733b0d4d6e5df98，与旧捕获仅多一个末尾空行的差异。

### 我们的实际失败

workflow.py:209无条件把image_targets中真实message_id/index加入image_target_references，包括旧目录路径。test_canvas_material_handoff.py:149原来要求旧路由请求不包含真实消息ID，模拟路由因此抛AssertionError；classify_workflow捕获后返回unavailable，测试随后访问request_context才出现KeyError。

这是旧输入合同被改变，不等于真实供应商调用失败或签名密钥泄露。不能只删除“ID不可见”断言掩盖版本边界不清。

### 建议

本次最小修复维持已有两条版本合同：旧检查点使用material:n/result:n短引用，映射保留宿主，不额外重复暴露message_id；catalog_version=2保留已确认的真实消息ID＋content_index，路由和纠正工具使用同一合同，目录保留轮次、名称、来源与用途。不要为修这一个旧路径测试再引入第三种公共编辑参数。

两条路径进入后台后统一为真实对象引用，核对可见范围、租户/会话权限、输入版本及对象是否存在；不默认最后一张图，不从旧编号猜历史图片。未来如需给新工具增加短别名，应有输入快照限定的映射和真实模型对照评估，不能宣称一定优于当前UUID方案，本次不扩大范围。

验证旧路径输入仅有短引用且宿主正确还原、新路径UUID/index与轮次来源一致；再测越界、附件删除导致编号不连续、多图及明确历史引用、过期输入与非法跨会话引用均不派发。

## 2. 路由参数：限制非法组合，区分归一与业务纠错

### 官方依据

- [OpenAI Function calling最佳实践](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)：建议用enum和对象结构减少非法状态，宿主已知的参数尽可能由代码承担。这支持减少无关参数，不等于允许替模型更换业务目标。
- [Gemini Function calling最佳实践](https://ai.google.dev/gemini-api/docs/function-calling#best-practices)：明确要求执行前验证调用、强类型及错误处理。
- [OpenAI Agents SDK错误处理](https://openai.github.io/openai-agents-python/tools/#handling-errors-in-function-tools)：可将工具失败作为结果返回模型纠错，也可选择抛异常。不能说厂商惯例是所有错误都吞掉或所有错误都结束整个对话。

### 我们的实际失败

test_ecommerce_recovery.py:222输入ordinary_image＋write_then_submit_images＋retry/reuse=2，旧预期unavailable。当前classify_workflow把普通图片写作的策划专用mode/reuse归一为new/0，因此返回ordinary_image。是行为合同变化，不是外部调用或数据库失败。

### 建议

保留普通图片与策划复用的职责区分：普通图片分支不依据策划器的retry/reuse恢复旧任务；对已知普通分支的无关策划控制字段只做明确、有记录的new/0归一。记录原始结构化选择与规范化结果，便于解释模型看见什么、填写什么、后台改了什么。

修改工具说明/可表达的分支结构，减少模型同时填写互相矛盾控制字段；按供应商支持程度使用不同分支的参数对象，旧检查点仍能完成。不能依靠用户话术关键词选择分支。

目标ID、保存稿版本、批准条件、画布和供应商重试身份不属于这种归一。错误ID、缺失目标、歧义、修改冻结稿规格、冒用批准必须在业务派发前拒绝并返回字段路径/错误码/正确填法。供应商重试继续沿用实际回执与幂等账本，不能因mode归一变成再次收费。

相应测试应检查新/0归一结果且没有获得旧任务恢复授权；原来的非法类型、额外字段、策划new＋reuse冲突拒绝测试保留。补充错误目标不能归一成当前目标、失败后0派发及可纠正再提交路径。不能只把expected改成ordinary_image就结束。

## 3. 启动测试：补齐上下文读取合同，保持缺失即停止

### 官方依据

[Google ADK评估准则](https://google.github.io/adk-docs/evaluate/criteria/)区分工具轨迹的EXACT、IN_ORDER、ANY_ORDER，以及最终回复/多轮任务成功评估。严格模式用于必须遵循的调用路径，灵活匹配用于允许多种实现路径的场景。它支持按合同选择测试强度，不支持为通过而把严格模拟改成“所有未知接口都成功”。

没有厂商文档能直接规定我们的read_agent_request_context RPC应如何实现；下面是结合我们Actor、输入版本及隔离PG机制的工程建议，不冒充厂商私有实现。

### 我们的实际失败

executor.py:107新模型驱动任务并行读取followup、working_plan_candidates和request_context，并校验上下文version及input_message_id。test_task_execution_bootstrap.py:137的模拟只认识前两者，第三个新接口进入旧assert，尚未运行到实际数据库返回校验。此证据说明夹具未同步，不能据此删除生产中的新读取或跳过可信输入校验。

### 建议

给启动夹具明确添加read_agent_request_context分支，返回与当前任务/输入一致的真实合同；未知接口继续立即失败。旧检查点、旧模式、关闭新入口时继续验证原来的读取路径和恢复策略。

补充新上下文缺失、接口失败、版本无效、输入消息不符时不派发；有效上下文进入模型消息；旧检查点恢复不被当前开关改写。与隔离PG中的真实函数、租约/权限/轮次及HTTP Actor实验共同验证，不能仅用成功Mock证明SQL可用。模型路径存在多种合法顺序时评估关键行为，身份、权限和版本等确定性合同继续严格断言。

## 实施与验收建议

先修第一处版本投影；明确第二处普通/策划分支的归一边界并同步正反测试；补第三处启动夹具和失败用例。优先执行这三个原失败文件及现有目标/目录/编辑合同回归，随后重新走发布入口完整测试。目标、保存、批准、版本及幂等不以“少报错”为理由放宽。

真实客户补测至少覆盖A保存→B讨论→确认B、明确历史A重做、A生成结果回显；核对模型原始请求、工具调用、对象ID、原生受理和实际图片块。供应商未执行的任务只记受理通过。最终测试/构建和发布检查全过后才能声称已上线，不复用ab38d5b0的旧检查放行新代码。
