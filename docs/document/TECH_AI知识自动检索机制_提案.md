# 个人知识库 AI 主分支、自动检索与经验沉淀方案

日期：2026-10-25。状态：用户已授权在深入源码调研后实施；任务工作树已进入实现与验证。本文保留总体设计与质量目标，实际落地机制、验证和未完成的线上验收以[源码对照及实施记录](./TECH_AI主分支_源码对照与实施.md)为准。未部署、未写入或清理生产知识数据。
依据：[生产只读核查](./PROD_知识库只读核查与方案修订.md)；成功生产基线`2a82500a`。此前ea97ae93主线方案已归为[历史记录](./TECH_AI知识自动检索机制_历史主线提案.md)，不继续作为实施清单。

## 1. 推荐结论

按用户最新明确要求：**不新建知识库、不增加独立容器、不另做隐藏经验库。只在当前用户现有个人知识库内创建一个顶层主分支「AI 工作记录与使用习惯」**，下设使用习惯、工作方法、工作情况。它就是普通知识画布中的主题树，用户可以查看、改名、编辑、移动和删除。

```text
现有个人知识库
├── 用户原有主分支（保留）
└── AI 工作记录与使用习惯
    ├── 使用习惯：表达偏好、常用格式、明确的做事要求
    ├── 工作方法：适用条件、操作步骤、验证结果、失败解决办法
    └── 工作情况：重要任务进展、结果、待办和阻塞
```

主分支显示名称只是建议，稳定对象ID用于定位，用户改名不失联。AI根据任务按需读取这些内容，工作后自动整理、补充和更新；不要求用户逐次@该分支或逐条批准常规记录。

改进生产已经存在的自动知识链路，不再另建一套自动接入、索引和派生系统。把自动检索单独设计为“任务知识决策＋任务范围选择＋证据充分性控制”，复用既有搜索和读取工具；先以金标评测找出误查/漏查/错范围，再校准具体参数。

旧库里有价值且能确认归属的经验，经整理迁入这个主分支；以后新增经验也在这里沉淀，替代旧knowledge_nodes的经验记录职责。旧指标、评分审计继续作为后台运行数据保存，不变成知识节点；模型参数以配置为准。迁移完成并验证新闭环后才退出旧经验生产者/工具，最后考虑物理退役。不将全局或归属不明的旧经验批量复制给每个用户。

官方公开做法可用来选择机制，不能保证复制任何厂商的准确率；详见[研究中的官方来源](./RESEARCH_知识库现状与检索机制.md)。本项目是否精准，以自己的业务保留集、真实提供商运行和人工核验为准。

## 2. 生产已有能力与只需增量建设的部分

| 已有，保留 | 下一步补充/修正 |
|---|---|
| 默认可见根自动快照、显式@、实时RLS | 默认全部可见根改为可信任务范围；根发现与正文检索分开 |
| source/manual/material/rollup派生表示、向量、worker | 统一证据类型与索引/覆盖状态，避免再建chunk表和worker |

| 简单问句程序预检索、复杂任务工具循环 | 两路共用充分性检查；修正简单词法阈值直接决定answer/missing的风险 |
| 规则随read返回、来源URL规范化 | 必要规则读全、例外/冲突识别、执行前条件和逐事实依据 |
| 预算、重复/空搜停止、checkpoint | 区分“没有新增候选”和“已有候选还没核验完整”；统一跨路径预算与观测 |
| 图片/视频提取、历史版本和文件授权 | 严格保留partial，按实际页/时间范围说明覆盖，不宣称全量理解 |

当前可见29项、163块，足以先在现有PostgreSQL和派生表示上优化。没有立即上新向量数据库、外部搜索集群或新增收费重排服务的规模依据。

## 3. 独立机制：何时查、查哪里、查到什么才可以工作

### 3.1 第一层：任务知识依赖

引入结构化KnowledgeDecision，服务端持久保存而不是只写一句提示词：

```text
mode = none | required | optional | clarify
reason = explicit_reference | internal_fact | applicable_rule |
         source_transform | generic_task | ambiguous_entity
evidence_needs = [{id, question, entities, must_resolve, source_type}]
coverage_goal = relevant | exhaustive
selected_scope = server-owned scope binding
```

确定的规则由服务端处理：显式@保留指定范围；“只根据这段话”限制来源；通道身份不能取得私人范围。涉及语义的任务由模型结合当前问题、必要指代与有限可见目录判断；使用现有ModelGateway，模型与是否独立前置调用通过对照评测决定，不默认每条消息加收费分类调用。

具体行为：

| 请求 | 推荐行为 |
|---|---|
| 普通润色、翻译、闲聊 | 可应用本轮已校验的简短使用习惯；不为此搜全库或建立所有空间全量快照 |
| 按我司规范改写、给本商品写卖点 | 自动查适用规则/参数，不要求用户说“查库” |
| 按售后规则判断订单 | 政策来自知识库，订单实际情况来自ERP，分别有依据 |
| 查今天销售额 | 数值来自ERP；如依赖公司统计口径，则先取该口径，不能用文档旧数值回答 |
| 总结整个@框架 | exhaustive，遍历分页与必要正文，缺失明确标记 |
| 当前信息足以回答的纯资料变换 | 使用已提供信息；不能把“无需检索”解释为“无需遵守明确的品牌/规则要求” |

程序分类失败不是none。主模型后续发现缺口可升级为需要知识；不得因前置判断漏查永久禁用搜索。知识依赖不足时允许给出不依赖该证据的部分结果，但不能把整项任务标记完成。

### 3.2 第二层：任务范围选择

生产当前无@会取得RLS可见的全部容器；这保证权限上界，却没有解决项目相关性。

推荐的默认行为：

1. 显式@或明确“仅根据某项目”是本轮内容边界，不悄悄扩展到其他项目。
2. 已验证的任务绑定/本轮延续根优先；浏览器画布选中态不能私自作为聊天事实。
3. 用户明确命名项目/商品且可唯一定位时，自动选择匹配范围，无需用户逐节点操作。
4. 没有明确项目时，只在当前身份和组织内对可见根标题/简介做有界候选发现，再进入选中的正文范围；同名商品/多个同等可能项目时才追问。
5. 与任务有关的个人/团队知识可以自动使用；不默认遍历所有项目正文。用户明确跨项目对比时允许本次多根。

AI主分支的读取按内容用途拆开：与当前任务相关的稳定使用习惯进入有限上下文；工作方法按任务检索；工作情况仅在接续任务、追问进展或相关待办时读取。不能每次加载整棵AI工作记录。用户明确“只用这段资料”时不增加外部业务事实；已确认的格式偏好不扩大资料范围，当前用户指令优先。

根发现先于正文快照。可信scope binding记录explicit/automatic来源、根ID、选择原因码、输入与执行身份；用户knowledge_refs不被伪造或覆盖。模型候选不是授权，仍需服务器核验/RLS。

保留同轮版本一致性：先选根再冻结；重试/恢复沿用原选择与版本并重新鉴权，新消息取得最新保存内容。先支持真实引用链的受控扩展；任意新增项目若发生在读取后，不能把旧快照和新时刻资料混成同一份依据，首版应明确缺口/开启新尝试并重读。

### 3.3 第三层：查询与阅读

基于现有query/route/evidence完善QueryPlan：原问题、必要指代、主体/SKU、平台、时间、证据子问题、已确认范围。改写时不能丢掉否定、型号或条件。

三条召回通道在相同授权/快照下执行：精确型号/短语、中文关键词、语义匹配。先利用已有jieba、标题/路径和向量；用统一候选结构保留各通道原分数，再比较当前加权方案与RRF融合。不要把ts_rank_cd叫BM25，也不要先引入新服务再找收益。

已有工具搜索、画布搜索、程序快答的语义阈值/排序不同，应统一到共享的检索服务或至少统一契约与可观测配置。不同来源重复块去重按版本/位置/引用关系，不把相似但冲突的条款合并覆盖。

排序考虑实体、范围、原始来源、上下文和来源多样性；0.55/0.62等当前阈值是生产参数，不是正确率。以业务评测重新校准。只有候选歧义或复杂任务需要重排；是否新增模型由消融收益和延迟/费用决定。

source/manual用于最终事实核验；material/rollup可用于定位和概览，但不能成为不可追溯的权威。人工存储保护不代表业务优先级。source/manual相互冲突时同样应报告。

### 3.4 第四层：证据充分性

每个must_resolve项记录unresolved/resolved/conflict/unavailable，关联本次真实读取的源版本与位置。三种状态分开：处理ready、读取complete、回答依据sufficient。

例如“能否退货”不是搜到含“退货”的一句话就结束，至少要确认商品/订单身份、适用政策、时间条件、例外，以及必要事实。服务端检查来源/版本/规则读取完整；模型检查语义支持、例外与冲突，并用人工金标校准。

沿用适用规则解析，不让top-K把祖先/局部必读rule排掉。规则超长时分页补读，未读全的required任务不能进入依赖它的执行。业务规则不能解锁文件、工具或外发权限。

优先补查最小缺口：读原文/同章条件→换词/拆子问题→授权范围内扩一级→说明不足。已有候选未读时不因“没有新命中”停止核验；反复同问同范围无新证据也不能无限搜索。

停止原因统一为sufficient、no_match、conflict、ambiguous_scope、source_partial、permission_revoked、service_error、budget_exhausted、no_progress。语义服务失败与无资料分开，不能吞成“没有答案”。

### 3.5 程序快答与执行保障

保留现有answer_plan的速度优势，但“候选少且规则未截断”只能作为快答候选，不能直接等于答案有据。加入必要证据项检查；快答和复杂工具路共用同一事实/规则账本。

现有mode=answer/missing会移除工具。改为只有证据充分且无需后续动作时进入最终合成；否则保留定向补查能力。missing必须解释为“当前范围当前问题缺资料”，不引入其他项目或旧历史数字。

required任务先显示读取进度，确定结论和有成本/副作用的动作等依据足够后执行；none任务保留即时流式响应。完成草稿核对关键事实和来源，不能只在最后附一个文档列表。语义核验有误差，仍要评测，不能承诺一个检查器证明全部事实正确。

知识口径传给ERP等子任务时使用受控evidence字段，保留来源与版本；同步修订“task只能复述用户原话”的旧策略。统计数值依然必须来自真实查询/计算。

历史工具正文、摘要、恢复checkpoint也要受新一轮当前权限约束；只禁止新读取而继续使用已撤权旧上下文不够。已有原件物化授权/清理保持，不宣称能撤回用户已经下载的副本。

## 4. AI 主分支的自动记录与更新闭环

### 4.1 内容与可靠性

| 内容 | 自动保存条件 | 后续怎样用 |
|---|---|---|
| 使用习惯 | 用户明确表达/纠正的偏好可直接更新；单次行为推测只记待验证，不自动变成永久偏好 | 只应用与本任务相关且仍有效的习惯；最新明确指令优先 |
| 工作方法 | 有可追溯执行结果/验证；仅“没有报错”不能证明业务结果正确 | 已验证方法按适用范围复用；待验证经验只作线索，不能当业务规则 |
| 工作情况 | 重要任务的真实创建、阶段变化、执行结果、阻塞/待办事件 | 按同一任务持续更新；不能把知识里的摘要当当前执行状态的唯一来源 |

方法条目包含问题类型、适用条件、步骤、验证依据、例外/失效条件、来源与更新时间；状态为待验证/已验证/已失效。状态和置信度不是命中次数推出来的，失败结果不能自动归因为“某模型不行”。自动生成内容默认使用document，不自动创建rule或升级为公司制度。

工作情况保存可复用的简要进展与结果，不保存整段对话、客户/订单明细、密钥或原始工具输出。详细日志仍在原审计链；生成记录只链接获准任务与源版本。成功必须取实际任务结果，暂停/取消/失败不能记成完成。

### 4.2 更新流程

```text
任务读取相关习惯/方法 → 执行与验证
  → 形成待沉淀候选（明确偏好、有效方法、重要任务事件）
  → 检查归属/权限/价值/重复/冲突
  → 定位AI主分支中的既有条目
  → 有同一条目则更新修订；没有则创建；证据不足标待验证
  → 通过既有受控命令保存 → 既有派生更新 → 下一轮按需读取
```

不每轮新增一篇文章，不记录没有新信息的闲聊。工作方法按问题/步骤及适用实体归并；工作情况按任务ID更新；使用习惯按偏好维度更新。语义相似只用于找候选，不能自动合并不同商品、企业、条件或相互矛盾的规则。

更新不覆盖用户人工修改：沿用expected_revision、版本和冲突处理；冲突后重新读当前内容，再做保留双方事实的合并，无法安全合并则保留待处理候选，不反复覆盖。用户可编辑/删除/停用记录；删除后保留“不因旧事件重放重新创建”的标记，未来新事实仍可正常记录。改名沿用对象ID，移动出受控子树后停止自动更新该条目，不自动搬回。

### 4.3 归属、授权和持久化

- 归属按真实actor与当前个人容器决定；不同用户、不同组织上下文不混用。组织管理员不因此看到私人分支；个人方法不自动成为团队知识。共享继续走既有明确授权。
- 首次需要记录时幂等创建主分支和三个子分支，复用已有个人空间，不增加容器。用服务端保留的分支定位元数据和稳定ID避免并发重复，名称不作为授权；新定位元数据不承载第二份知识正文。
- 只读知识工具保持只读。新增受限记录入口/服务，只能在该用户AI主分支子树写候选内容，继续检查真实身份、容器写权限、版本和命令幂等。不能为自动沉淀而给模型全知识库任意改写能力。
- 幂等关联actor/org、任务/输入/事件类型；事件提交后异步整理，不阻塞主回复。记录失败不改写任务成功状态；可重试、可观察，重放不重复写。只在源任务和身份仍有效时处理，不从已撤权资料提炼新的私人记录。
- 每个任务有记录长度、更新次数和整理预算；不因派生更新再次触发经验提取，避免自我总结循环和重复收费。复用现有后台任务框架，持久任务失败恢复，不在本轮创建定时自动化。
- 现有Mem0/个人记忆也是潜在习惯来源：本次不顺手重做或删除整个记忆系统。新分支内条目为本功能可见可编辑的内容真相；相同偏好避免同时注入两份，用户更新/删除不得被旧记忆覆盖。实施时盘点现有提取/注入点，用来源ID和当前分支修订做兼容，不建立无版本的双向同步。

### 4.4 旧经验迁入规则

先做可审阅迁移清单，按以下四类处理，而不是按旧置信度批量导入：

1. 可验证且能确定个人归属的方法/失败解决办法：整理到对应用户AI主分支，保留旧节点ID与验证来源，幂等导入。
2. 有用但不能验证的方法：迁入该用户待验证条目，不能作为已验证方法自动执行。
3. 全局、仅有org或归属不明的经验：留在只读归档/待分配清单，不分发到每个人私人分支；确认归属后才迁移。
4. 过期参数、重复节点、原始指标/评分：不迁成个人方法文章；必要参数以当前配置核验，历史指标/评分保留后台审计。

当前生产核查仅取得汇总，尚未逐条读取655条旧节点；因此不能给出已确认的可迁条数。实施前的逐条整理限于授权内容，不在日志中输出私人正文。旧经验写入的暂停与新受限沉淀入口启用协调进行，避免切换期间继续无界积累或丢失待记录事件。

## 5. 统一观测与评测

统一记录knowledge_run→decision→scope→search→read→assessment→answer/execution；包括程序预检索和模型工具两路。只记录原因码、源版本、阶段状态、耗时/费用与覆盖，不默认记录全文或模型隐藏思维链。

现在回执/工具审计/程序快答不是同一口径，不能相互替代。命中次数只记使用频率，不提高内容可靠性。

先建立约200个起始审核样例（不是统计充分性承诺）：该查/不该查、隐式规则、SKU、同义词、上下文、多项目、例外、冲突、缺资料、媒体partial、撤权、提示注入、整库任务。真实业务资料需脱敏和允许使用；调参与保留集分离。

分层测：触发召回/精确率、选根正确率、必要证据Recall@K/排序、规则/例外覆盖、答案正确与有据、引用、澄清/拒答、p50/p95延迟和每成功任务费用。主要模型和故障切换模型分开测，真实Web/Actor/WS端到端与mock分开报告。

建议起始质量目标仍为待确认：必查召回≥95%、触发精确率≥90%、必要证据Recall@10≥95%、引用准确≥98%；同时报告样本量和分组结果。已知越权、必要规则缺失却允许执行、伪造来源属于不可放行问题。延迟/费用上限先量基线，再由用户取舍，不编造毫秒SLA。

必须对照生产现有机制：当前完整管线→只调整范围→调整召回→加充分性补查；每次增加复杂度都报告净收益。当前小库不支持以大厂案例提升比例代替本项目验证。

增加AI主分支验收：首次/并发只建一棵主分支；无价值内容不写；同一事件重放不重复；明确偏好更新、待验证方法不冒充规则、失效方法不继续复用；重要任务状态与原任务一致；用户编辑/改名/移动/删除得到尊重；跨用户/组织不泄露；Mem0旧偏好不覆盖用户新修改；写入或派生失败不阻塞原任务；旧节点迁移可追溯、归属不明不误分配。验证“任务→记录→下次读取→更新”完整闭环，而不只测试保存成功。

## 8. 回滚与确认边界

自动范围/充分性改造用独立开关灰度；关闭新策略回到已有生产路径，保留显式@、资料和快照。运行中的required任务安全完成或明确停止，不静默忽略知识绑定；数据库新增字段采用兼容前向迁移。

旧指标始终独立保留；旧工具兼容回退不意味着重新启用所有自动提取和评分。物理清理前必须具备可恢复归档和明确授权。

关闭自动记录只停止新的候选处理，不删除个人AI主分支和用户编辑；已提交记录保留修订历史。暂停/恢复要保留事件幂等记录，不能因重放复建用户删除内容。旧库迁移按旧ID/目标ID/修订保留映射，失败可断点继续，不覆盖用户后续修改。

已确认的定位：现有个人知识库内一个AI主分支，存储使用习惯、工作方法、重要工作情况，AI自动按需读取和整理更新，用户可管理；不单独创建知识库。该定位不再作为待确认问题。

2026-10-25用户已授权深入参考开源源码并在无重大未决问题后实施，上述核心方向不再要求重复确认。生产部署、生产逐条迁移、物理删除仍需对应授权；本地代码和合成测试不代表已经完成生产验收，也不代表达到了第5节待校准的统计目标。
