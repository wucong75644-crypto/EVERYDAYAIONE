只对本版本新启动且冻结 `delivery_policy={version:1,retry_cost:platform}` 的页面运行启用。既有历史失败计划、聊天任务、Skill试运行不因部署自动复活或付费。原模型选择、用户原文、三份专业提示词、原图ID／角色／顺序、比例与清晰度均沿用；不增加隐式换模型、压缩或搜索。AI帮写仍是独立的人工核验草稿步骤，本批不将其改造成后台持久任务。

### 复用链路及状态

1. 原 `DetailPageWorker` 扫描当前项目run，继续调用原三阶段执行器。原单轮时限、每阶段最多3次及格式／事实校验保留；有效阶段和第三阶段局部草稿原样保存。
2. 新 `285_detail_page_delivery_recovery.sql` 只在 `ecom_image_plans` 增加 `delivery_recovery`，分别保存计划、图片受理及每个item的恢复作业。作业持有来源、稳定request_id、执行token、60秒租约、尝试次数、下次时间；5秒起指数退避，上限5分钟，后续轮次继续保留，不以次数耗尽向用户终结临时故障。
3. 计划只在失败且无有效租约时恢复；旧窗口及不确定usage归档并保留为未知，不伪造“上游明确未受理”。新窗口由平台承担潜在额外成本，从未完成阶段继续。服务停机取消对新页面策略记为可恢复中断，旧聊天取消语义保持。
4. 已保存完整提示词但受理失败，只清除对应受理错误并重试原 `accept_detail_page_group`，不重新调用模型。恢复包装函数复用原resume并在同一事务内校验token、租约、当前run和停止标志。
5. 图片只对最新且已结算为failed的item调用原 `ChatImageControls.replay`，产生新任务版本，继续原claim→dispatch→query／callback→落盘→publish结算链路。成功项不重生；图片任务回执丢失复用同一request_id。原图核验、价格、图片顺序及冻结请求完整性检查保留。
6. 已受理／结果未知的图片先查询和等待原结果，达到原不确定截止时间后按既有平台责任路径退款／结算，再创建新的尝试。已取得结果的下载／资产落库故障继续复用原结果，不重新生图；迟到旧回调不覆盖已结算结果。
7. 自动恢复的任务保持项目analyzing／generating，以便刷新、重新进入页面和Worker重启后继续。只扫描当前run；有界扫描轮转更新时间，避免长期恢复项目占满前20项，阻塞后来的任务。

### 结算及界面

- 复用现有积分账本和原子stage保存。新策略的失败／格式不合规文字尝试不扣用户积分，usage标记platform；有效阶段一、二先记pending_delivery，最终完整ready时一次结算三个有效阶段，幂等回执防止重复扣费。已保存有效阶段不再收费；原聊天／旧页面仍按原规则结算。
- 图片继续使用原失败退款／成功结算与不确定供应商成本记录。恢复不会修改原图或价格；价格变更要求用户重新确认，不静默接受新费率。
- 右侧复用原步骤动画、图片占位符、任务详情和下载。临时故障显示“自动恢复中／自动补图”，不让用户反复手动重启；硬性问题保留失败原因，重试才发现的原图／费用／积分／权限变化投影为可读原因，保持暂停。
- 增加“停止自动重试”及 `POST /detail-projects/{project_id}/stop-recovery`。只停止后续恢复，原先执行及已提交给供应商的任务继续结算；数据库project锁、token及插入触发器共同处理停止与重试竞争。自动恢复期间阻止重复手动生图入口。
