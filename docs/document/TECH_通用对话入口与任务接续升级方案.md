# 通用对话入口与任务接续升级方案

本方案覆盖首轮输入、运行中追加、跨轮组合任务和断线恢复。基线为任务分支 `c850060e`。在现有 Actor、权限策略、成果目录、原生任务与积分账本上实施。关联设计见 [通用对话执行架构](TECH_通用对话执行架构最终改进方案.md) 和 [多轮操作身份与交付闭环](TECH_多轮对话操作身份与交付闭环方案.md)。

## 已复现的问题

| 编号 | 场景与证据 | 结论 |
| --- | --- | --- |
| R1 | 新对话上传福字图并说「这个是图片。你用你写的提示词帮我生成新的图片」。用 `test_first_turn_reference_with_only_uploaded_image_asks_without_sampling_or_dispatch` 复现。模型调用 0，生图派发 0，输出与截图一致。常规首轮图生图和文生图此前在隔离 PostgreSQL 的两种角色下均通过。 | `content_tools.selects_previous_item` 将「你写的提示词」视作强制沿用原稿，`execution_engine` 在采样前直接返回。相同判断还会影响工具定义和后续调用校验。 |
| R2 | 对实际 `handleSubmit`、`sendSteer` 和 WebSocket 发送函数做隔离复现。文本为「等等，改白底」。连接打开时网络发送 1 次，断开时 0 次，两种情况下输入框都清空，均未转 HTTP。 | 当前本地事件被当成送达。断开时输入会丢，连接正常也没有普通追加要求的持久化回执。WS 服务端收到后已有持久化命令入口。 |
| R3 | 对实际重连恢复与任务对账函数注入同一对话的两个状态。视频已完成，前端仍显示待处理。同一对话没有活跃聊天时历史请求 1 次并更新，有另一个聊天在运行时历史请求和更新都为 0。 | 现有视频实时交付正常。漏掉完成事件时，视频没有图片的单条终态对账，整段刷新又被同对话里的活跃任务挡住。 |
| R4 | 直接运行实际意图函数。「把这份表做成 Excel」识别为文件交付，「把这份表整理成可下载的 Excel」未识别。「解释怎么算转化率，然后导出 Excel」未识别交付。「查近期的文具趋势，再生成一张图」未识别生图。 | 这是交付识别及后续保护的缺口。主模型仍可能主动调用工具，因此不能据此断言这些措辞每次都会失败。 |
| R5 | 直接运行知识库快答资格函数。「公司报销规则是什么？然后导出 Excel」在分层检索模式下仍满足快答资格，「公司报销规则是什么？再生成一张流程图」在两种模式下都满足。代码在快答实际进入 `answer` 或 `missing` 时会关闭普通工具。 | 在已启用相关知识上下文且确实走到快答时，复合任务可能只回答前半句。这次确认了路由条件和工具关闭分支，尚未跑带真实知识快照的线上组合任务。 |
| R6 | 既有线上第 4 条脚本验收中，一轮自然语言请求以「没有视频工具」结束，后台只有聊天任务。明确要求发现工具后，下一轮有真实工具定义，经纠错最终只受理、播放、结算一次。 | 接续后恢复已有发现已修通，首次需要工具时仍依赖模型主动发现。还有一条独立的能力边界，当前通用对话视频入口只接受文字脚本。 |

R2 和 R3 使用源码函数和受控传输或任务状态复现。R4 和 R5 为实际函数的输入输出对照。现有内容、执行收尾、批次恢复及 ERP 部分成功回归 130 项通过。同一代码基线下，定时任务提交、公开搜索适配与知识快答回归 72 项通过，前端提交与恢复回归 59 项通过。这些自动化结果与生产真实付费验证分别记录。

## 除生图以外需要覆盖的用法

| 使用场景 | 已有基础 | 本次需要验证或补齐 |
| --- | --- | --- |
| 上传 PDF、表格或多个附件，查内容、比较、整理成文件 | `file_analyze`、`file_search`、沙箱和文件成果登记 | 本轮附件的顺序和权限、两份同名表的指代、扫描件不可读时的提示。分析后导出可下载成品，部分文件无法读取时明确指出缺口。输出以文件成果为准。 |
| 搜索现行资料、查公司知识库，再汇总或生成文件 | 公开搜索、知识库检索、固定知识快照和来源引用 | 明确来源范围、时间范围和来源证据。内部资料查询与公开搜索分别按权限执行。只读快答有结果时继续完成已明确的后续交付。没有查到时说明来源范围。 |
| 首轮文字生视频、用历史脚本再做一条、用照片做视频 | 通用聊天的文字脚本视频链路、模型发现、KIE 受理与异步交付 | 文生视频验证首次自动获得工具，验证按原稿重做和只写脚本。照片转视频在当前聊天入口没有执行合同，需单独确认选用模型、素材限制、规格和价格，再纳入产品范围。 |
| 查订单、对比库存，再整理表格或修改业务记录 | ERP 读取工具、写入权限、原生回执和结果核验 | 读后导出可自动接续。提出修改时定位准确记录并保留既有权限或确认要求。部分完成时显示对应项，供应商返回不确定时核对原操作。 |
| 定时提醒、暂停或修改原定时任务 | 结构化任务定义、既有调度链路和操作身份 | 区分立即执行和未来安排，验证时区、接收渠道、一次性与周期、仅改一个字段、同名任务和回执恢复。 |
| 运行中临时插一句普通问题，随后回来继续 | Actor 支持持久化追加、串行及分支任务，原生派发前检查需求版本 | 提供可观察的输入归属。用户可以追加当前任务或发一条排队消息。清楚显示尚未送达、已收和已纳入，避免把无关问题当成原任务的修改。 |

## 分阶段实施

### 0 固定基线和验收样本

固定 R1 至 R6 的输入、附件及控制组。将截图原话、断开 WS、双任务并发、只读加导出写成自动回归。采集每次真实执行的输入消息、所选来源、操作、子任务、供应商回执和积分行的身份及数量。记录权限拒绝和未受理原因，日志使用内部标识和摘要。

### 1 统一本轮意图、来源和工具准备

- 修改 `backend/services/handlers/chat/content_tools.py` 中的来源和交付判断。采用同一轮事实表达，至少区分当前附件、明确历史引用、新稿、只读或只写，以及可独立执行的多个要求。文字匹配用于提供线索，已核验的来源、权限和用户授权用于决定能否执行。复合请求按要求分别判定。
- 修改 `backend/services/handlers/chat/execution_engine.py` 的首轮拦截、工具合同投影、保存与派发校验、交付检查。各阶段使用同一轮判定和输入版本。对明确的文件、视频等任务，在当前工具策略许可下准备所需定义。低置信时做一次有限发现，仍有歧义时只问影响结果的问题。
- 复用 `content_objects.py`、`inline_image_action.py`、`direct_loop.py` 的素材引用、原稿、版本、原生操作身份。单张可用图片加明确出图要求可以直接起稿。明确要求旧稿时只查对应版本。如果引用不唯一或素材确实不可用，询问具体来源。
- 修改 `backend/services/knowledge_workspace/answer_plan.py` 的快答资格与 `execution_engine.py` 的工具关闭条件。只读请求保留快答。复合交付可先完成受限检索，再带入该快照下的证据继续生成文件或图片。查不到来源时按任务依赖决定后续能否执行。
- 验收 R1、R4、R5、R6。至少包含截图原话、单图明确修改、纯文字创建、只发图、只写稿、缺失指定旧稿、搜索加生成、知识库加 Excel、首轮文字视频。明确旧稿或用户给定限制必须保留。一个可执行目标只创建一次相应业务操作。

### 2 让运行中追加有持久化确认

- 修改 `frontend/src/components/chat/input/useInputSubmission.ts`、`useInputTaskControls.ts`、`frontend/src/hooks/useWebSocket.ts`、`frontend/src/contexts/WebSocketContext.tsx`。发送前生成稳定的客户端请求标识。请求明确拒绝时，可在原输入上修正。未确认时保留同一条输入的待送达状态，重连核对或重发沿用同一标识。收到与标识一致的持久化回执再清空或确认草稿。
- 修改 `backend/api/routes/ws.py` 和 WebSocket 消息类型、构造器。复用 `services/conversation_command_store.py` 的去重入口，以当前用户、会话、目标任务与客户端标识绑定追加命令。持久化后返回确认。旧客户端继续走现有兼容路径，新客户端遇到旧服务端时可保留草稿并提示状态。需要带附件追加时，引用走现有鉴权的消息或素材持久化入口，命令仅承载核验后的引用。
- 保留 `task_execution/user_changes.py`、`requirement_changes.py` 和原生派发前版本检查。队列进入、原任务纳入变更、外部任务已受理分别记录。旧任务已经结束或追加带来的目标发生变化时明确返回归属结果。外部已经受理的工作以供应商结果或取消能力为准。
- 验收 R2，并覆盖已收但回执丢失、重连重发、收到后立即关页、原任务结束、运行中换原图、追加与派发同时发生。每条追加最多持久化一次，并验证已经受理的其他操作不受错误撤销或重复计费影响。

### 3 按子任务对账恢复交付

- 修改 `frontend/src/utils/taskRestoration.ts`、`frontend/src/contexts/WebSocketContext.tsx` 和 `wsTaskMessageHandlers.ts`。按子任务和消息 ID 处理终态，沿用当前消息合并和防旧事件覆盖的逻辑。图片重试继续保留其尝试版本。视频漏收事件时先通过 `backend/api/routes/message.py` 的现有鉴权消息详情读取终态，再合并到原卡。后端仅在现有接口缺少必要状态时补齐可兼容字段。
- 处理任务已终止但前端没有收到占位事件、同一对话聊天仍在流式输出、刷新只加载近期消息、终态前后顺序相反等场景。结果归属以任务及消息身份为准。
- 验收 R3，并覆盖视频成功及失败、图片和视频同时完成、重连后未重放终态通知、晚到的待处理事件，以及同一个卡片的新旧图片尝试。活动聊天内容保持完整，只有匹配卡片更新，完成或退款只结算一次。

### 4 验收多轮组合和其他工具

- 在 `task_execution/direct_loop.py`、`progress.py`、`receipt_continuation.py` 核对组合任务的依赖、等待和部分结果展示。复用 `sandbox_operations.py`、`scheduled_operations.py`、`erp_postconditions.py` 里的现有原生回执及核验。
- 覆盖相互独立、必须按顺序、需用户确认后才执行三种关系。工具超时、权限拒绝和部分完成分别回填到对应步骤。用户说「只补第 2 项」时按已核实的结果继续。聊天模型可在有限次数内修正派发前参数和引用。
- 先用确定性的供应商替身、隔离数据库和浏览器断网测试覆盖恢复矩阵，再用生产配置对应的真实模型验证自然措辞。真实计费场景按已批准次数执行，完成后检查供应商任务和积分账本。文件需可下载且内容对得上，搜索需有依据，ERP 写入和定时任务核对权威回执。

## 端到端验收矩阵

| 编号 | 操作 | 判定通过 |
| --- | --- | --- |
| A1 | 新对话上传福字图并发送截图原话，再用另一张图做一次明确的白底修改 | 每轮分别绑定自己的上传原图，生成一张并在同一张卡显示结果。每轮各一次供应商受理和一笔图片积分结算。 |
| A2 | 只发图、只写提示词、明确引用缺失的上次第 2 条原稿 | 三种场景均为零派发。分别提供适用的澄清、文字稿或指定来源问题。 |
| A3 | 执行中发送「等等，改白底」，模拟发送前掉线和入库后回执丢失 | 前者保留草稿并可续发，后者查到同一条记录。两者最终各只有一个持久化追加命令，派发前读到正确的需求版本。 |
| A4 | 断开 WS，视频完成后恢复，同时在同对话保留一个正在输出的聊天 | 只更新原视频卡，聊天输出继续。补偿后乱序到达的旧状态不覆盖成片。供应商任务和积分不增加。 |
| A5 | 生成两张图，等待确认才用第二张做下一步。让第一张成功、第二张校验失败，再指示只补第二张 | 第一张结果保持。第二张仅在可安全派发时重试，用户确认前下游派发为零。 |
| A6 | 首轮纯文字视频，随后明确用同一脚本再生成，模拟第二次请求重传 | 模型自动得到可用工具。两次真实用户请求各有一个子任务，第二次网络重传沿用同一任务和积分记录。 |
| A7 | 同名表格比较后导出 Excel，使用原附件而非同名历史文件 | 所选附件身份正确，下载得到可打开的 Excel，数据和来源一致。缺一份时定位缺失对象。 |
| A8 | 询问公司报销规则并导出 Excel，再单独询问同一规则 | 组合任务使用有权限的公司依据并产出 Excel。单问规则仍能走快答。 |
| A9 | 查当前公开资料并汇总，再查询 ERP 库存并导出 | 公开搜索呈现实际来源及日期，ERP 数值按指定对象和时间范围核验。两例各自完整交付，未授权的 ERP 写入为零。 |
| A10 | 创建定时提醒，修改原任务时间而保留渠道，模拟回应丢失 | 时区和生效时间正确，真实任务 ID 可查。修改沿用原任务，重复响应不新增计划。 |

A5 的下游通过现有支持的输出验证条件依赖。照片转视频只有在该能力独立确认并接入后才可作为实际下游用例。

## 风险、兼容与收口

- 误触发付费。首轮默认仅在明确要求执行且来源、授权和工具能力满足时派发。只发素材、只写稿、否定执行和条件未满足均做零派发验收。
- 误用同名、旧版或跨权限素材。绑定当前输入及成果版本。历史读取和派发均验证用户、组织、会话及素材作用域，工作区文件、公开网页和内部知识各自保留权限边界。
- 断线、刷新或多端导致重发。追加使用稳定客户端标识，业务调用使用原操作身份。已受理或状态不确定时核实原记录。重复与乱序事件更新版本较新的同一条记录。
- 混合任务丢失子目标。快答与交付检查依据各自步骤，只对失败的部分继续。达到预算时明确展示未完成项。
- 版本兼容与回滚。优先复用已有字段及接口，协议新增字段应兼容旧客户端。若验证发现需要迁移，只使用兼容新增和可读的版本化状态，先上线可读两种状态的服务端。发生回滚时保持运行中子任务可查询、回执可补偿和积分可结算，回滚后的任务禁止重新确认已执行的付费操作。发布前后用同一组基线对照权限、账本和历史成果。
- 一期收口条件是 R1 至 R6 对应的自动用例跑通，首轮、多轮、断线和其他工具的端到端矩阵结果有明确证据等级。图生视频等新增供应商能力在需求及规格确认后单独扩展。

## 本地实施记录

- 首轮用本轮唯一可用原图处理截图原话。明确的历史序号和历史措辞仍要求核对原稿。复合交付按分句识别，明确文件和视频请求按现有权限准备工具，知识库只读快答在有交付时让出完整执行入口。
- 文字追加由 `steer_result` 确认。同一份未确认的补充在当前页面重试时复用请求 ID 和原目标任务。服务器可查询已入库的旧回执，复用原有命令去重。旧客户端可省略新增字段。知识引用继续使用现有 HTTP 输入路由。个人通用聊天运行期间，图片和文件以签名版本引用随同一追加命令入库。当前入口尚未打开或请求未确认时，编辑器保留补充文字和素材。
- 聊天视频按终态子任务的消息身份补读现有鉴权接口。回填校验对话、来源和任务身份，采用消息版本过滤较旧的更新。已完成的独立结果不会覆盖另一条正在输出的聊天。
- 对明确的「等我确认后再生成视频」增加派发前检查，用例验证即使视频工具可用也不会提前派发。明确编号的同类图片和视频组合按保存的方案、版本和条目绑定确认。用户只发「确认第 2 条」时，本轮授权仅覆盖对应条目。来源冲突时返回澄清，既有任务使用原回执。

追加附件是当前任务的输入修订。工作区签名引用保留所有者、相对路径和文件版本。模型可在安全点读取追加素材，原生工具再次核验文件仍属于当前工作区及所选版本。已受理的外部任务继续按原回执交付。终态提交与新附件入队共享任务锁；队列中有尚未纳入上下文的附件时，原任务恢复，关闭后收到的请求保留在编辑器。

附件命令仅对可以持久化追加的个人通用聊天开放。尚未确认的草稿保留在当前页面。迁移回退入口停止接收新的带附件命令，保留已入库记录和读取函数。已经承载新版附件或确认数据的任务应由支持该状态的后端接续，恢复前先核对任务与回执。

同类方案的原生调用记录包含已登记成果的稳定条目身份。确认某条只放行该成果中的该条。前一条已有受理回执时，新确认的兄弟条目可以进入自己的派发记录。工作区素材变化、取消和其他未获授权的要求仍触发现有派发核验。重复确认只回到同条既有记录，受理状态不明时继续核验。
