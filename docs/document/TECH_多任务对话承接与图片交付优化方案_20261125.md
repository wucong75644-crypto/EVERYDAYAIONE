## 2. 当前设计实际上如何工作

1. 每条真实用户消息有物理 chat task、turn、输入消息和上下文版本。运行使用 execution token、lease 和 safe point/checkpoint 防止并发旧执行写入。
2. `executor.py:93` 在新用户运行尚无逻辑执行状态时，调用 `read_agent_task_followup`；另读取 working plan 候选。数据库限定用户、组织、会话、上下文可见性等。
3. 迁移 `378_agent_content_followup_groups.sql:24` 从已有 `agent_task_states` 与已完成物理 owner 中，按 queue_sequence 倒序挑可恢复逻辑任务。第一个为 `source`，其他部分成果为 `other_groups`。它回答“哪些旧任务可恢复”，没有覆盖“所有最近讨论过的新需求”。
4. `EcommerceWorkflow.action_context():431` 优先从当前执行状态或 followup candidate 投影 saved_groups、image_results、original_user_request。`action_input():449` 提供本条输入、本窗口已送达追加、可用历史图片。此专用路由没有直接收集跨窗口最近几轮新需求及未提交事实。主聊天模型有自己的历史输入，不能据此断言它也完全看不到那些消息。
5. `identify():473` 冻结图片动作 intent、materials 等到 workflow。主模型看 content catalog，再决定使用哪个 content_source 或 resume_task_execution。
6. `select_content_owner():653` 根据模型选择的 artifact 查归属；`can_resume_content_calls():673` 校验可编译性；`resume_from_model():746` 把成果调用解释成 continue/amend，并绑定真实当前用户消息。
7. `followup.payload():29` 复制旧 checkpoint，保留原目标、成果和方法，并接入新窗口。数据库 adopt 在会话锁下核对原状态 revision、checkpoint hash、输入和租约。恢复后 `restored_content_calls()` 可以续用已选参数。
8. `item_confirmation.py` 已有 artifact/revision/条目/用户事件绑定和确认账本；主要处理用户设定的等待条件，不是全体普通后续指令的统一目标选择协议。
9. `image_reuse.py:36` 解析原生请求并精确比较提示词、素材内容和角色、模式、画布和相关选项。它解决相同请求复用与避免重复付费，不负责判断“用户是否还在说这个业务”。
10. 原生 operation/receipt 与异步 continuation 负责真实执行和交付。无调用时的 `unconfirmed_image_reply()` 仍可能保留模型虚构的受理文字，再追加“本轮没有提交图片任务”，产生矛盾状态。

因此这不是没有 ID 或没有轮次控制的系统。主要缺口是“本次语义目标 → 真实请求/方案版本”的绑定覆盖不足。

## 5. 推荐方案：复用现有账本，补全请求目标解析

### 5.1 把“有需求但没执行”也纳入上下文

候选读取分为两个视图，不再将“可恢复执行任务”作为唯一上下文来源：

- 最近请求事实：从已有 user messages、物理 task、workflow 和 checkpoint 投影真实输入、图片引用、回复消息、动作意图、是否登记方案、是否存在受理回执。即使没有 agent_task_state 也存在。
- 可执行对象：现有已保存方案、版本和条目，以及运行/完成作业。继续使用原 content catalog、操作和回执账本。

“未提交”不能改写成“等待批准”，也不能从助手声称受理推导已经执行。最新需求无稿时只标记为未准备/未提交；模型应依据其真实输入补齐执行稿，无需要求用户无故重发。普通讨论不能自动成为待执行任务。

先基于现有数据查询投影，不新建第二套任务队列或泛化业务根表。候选只给有界摘要和可读取的真实引用；更早历史仍可按用户指向检索。

### 5.2 动作与目标共同解析，并固定一次结果

扩展现有语义结果，而不是新增互相独立的多轮分类器。目标可指向当前输入、历史真实请求、已保存方案条目或实际成图；选择与动作一同冻结，主模型可读取和纠正，但不得静默换对象。

建议内部绑定（设计字段，尚不存在）：

```json
{
  "input_message_id": "本次真实输入",
  "input_revision": "已有输入版本摘要",
  "action": "execute_saved | edit | generate | show_existing | inspect_status",
  "target": {
    "kind": "request | content_item | image_result",
    "source_message_id": "被承接需求或结果的真实消息",
    "root_task_id": "存在时绑定原任务",
    "artifact_id": "存在时绑定已保存稿",
    "revision": 1,
    "item_indices": [1]
  },
  "resolution": "resolved | ambiguous | needs_preparation"
}
```

按 kind 定义严格互斥类型，示例不表示所有字段可以随意组合。宿主生成/核对身份、版本和权限，模型从候选选择引用并理解用户含义。`input_revision` 证明输入未变，不证明理解必然正确。

本轮有新指令/新附件时优先解释其实际用途，但不能硬性断言有附件必新任务；“换图继续旧方案”仍可明确选择旧方案并绑定新素材。已完成历史对象保留只读和明确重用能力。

### 5.3 泛指确认不能跨过未处理的新需求自动承接旧成品

- “开始吧”只有在当前对话能够唯一绑定目标时才执行。时间最近是排序证据，不是充分授权或语义证明。
- 新本子需求尚未提交时，下一句“开始吧”应承接该需求；如它的执行稿尚不存在，先准备本子稿，不能因为灯塔稿是唯一可执行稿就选它。
- 用户明确说“回到之前灯塔那张”时允许选历史对象；明确“再生成一张”保留新的生成身份；“把原图发我”只展示已有结果。
- 真正有多个合理目标时，提供简短候选供用户选择，暂不派发；不为每次普通编辑增加确认门。
- `execute_saved` 必须关联具体方案和版本，不再仅凭 intent 标记改变工具暴露策略。没有可执行稿的 request 目标走 preparation，而非伪造 content_source。

将本次目标绑定存入已有 checkpoint 的新版本扩展，建议 `_request_resolution_v1`。它只记录选择事实，不是权限源；继续以真实用户消息及原权限策略授权。

### 5.4 先校验目标，再允许 adopt、参数恢复、派发和复用

在 `select_content_owner`/`resume_from_model` 前验证：调用所指 root/artifact/revision 与已冻结目标一致。SQL adopt 在原会话锁、租约和输入版本检查下重验目标绑定，避免检查后变化。后续 `restored_content_calls` 核对同一绑定，不能在恢复时继承另一目标的已选参数。

当前目标变化时，新输入重新解析；旧运行结果仍按原 operation 交付为旧任务结果，不能变成新任务成功回执。已受理操作继续按原幂等账本查询，不因新输入重复发送。

`item_confirmation` 复用现有事件/方案/版本账本。需要批准的场景必须解析到具体 artifact/revision/条目；过期批准不能沿用至新版本。不要求全部生成场景都走人工审批。

继续保留精确图片复用，但它只能在目标绑定通过之后运行。无语义绑定的存量请求不能通过默认旧对象自动补齐。兼容策略：旧已受理/运行中 continuation 按原账本完成；新的用户执行请求必须在当前窗口解析目标。实际回滚不能删除已受理 operation。

### 5.5 状态回复以原生事实为准

统一 `not_submitted / accepted / running / completed / failed / reused` 状态投影，用真实 operation、job、artifact 判断。图片在最新回复出现不代表它是本次新生成。

不再保留“已提交后台处理”再追加“没有提交”的矛盾组合。生成型回复延后状态宣告；未提交时保留业务说明正文，由宿主给出一致的未提交状态。只读展示和复用明确说明是已有结果；新生成受理只引用绑定到本次目标的回执。不能靠关键词删句作为唯一正确性机制。

## 6. 实施落点与顺序

1. 请求上下文：`executor.py` + 新只读候选 RPC（后续迁移），从现有消息/任务/checkpoint 投影最近请求事实，保留租户、会话和 base_context_revision 过滤。新 resolver 模块集中类型与校验，不能散落多个实现。
2. 语义投影：`workflow.py` 的 action_input/action_context/identify 读取同一份近期请求及可执行候选；扩展结构化 target；`direct_loop.context_message()` 给主模型呈现同一事实，历史完成项标明用途。
3. 承接事务：`direct_loop.py`、`followup.py` 及新的 adopt 校验迁移绑定同一输入、目标和版本。保留现有 revision/hash/token 机制。
4. 业务边界：`item_confirmation.py`、`image_reuse.py` 和 execution_engine 在目标有效后处理确认、复用和真实派发；保留此前统一编辑参数和多场景选图。
5. 回复：`content_tools.py`/execution_engine 使用统一回执状态，修复未提交却声称已受理。记录 resolution 候选、选择依据来源、拒绝码、目标和回执关系；日志不输出图片 URL 签名或用户文件内容。

不新增供应商、不另建执行器、不改变现有图片底层供应商调用。对普通图片先落地公共目标类型与校验，并核对 generate_video/code_execute 复用 content_source 的入口，避免强加图片动作枚举给非图片工具。跨工具推广需要各自交付语义验证，不能凭本次图片测试声称全部覆盖。

数据库迁移只扩展新绑定契约和读取能力，不回写历史业务归属。新旧 worker 混跑需有版本兼容策略：未识别新契约的 worker 不领取要求该契约的新窗口；部署切换和 drain 沿现有发布流程。回滚关闭新请求解析入口前处理或保留已准备 checkpoint，旧路径不得静默执行新目标绑定；实作时以实际 worker 版本机制决定迁移细节。

## 7. 必须验证的场景

| 输入/状态 | 预期 |
| --- | --- |
| A 灯塔已完成 → B 本子有输入但无工具 → 开始吧 | 绑定 B；补齐 B 执行稿；绝不恢复/复用 A |
| A 已完成 → B 只有讨论，无实际执行意图 | 不凭讨论创建作业，也不自动重用 A |
| B 有登记稿且唯一明确 → 生成 | 绑定 B 的指定版本条目 |
| B 新图明确引用 A 方案修改 | A 方案 + B 明确素材，保留用户指定关系 |
| 明确回到 A，查看旧结果 | 展示 A，不新收费 |
| 明确回到 A，再生成一张 | 新生成身份，不被相同配方复用吞掉 |
| A/B 均合理且指代不明 | 询问具体目标，无业务副作用 |
| 等待确认 v1，修订成 v2，再确认 | 旧批准不得授权 v2；重新解析具体版本 |
| 目标绑定后追加新素材或指令 | input_revision 失效，重新解析；不派发旧绑定 |
| adopt 前/后崩溃重试 | 同一绑定恢复，不重复派发，不恢复错参数 |
| A 异步完成时 B 已开始 | A 回执归 A，B 状态不被宣布完成 |
| 同请求断线重试/查询 | 继续原 operation 或复用合法结果，不重复计费 |
| 模型无调用却声称已提交 | 一致显示未提交，正文不出现矛盾状态 |
| 当前附件/历史上传图/上一张生成图/多图角色 | 保留统一编辑参数方案的选图能力和真实资源校验 |
| 其他用户/组织、不可见修订、伪造 artifact | 拒绝，不能退回任意旧成果 |

现有 Postgres 测试覆盖真实归属事务、旧稿选择、资源、复用和恢复；其中主模型选择经常由固定 stand-in 给出。它们不能证明真实模型会在 A/B 混杂对话中选择正确目标。新增测试应分别验证候选投影、目标一致性、状态交付与真实模型选择：固定真实脱敏会话回放 + 本地数据库/原生适配器集成 + 小量真实模型决策评测；图片供应商可先使用 transport fixture，不把模型决策评测自动变成付费生图。

验收应证明 A/B 反例被阻止且 B 可继续成功，而非仅让 A 不出图。语义仍有误判可能，工程保证是目标不确定/不一致时不静默派发到另一对象，不能承诺模型理解百分之百正确。

## 8. 本地实现与兼容边界

- 新迁移 384 提供只读 `read_agent_request_context`：查询同租户、同会话、上下文可见的最近 12 个真实请求，包含没有逻辑执行状态的请求；另提供最近 16 张实际助手图片的引用。只投影需求及真实执行状态，不把未提交当作等待批准或成功。长需求摘要标明须读全文；执行前校验完整读取记录。
- 新 `request_resolution.py` 定义严格 Target 和宿主绑定，记录本次 input_message_id、input_revision、执行窗口及所选对象的真实引用。`resolved` 仅表示指代已解析，不代表方案已准备、已授权执行或已受理。`request` 目标没有已保存稿时走原准备/保存流程；只有真实 content 对象能作为 content_source。
- 最近焦点基于已存语义动作及承接关系，不对用户文字或标题做关键词/正则匹配。新业务讨论即使未执行也保留为当前焦点；无关解释仅在结构化 retain_previous 时保留此前焦点；泛指承接不能越过新需求绑定旧 root。明确历史指向仍由模型选择，后台验证真实对象和版本。`current` 表示本条新任务，不代表自动选最近图片。
