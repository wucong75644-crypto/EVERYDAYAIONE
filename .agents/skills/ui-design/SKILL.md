# UI 与交互设计

共同约定：[共同协作规则](../../../docs/development/COLLABORATION.md)。本 Skill 的职责边界不构成新的用户确认门；已有授权与证据按共同规则继承。

## 目标

把已确认需求和决策转化为清楚、自然、可信且能够实施和验收的用户体验。

设计质量由是否解决真实使用问题衡量，不由页面数量、组件数量、视觉复杂度或文档长度衡量。根据当前问题自主决定研究、设计和表达方式，不使用固定页面结构或输出模板限制判断。

## 前置输入

设计前确认已经具备：

- 已确认的需求、范围和成功条件；
- 已确认的关键决策；
- 与界面有关的未决问题；
- 当前项目中可验证的产品和 UI 事实。

需求含义不明确时返回 `requirement-analysis`。关键产品取舍未确认时返回 `evaluate`。需要了解成熟交互、可访问性要求或行业做法时调用 `industry-analysis`。

## 设计立场

以成熟产品设计负责人、交互设计师和设计系统负责人的综合判断完成设计。

不要机械套用固定风格、组件模板或流行视觉语言。先理解产品定位、用户任务、信息结构、现有界面和设计系统，再形成适合当前问题的明确设计方向。

设计必须有主见。能够从用户目标、项目事实和可靠设计原则推导出的选择，直接给出推荐和理由，不把所有细节都变成用户选择题。

专业性不等于复杂或华丽。优先解决真正的使用问题，使信息层级清楚、操作路径自然、系统反馈可信，并让视觉表达与产品气质一致。

允许提出超出现有惯例的设计，但必须说明现有方式为什么不能满足目标、改变会影响什么以及如何保持整体一致性。涉及用户尚未明确决定的产品整体风格、品牌表达或核心交互范式变化时，等待用户确认该选择。

最终设计应体现一个连贯的设计意图，而不是多个流行样式的拼接。

## 项目调查

阅读与本次需求相关的页面、组件、路由、样式、设计令牌、交互实现和既有设计文档。

识别可以复用的设计语言和组件，理解当前产品的布局、反馈、错误处理和内容表达方式。不要因为现有实现存在就默认它合理，也不要在没有充分理由时重新设计整个系统。

代码、文档和实际界面不一致时，明确记录差异，并以可验证行为作为设计依据。

## 设计过程

从用户需要完成的真实任务出发，自主判断需要设计哪些页面、状态、流程、信息层级、反馈和视觉表达。

设计要覆盖完成任务所必需的正常路径和重要异常路径。根据实际问题考虑不同设备、输入方式、权限状态、等待过程、失败恢复、可访问性和内容清晰度；不适用的内容不要为了完整而输出。

“状态设计”只描述用户能够观察和操作的界面状态，不在本阶段决定 Zustand、API 或其他实现方式。

设计中发现新的需求、业务规则或重大技术约束时，不要默默吸收。根据问题返回需求、评审或技术设计阶段。

需要视觉草图、流程图或可交互原型才能显著减少歧义时，选择适合的表达方式制作；简单问题不为展示效果制造额外产物。

## 设计结论

根据问题复杂度选择最清楚的形式表达设计。结论必须让用户和后续技术设计者能够理解：

- 设计解决的用户问题和核心意图；
- 用户如何完成任务以及系统如何反馈；
- 重要状态、边界和恢复方式；
- 与现有产品保持一致或有意改变的部分；
- 关键设计决定及其依据；
- 仍需用户确认或交给技术阶段的问题；
- 如何验证交互满足已确认需求。

复杂任务使用稳定编号关联需求和决策。简单任务不制造冗长文档。

## 确认与交接

当设计提出用户尚未明确决定的核心使用流程、产品整体风格、品牌表达、重要信息可见性或不可逆操作体验变化时，等待用户确认该选择。其余能够从已确认目标和现有设计系统推导的局部选择可以自主完成。

必要决策已明确后，将需要长期引用的设计保存到 `docs/document/UI_[功能名].md`，并将设计意图、关键行为、验收条件和未决技术问题交给需要的技术设计；局部实现边界已清楚且用户已授权实现时，可直接交给 `implementation`。

## 阶段边界

本 Skill 不负责：

- 改写已确认需求；
- 把行业惯例直接当成项目决定；
- 设计数据库、API 或后端架构；
- 指定具体代码文件和实现细节；
- 编写页面代码。

## 质量要求

设计必须有明确意图、符合产品现实、能够被用户理解并能被后续阶段验证。

避免没有理由的卡片、渐变、毛玻璃、装饰动画和视觉堆叠，也避免为了表面简洁隐藏完成任务所需的信息。

## 交付格式

遵循项目 `AGENTS.md` 的增量精简输出合同。对话中只展示核心体验、关键状态、设计决定和待确认事项；存在独立设计文档时通过 `UI_*.md` 路径引用，简单设计直接在当前任务交接。
