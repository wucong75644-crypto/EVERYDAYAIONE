# 通用工具发现与内容执行接入方案

状态为首批本地实施。基线 `cf0c1625`。本稿整合通用 Agent 架构、内容引用与 46 项工具盘点。视频与文件用于验证同一机制。方案按现有模型主导聊天和原生执行链渐进接入。

## 用户流程

用户让 AI 写三条文案，再让它改短第二条。现有消息提交保存两次正文。下一轮「把刚改的第二条做成短视频」或「把刚改的第二条原样做成 Word」时，主模型定位修订后的原文并判断动作。已加载的历史足够时直接定位，历史压缩或歧义时按需回读。动作不明确时只问要做什么，保留已定位的来源。用户看到正文、实际执行状态、必要确认及结果。

## 三个接入点

| 接入点 | 复用 | 补齐 |
|---|---|---|
| 内容读取 | `ContextAnchor`、闭合历史、资源边界、`TaskArtifactReader`。现有 `get_conversation_context` 的 `text_exact` 已能选取并核对历史原文。 | 在聊天内提供面向普通消息和现有成果的受限读取，复用精确片段校验。解除通用读取对图片开关及图片字段的依赖。保留旧图片协议。 |
| 工具发现与披露 | `ToolSpec`、`ToolCatalog`、`Registry`、`ToolPolicy`、`prepare_tool_turn` 和下一轮的 `discovered_names` 注入。 | 增加一个内部只读发现入口。以当前作用域、已启用能力、Skill 上限、任务阶段和功能开关过滤候选，再按能力名、用途及少量同义词匹配。结构化返回工具身份，下一模型轮由现有组装路径提供完整的实时 schema。 |
| 调用与恢复 | `_execute_tools_impl`、`stage_native_calls`、`ToolRuntime.execute`、派发前校验、现有检查点与原生回执。 | 在记录待执行调用前绑定已核实的来源与参数。派发前重查权限与引用有效性。确认后发生变化时用现有失效规则重新判断。恢复时重读已绑定的引用和回执。 |

常用工具随每轮直接提供。发现用于当前工具不够时。候选说明写清用途、限制和结果类型。正式调用以当前 schema 的字段、类型、必填项和支持的参数组合为准。难用的工具在同一注册定义旁放短示例。发现和展示使用同一套权限和阶段约束。查询命中只更新本任务的工具可见状态，执行仍需原有校验。已发现的身份随检查点保存，恢复时重建当前定义。未命中可按能力分类或精确名称再查一次，仍不可用时说明缺口。

第一版复用现有目录做匹配。实现前以测试确定实际候选质量，暂不引入单独索引或分类模型。ERP 专用查询留在原业务域。定时和预检保持批准范围。内部兼容工具、关闭的功能和供应商专用工具各自沿原入口。

## 共同输入契约

- 来源使用消息 ID、内容块与精确片段，或任务成果的原生身份。宿主在本轮历史边界内读取真实内容并计算版本证据。旧消息按需定位，普通回复继续随消息保存。
- 每个接入能力声明支持哪些来源及其作用。精确复用的参数由宿主填入已验证原文。派生参数由模型按用户意图生成，记录原文与派生输入的关系。来源证据由宿主处理，底层适配器继续接收自己的参数。
- 未找到原文、来源有歧义、内容不可访问或参数校验失败时，不派发该动作。已完成结果保持可查。状态未知时先核原回执。
- 首批保持现有版本及恢复机制。字段编码和检查点落盘位置在实现前结合原生事务确认。使用可选字段和逐能力开启，回退时保留已存的来源、旧成果及回执读取。

## 视频走一遍

1. 用户说「把刚改的第二条做成短视频」。模型定位第二条修订稿，必要时用通用回读。
2. 本地盘点中 `generate_video` 已登记且在合成组织自动场景通过名字级策略，普通聊天默认没有。模型查「根据文字生成短视频」，发现服务命中。下一轮拿到当前定义。现有公开参数要求 `prompt`，描述支持短视频生成。时长、模型等参数以实际能力声明为准。
3. 用户要求根据文案制作时，模型可组织镜头和动作，后台把已验证文案与派生的 `prompt` 绑定。如果用户要求原样使用，宿主把确切原文填入对应参数。
4. 走 `ToolRuntime` 与现有原生视频操作。受理返回子任务身份，已发布视频及可用资产由回执验证。预算、确认、计费、重复和恢复沿原生视频规则。受理期间显示生成状态，最终展示视频。
5. 复用视频定义、执行和回执。补通用发现、文字来源绑定，以及无 Skill 场景下的回归。

## 文件走一遍

1. 用户说「把刚改的第二条原样做成 Word」。同一来源解析返回同一份修订稿。无需为了文件另建内容索引。
2. 本地盘点中 `code_execute` 在文件工作区及沙盒条件满足时可按策略提供。目录无专用 Word 导出工具。能看到现有沙盒时可以直接选，缺少时按当前权限查询。模型需要看清代码输入契约、沙盒允许的文件输出方式、如何交付下载结果。文件查找和分析用于读取材料。
3. 保真路径由宿主把核实后的原文作为数据交给沙盒。模型提供排版逻辑。首版拟通过受限输入文件交接，复用沙盒已有文件权限和路径约束。验证实际沙盒依赖、输入注入和 .docx 回传前，该路径仍属待验证设计。
4. 复用沙盒结果、现有文件产物核验和回执。通过检查可下载产物及正文来确认成功。无权限、依赖不可用或没有产物时明确反馈。
5. 补普通内容到沙盒输入的可验证绑定，以及 Word 实际可下载的本地验证。首批方案无需新增业务工具。

## 实施顺序与验收

1. 先验证视频发现和内容回读的实际最终模型工具列表。用受控模型请求覆盖常用、按需、未命中、相似工具、阶段受限和撤权。已启用能力应有可验证的路径，公开定义须与执行契约一致。
2. 接入同一来源对视频 prompt 和文件输入的绑定。用同一修订稿测试精确传递和派生两种用法。验证历史压缩、同名条目、旧版本、失效附件及跨组织边界。
3. 用受控视频回执和隔离沙盒验证实际执行顺序、成果、确认变化、重复提交和恢复。视频使用替身，文件检查真实可下载内容。补充失败路径及空结果。已有图片方案继续从原生读取入口按项复用，图片内容与旧快照无需迁移。
4. 真实模型选法、额外轮次、延迟及生产账号的最终工具列表另行验收。模型工具选择准确率通过场景测量，不能仅由目录覆盖推出。

### 2026-11-18 来源绑定补齐

复用 `_chat_content_tools` 检查点保存精确读取成功后的选择。后续视频、图片和沙盒调用漏传 `chat_text_source` 时，由宿主自动接上当前选择，再经过已有 `bind_call`、任务参数绑定和运行前重读校验。显式的旧图片方案与 `source_prompt` 继续使用原生来源协议。选择失败或只召回消息而未确定片段时，阻止本轮内容工具派发，直到精确选择成功。读取本身不建立新的执行任务。

默认沿用选中的原文，用户要求改编时模型显式声明 `adapted`。本机制保证已选来源进入实际执行参数，首次识别复用意图和选择正确条目仍由模型完成。模型完全跳过来源读取且未提交来源时，宿主无法仅凭普通 prompt 证明该请求是否属于复用，本次未加入关键词猜测或额外分类调用，需通过后续真实模型回放继续验收。

Word 原样路径在 SandboxToolMixin 中按现有 dispatch call ID 获取经过验证的来源，交给宿主 SandboxExecutor。上传 .docx 前重新读取文件，按段落以换行拼接的正文精确比对，包含表格时拒绝原样交付。显式 emit_file 与漏 emit 的自动收集共用上传入口，因此两条路径都受校验。改编模式保留模型排版执行方式。当前校验覆盖普通段落正文，复杂 Word 结构需另行定义保真契约。

本地验证使用原 Skill 导出和原五项方案，视频及生图调用使用替身，Word 由真实沙盒生成并重新打开核对。另验证错稿 .docx 在显式上传及自动收集两条路径均被拒绝，来源选择失败后裸 prompt 无法绕过。首次沙盒启动因字体缓存初始化超时，预热本地固定字体缓存后通过。未进行付费调用或生产发布。

#### 诊断补充

原六条提示词均在原消息中唯一匹配，六个模型提交的 sha256 全部不匹配。原生参考图定位可以解析。此前在线只读重放提示词错误时，任务已存在后续受理的图片子任务，其 1:1 尺寸记录影响了尺寸继承。按初始记录还原并执行发布提交原版 `prepare_input` 后，首先复现 `IMAGE_ASPECT_RATIO_UNSUPPORTED`，因为原图为 480×474、比例80:79，而原调用丢失了已选方案的1:1输出规格。两种独立失败原先都被包装为 `TASK_IMAGE_INPUT_UNAVAILABLE`，导致模型换消息定位、查文件、改 file_id 反复重试，最后改为无参考图文生图。不能把该过程归因为参考图丢失。

首批六次读取实际返回共68,879字符，每次含完整策划内容，末尾选中来源被通用长结果持久化预览遮住，模型无法完整看到它需要复制的来源信息。新入口原先保存单个 `selected_source`，没有接入旧 `get_conversation_context` 的选中结果，并行读多条也可能只剩最后一项。

#### 实施

- 新旧读取共用 `content_tools.select_text_fragments`，支持单条 `text_exact` 和批量 `text_exacts`，保留请求顺序并要求唯一原文匹配。精确读取只返回选中片段及相关图片元数据。精确结果上限30,000字符，超量明确要求分批，普通历史预览明确标记截断和原始长度。
- 精确结果经过真实 `ToolResult` 和旧结果信封验证；原有默认3,000字符的旧结果分流不能把有界精确来源重新变成预览。来源观察从原始 `ToolResult.raw` 取证，兼容旧字符串与AgentResult返回。完整历史等非精确结果保持原分流方式。
- 复用 `_chat_content_tools` 检查点保存多条选择。同批并行读取合并全部来源，后续独立选择替换旧集合。兼容旧单来源检查点。旧消息和中断文本复用既有原生历史边界与冻结目录校验。
- 模型可发送现有消息定位和完整正文，也可选择已读取来源，省略再次回传正文。后台补齐实际 prompt、原文变量及哈希，再进入原调用参数绑定、权限、确认、计费和回执链。旧 `source_prompt` 可省略 sha256；显式提交的错误值仍拒绝。模型可见的输入选择分支不改变原生适配器接收完整输入的契约。
- 已核验选中原文中的明确“输出比例/画布比例/输出尺寸/输出分辨率”使用原尺寸解析器。当前用户及已确定的尺寸约束优先，产品自身比例不作为输出规格，精确像素保持精确限制。该场景的1:1来自六条原文，成功回放无需增加用户确认语句，也无需改写原文。用户明确要求沿用80:79时仍准确拒绝，不近似转换。
- 同一批图片准备共用一次引用解码结果，每项仍检查当前授权、来源和文件版本。缓存限当前批次，正式受理前重新进行原生完整校验。原参考图发生删除或变化时拒绝继续使用缓存。
- 保留具体失败码和指导信息。来源、素材或尺寸条件失败时停止当前自动提交，停止状态与选择随原检查点原子保存。恢复后不再额外采样模型，也不会移除参考图或改写提示词购买替代结果。成功项目和原回执继续保留。
- 会话来源读取留在执行记录和检查点，流式预览、持久消息和前端历史展示均不显示该后台卡片。正文、现有确认入口、实际生图状态和错误说明继续展示。
