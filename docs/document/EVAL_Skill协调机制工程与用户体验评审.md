## 1. 决策依据与适配程度

现有项目已具备 SkillRuntime、共享激活入口、工具权限上限、Actor 安全点、版本固定、数据库检查点和图片受理账本。统一协调可落在已有职责内，不需要新增服务、模型裁判或跨服务事务。

主要成本来自跨入口一致性和兼容迁移，不是算法计算：聊天、会话绑定、计划任务、直接媒体任务有不同执行边界；不能为了整齐都套进聊天 Actor。原方案已明确分别接入，这是正确方向。

本次事故还包含参数语义与供应商 ID 两个独立缺陷；协调机制不能代替这些修复。保留它们作为同一交付的独立验证项合理。

官方研究只能支持受控组合、交接和适配边界，不能推导“大厂都能自动检查任意 Skill 冲突”。无需为了对齐框架名引入 Microsoft Agent Framework 或 Google ADK。

## 2. 工程视角：必须在设计中解决的问题

### E1：控制权必须按本轮动作/当前阶段生效，不能与加载状态永久绑定

**影响：高；属于实施前的设计阻塞项。**

方案 3.1 用静态 `claims` 描述策划与提交控制权，3.3 要求固定方法和手选完整预检，但没有充分规定：Skill 虽然继续加载，其某项流程声明何时不适用。

现有 `services/skills/context.py::model_messages` 已明确“加载不等于执行完整流程”；电商 Skill 正文也允许用户直接执行最终提示词时跳过策划。

若把激活 Skill 的全部 claims 无条件占用，会造成：用户已经确认稿件后说“开始生成”，系统仍判定策划控制权冲突；或者固定了一个只在某阶段适用的方法，其他请求都被它拦住。这会破坏现有短指令续接和复合任务能力。

**建议约束 D1：**区分“已选择/已加载的方法”和“当前执行阶段的控制者”。发布声明描述潜在适用范围；协调结果只落实本轮真实动作所需的控制权。适用性从当前用户动作、可信原任务状态和领域证据确定，不能单靠模型正文自报。辅助参与和流程控制也必须分开，不能仅因两个方法都参与设计就判互斥。

验证必须补齐：策划→确认→生成、直接执行已有提示词、保留会话固定方法时的新话题、两种专业方法为同一张图提供辅助意见。它们既要保留绑定及权限限制，又不能重启不需要的流程。

### E2：可选自动方法被拒绝，不能拖垮其他可执行方法

**影响：高；属于实施前的设计阻塞项。**

方案 4.1 写“动态控制批次整批冲突则不提交部分激活”，4.3 又允许拒绝普通自动候选后继续。两条规则在同批多个自动候选时存在歧义。

例如主方法 A 已确定，自动候选 B 与 A 兼容，C 与 A 冲突。如果简单回滚整批，B 也被丢掉；如果整个任务停止，自动辅助能力反而退化。另一方面，不能在缺少依赖方法时把 B 的一部分状态提交出去。

**建议约束 D2：**先按来源和依赖区分“必须共同成立的集合”和“可选独立候选”。必须集合整体校验与原子提交；可选候选冲突仅拒绝该候选及真实依赖项，保持主任务和无依赖的兼容方法可用。最终决定只提交一次完整快照，不暴露候选中间状态。共享必需能力也必须在最终集合上重新校验。

没有声明依赖的多个自动候选不能仅因位于同个模型批次就被视为业务事务，也不能凭加载顺序改变原有明确选择。

### E3：legacy 的不确定性需要明确处理表，不能同时承诺“不拒绝、不默认兼容、全部自动防冲突”

**影响：高；属于实施前的设计阻塞项。**

方案 6.1 正确认识到旧正文与哈希不能重写，但“保留 legacy，不认作完全兼容，也不一律拒绝”还不是可直接实现的决策规则。

若未知旧 Skill 可任意加入流程，语义冲突可能继续发生；若全部禁用，又会失去用户现有的自定义/自动功能。正文相似度或一次 LLM 判断不能可靠填补这个缺口。

**建议约束 D3：**上线前针对实际存量给出有证据的分类和处置：已知工作流登记精确契约；经核实的辅助方法保留组合；未分类版本保留原有单方法功能与权限，不能因此获取新控制权，并明确其自动组合的可验证边界。对尚未核清、且当前确实会自动组合的存量，不可自行一刀切禁用，须先列实例、影响和可选处置，再决定发布范围。

兼容注册表只能用于历史迁移，不应使“每新增一个普通 Skill 都必须修改后端代码并发布”。使用已支持执行方法的新 Skill 应通过既有编辑/发布链路声明；只有新增真正业务协议才需要开发宿主适配器。

## 3. 工程视角：应保留的设计与成本控制

| 判断 | 理由及实施约束 |
| --- | --- |
| 保留纯策略协调模块 | 可确定性测试，不增加每次激活的模型费用，不承担业务派发。 |
| 保留工具权限交集 | `skill_tool_ceiling` 和现有测试依赖此语义；不能借组合机制改为权限并集。 |
| 保留 Actor 原子提交 | 现有工作流绑定与检查点是分开保存的；仅做内存校验不足以保证恢复一致。 |
| 限制公共 SQL 的职责 | 通用检查点只处理身份、版本、token、修订与投影一致性；不要把各行业策略塞进公共保存函数，每加业务就改它。领域业务合法性仍在领域受理函数核验。 |
| 保留 v1/v2 双读与先读后写 | 旧格式严格限制版本，不能只新增字段就宣布兼容；回滚必须回到具备双读能力的版本。 |
| 保留媒体/计划任务各自入口 | 它们已有 explicit-only、无动态发现等边界，不应因统一协调而获得聊天工具或动态切换能力。 |
| 控制检查频率 | 新组合或真实动作变化时重新判定；同一组合下的模型 chunk 不做数据库/路由查询，不逐 token 重算。 |
| 先轻校验再加载资源 | 能由已验证元数据判定的冲突应在模板/附件 IO 前发现；通过后仍完成内容哈希和完整权限校验。 |
| 不先建设全行业流程 DSL | 第一版提供本次真实需要的控制权、动作适用性、来源与有限交接；未来场景以证据扩展，不一次设计所有流程语法。 |

可行性判断：已有代码基础适合增量完成。影响范围覆盖共享核心路径，验证深度应高于普通生图 Bug；缺少存量库存和端到端证据前，不给未经测量的工期、性能收益或“零回归率”承诺。

## 4. 用户视角：可用不等于方便

### 4.1 已有体验值得保留

- `SkillSelector.tsx` 支持选中后关闭面板并将焦点送回输入框。
- `SessionSkillBindings.tsx` 已区分“仅本条消息”和“固定到当前会话”，并说明发送后清除及后续持续使用。
- `useSkillBindings.ts` 在写入结果不确定时会核对服务器，防止用户在配置未确定时继续发送。
- `ScheduledSkillPicker.tsx` 明确固定版本，新版不自动替换。

这些都是用户已形成的操作习惯。新协调机制应尽量只改异常反馈，不重新设计正常操作路径。

### U1：把冲突恢复从“报错后刷新”改为清楚的下一步

当前 `useSkillBindings.ts` 会将不同错误统一变成“版本或权限可能变化，请刷新”；`services/skills/feedback.py` 对新增未知错误码也会落到“暂时无法启用，请稍后重试”。直接加入后端冲突码不会自动得到可用体验。

需要区分：已明确拒绝（没有写入）、版本变化、权限不足、写入结果不确定。确定的业务冲突不应显示“刷新重试”；只有结果不确定才保留现有核对/阻塞发送机制。

用户看到的是具体方法名和结果，例如：“当前会话固定了 A，你这次选择的 B 使用另一套制作流程，请保留其中一种。”提供“调整本次选择”和“管理会话固定方法”的入口。不能显示 method/scope/revision 内部错误码；没有权限修改组织限制时不能给用户一个无效的解除按钮。

**无冲突路径不增加任何确认；系统自己找到的不兼容辅助方法由系统跳过，不让用户裁决内部路由。**

### U2：调整方法不能要求重传图片、重打要求

在发送前发现冲突，保持编辑区文字、附件、图序和本条选择；调整只影响明确选中的设置，不自动解除会话固定方法。

执行后才发现问题，恢复动作绑定原任务和原输入，不能将最后一条“为什么失败”或报错截图当作新的商品需求。已受理图片保留结果关联；不能因用户点击“继续”重复提交整组。

对“仅本条”选择要考虑发送后标签清除：失败恢复界面显示原任务采用的方法，而不是要求用户凭记忆重新选择。保持原任务重试与重新生成的区别。

### U3：创建 Skill 的人不应该被迫学架构术语

普通作者继续写方法、上传附件和发布。控制关系使用可理解的选项和已支持方法提示；不得要求填写 scope、method、body hash 或编写交接图。

系统可辅助形成契约草稿，但声明会改变执行行为时必须可查看、可修改并走现有审核/发布校验，不能在后台悄悄把个人方法改成服务器策划。

使用已有协议不应要求提交后端代码；旧版本内容不因新功能自动重写。

### U4：会话固定不应变成“每句话都被锁死”

用户固定某制作方法，是希望相关任务持续沿用，不代表后续询问原因、调整文字或新话题都必须重跑制作流程。D1 必须落实到可观察行为。

方法固定及工具安全上限继续有效；“本轮没有执行该流程”不等于偷偷解绑或扩大工具权限。确需换互斥方法时解释并提供调整入口，不要求用户理解冲突发生在哪个模块。

## 5. 体验验收情境

| 情境 | 期望操作与反馈 |
| --- | --- |
| 新用户上传图片要求五张详情图 | 不必选择 Skill；沿现有自动能力完成，不弹出内部方法选择题。 |
| 熟练用户手选完整融合版 | 选中→输入→发送，正常路径与现在相同；系统不换方法、不重复问授权。 |
| 自动补充辅助方法 | 无冲突时后台完成；不兼容候选被跳过，主任务继续，用户无需处理。 |
| 本次选择与会话固定冲突 | 发送前能判断则提前说明；保留输入，并能直接到对应设置调整。运行时仍复核。 |
| 方案已完成，用户说“开始生成” | 使用正确原方案/提示词，不重新问商品资料或再次策划。 |
| 用户追问“为什么失败” | 回答具体错误和原任务状态，不把问题解释成启动新方案。 |
| 部分图片已受理，用户重试 | 能看到已接受与未接受范围，不丢已有结果，不重复提交已接受项。 |
| 会话绑定保存超时 | 告知状态正在核对；核对前不错误放行，确认后恢复正常，无需重填输入。 |
| 计划任务选择冲突 | 在配置时解释冲突，不等到定时执行失败才通知。 |
| 手机/键盘操作 | 复用现有弹层、焦点与标签；错误不只用红色表达，恢复按钮可键盘访问。 |

普通用户应不需要新增概念学习；高级作者仅在定义执行方法时接触声明。判定“便捷”的标准是正常路径不增加操作，异常路径不用丢失输入或反复重试，不是单纯隐藏所有错误。

## 6. 需要补充的验证证据

1. D1–D3 的确定性策略与调用链测试，明确候选拒绝不会使主任务停摆。
2. 采用同一基线任务比较正常路径：额外用户确认次数为零，纯协调不得新增付费模型调用；延迟和额外数据库次数实测后再设门槛。
3. 三类库存抽样并最终覆盖上线范围：平台、组织、个人方法；不能只证明两个电商版本可用。
4. 实际用户走完五类核心任务：自动生图、手选生图、固定方法冲突恢复、开始生成、失败重试。记录是否误选、是否需要指导、是否重传附件。
5. 前后端联合验证明确拒绝与结果不确定两种错误，确保不把所有业务冲突都当成网络故障刷新。
6. 保留原方案 T01–T18，增加本评审情境；数据库原子性仍需真实 PostgreSQL 故障注入。

## 7. 推荐决定与下一步

- **建议继续采用统一协调方向**，复用现有 Runtime/Actor/权限体系，不建设新的独立平台。
- **原技术稿暂不直接进入实现**：先将 D1–D3 写成无歧义规则，并把 U1–U4 变成具体交互与验收要求。它们是同一目标的必要收紧，不是另开一项产品功能。
- 对未知存量方法是否暂停某些自动组合，需要库存实例支持后再决定，不能以评审意见擅自禁用；若影响现有产品能力则提交用户确认。
- 本轮没有修改业务代码，没有运行用户体验实测或修复后回归，不声称已证明现网兼容。

最终判断：工程上可行，主要风险可落到现有机制内治理；体验上有改善空间，但仅“把系统崩溃改成冲突报错”不足以满足便捷性。只有补齐动作适用性、可选候选隔离和无损恢复，才值得作为完整修复实施。
