# 发布前 GitHub 检查

日常开发和页面预览继续在 Codex 云端任务内进行。本流水线只在准备发布时检查确定提交；不包含部署任务、生产 Environment、SSH 或生产凭据，不连接生产数据。当前只有一台生产服务器，不在上面新增测试实例。本文件只描述检查；用户明确说“提交部署”后的自动发布另见APPROVED_DELIVERY.md。

## 请求与结果

1. 在原 `codex/task/*` 工作树完成修改及定向测试，通过受控 `git-push.sh` 提交推送。
2. 运行 `python3 scripts/ci/request-check.py`。该命令拒绝脏工作树、非任务分支、与远端不一致的 HEAD；只推送指向该提交的新 `preflight/*` 检查标签，不修改任务分支，不强推。
3. 打开仓库 Actions 的 **Pre-release checks**，核验完整 SHA、前后端两个 job 均成功。请求成功、某一个 job 成功或旧提交成功均不能作为发布通过。失败/超时先检查阶段，再修复并对新 SHA 重新请求。
4. 检查通过只表示该 SHA 的检查结果，不授权生产部署。后续合入 main、解决冲突或提交其他修改，均需检查最终候选；不复用旧 SHA 的通过结果。

标签触发不依赖工作流已合入默认分支，适合本任务仍未合入 main 的阶段。后续工作流合入 main 后也可在 Actions 界面选择任务分支手动运行。普通业务提交不触发此流水线；修改流水线自身会自动执行自检。检查标签保留作为审计记录，不自动清理远程历史。

## 检查范围与时间

两个 job 并行：

- frontend：Node 22，`npm ci`，全部 Vitest 测试（当前177文件/1834项），TypeScript/Vite 构建。
- backend：一次性 Debian trixie/Python 3.12、非 root `/workspace` 检出；只复制 `git archive HEAD` 的受跟踪代码，生成新的私有 `.env`。校验原生包，从空库初始化任务专属 PostgreSQL/pgvector 与 Redis，重复核验，运行19项原生/工具集成测试、11文件242项后端定向回归、流水线安全测试、真实API smoke及20秒后台观测。不是整个后端测试集合，也不验证外部模型/短信/OSS。

后端不依赖前端开发服务器，真实API只监听loopback；前端在另一个job独立测试/构建。日常的前后端连通预览及重启持久性仍由Codex云端验证。每个GitHub job独立临时机器，数据不共享，测试结束停止本次进程；机器销毁回收测试数据。

缓存只包含npm/pip下载，不缓存`.env`、数据库、虚拟环境或日志。冷启动包含排队、容器拉取、系统/应用依赖安装。前端job上限20分钟，后端30分钟；内部每阶段另有超时。定时报告只上传阶段名称、耗时、退出状态和允许的测试计数，原始日志及连接信息不上传artifact。报告保留14天。超时和取消意味着检查未通过，不自动重试。

同一个ref的重复检查可取消旧运行；不同任务的检查可以并行。每个显式检查标签是独立请求，不保证GitHub按提交时间排序，也不将并发设置当作生产锁。发布协调仍须遵守现有生产锁和验收流程。

## 多对话约束

不同云端对话必须使用不同任务工作树、`codex/task/*`分支、数据库和Redis实例。GitHub检查本身可并行；同一生产环境的部署及验收仍串行。A验收并合入main后，B在自己的工作树合入最新main、解决冲突并重新检查最终SHA，不能直接覆盖A。稳定基座元数据同步不等于自动把代码写入其他任务工作树。

本文件只描述只读检查流水线。Codex指令发布另见 [APPROVED_DELIVERY.md](APPROVED_DELIVERY.md)，配置/演练阶段生产开关保持false。未配置固定网址的自动预览。实际GitHub运行、阶段耗时和限制在任务交付中记录，不能用本地单测代替GitHub实跑。
