# 真实对话选错目标：模型输入与责任分析

## 证据范围

仅分析第三轮真实客户测试的“完成 A → 新 B 只讨论 → 没问题，开始生成吧”回合，不推测模型内部思维。本轮路由与主模型实际都是 qwen3.8-flash，属于两次职责不同的模型调用。真实供应商随后完成了 B。没有为本次诊断新增付费调用或修改业务实现。

完整实际模型传输已保存在 `/private/tmp/skill-supplier-two-bugs-customer-88f5b32942/evidence.json`，本回合原样提取为同目录 `wrong-target-exact-wire.json`，包含路由 system_prompt/input/tools/原始输出，以及三次主模型 HTTP 请求。

ID 对照：

- A 用户消息：`5a1c62a2-6967-45a4-9ae0-347d20ca2ecc`，要求波点封面原图改暖米白背景。
- A 保存稿：`content-994a52915c2f7d8196c6aa88df5c385e`，revision 1，item 1。
- B 用户消息：`e629af13-bcea-4ad3-8996-07e7953c606f`，要求星星封面大五角星改细线月牙，先复述、不生成。
- 当前用户消息：`0b78a5f7-162c-4524-942a-fbe73f639ef9`，原话“没问题，开始生成吧。”

## 第一处错误：路由模型，而非生图供应商

路由模型被要求调用 `select_image_workflow`。它收到的实际 input 中：

- `raw_user_input` 为“没问题，开始生成吧。”
- `available_context.original_user_request` 是 B 完整要求。
- `request_resolution.active_request_message_id` 指向 B。
- `recent_requests` 包含当前确认、B、A，顺序正确；B 标记 focus=current_request、has_execution_state=false，A 为 true。
- `saved_groups` 仅有 A 已保存稿，名称为泛化的“编辑本轮指定图片”；其 item.image_status 仍显示 accepted。另一个 image_results 目录已有 A 的实际完成图片。
- `image_target_references` 同时提供 A 原图、B 原图、A 成图。B 对应 material:2，A 成图同时存在 material:3 和 result:1 两个引用别名。

路由提示原文已经明确要求：

> 没有明确历史指向的后续确认应承接active_request_message_id；它没有执行稿时先准备该需求，不能跨过它执行更旧的完成稿。

以及：

> 只有用户实际明确指向历史对象时basis=explicit_reference，不因历史稿唯一或已完成就使用explicit_reference。

路由实际输出中关键字段如下，省略未相关字段：

```json
{
  "intent": "execute_saved",
  "request_context": {
    "materials": [{
      "material_index": 2,
      "role": "本轮待编辑的星星封面原图",
      "usage": "input"
    }],
    "target": {
      "kind": "content",
      "basis": "explicit_reference",
      "artifact_id": "content-994a52915c2f7d8196c6aa88df5c385e",
      "revision": 1,
      "item_indices": [1]
    },
    "focus": "current_request"
  }
}
```

这证明路由已经识别 B 素材，却把目标指向 A 的保存稿。用户没有明确回指 A，模型仍声称 explicit_reference，违反了收到的指令。不能将本次错误归因于“模型根本没看到 B”或“缺少 B 的图片 ID”。不能从一次输出证明换模型即可解决，也不能获知其内部为何作此判断。

## 第二处：后台接收与主模型上下文

后台把原始 main_images 路由归一为 ordinary_image，清除没有真实待确认项支持的 approved，但保留了 `intent=execute_saved` 和 A 的 target。`freeze()` 对 A 的真实稿件、版本和条目校验通过；focus 一致性只在 basis=active_request 分支进行。模型声称 explicit_reference 时，后台验证对象真实存在，不能证明用户真的表达过这个指向。

因此主模型实际收到的系统层 `[Server main-image workflow]` 是：执行旧 A 稿，但 materials 是 B。另一系统层 `[Model-directed execution]` 又明确提供 active_request=B 和 resolution=A。冲突是应用把错误路由提升为“已提取的结构化信息”后形成的，不是客户输入自相矛盾。

不能把“后台验证了真实 ID”解释为“后台验证了用户语义”，也不能说本轮后台自动拦住了路由错误。本轮主模型先自行纠正，没有先派发 A。

## 第三处：纠正合同与最终执行

主模型第一次调用 `resolve_request_target` 时 intent 已选 edit、素材为 B，但 target 只填 kind=image、basis=current_input，缺 source_message_id/content_index，被结构校验拒绝。

第二次补齐 B 的真实 message_id 和 content_index=1 后成功；宿主将历史焦点图片的 current_input 关系归一为 active_request，没有更换来源。随后执行了 B 的真实图片编辑，供应商产出月牙结果。

两个模型接口表示同一张图的方式不同：路由要求 image_reference=material:2，不填写真实消息位置；纠正工具要求 source_message_id/content_index。此差异客观存在，会增加填写负担；但“它导致第一次漏字段”仍是待实验验证的解释，不能当已证实根因。

## 责任划分

| 层级 | 已证实事实 | 可作结论 |
|---|---|---|
| 路由模型输出 | B 素材 + A 执行稿，且无明确历史指向却声明 explicit_reference | 本次确实有语义选择错误、字段不一致 |
| 输入组织 | B 完整需求和焦点已给；A 作为唯一正式保存稿仍在同层目录；模型一次兼顾多种动作/规格/确认/目标 | 不是漏历史信息；目录呈现和复杂合同存在改进空间，是否造成误选需对照实验 |
| 后台/上下文 | 真实性校验放行了模型声明的 explicit_reference，并向主模型发送冲突的结构化选择 | 系统缺少对错误语义声明和关联不一致的充分保护，不能单独归咎模型 |
| 纠正工具 | 第一次缺字段被拒，第二次正确；两个接口图片引用形式不同 | 结构校验正确；合同一致性、纠错可理解性需要改善 |
| 图片供应商 | 本回合执行正确 B 来源并产出结果 | 本次目标误选不发生在供应商 |

输入量、唯一保存稿、通用标题或模型能力都可能影响错误率；仅靠本次日志不能分配各因素的因果权重。需要在同一客户回合保持模型参数不变，分别对照目录呈现、目标选择合同与路由/主模型职责，再评估稳定率。后台不能通过关键词识别“开始生成”来掩盖问题，也不能全禁历史选择来破坏合法回指。

建议的后续修正方向是：让对象的任务归属清楚呈现、目标选择与后续操作共享同一引用表示、关联字段不一致时不升格为已确定选择；明确历史选择保留，但须能关联真实用户输入依据。具体采用何种语义验证机制还需要设计和对照验证，不能承诺仅加一条提示词便可靠。


## 具体优化方案：以真实需求归属组织候选（待实施）

目标是修正这次输入组织缺陷，同时保留任意可见历史需求、原图、成图和跨任务参考。以下为本次代码核对后的方案，尚未实施或真实验证。

1. **消除持久对象中的相对时态标题。** `inline_image_action.py` 当前分支仍硬编码“编辑本轮指定图片”，会持久保存并在后续轮次进入目录。新建普通编辑记录改用中性名称；模型目录必须同时显示来源需求 message_id、原始需求摘要、原图和成果引用。旧稿仅在模型投影中补充归属，不改写历史正文、ID、版本、指纹或已受理参数。标题不作为路由规则。
2. **同一需求目录纳入有稿与无稿请求。** 基于 `request_resolution.model_context()` 已有的真实请求，按归属关联 `content_objects.catalog()` 与实际成图目录。B 即使没有逻辑执行状态，也作为完整可选需求出现，包含原始输入及图片、saved_contents=[]、实际无派发事实；不是为 B 凭空生成一份已保存/已授权方案。A 则显示其真实需求、保存稿与成果。无法证实归属的旧对象独立标识来源待核对，不按相近标题猜配。
3. **先选择需求，再解析该需求内的操作对象。** 普通图片承接的选择合同先输出真实 request/message 引用，再选择编辑底图、保存稿版本/条目或生成结果；后台将执行用稿件目录限定到该选定归属，不再让任意旧稿 ID 与另一需求自由组合。可在现有路由→主模型步骤实现，不预设必须新增一次模型调用。主模型仍可在副作用前显式改选；改选成功后替换同一份投影，不同时保留互相冲突的“已确定”指令。
4. **保留历史能力。** 模型始终可看见带原始要求的历史需求索引。用户要回到 A 时，模型明确选 A，随后读取 A 的全文/稿件/成图；不会因为 A 不是最新任务而被一律禁止。当前焦点是承接线索，不是永久锁。编辑成图、按旧稿重做、展示旧图用各自真实对象，不能互相替代。
5. **结构一致性而非关键词路由。** 校验所选稿件/成图是否确实归属于选择的需求、版本与窗口是否有效；目标缺稿则允许依据真实 B 输入准备新稿，不执行 A 补缺。图片引用在路由、纠正、执行之间共用同一表达或宿主明确映射；不让模型在修复目标时重填大量无关媒体字段。跨任务材料作为明确角色参考允许保留，不能简单要求所有参考图属于同一个任务；本次明确的 B 编辑底图则不得无声替换成 A。引用存在和字段一致仍不能证明全部自然语言意图，语义错误率需实测。
6. **状态分开。** 聊天回合完成、是否有保存稿、图片任务是否受理/完成分别来自对应事实，避免将 B 的“讨论回合完成”写成图片完成，或用 A 的旧 accepted 记录代替当前实际完成状态。展示必须检查真实发布的图片 part，不能用模型的 view_image 读取或文字承诺作为交付证据。

落点：`inline_image_action.py` 中性标题；`request_resolution.py` 同源目录、目标选择与归属校验；`workflow.py` 路由输入及合同；`direct_loop.py` 主模型投影；`execution_engine.py` 同合同纠正和实际交付校验。若现有迁移384投影不能完整证实关联，再补 SQL 只读投影，不先假设要新建任务表；原租户/权限/检查点/幂等保护保留。兼容旧检查点，不通过重保存旧稿改变版本来完成映射。

验收按同一组客户语句对比：A已完成→B仅讨论→泛指确认必须生成B；明确回A按旧稿新生成；明确回A成图再编辑；仅展示A确实交付图片且无新派发；B底图+A风格参考仍可执行；多个任务均可能时询问而不猜；改选时新输入/旧版本失效且不重复受理。每项保留路由输入、原始选择、主模型请求、最终供应商图片来源指纹和用户收到的内容。不以固定响应测试或单轮成功宣称稳定。

实施按投影/标题→统一选择合同和消费方→归属/失败语义→固定回归与真实客户对照推进。回滚需成组恢复同一合同生产/消费方；不改写已提交的原生执行事实，也不重新派发旧已受理任务。
